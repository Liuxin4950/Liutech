# 02-架构师审查报告

## 一句话总评

整体架构方向正确（前后端分离 + 微服务 + Docker 编排），基础设施层（Security/异常处理/日志切面）做得扎实，但后端 Controller 层存在系统性分层污染，AI 服务的 tools 隔离机制只做了一半，前端 Web 与 Admin 两套代码存在大量重复且分层不一致——项目处于"能跑起来"到"拿得出手"之间的关键 refactor 窗口期。

---

## 1. 后端分层污染分析

### 1.1 PostsController（`LiuTech/.../controller/web/PostsController.java`，520行）

**核心问题：Controller 承担了请求组装 + 认证检查 + 异常处理 + 日志记录四重职责，本该只做"参数接收 -> 调 Service -> 返回 Result"。**

具体该下沉的逻辑：

1. **L85-94：PostQueryReq 手动组装**。Controller 里 new 一个 Req 对象然后逐字段 set，这是 DTO 转换逻辑，应在 Service 方法签名中直接接收原始参数，或用一个工厂方法/mapper 完成转换。Controller 只需 `postsService.getPostList(page, size, categoryId, tagId, keyword, sort, currentUserId)`。

2. **L136-139, L166-169, L267-270, L295-298, L323-326, L377-380, L410-413, L455-458, L496-499：重复的 `userUtils.getCurrentUserId() == null` 判空 + 返回 UNAUTHORIZED**。这个模式出现了 **9 次**。`@PreAuthorize("hasRole('ADMIN')")` 已经在方法上标注了（L261, L290, L319, L346, L373），Spring Security 会拦截未认证请求，这些 null 检查是冗余的。对于无 `@PreAuthorize` 的接口（如 L131 toggleLike），应在 SecurityConfig 白名单层处理，而非每个方法里手写。

3. **L141-151, L172-182：try-catch 包裹 Service 调用并返回 SYSTEM_ERROR**。已有 `GlobalExceptionHandler` 兜底，Controller 不应再 catch 业务异常。这些 try-catch 把本该由全局异常处理器统一处理的逻辑又拉回了 Controller，造成 9 处重复。

4. **L264-278, L292-308, L321-335, L348-362, L375-389：createPost/updatePost/deletePost/publishPost/unpublishPost 五个方法的 try-catch 结构完全一致**。这是典型的"复制粘贴编程"，应提取为一个模板方法或直接依赖 GlobalExceptionHandler。

**重构原则：瘦 Controller / 胖 Service**

```
// 目标形态
@PostMapping
@PreAuthorize("hasRole('ADMIN')")
@OperationLog(action = "create", targetType = "post", description = "创建文章")
public Result<PostCreateResp> createPost(@Valid @RequestBody PostCreateReq req) {
    Long authorId = userUtils.getCurrentUserId();
    return Result.success(postsService.createPost(req, authorId));
}
```

Controller 方法体理想长度：3-5 行。认证由 `@PreAuthorize` 保证，异常由 `GlobalExceptionHandler` 兜底，日志由 AOP 切面记录，Controller 只做"接收参数 -> 调 Service -> 包装 Result"。

### 1.2 AnnouncementsController（`LiuTech/.../controller/web/AnnouncementsController.java`，458行）

**核心问题：Controller 内嵌了 5 个静态内部类作为请求 DTO，且 admin 接口与前台接口混在同一个 Controller 中。**

1. **L342-457：5 个静态内部类（ExportRequest, StatusUpdateRequest, BatchStatusUpdateRequest, TopUpdateRequest, BatchTopUpdateRequest）**。这些是请求 DTO，应放在 `req/` 包下作为独立文件。把 DTO 塞进 Controller 不仅违反单一职责，还让 Controller 文件膨胀了 116 行（占全文 25%）。

2. **L104-110, L121-132, L139-145, L153-162, L169-176, L183-190, L197-204, L211-218, L226-234, L241-248, L255-262, L270-278, L285-292：admin 接口（带 `@PreAuthorize("hasRole('ADMIN')")`）和前台接口混在 `/announcements` 下**。应拆分为 `AnnouncementsController`（前台，`/announcements`）和 `AnnouncementsAdminController`（管理端，`/admin/announcements`），与 `PostsController` / `PostsAdminController` 的分离模式保持一致。

3. **L302-316：exportAnnouncements 方法直接操作 HttpServletResponse**。文件下载的 Response 头设置和流操作应封装在 Service 层或专门的 ExportService 中，Controller 只需传入参数。

**做得好的地方**：相比 PostsController，AnnouncementsController 的方法体更简洁，没有 try-catch 泛滥，基本是一行 Service 调用 + Result 包装，方向正确。

### 1.3 UserController（`LiuTech/.../controller/web/UserController.java`，408行）

**核心问题：Controller 内直接操作密码加密、JWT 生成等本该在 Service 层的逻辑。**

1. **L336-353：resetPassword 方法在 Controller 里直接调用 `passwordEncoder.encode()`、`userManagementService.updateUser()`、`verificationCodeService.markUsed()`**。这是一个完整的业务流程（验证码校验 -> 查用户 -> 加密密码 -> 更新用户 -> 标记验证码），应整体下沉到 `UserAuthService.resetPassword(req)`，Controller 只调一行。

2. **L377-401：verifyEmailLogin 方法同理**。Controller 里做了验证码校验 -> 查用户 -> 检查状态 -> 生成 JWT -> 更新登录时间 -> 标记验证码，6 步业务逻辑全部暴露在 Controller。应封装为 `userAuthService.emailLogin(req)`。

3. **L128-136, L207-213：getCurrentUser / getUserById 中手动 `BeanUtils.copyProperties` + `setPasswordHash(null)`**。DTO 转换和脱敏应在 Service 层完成，Controller 不应接触实体对象（`Users`）。

4. **L321-329, L362-370：forgotPassword 和 sendEmailLoginCode 中"查用户 -> 判空 -> 发验证码"的逻辑**。防枚举攻击的业务判断应在 Service 层封装，Controller 不应知道"为什么要先查用户再决定是否发码"。

5. **L182-191：getUsers 方法用 `@RequestParam` 接收 id 和 username 两个可选参数，返回 `Result<?>`**。一个接口承担"获取所有用户"和"按条件查用户"两个职责，应拆分或用明确的 DTO。

### 1.4 FileUploadController（`LiuTech/.../controller/web/FileUploadController.java`，307行）

**核心问题：参数过多 + 内嵌响应 DTO。**

1. **L94-109：uploadResource 方法有 7 个 `@RequestParam`**。应封装为 `ResourceUploadReq` DTO，用 `@Valid` 校验。

2. **L267-286：createExternalLinkResource 方法有 8 个 `@RequestParam`**。同上，应封装为 DTO。

3. **L199-232：TinyMCEResponse 和 TinyMCCEErrorResponse 两个静态内部类**。应放在 `resp/` 包下。

4. **L176-194：uploadImageForTinyMCE 方法返回 `Object`**。类型不明确，应定义专门的返回类型或用 `@ResponseBody` + 专用 DTO。

**做得好的地方**：FileUploadController 的方法体本身比较简洁（获取 userId -> 调 Service -> 返回 Result），没有 try-catch 泛滥的问题，分层方向正确。

### 1.5 PostsAdminController（`LiuTech/.../controller/admin/PostsAdminController.java`，265行）

**问题：每个方法都有 try-catch + handleException 模式，与 GlobalExceptionHandler 功能重复。**

L52-57, L64-70, L78-88, L96-107, L114-126, L133-139, L146-158, L164-171, L178-190, L196-207, L214-222, L229-236, L242-250, L256-264——**14 个方法全部包裹 try-catch**。`BaseAdminController.handleException` 本意是减少重复，但它做的事情和 `GlobalExceptionHandler` 完全一样：记日志 + 返回错误 Result。有了全局异常处理器后，Controller 里的 try-catch 是纯冗余。

**做得好的地方**：`BaseAdminController` 抽象基类的设计思路正确（提取公共方法），但应只保留 `checkResourceExists` 这类有业务语义的方法，去掉 `handleException` 和 `handleOperationResult`。

## 3. 前端架构统一性评估（Web vs Admin）

### 3.1 分层结构对比

| 层 | Web | Admin | 一致性 |
|----|-----|-------|--------|
| API 实例 | `services/api.ts`：多实例（ServiceType 枚举，支持主服务 + AI 服务） | `services/api.ts`：单实例 + `services/aiClient.ts` 独立 AI 实例 | 不一致 |
| Service 文件命名 | `post.ts`, `user.ts`, `category.ts`（单数） | `posts.ts`, `user.ts`, `categories.ts`（复数混单数） | 不一致 |
| Store | `stores/` 下 5 个 store（user, chat, category, tag, announcement, postInteraction） | `stores/` 下 3 个 store（user, settings, tabs） | Admin 过少，状态管理不充分 |
| Composables | 10 个，含 `usePostEditor`（846行巨型 composable） | 8 个，含 `useTablePage`, `useCrudActions` 等通用 CRUD 组合 | Admin 抽象更好 |
| 类型定义 | 类型散落在各 service 文件中 | `services/types.ts` + `types/agent.ts` 集中管理 | Admin 更规范 |

### 3.2 关键问题

1. **API 基础设施不统一**。Web 用 `ServiceType` 枚举 + 多 axios 实例，Admin 用单实例 + 独立 AI 实例。两套方案都可行，但应统一为一种。Web 的多实例方案更灵活，建议 Admin 也采用。

2. **`usePostEditor.ts`（Web）846 行，是全项目最大的单文件**。它承担了表单状态、附件管理、图片上传、分类/标签 CRUD、AI 建议处理、草稿保存、文章提交等 **7+ 个职责**。应拆分为 `usePostForm`, `usePostAttachments`, `usePostImageUpload`, `usePostTaxonomy`, `useAiWritingAssistant` 等独立 composable。

3. **AI Agent 代码重复严重**。`Web/src/services/adminAgent.ts` 和 `Admin/src/services/agent.ts` 的 SSE 解析逻辑几乎完全相同（handleEvent 方法、envelope 解析、buffer 处理），类型定义也重复（`AdminArticleDraftSnapshot`, `FieldUpdatePayload`, `WritingDraftPayload` 在 Web 和 Admin 各定义一份）。应提取为共享包或至少共享类型定义。

4. **Admin 的 `PostsManagement.vue`（1003行）将表单 CRUD、AI Agent 集成、分类/标签管理全部写在一个 SFC 中**。AI Agent 相关逻辑（L297-440）应提取为独立 composable，与 `usePostEditor.ts` 共享。

5. **Web 的 store 使用不均匀**。`postInteraction.ts` store 存在但 `post.ts` 没有 store，文章数据管理散落在 composable 中。Admin 几乎没有业务 store（只有 UI 状态 store），CRUD 数据全靠 composable 本地 ref 管理，刷新即丢失。

### 3.3 做得好的地方

1. Admin 的 `useTablePage` + `useCrudActions` + `useModalForm` 组合式 CRUD 抽象设计得不错，大幅减少了管理端页面的样板代码。
2. Admin 的 `useTableColumnPrefs` 和 `useTableExport` 是有价值的通用 composable，体现了对复用的思考。
3. Web 的 `config/services.ts` 用 `ServiceType` 枚举管理多服务实例的思路正确。

## 4. AI 服务隔离架构方案

### 4.1 当前状态

当前隔离方案：

- **SecurityConfig（`LiuTech-AI/.../infra/config/SecurityConfig.java` L117）**：`/ai/writing` 和 `/ai/writing/stream` 限制 `hasRole("ADMIN")`，`/ai/chat` 和 `/ai/chat/stream` permitAll。这一层做对了。
- **SiliconFlowChatClient（`LiuTech-AI/.../service/SiliconFlowChatClient.java` L140-142）**：`resolveTools(ChatMode mode)` 按模式分派工具——CHAT 模式给 `BlogMcpTools`，WRITING 模式给 `WritingTools`。这一层也做对了。
- **PromptService（`LiuTech-AI/.../service/PromptService.java` L195-205）**：`capabilityBoundaryRules()` 明确声明了路径边界和能力边界。

**问题在于**：工具隔离是"按模式"（CHAT vs WRITING）而非"按角色"（user vs admin）。当前架构下，如果未来用户 Agent 也想用 WRITING 模式（或者代码有 bug 导致模式分派错误），用户就能加载到 `WritingTools`。隔离依赖于调用路径正确，缺乏防御纵深。

### 4.2 推荐方案：基于角色的 Tools 注册器 【待质疑：运维验证部署可行性/测试验证可测试性】

**核心思路：不依赖 ChatMode 枚举做硬编码分派，而是引入 `ToolRegistry` 按角色动态注册 tools。**

```
// 新增：工具注册接口
public interface ToolRegistry {
    /** 按角色获取该角色可用的 tools 列表 */
    List<Object> getToolsForRole(String role);
}

// 实现
@Component
public class RoleBasedToolRegistry implements ToolRegistry {
    private final BlogMcpTools blogMcpTools;      // 所有用户可用
    private final WritingTools writingTools;       // 仅管理员可用

    public List<Object> getToolsForRole(String role) {
        List<Object> tools = new ArrayList<>();
        tools.add(blogMcpTools);                   // 看板娘聊天工具，所有人可用
        if ("ADMIN".equals(role)) {
            tools.add(writingTools);               // 写作工具，仅管理员
        }
        return tools;
    }
}
```

**调用链改造：**

1. `AiChatController` 从 JWT 中解析用户角色（已有 `AuthUtils`）
2. 传递角色到 `AiChatService.processChat(request, userId, role)` / `processWriting(request, userId, role)`
3. `SiliconFlowChatClient` 不再用 `ChatMode` 枚举分派工具，改为接收 `List<Object> tools` 参数
4. `ToolRegistry.getToolsForRole(role)` 产出 tools 列表

**防御纵深：**

1. **SecurityConfig**（已有）：URL 层面 `/ai/writing/**` 限制 ADMIN
2. **ToolRegistry**（新增）：工具层面按角色过滤，即使 URL 配置错误也不会泄露
3. **PromptService**（已有）：系统提示词中声明能力边界

三层防御，任意一层失效都不会导致 tools 越权。

【待质疑：当前方案将角色从 Controller 传递到 Service 再到 ChatClient，调用链变长。测试需验证：(1) 游客无法触发 WritingTools；(2) 普通用户无法触发；(3) ChatMode 枚举移除后是否有遗漏引用。运维需验证：JWT 角色解析在 SSE 异步线程中是否可靠（SecurityContext 在 CompletableFuture 中可能丢失）。】

### 4.3 MCP Tools 的注册与按角色过滤

当前 `BlogMcpTools` 和 `WritingTools` 都用 `@Component` 注册为 Spring Bean，通过构造注入到 `SiliconFlowChatClient`。Spring AI 的 `@Tool` 注解扫描是在 `ChatClient.prompt().tools(object)` 调用时发生的，传入哪个 Bean 就注册哪个 Bean 的 `@Tool` 方法。

**改进：**

1. 为每个 Tool 类添加 `@ToolGroup` 注解或实现 `ToolGroup` 接口，声明该工具组的目标角色：

```java
public interface ToolGroup {
    /** 该工具组允许的角色列表 */
    Set<String> allowedRoles();
}

@Component
public class WritingTools implements ToolGroup {
    @Override
    public Set<String> allowedRoles() {
        return Set.of("ADMIN");
    }
    // ... @Tool 方法
}

@Component
public class BlogMcpTools implements ToolGroup {
    @Override
    public Set<String> allowedRoles() {
        return Set.of("ADMIN", "USER", "GUEST");  // 所有人可用
    }
    // ... @Tool 方法
}
```

2. `ToolRegistry` 自动扫描所有 `ToolGroup` 实现，按角色过滤：

```java
@Component
public class RoleBasedToolRegistry implements ToolRegistry {
    private final List<ToolGroup> allToolGroups;

    public RoleBasedToolRegistry(List<ToolGroup> allToolGroups) {
        this.allToolGroups = allToolGroups;
    }

    public List<Object> getToolsForRole(String role) {
        return allToolGroups.stream()
            .filter(group -> group.allowedRoles().contains(role))
            .collect(Collectors.toList());
    }
}
```

这样后续新增 `AdminPostTools`（修改文章）、`AdminCategoryTools`（管理分类）等管理员工具时，只需实现 `ToolGroup` 并声明 `allowedRoles = Set.of("ADMIN")`，无需改任何调用链代码。

【待质疑：ToolGroup 接口引入了新的抽象层，是否过度设计？项目角色只有 user/admin 二值，硬编码 if(role==ADMIN) 可能更简单。PM 需评估是否有未来扩展多角色的需求，若无则此抽象属于 YAGNI。】

## 5. "AI 读取内容并制定修改"端到端设计

### 5.1 当前状态

当前已有雏形：

1. **前端**：`AdminAgentSidebar.vue` 在文章编辑弹窗右侧，通过 SSE 调用 `/ai/writing/stream`，发送 `draft` 快照（标题/正文/摘要/分类/标签）。AI 返回 `writing-draft` 或 `field-update` 事件，前端通过 `handleFieldUpdate` 将修改写入表单，支持撤销。
2. **后端**：`ChatServiceHelper.prepareMessages` 把 `request.getContext()` 和 `request.getMessage()` 组装成消息列表，但 **draft 快照没有被注入到 AI 的上下文中**——`PromptService.buildContextPrompt` 只处理 `page` 和 `postId`，不处理 `draft` 字段。
3. **WritingTools**：只有 `listCategories()` 和 `listTags()` 两个查询工具，没有"读取当前文章内容"和"修改文章字段"的工具。

**核心缺失**：AI 看不到当前文章内容（draft 快照传了但没注入 prompt），也没有 tools 来执行修改。

### 5.2 端到端方案

```java
private String buildDraftContext(AdminArticleDraftSnapshot draft) {
    StringBuilder sb = new StringBuilder();
    if (draft.getPostId() != null) sb.append("文章ID: ").append(draft.getPostId()).append("\n");
    if (draft.getTitle() != null) sb.append("标题: ").append(draft.getTitle()).append("\n");
    if (draft.getSummary() != null) sb.append("摘要: ").append(draft.getSummary()).append("\n");
    if (draft.getContent() != null) sb.append("正文（Markdown/HTML）:\n").append(draft.getContent()).append("\n");
    if (draft.getCategoryId() != null) sb.append("当前分类ID: ").append(draft.getCategoryId()).append("\n");
    if (draft.getTagIds() != null) sb.append("当前标签ID: ").append(draft.getTagIds()).append("\n");
    return sb.toString();
}
```

**D. AI 输出 field-update 事件**

当前 AI 的输出是自然语言文本（通过 `data` 事件），`field-update` 事件需要 AI 输出结构化 JSON。两种方案：

**方案 A（推荐）：JSON 指令注入 prompt，AI 输出 JSON，后端解析后发 SSE 事件**

【待质疑：此方案依赖 AI 模型严格遵守输出格式，流式场景下 JSON 标记可能跨 chunk 分割，解析器需要处理不完整 JSON。测试需验证：(1) 不同模型的格式遵从度；(2) JSON 标记跨 chunk 的边界处理；(3) AI 输出恶意/畸形 JSON 时的降级策略。运维需确认流式缓冲区大小是否足够暂存完整 JSON 块。】

在写作模式的系统提示词中追加输出格式约束：

```
当你需要修改文章字段时，输出以下 JSON 格式（独占一行，前后用 --- 分隔）：
---field-update---
{"title": "新标题", "summary": "新摘要", "contentHtml": "<p>新正文</p>", "categoryId": 5, "tagIds": [1,3], "suggestedTagNames": ["新标签"]}
---end---
```

`StreamingChatService` 在收到 chunk 时检测 `---field-update---` 标记，解析 JSON，通过 SSE 发送 `field-update` 事件。

**方案 B：用 Spring AI 的 StructuredOutput / BeanOutputConverter** 【待质疑：此方案更优雅但与当前流式架构兼容性未知】

让 AI 直接返回 `FieldUpdatePayload` 对象，Spring AI 自动做 JSON 反序列化。更优雅但需要调整 ChatClient 调用方式。需验证 Spring AI 的 BeanOutputConverter 是否支持流式场景（Flux<String>），当前 StreamingChatService 的 subscribeStream 方法直接订阅 chunk 文本流，结构化输出可能无法在流式模式下工作。

## 6. 代码优雅度问题与命名改进

### 6.1 命名问题

1. **`PostsController` vs `PostsAdminController`**：命名规范一致，赞。但 `UserController` 中混入了 admin 接口（L182-267），应迁移到 `UsersAdminController`。

2. **`AnnouncementsController` 中 admin 接口路径用 `/announcements/admin/**`**：与项目其他模块的 `/admin/**` 前缀不一致。其他模块都是 `/admin/posts`、`/admin/users`，公告应是 `/admin/announcements`。

3. **`SiliconFlowChatClient.ChatMode`**：枚举名 `ChatMode` 过于宽泛，实际语义是"工具集分派模式"，建议改为 `ToolSet` 或 `AgentMode`。

4. **`BlogMcpTools`**：类名包含"Mcp"但实际使用的是 Spring AI 的 `@Tool` 注解，不是 MCP 协议。建议改为 `BlogTools` 或 `PublicBlogTools`。

5. **`WritingTools`**：名称太泛，建议改为 `AdminWritingTools`，明确管理员专用。

6. **`markLegacyRoute`**（`AiChatController` L184-188）：方法名叫"标记遗留路由"但实际只是加了一个自定义 header，且注释说"后续如引入 v2 版本可用来区分"——这是为未来设计的但当前无实际用途，属于 YAGNI 违规。

### 6.2 目录组织

1. **AI 服务的包结构不一致**：`common/mcp/` 下放 tools，`common/client/` 下放 HTTP 客户端，`common/tts/` 下放 TTS 相关，`common/utils/` 下放工具类，`common/monitor/` 下放监控。但 `infra/` 下又放了 `config/`、`security/`、`filter/`、`exception/`。`common/` 和 `infra/` 的边界不清晰——建议统一到 `infra/` 下（或统一到 `common/` 下），不要两个都用。

2. **主后端的 `req/` 和 `resp/` 包**：从 import 看存在（`PostCreateReq`、`PostDetailResp` 等），但未在目录列表中看到独立目录——需确认是否在 `model/` 下。如果是，建议拆分为 `model/dto/req/` 和 `model/dto/resp/`。

3. **Admin 前端的 `services/types.ts`**：类型定义集中在一个文件中，随着接口增长会变得臃肿。建议按领域拆分（`types/post.ts`、`types/user.ts` 等）。

### 6.3 其他优雅度问题

1. **`PromptService.buildGuestPromptMessages`（L210-229）**：L218-219 两次判空 `content`（`if (tempMessage.getContent() == null ...)` 和 `if (content == null || content.isBlank())`），第二次判空永远不可能为 true 因为前面 continue 了。冗余代码。

2. **`StreamingChatService.subscribeStream`（L212-337）**：125 行的巨型方法，包含 onNext/onError/onComplete 三个 lambda，逻辑高度耦合。建议提取为三个独立方法。

3. **`UserUtils.getCurrentUserId`（L51-85）**：35 行方法包含 4 层 if-else 嵌套，可简化为先判空返回、再逐步取值。

4. **`SecurityWhitelist`**：白名单用 `List<String>` + `startsWith` 匹配，性能和可维护性都不如 `Set<String>` + 精确匹配。前缀匹配还可能导致意外放行（如 `/posts/` 前缀会匹配 `/posts/admin/secret`）。

## 8. 给学生的话

你的项目在在校生作品里已经属于上乘——Docker 编排、JWT 认证、SSE 流式、Spring AI 集成、AOP 日志切面、全局异常处理，这些基建很多工作 2-3 年的开发都未必能搭出来。面试时这些都是能讲出深度的亮点。

**你需要建立的架构思维：**

1. **Controller 是门卫，不是厨子**。Controller 的职责是"验明身份、接收参数、转发给 Service、返回结果"。如果你在 Controller 里写 try-catch、做 DTO 转换、调多个 Service 拼业务流程，说明 Service 层缺了一个方法。一个好的 Controller 方法应该不超过 5 行。你已经有 `GlobalExceptionHandler` 和 `@PreAuthorize` 这两把刀，但没用到位——Controller 里还在手动判空和 catch 异常，相当于买了保险箱但把钥匙挂在门上。

2. **防御纵深不是"多写几个 if"**。AI 服务的 tools 隔离是个好例子：当前靠 ChatMode 枚举 + URL 权限两层隔离，看起来够了，但如果模式分派出 bug 就直接穿透。真正的防御纵深是"每一层都假设上一层已经失效"——URL 权限层、ToolRegistry 角色过滤层、系统提示词约束层，三层独立工作，任意一层被绕过都不会导致越权。

3. **重复代码是技术债的利息**。Web 和 Admin 两套 AI Agent SSE 解析逻辑几乎完全相同，你每次改一处都要同步改另一处，漏改就是 bug。这不意味着要过度抽象，但至少类型定义和 SSE 解析器应共享。同理，9 处 `getCurrentUserId() == null` 检查、14 处 try-catch，都是"复制粘贴"的代价。

4. **"能跑"和"拿得出手"之间隔着的是一致性**。你的 AnnouncementsController 把 admin 和前台接口混在一起，而 PostsController 已经拆分了；UserController 注入了 passwordEncoder，而其他 Controller 没有。这种不一致会让面试官觉得"知道最佳实践但没贯彻到底"。选定一种模式，全项目执行——这比写出一段优雅代码更能体现架构能力。

5. **先做 P0 再做 P1**。Controller 去冗余是低风险高收益的"热身"重构，做完之后你对代码的理解会更深，再做 AI tools 隔离这种涉及调用链改造的任务时更有把握。不要一上来就改最复杂的部分。
