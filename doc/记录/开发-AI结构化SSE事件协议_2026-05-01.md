## 1. 问题背景

前任 AI 模型（基于 GPT-5.5 Pro/Codex）执行了实现 PRD 的编码，但审查发现 3 个严重问题和 2 个中等问题，阻塞交付。

## 2. 发现的问题与修复

### 严重问题 1：Web 前端旧 `[[RECOMMEND]]` 链路完全未移除

**问题**：`Web/src/components/AiChat.vue` 仍完整保留 `extractRecommendParams`、`loadMessageRecommendation`、`messageRecommendations`、`loadAllMessagesRecommendation`、`buildRecommendationContext` 等旧推荐链路代码，违反 PRD 验收标准 AC4、AC5。

**修复**：
- `AiChat.vue`：移除 `extractRecommendParams`、`loadMessageRecommendation`、`messageRecommendations`、`loadingMessageIds`、`loadAllMessagesRecommendation`、`buildRecommendationContext`、`recommendationsByMessageId`、`handleCategoryClick`、`cleanMessageContent` 函数及相关 import
- `AiChat.vue`：简化 `buildChatContext` 不再包含旧推荐上下文
- `AiChat.vue`：移除流结束后触发旧推荐加载的 `watch`、`onMounted` 中的 `loadAllMessagesRecommendation` 调用、`loadConversation` 中的旧推荐加载
- `AiChatBody.vue`：移除 `recommendations` prop、`getMessageRecommendData`、`emitCategory`、旧推荐渲染模板分支、`openCategory` emit

### 严重问题 2：后端工具调用未走 `AgentToolExecutionService`

**问题**：`AgentOrchestrator` 中 `handleArticleSearch`、`handleArticleRecommendation` 仍直接调用 `toolCallRecorder.record()`，绕过了 `AgentToolExecutionService`，导致搜索/推荐时不发送 `tool-start/tool-result` 事件，违反 PRD 验收标准 AC10。

**修复**：
- `AgentOrchestrator`：`handleArticleSearch` 和 `handleArticleRecommendation` 增加 `AgentSseContext context` 参数
- 有 context 时使用 `toolExecutionService.execute()`（发送 SSE 工具事件 + 审计）
- 无 context 时（非流式调用）fallback 到 `toolCallRecorder.record()`（仅审计）
- 工具执行结果增加 null 保护（`toolExecutionService.execute()` 失败时返回 null）

### 严重问题 3：`AgentSseEnvelope.contractVersion` 默认值问题

**问题**：`private final int contractVersion = 1` 使用 `int` 基本类型，Lombok @Builder 默认值未生效。

**修复**：添加 `@Builder.Default` 注解，确保 builder 构造时 contractVersion 默认为 1。补充序列化验证测试。

### 中等问题 4：`sendData()` 未使用 `DataPayload`

**问题**：`AgentStreamPublisher.sendData()` 使用 `Map.of("content", content)` 而非已定义的 `DataPayload`。

**修复**：改为 `DataPayload.of(content)`，补充 import。

### 中等问题 5：测试覆盖不足

**问题**：`AgentStreamPublisherTest` 只验证 `emitter.send()` 被调用，未验证 envelope 结构。

**修复**：在 `AgentSseEnvelopeTest` 中补充 `shouldSerializeToJsonWithContractVersion` 和 `shouldDefaultContractVersionToOneViaBuilder` 测试。

## 7. 2026-05-02 测试修复

### Bug 1：前端 `shouldUseAgent` 关键词匹配过窄

**问题**：用户发送"有java的吗"、"有没有其他的文章啊"等自然语言，`shouldUseAgent` 正则未命中，请求走了 `/chat/stream`（纯 LLM 聊天）而非 `/agent/stream`（Agent 结构化事件），导致不显示推荐卡片。

**修复**（`Web/src/stores/chat.ts`）：
- `有.*的吗` → `有.{0,8}的`（去掉"吗"结尾限制）
- 新增 `有没有.{0,15}` 匹配"有没有xxx"句式
- 新增独立 `文章` 关键词兜底

### Bug 2：后端 `extractRecommendationKeyword` 提取无意义词

**问题**：用户发送"推荐一下？"，意图分类为 `RECOMMEND_ARTICLES`，但关键词提取去掉"推荐"后剩"一下"，拿"一下"去搜索当然无结果。

**修复**（`AgentOrchestrator.java`）：在 `extractRecommendationKeyword` 的停用词列表中新增"一下"、"几个"、"哪些"、"什么"、"有什么"、"呢"、"啊"，使这些词被过滤后关键词为空，回退到泛推荐（最新文章）。

### Bug 3：重启时 API Key 未加载

**问题**：手动重启 LiuTech-AI 时未从 `.env` 读取 `SPRING_AI_OPENAI_API_KEY`，用了测试 key，导致 401。

**修复**：重启时从 `.env` 读取真实 key。

## 8. 待改进（需走 PRD）

### 改进项 1：意图识别改为 LLM Tool Use（重大架构变更）

**现状**：`AgentIntentClassifier`（后端）和 `shouldUseAgent`（前端）都用正则关键词匹配来分类意图。每种用户表达都要加一条规则，永远补不完。

**问题示例**：
- "推荐一下" → 提取"一下"去搜索（无结果）
- "有没有其他文章" → 可能误分类
- "帮我看看有没有写docker的文章" → 依赖多个关键词组合匹配

**目标方案**：改用 LLM Tool Use / Function Calling 模式：
1. 定义工具（searchArticles、recommendArticles、createDraft 等）
2. 用户消息直接发给 LLM，LLM 理解意图后自主决定调用哪个工具
3. 前端不再需要 `shouldUseAgent`，统一走 Agent 端点
4. 后端不再需要 `AgentIntentClassifier`，LLM 天然理解语义

**影响范围**：`AgentOrchestrator`、`AgentIntentClassifier`、`AgentChatController`、前端 `shouldUseAgent`、`aiStream.ts` 路由逻辑

**优先级**：高。当前正则方案是技术债，每种新表达都是维护负担。

### 改进项 2：Admin 后台 Agent 侧边栏缺少 tool-start/tool-result 展示

**现状**：`Admin/src/components/agent/AdminAgentSidebar.vue` 有 plan、answer、articles、confirmation 的 UI，但 tool-start/tool-result 事件的回调未接入，工具执行过程不可见。

**影响范围**：仅 Admin 前端。

**优先级**：中。PRD 已注明"首期轻量处理，至少不报错"，功能正常但体验不完整。

## 9. 2026-05-02 智能模式统一入口修复

### 问题：前端关键词分流让 Agent 能力不可预测

**问题**：Web 前台通过 `shouldUseAgent` 正则决定是否请求 `/ai/agent/stream` 或 `/ai/agent/chat`。这会让“能不能触发 Agent”取决于用户是否命中特定关键词，而不是产品模式。用户自然表达一旦没命中，就会绕回旧 `/ai/chat/stream` 或 `/ai/chat`，无法稳定返回 `article-results`、身份识别、工具事件等结构化能力。

**修复**：
- `Web/src/stores/chat.ts`：删除 `shouldUseAgent`，Web 看板娘聊天请求统一携带 `agentEnabled: true`。
- `Web/src/services/aiStream.ts`：`agentEnabled` 未显式为 `false` 时默认请求 `/ai/agent/stream`，旧 `/ai/chat/stream` 仅保留为遗留兼容入口。
- `Web/src/services/ai.ts`：非流式聊天默认请求 `/ai/agent/chat`；`Ai.sendMessage` 也同步遵循该规则，避免未来绕过 Agent。
- `Web/src/components/AiChatHeader.vue`：将 UI 文案从“流式模式/普通模式”调整为“实时响应/完整响应”，明确它只控制返回方式，不控制是否启用 Agent。

**结论**：Web 看板娘只保留智能模式；`stream` / `normal` 只代表响应方式。Agent 内部仍可把普通闲聊识别为 `CHAT` 并自然回复，前端不再承担自然语言意图判断。

## 10. 2026-05-02 文章发现意图后端兜底修复

### Bug：进入 Agent 后仍可能只返回文本，不返回文章卡片

**问题**：Web 前端已经统一进入 Agent，但后端 `AgentIntentClassifier` 仍然把“有java的吗”这类自然语言判成 `CHAT`。结果模型可能根据提示词或上下文用自然语言回答“我找到了 Java 相关文章”，但后端没有执行文章工具，也不会发送 `article-results`，前端因此无法渲染可点击文章卡片。

**修复**：
- `AgentIntentClassifier`：增加文章发现问题兜底识别，覆盖“有 X 吗”“有没有 X”“想学/学习/了解 X”等表达。
- `AgentOrchestrator`：搜索和推荐共用文章关键词提取逻辑，优先识别 `java`、`docker`、`spring boot` 等已知技术主题。
- `AgentIntentClassifierTest`：补充“有java的吗”和“我在学习docker你有推荐的吗”回归用例。

**架构判断**：这是后端 Agent 路由兜底，不是恢复前端关键词门槛。短期必要，长期应升级为 LLM tool selector；权限、发布确认、草稿优先等安全规则仍必须由代码硬约束。

## 11. 2026-05-02 看板娘自称规范修复

### 问题：模型会自称 AI 看板娘

**问题**：用户希望看板娘对外自称“纳西妲”，不要在自称中带“AI”。旧系统提示词和安全提示词仍包含“站内 AI 看板娘 / 智能助手”等表述，模型在打招呼或介绍能力时容易回复“我是 LiuTech 博客的 AI 看板娘”。

**修复**：
- `application.yml`：系统角色改为“你叫纳西妲，是 LiuTech 博客里的站内看板娘”，并明确禁止自称“AI / AI 看板娘 / AI 助手 / 大模型 / 机器人”。
- `AiPromptSecurityPolicy`：安全规则同步要求始终保持“纳西妲 / 站内看板娘”身份，不在对用户自称中使用 AI 相关表述。
- `BottomNavigation.vue`：入口按钮的 `aria-label` 和 `title` 从“AI助手”改为“纳西妲”。
- `AgentOrchestrator`：默认草稿标题/摘要里的“AI 生成”改为“纳西妲生成”。

**架构判断**：无新的模块边界变化；这是统一产品人格和用户可见文案的行为修复。
