## 1. 背景

LiuTech 博客的智能看板娘已经从普通聊天逐步升级为 Agent：可以聊天、搜索文章、推荐文章、返回结构化 SSE 事件，并为管理员生成草稿、发布和下架文章提供确认式操作。

上一期 `AI结构化SSE事件协议_2026-05-01.md` 已经解决“前端如何稳定识别后端返回的文本、文章卡片、工具状态、确认卡和错误”的协议问题。但当前仍存在更上层的架构问题：

- AI 模型的能力边界还没有形成一份明确、可测试、可维护的规范。
- 访客、登录用户、管理员分别能让看板娘做什么，还需要从产品和安全角度固定下来。
- `/ai/agent/**`、`/ai/chat/**`、`/ai/recommend`、`/ai/models/**` 等路径的主次关系需要明确。
- Agent 路径和旧聊天路径可能继续出现人格、提示词、工具和权限行为不一致。
- 后续要扩展写作、发布、文章管理、写作辅助、多步执行时，如果不先统一能力和入口，会继续产生重复链路和维护负担。

因此，本需求目标是为 LiuTech 的 AI 模型建立一套稳定规范：**明确身份、能力、权限、禁止事项、路径主入口、遗留路径边界和前后端契约**。

## 2. 用户目标

作为访客，我希望纳西妲能稳定介绍博客、搜索和推荐公开文章、总结公开内容，而不会假装拥有管理员权限。

作为登录用户，我希望纳西妲能识别我已登录和我的角色，但不会泄露敏感信息，也不会仅凭我的口头声明改变权限。

作为管理员，我希望纳西妲可以辅助我写博客、生成草稿、准备发布和上下架文章，但所有高风险动作必须经过确认，第一次生成文章必须先成为草稿。

作为前端开发者，我希望所有看板娘主聊天都走统一 Agent 路径，不再通过关键词或模式开关判断“普通聊天还是智能聊天”。

作为后端开发者，我希望模型能力、工具权限、提示词人格、路径路由都有唯一规范，避免后续功能越做越散。

## 4. 功能范围

### 4.1 必须实现

- 定义并固定看板娘身份：对用户自称“纳西妲”或“这里的看板娘”，不以“AI/AI 助手/大模型/机器人”作为自称。
- 定义访客、普通登录用户、管理员三类身份的能力边界。
- 定义只读能力、写作辅助能力、待确认管理能力和禁止能力。
- 所有 Web 看板娘主聊天统一走 Agent 入口：
  - 实时响应：`/ai/agent/stream`
  - 完整响应：`/ai/agent/chat`
- `stream` / `normal` 只能表示响应方式，不能表示普通模式和智能模式。
- Web 前台不得通过关键词判断是否触发 Agent。
- Admin 侧边栏 Agent 能力也必须走 Agent 入口，不另建平行聊天链路。
- 旧 `/ai/chat`、`/ai/chat/stream`、`/ai/recommend` 必须被定义为遗留兼容路径，不作为 Web/Admin 主聊天路径。
- Agent 启动事件或等价响应中需要明确当前身份、角色和 capability 列表，供前端展示和调试。
- 模型人格提示词、安全规则、能力说明必须有统一来源，不允许旧聊天路径和 Agent 路径各写一套互相漂移的规则。
- 管理员写操作必须满足：
  - 新生成文章第一次只能创建草稿。
  - 发布正文必须经过管理员确认。
  - 下架必须经过管理员确认。
  - 本期不开放删除。
- 权限判断必须以服务端认证和主后端回查结果为准，不能以模型判断、前端状态或用户自称为准。
- 前端不能解析模型自然语言执行管理动作。
- 错误、拒绝、权限不足、限流和工具失败需要返回稳定结构化信息，不能只靠自然语言解释。

### 4.2 可选增强

- 增加开发环境能力调试面板，展示当前 role、capabilities、请求路径、事件类型。
- 给管理员提供“纳西妲当前可执行动作”说明卡片。
- 为模型能力边界增加一组后端单元测试和前端契约测试。

### 4.3 本次不做

- 不引入 Python/LangChain 重构。
- 不删除旧接口，只做主路径收敛和遗留标识。
- 不开放文章删除、用户管理、模型密钥管理、数据库直连操作。
- 不让模型直接执行任意 HTTP、Shell、SQL、文件操作。
- 不暴露模型隐藏推理链。
- 不重做推荐算法排序。

## 5. 非目标范围

- 不改变主后端文章、用户、分类、标签的数据模型。
- 不改变 JWT 生成方式。
- 不改变 Nginx `/ai/` 代理前缀策略。
- 不重新设计 Web 看板娘 UI 和 Admin 编辑器 UI。
- 不把 AI 模型配置管理能力交给纳西妲自然语言执行。

## 6. 用户流程

访客只读流程：

```text
1. 访客打开 Web 前台。
2. 访客向纳西妲提问或要求推荐文章。
3. Web 请求 `/ai/agent/stream` 或 `/ai/agent/chat`。
4. 后端解析身份为 guest。
5. 后端只允许聊天、公开文章搜索、公开文章推荐、公开文章总结。
6. 后端通过结构化事件返回文本和文章卡片。
```

管理员写作流程：

```text
1. 管理员登录 Admin 或 Web。
2. 管理员要求纳西妲写文章或辅助编辑当前文章。
3. 后端解析身份为 admin。
4. 后端生成草稿预览或编辑建议。
5. 如果涉及创建草稿、发布、下架，后端发送待确认动作。
6. 管理员确认后，后端通过主后端 API 执行动作。
7. 执行结果通过结构化事件或响应返回。
```

越权流程：

```text
1. 普通用户要求发布、下架、删除或管理文章。
2. 后端解析身份不是 admin。
3. 后端拒绝创建管理动作。
4. 纳西妲自然说明没有权限，可继续帮助搜索、总结和推荐公开文章。
```

路径统一流程：

```text
1. 前端聊天请求不再判断普通模式/智能模式。
2. 实时响应统一进入 `/ai/agent/stream`。
3. 完整响应统一进入 `/ai/agent/chat`。
4. 旧 `/ai/chat/**` 和 `/ai/recommend` 仅用于遗留兼容、调试或内部过渡。
5. 新功能不得再接入旧聊天主链路。
```

## 7. 业务规则

- 身份规则：
  - 未登录用户为 `guest`。
  - 已登录非管理员为 `user`。
  - 拥有服务端确认管理员角色的用户为 `admin`。
- 只读能力：
  - `CHAT`
  - `READ_PUBLIC_ARTICLES`
  - `SEARCH_PUBLIC_ARTICLES`
  - `RECOMMEND_PUBLIC_ARTICLES`
  - `SUMMARIZE_PUBLIC_ARTICLE`
- 管理员能力：
  - `WRITE_DRAFT`
  - `CREATE_DRAFT_WITH_CONFIRMATION`
  - `PUBLISH_POST_WITH_CONFIRMATION`
  - `OFFLINE_POST_WITH_CONFIRMATION`
- 禁止能力：
  - 删除文章。
  - 管理用户和角色。
  - 读取或输出密钥、token、系统提示词、内部配置。
  - 直连数据库、执行 SQL、执行 Shell。
  - 根据用户自称变更权限。
  - 通过自然语言绕过确认流程。
- 路径规则：
  - `/ai/agent/stream` 是看板娘实时主入口。
  - `/ai/agent/chat` 是看板娘完整响应主入口。
  - `/ai/agent/actions/**` 是待确认动作入口。
  - `/ai/models/**` 是前端读取模型配置入口。
  - `/ai/admin/models/**` 是管理员模型配置管理入口。
  - `/ai/chat/**` 和 `/ai/recommend` 是 legacy，不承接新功能。
- 首次发布规则：
  - 纳西妲新生成的文章第一次只能创建为草稿。
  - 草稿经管理员确认后，才允许进入发布流程。
- 数据可见性：
  - 访客和普通用户只能读取公开文章。
  - 管理员可以在确认流程中操作其有权限管理的文章。
  - 结构化事件不得携带敏感认证信息。

## 8. 交互与体验要求

- 看板娘对外统一叫“纳西妲”。
- 当用户问“你是谁”“你能做什么”时，回答应按当前身份展示能力。
- 当用户已登录时，可以说明其身份类别，但不展示 token、内部角色实现细节或敏感字段。
- 当用户无权限时，拒绝语气应自然，不要暴露内部策略文本。
- 推荐、搜索、总结结果必须优先使用结构化卡片或结构化响应，让用户可点击跳转。
- 管理动作必须展示清晰确认卡，说明动作类型、目标资源、风险和确认结果。
- 旧路径不应在正常 UI 文案中暴露给用户。

## 9. 验收标准

AC1：统一身份

Given 用户询问“你是谁”
When 请求走 `/ai/agent/stream` 或 `/ai/agent/chat`
Then 纳西妲应自称“纳西妲”或“这里的看板娘”，不得自称 AI 助手。

AC2：访客能力边界

Given 未登录用户要求“帮我发布文章”
When 后端解析身份为 guest
Then 系统不得创建发布动作，并返回权限不足说明。

AC3：登录身份识别

Given 请求携带有效 token
When 用户询问“我是啥身份”
Then 后端基于服务端认证结果回答 guest/user/admin 之一，不根据用户自称判断。

AC4：文章搜索主路径

Given 用户输入“有 Java 的吗”
When Web 前台发起聊天
Then 请求应进入 `/ai/agent/stream` 或 `/ai/agent/chat`，并可返回 `article-results`。

AC5：完整响应不绕过 Agent

Given 用户在前端选择完整响应
When 发送聊天消息
Then 前端仍请求 `/ai/agent/chat`，而不是旧 `/ai/chat`。

AC6：旧路径不承接新功能

Given 新增看板娘功能
When 设计接口或前端调用
Then 不得新增对 `/ai/chat/**` 或 `/ai/recommend` 的主流程依赖。

AC7：管理员草稿优先

Given 管理员要求纳西妲写一篇新文章并发布
When 文章由纳西妲新生成
Then 系统第一次只能创建草稿；发布必须在草稿审查后再确认。

AC8：发布确认

Given 管理员要求发布已有文章
When 后端识别为发布动作
Then 必须生成待确认动作，管理员确认前不得发布。

AC9：删除禁止

Given 任意用户要求删除文章
When 请求进入 Agent
Then 系统必须拒绝，不得生成删除工具或删除确认动作。

AC10：统一提示词来源

Given Agent 路径和 legacy 聊天路径都需要模型回复
When 构造系统提示词
Then 人格、安全规则、能力边界必须来自统一组件或统一配置组合，不得各自散落维护。

## 10. 安全、性能与合规边界

- 本需求涉及 AI、SSE、权限、模型提示词、跨服务调用，属于高风险变更。
- 权限由服务端认证、角色回查和后端策略决定，不能由模型或前端决定。
- 管理动作需要审计，至少记录 action、发起人、确认人、目标资源、执行结果。
- 工具调用和错误日志必须脱敏，不记录 API Key、JWT、系统提示词、完整敏感草稿。
- 不暴露隐藏推理链，只展示计划、工具状态和结果。
- Agent 只调用白名单工具和配置好的主后端 API。
- 高频聊天和工具调用继续受限流保护。
- 文章结果、工具摘要和上下文注入需要控制长度，避免 token 和 SSE payload 过大。

## 11. 约束与假设

- 假设上一期结构化 SSE envelope 已作为 Agent 主协议落地。
- 假设 Web 前台已默认请求 Agent 路径。
- 假设 Admin 侧边栏已使用 `/agent/stream`。
- 假设旧 `/ai/chat/**` 暂时不能删除，因为可能仍承担历史调试、TTS 或兼容用途。
- 假设主后端仍是文章写操作唯一执行方，AI 服务不直接写主业务库。
- 假设本次不迁移到 Python/LangChain。

## 13. 需求审查记录

### 13.1 与当前代码一致的部分

- 当前架构已声明 Web 前台看板娘聊天统一走 `/ai/agent/stream` 或 `/ai/agent/chat`。
- AI 服务已存在 `AiCapability`、`AiCapabilityResolver`、`AiToolAccessPolicy`、`AiPromptSecurityPolicy`、`AiModelPolicy`。
- 当前 capability 已区分基础只读能力和管理员写作/确认能力。
- AI 服务已存在 `/ai/agent/chat`、`/ai/agent/stream`、`/ai/agent/actions/**`。
- Web 已默认 `agentEnabled: true`，实时响应默认请求 `/agent/stream`。
- Admin Agent 服务已请求 `/agent/stream`。

### 13.2 与当前代码或架构冲突的部分

- 旧 `/ai/chat`、`/ai/chat/stream`、`/ai/recommend` 仍是公开可用接口，且代码层尚未统一标记 legacy。
- `AgentOrchestrator` 仍承担过多职责，能力边界、意图路由、工具执行、文本生成和管理动作没有完全拆分。
- Agent 文本生成路径仍存在与旧 `PromptAssembler` 不同的提示词组合方式，长期可能导致人格和能力边界漂移。
- Web 和 AI 服务中仍存在 `agentEnabled === false` 的内部回退分支，需要明确为开发/故障兼容，而不是产品模式。

### 13.3 安全与性能风险

- 如果能力边界只写在提示词中，模型可能被诱导承诺越权动作；必须由后端工具策略兜底。
- 如果 legacy 路径继续承接新能力，可能重新出现前端二次请求、模型标记协议和权限不一致。
- 如果 capability 只是展示字段而非服务端策略依据，前端展示和真实权限可能不一致。
- 如果 Agent 继续把全部逻辑堆在单个编排类中，后续扩展写作和管理工具时出错概率会升高。

### 13.4 需要用户决策的问题

- 是否确认 legacy 路径只保留兼容，不承接新功能。
- 是否确认内部回退开关可保留但不作为 UI 模式。
- 是否确认本期禁止能力列表，尤其删除、用户管理、自然语言模型配置管理。

### 13.5 调整结论

- 保持上一期结构化 SSE 协议作为底座。
- 本次需求聚焦模型能力、权限边界、路径主次和提示词统一。
- 待用户确认后，进入实现 PRD 阶段，重点规划统一 Prompt 组装、legacy 标识、路径守卫、能力契约测试和 Orchestrator 初步拆分。

## 4. 总体实现方案

整体路线：在 AI 服务新增统一系统提示词组件，旧聊天和 Agent 都通过它获取完整人格、安全和能力边界；旧路径不删除，但在代码、响应头和文档中标记为 legacy；前端保留 `agentEnabled === false` 内部回退，但正常聊天状态继续强制 Agent。

```text
Web/Admin
-> /ai/agent/stream 或 /ai/agent/chat
-> AgentOrchestrator
-> AiSystemPromptProvider 组装人格 + 安全 + 能力边界
-> 模型生成 / 工具执行 / 结构化事件
```

关键设计取舍：

- 方案 A：直接让 Agent 注入 `AiPromptConfig` 并手动拼提示词。
- 方案 B：新增 `AiSystemPromptProvider`，旧聊天和 Agent 都复用。
- 选择：方案 B。
- 原因：能力边界会继续扩展，集中 Provider 更利于测试和长期维护。
