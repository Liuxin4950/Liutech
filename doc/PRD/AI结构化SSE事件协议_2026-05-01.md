## 1. 背景

当前 AI 聊天存在两条混合链路：

- 旧链路：模型在自然语言中输出 `[[RECOMMEND]]` 标记，前端解析标记后再请求 `/ai/recommend`。
- 新链路：后端 Agent 调用站内工具，直接通过 SSE 发送 `article-results` 等结构化事件，前端按事件渲染文章卡片。

真实联调日志显示，旧链路中模型已经通过 Spring AI tool 调用了 `searchPosts`，随后又输出 `[[RECOMMEND]]`，前端再请求一次 `/ai/recommend`。这会造成协议不稳定、重复查询、前端依赖模型格式、AI 不知道前端二次请求结果等问题。

用户理想中的体验是：后端通过站内工具拿到博客真实数据，通过某种稳定格式返回给前端，前端可直接渲染可点击卡片；模型负责自然语言表达，不负责输出协议标记。

本需求目标是把 AI 与前端的流式对接规范为“结构化 SSE 事件协议”，让文本、文章卡片、确认按钮、工具结果、错误都成为同一条 SSE 流中的不同事件，并将模型文本标记协议退出 Web 聊天主链路。

## 2. 用户目标

作为博客访客，我希望当我要求搜索或推荐文章时，看板娘能一边自然回复，一边稳定展示真实可点击文章卡片，而不是依赖模型输出特殊标记。

作为管理员，我希望 AI 执行写作、草稿、发布、上下架时，前端能稳定显示计划、确认卡片和执行结果，而不是从自然语言里猜动作。

作为前端开发者，我希望 AI 后端返回明确事件类型和 payload 契约，以便前端只按事件渲染，不解析模型文本。

作为后端开发者，我希望模型只负责表达，工具数据和前后端协议由后端服务控制，以便降低幻觉、格式错误和重复请求。

## 3. 用户场景

| 场景 | 触发条件 | 用户行为 | 期望结果 |
| --- | --- | --- | --- |
| 搜索文章 | 用户输入“找一下 Spring 文章” | 看板娘回复并展示卡片 | 后端发送 `data` 文本事件和 `article-results` 卡片事件 |
| 主题推荐 | 用户输入“我在学习 Docker，有推荐吗” | 看板娘推荐相关文章 | 前端不解析 `[[RECOMMEND]]`，直接渲染后端文章结果 |
| 无结果 | 站内没有相关文章 | 用户要求推荐某主题 | 后端发送空 `article-results` 或仅发送说明文本，不混入无关卡片 |
| 管理员创建草稿 | 管理员要求生成草稿 | AI 生成预览并要求确认 | 后端发送 `confirmation-required`，前端渲染确认卡 |
| 工具执行中 | Agent 调用站内查询或管理接口 | 用户等待结果 | 前端可展示 `tool-start` / `tool-result` 或轻量计划状态 |
| 错误处理 | 限流、权限不足、模型失败 | 用户继续对话 | 后端发送结构化 `error`，前端显示稳定错误文案 |

## 4. 功能范围

### 4.1 必须实现

- 明确 AI SSE 是多事件流，而不是单一文本流。
- 统一 AI 后端 SSE 事件命名和 payload 契约。
- 搜索、推荐、当前文章总结/相关推荐等站内任务必须走 Agent 结构化事件链路。
- 后端通过工具获取真实博客数据后，直接发送 `article-results` 给前端。
- 前端不得依赖模型自然语言中的 `[[RECOMMEND]]` 作为聊天协议。
- 模型不得负责输出可点击卡片 JSON；卡片数据必须由后端 DTO 生成。
- Agent SSE 数据必须带 `contractVersion: 1`，为后续协议演进留出版本边界。
- Agent SSE 需要支持 `tool-start` / `tool-result` 事件，前端至少能够识别，首期可轻量展示或仅作为状态信息。
- `data` 事件只承载自然语言文本。
- `article-results` 事件只承载文章卡片列表和推荐/搜索元信息。
- `confirmation-required` 事件只承载待确认动作，不由模型自然语言触发。
- `error` 事件必须包含稳定错误码和阶段字段。
- 前端需要按事件类型分别处理文本、文章卡片、确认卡、完成状态和错误。
- Web 聊天主路径必须移除旧 `[[RECOMMEND]]` 标记解析和由此触发的 `/ai/recommend` 二次请求。
- 后端应避免同一轮对话中“模型 tool call 查一次 + 前端二次推荐接口再查一次”的重复链路。

### 4.2 可选增强

- 增加 `thought` 或 `plan` 的轻量展示，但不暴露模型内部推理链。
- 前端增加事件调试面板，仅开发环境显示。

### 4.3 本次不做

- 不暴露模型隐藏推理链。
- 不让前端直接执行模型输出的命令。
- Web 看板娘聊天统一迁移到 Agent；普通闲聊也由 Agent 入口降级为自然回复，避免前端通过关键词判断是否启用 Agent。
- 不删除旧 `/ai/recommend` 接口；它可作为遗留 REST 能力或内部兼容入口保留，但 Web 聊天主路径不再调用它。
- 不引入 WebSocket，继续使用 SSE。

## 5. 非目标范围

- 不解决推荐算法本身的排序和相关性问题；该部分由 `文章发现推荐引擎_2026-05-01.md` 承担。
- 不重做 Admin 侧边栏 UI。
- 不改变主后端文章数据模型。
- 不改变管理员草稿优先、发布确认、不做删除的业务规则。

## 6. 用户流程

文章推荐结构化 SSE 流程：

```text
1. 用户输入“我在学习 Docker，有推荐吗”。
2. 前端判断为站内任务，请求 `/ai/agent/stream`。
3. 后端发送 `agent-start`，声明任务、身份、能力。
4. 后端发送 `agent-plan`，声明将搜索站内文章。
5. 后端调用公开文章工具获取真实文章数据。
6. 后端发送 `data`，例如“我按 Docker 帮你找了几篇相关内容”。
7. 后端发送 `article-results`，包含文章 id/title/summary/url/reason 等字段。
8. 前端追加文本，并在同一条 AI 消息下渲染文章卡片。
9. 后端发送 `complete`。
```

管理员确认结构化 SSE 流程：

```text
1. 管理员要求“帮我生成并保存草稿”。
2. 后端识别管理员身份和写作意图。
3. 后端生成草稿预览。
4. 后端发送 `confirmation-required`，包含 actionId、actionType、preview、riskLevel。
5. 前端渲染确认卡。
6. 管理员点击确认。
7. 前端调用 confirm action。
8. 后端执行主后端工具并返回 `action-result`。
```

协议迁移流程：

```text
1. Web 聊天发送前不再判断站内任务。
2. Web 看板娘统一请求 `/ai/agent/stream` 或 `/ai/agent/chat`。
3. 旧 `/ai/chat/stream` 不再承担 Web 看板娘主链路，仅作为遗留普通聊天入口保留。
4. 前端移除 `[[RECOMMEND]]` 解析和由标记触发的 `/ai/recommend` 二次请求。
5. 后端普通聊天提示词移除“必须输出推荐标记”的规则。
```

## 7. 业务规则

- 协议规则：
  - 自然语言和结构化数据必须分离。
  - 前端只根据 SSE `event` 名称选择渲染方式。
  - 模型输出文本不得作为前端动作的唯一依据。
- 数据规则：
  - 文章卡片必须来自后端工具结果。
  - 文章卡片必须包含跳转字段。
  - 结构化数据必须是 JSON payload，不嵌在自然语言里。
- 兼容规则：
  - 旧 `/ai/recommend` 可暂时保留为遗留 REST 接口。
  - Web 聊天主路径不得再解析 `[[RECOMMEND]]`。
  - Agent 任务不得同时要求前端再请求 `/ai/recommend`。
- 安全规则：
  - 管理员写操作仍必须走 `confirmation-required`。
  - 普通用户不能通过自然语言触发写操作。
  - 前端不能解析模型文本执行发布、下架、删除等动作。
- 性能规则：
  - 文章列表结果只传摘要和必要字段，不传完整正文。
  - 模型只接收必要的精简结果，不把完整卡片 JSON 强塞给模型。

## 8. 交互与体验要求

- 用户感知上仍是一条自然对话。
- 文本先出来时可以显示“我帮你找到了...”，随后卡片出现。
- 卡片必须可点击跳转。
- 无结果时不要显示空白卡片区域，应自然说明没有找到。
- 确认卡必须明确风险等级和动作结果。
- 错误提示应清晰区分限流、权限不足、工具失败和模型失败。

## 9. 验收标准

AC1：推荐文章通过结构化事件返回
Given 用户输入“我在学习 Docker，有推荐吗”
When 前端请求 `/ai/agent/stream`
Then 后端应发送 `article-results` 事件，前端不依赖 `[[RECOMMEND]]` 渲染卡片。

AC2：文本和卡片分离
Given 后端返回推荐结果
When 前端处理 SSE
Then `data` 事件只追加文本，`article-results` 事件只渲染文章卡片。

AC3：可点击跳转
Given `article-results.items` 非空
When 前端渲染文章卡片
Then 每项必须包含 `id/title/url`，用户点击可跳转文章详情。

AC4：不重复请求推荐接口
Given 同一轮 Agent 推荐已经返回 `article-results`
When 前端收到完整 SSE 流
Then 前端不应再因为模型文本标记请求 `/ai/recommend`。

AC5：旧标记退出主链路
Given 旧 `/ai/chat/stream` 仍可能输出 `[[RECOMMEND]]`
When Web 聊天展示 AI 回复
Then 前端不再解析该标记触发 `/ai/recommend`，普通 Markdown 渲染也不应显示协议残留。

AC6：管理员确认事件
Given 管理员要求发布文章
When 后端识别为高风险写操作
Then 后端必须发送 `confirmation-required`，管理员确认前不执行发布。

AC7：错误结构化
Given 后端触发限流
When 前端请求 AI SSE
Then 后端返回 429 或 SSE `error`，包含 `code=RATE_LIMITED`。

AC8：模型不负责协议
Given 模型自然语言没有输出任何特殊标记
When 后端已经拿到工具结果
Then 前端仍能通过后端 `article-results` 渲染文章卡片。

AC9：协议版本稳定
Given 前端收到 Agent SSE 任意结构化事件
When 解析 `data` JSON
Then 能读取 `contractVersion=1` 并基于事件名和 payload 处理。

AC10：工具事件可识别
Given Agent 调用公开文章工具或管理工具
When 工具开始和结束
Then 后端发送 `tool-start` / `tool-result`，前端能够识别且不会把它当自然语言渲染。

## 10. 安全、性能与合规边界

- 涉及 AI/SSE/前后端协议，属于高风险变更。
- 不暴露模型隐藏推理链，只展示计划、工具状态和结果。
- 不在 SSE 中发送 JWT、API Key、系统提示词或完整敏感正文。
- 结构化事件 payload 必须由后端生成并校验。
- 文章结果限制数量，避免 SSE payload 过大。
- 旧文本标记协议可能被提示词影响，新协议必须避免依赖模型文本格式。

## 11. 约束与假设

- 假设前端已经具备 fetch SSE 流解析能力。
- 假设后端 Agent 已有 `AgentStreamPublisher`。
- 假设前端聊天消息模型可以在同一条 AI 消息下挂载文章结果。
- 假设本期继续使用 SSE，不切 WebSocket。
- 假设文章发现推荐引擎会另行处理排序和相关性，本 PRD 只约定事件协议和迁移方向。

## 13. 需求审查记录

### 13.1 与当前代码一致的部分

- AI 后端已有 `/ai/agent/stream`。
- Agent 已能发送 `agent-start`、`agent-plan`、`data`、`article-results`、`confirmation-required`、`action-result`、`complete`、`error`。
- Web 前端 `aiStream.ts` 已支持按 eventType 分发。
- Web 聊天 store 已能把 `article-results` 挂到 AI 消息上渲染。

### 13.2 与当前代码或架构冲突的部分

- 旧 `/ai/chat/stream` 仍可能输出 `[[RECOMMEND]]`。
- 旧链路可能发生“模型 tool call 查一次，前端再请求 `/ai/recommend` 查一次”的重复请求。
- `[[RECOMMEND]]` 依赖模型遵守文本格式，协议稳定性不足。

### 13.3 安全与性能风险

- 继续依赖模型文本标记会导致前端协议被提示词影响。
- 前端二次请求会让 AI 不知道最终推荐接口结果，回答和卡片可能不一致。
- 混用旧链路和新链路会增加重复查询和调试复杂度。

### 13.4 需要用户决策的问题

- Web 看板娘聊天已确认全量迁移到 Agent SSE / Agent chat，前端不再通过关键词判断是否启用 Agent。
- 旧标记协议已确认退出 Web 聊天主路径。
- `tool-start` / `tool-result` 和 `contractVersion` 已确认纳入底层协议。

### 13.5 调整结论

- 保持现有 Agent SSE 方向。
- 将结构化 SSE 事件定义为 AI 与前端主协议。
- 将 `[[RECOMMEND]]` 从 Web 聊天主链路移除；`/ai/recommend` 仅作为遗留 REST 能力保留。
- 推荐算法相关内容继续交给 `文章发现推荐引擎_2026-05-01.md`。

- 用户目标：把 AI 与前端的对接从“模型输出文本标记，前端再猜”升级为“后端发送结构化 SSE 事件，前端按契约渲染”。

## 4. 总体实现方案

整体路线：保留 SSE 事件名作为浏览器分发入口，但 `data:` 内统一包一层协议 envelope；所有 Agent 结构化事件都用同一格式。前端先解 envelope，再按 `event` 或 SSE eventName 渲染。站内任务全部走 Agent；旧模型标记从 Web 聊天主链路撤出。

```text
用户输入聊天内容
-> Web 看板娘按回复模式请求 /ai/agent/stream 或 /ai/agent/chat
-> AgentChatController 创建 SSE
-> AgentOrchestrator 创建 task/plan
-> AgentStreamPublisher 发送统一 envelope
-> AgentToolExecutionService 发布 tool-start/tool-result 并记录审计
-> article-results / confirmation-required / action-result
-> 前端解 envelope 后渲染文本、文章卡、确认卡和工具状态
```

关键设计取舍：

- 方案 A：继续裸 payload，只给个别 payload 加 `contractVersion`。
- 方案 B：统一 envelope，SSE eventName 保留，payload 作为业务体。
- 选择：方案 B。
- 原因：底层一次统一后，后续新增事件不会继续发散；前端能做版本判断、错误兜底和调试追踪。

统一 envelope 建议：

```json
{
  "contractVersion": 1,
  "event": "article-results",
  "taskId": 123,
  "conversationId": 43,
  "timestamp": "2026-05-01T15:28:23.029",
  "payload": {
    "source": "search",
    "query": "Spring",
    "reason": "与 Spring 相关的文章",
    "items": []
  }
}
```

## 5. 后端实现方案

### 5.1 API 设计

| 方法 | 路径 | 权限 | 请求 | 响应 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `POST` | `/ai/agent/stream` | 可匿名，写操作需管理员 | `AgentChatRequest` | SSE 多事件流 | 本次主改造入口，所有 Agent 事件使用统一 envelope。 |
| `POST` | `/ai/agent/chat` | 可匿名，写操作需管理员 | `AgentChatRequest` | `AgentChatResponse` | 非流式保持现有响应结构，可补充 `contractVersion` 字段。 |
| `POST` | `/ai/recommend` | 可匿名 | `RecommendRequest` | `RecommendResponse` | 保留遗留 REST 能力，但 Web 聊天主路径不再调用。 |

Agent SSE 事件：

| event | payload | 说明 |
| --- | --- | --- |
| `agent-start` | `AgentStartPayload` | 任务、会话、意图、角色、能力。 |
| `agent-plan` | `{ steps: AgentPlanStep[] }` | 可展示计划，不暴露隐藏推理链。 |
| `tool-start` | `AgentToolEventPayload` | 工具开始，包含工具名、展示名、输入摘要。 |
| `tool-result` | `AgentToolEventPayload` | 工具结束，包含成功状态、耗时、结果摘要或错误。 |
| `data` | `{ content: string }` | 只承载自然语言文本。 |
| `article-results` | `ArticleResultsPayload` | 只承载文章卡片结果。 |
| `confirmation-required` | `ConfirmationRequiredPayload` | 只承载待确认动作。 |
| `action-result` | `AgentActionResult` | 确认动作执行结果。 |
| `complete` | `AgentCompletePayload` | 结束状态。 |
| `error` | `AgentErrorPayload` | 稳定错误码、阶段、消息。 |

### 5.2 Controller 层

- 修改 `AgentChatController`：
  - 异常分支不再手写裸 `error` map，改用 `AgentStreamPublisher.error(...)`。
  - `executeStream` 传入统一 `AgentSseContext`，包含 `taskId/conversationId/emitter` 的部分信息由 Orchestrator 创建后补齐。
- 不新增公开 Controller。

### 5.3 Service 层

- 新增/修改文件：
  - `LiuTech-AI/src/main/java/chat/liuxin/ai/agent/response/AgentSseEnvelope.java`
  - `LiuTech-AI/src/main/java/chat/liuxin/ai/agent/response/AgentToolEventPayload.java`
  - `LiuTech-AI/src/main/java/chat/liuxin/ai/agent/response/AgentErrorPayload.java`
  - `LiuTech-AI/src/main/java/chat/liuxin/ai/agent/application/AgentSseContext.java`
  - `LiuTech-AI/src/main/java/chat/liuxin/ai/agent/application/AgentToolExecutionService.java`
  - 修改 `AgentStreamPublisher`、`AgentOrchestrator`、`AgentToolCallRecorder`。
- 核心业务流程：
  - `AgentStreamPublisher.send(context, event, payload)` 统一组装 envelope。
  - `AgentToolExecutionService.execute(context, taskId, toolName, input, supplier)` 负责发送 `tool-start`、执行 supplier、记录审计、发送 `tool-result`。
  - `AgentOrchestrator` 不再直接调用 `toolCallRecorder.record(...)`，改为通过工具执行服务。
- 事务边界：无新增事务；工具审计继续单次 insert。
- 幂等性：SSE 事件是过程性消息，不做重试幂等；管理员确认 action 仍沿用现有 action 状态。
- 异常处理：工具失败发送 `tool-result(success=false)` 和 `error`，任务置为 `FAILED`。

### 5.4 Mapper / 数据访问

- 不新增 Mapper。
- `ai_agent_tool_call` 继续记录工具调用结果。
- 不新增索引，无 N+1 风险。

### 5.5 鉴权与权限

- 登录态和角色解析沿用 `AgentUserContextResolver`。
- 只读工具允许匿名；写操作继续由 `AiToolAccessPolicy` 与 pending action 兜底。
- `tool-start/tool-result` 不能泄露 token、系统提示词、完整正文、API key。

## 8. 接口与数据流

| 数据 | 来源 | 处理层 | 存储/输出 | 备注 |
| --- | --- | --- | --- | --- |
| 用户消息 | Web/Admin 输入 | `AgentChatController` / `AgentOrchestrator` | `ai_agent_task.input`、模型输入 | 用户输入不可信，必须经提示词安全包装。 |
| 文章查询结果 | 主后端公开文章 API | `PublicArticleTool` / `AgentToolExecutionService` | `article-results` SSE、工具审计摘要 | 只返回摘要和跳转字段，不传完整正文。 |
| 工具状态 | Agent 工具执行 | `AgentToolExecutionService` | `tool-start/tool-result` SSE、`ai_agent_tool_call` | 输入输出做摘要，不泄露敏感信息。 |
| 管理确认 | Admin 点击确认 | `AgentActionController` / `AgentActionService` | `action-result` | 仍校验管理员和 action 归属。 |
| 错误 | 后端异常/限流/权限失败 | Controller/Service | `error` envelope 或 HTTP 状态码 | 前端稳定展示。 |

- 用户输入是否可信：不可信。
- 后端是否二次校验：权限、写操作、模型选择、工具访问继续后端校验。
- 返回字段是否包含敏感信息：不应包含 token、key、系统提示词、完整私密草稿。
- 前端是否可能缓存敏感数据：Web 只缓存聊天历史；Admin 草稿上下文不应长期持久化到 localStorage。

## 9. 安全影响

- 认证与授权：不改变 JWT 和角色来源；写操作继续服务端确认。
- 输入校验：沿用 `AgentChatRequest` 校验；工具输入摘要要限制长度。
- XSS：文章卡片字段以 Vue 文本插值渲染；Markdown 仍经 DOMPurify。
- SQL 注入：不新增 SQL。
- 文件上传/下载：无影响。
- SSRF：AI 服务仍只调配置好的主后端地址。
- CSRF：使用 Bearer Token，沿用现有策略。
- 敏感信息日志：工具事件和审计不得记录 token/API key/系统提示词。
- Token/localStorage：不改变。

结论：

```text
安全风险等级：中
必须修复项：移除 Web 聊天对模型标记的协议依赖；工具事件不得泄露敏感内容。
可接受风险：旧 /ai/recommend 暂时保留为 REST 能力，但不在 Web 聊天主链路使用。
```
