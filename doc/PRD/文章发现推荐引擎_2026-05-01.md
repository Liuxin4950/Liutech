## 1. 背景

智能看板娘 Agent 首版已经具备文章搜索、最新文章推荐和结构化文章卡片能力，但真实对话中暴露了一个关键问题：用户明确表达“我在学习 Docker，你有推荐的吗”，系统最初触发了泛化推荐，返回了最新文章列表，推荐结果和用户主题不匹配。

这说明当前推荐能力还停留在“关键词触发接口”的阶段，缺少一个高级 AI 产品需要的文章发现管线：理解用户意图、抽取主题、查询真实文章、计算相关性、解释推荐原因，并把结构化结果稳定返回给前端。

本需求目标是将搜索/推荐从 Agent 编排器中的零散逻辑升级为独立、可测试、可解释、可持续扩展的文章发现能力。

## 2. 用户目标

作为博客访客，我希望当我说“我在学习 Docker，有推荐吗”时，看板娘能推荐真正与 Docker 相关的文章，而不是随便返回最新文章，以便我更快找到学习内容。

作为登录用户，我希望推荐能结合当前文章、我的问题和站内真实内容，以便继续阅读相关主题。

作为管理员，我希望推荐/搜索逻辑有明确契约、可审计、可调优，以便后续扩展 RAG、语义搜索或学习路径推荐时不会推倒重来。

## 3. 用户场景

| 场景 | 触发条件 | 用户行为 | 期望结果 |
| --- | --- | --- | --- |
| 主题推荐 | 用户提出明确主题 | “我在学习 Docker，有推荐吗” | 返回 Docker 相关文章，并说明命中原因 |
| 泛化推荐 | 用户没有主题 | “推荐几篇文章” | 返回最新/热门/精选文章，并说明是泛化推荐 |
| 当前文章相关推荐 | 用户在文章详情页 | “有没有类似文章” | 基于当前文章标题、分类、标签、摘要推荐相关文章 |
| 搜索文章 | 用户明确搜索 | “找一下 JWT 相关文章” | 调用站内搜索，返回匹配文章 |
| 无结果 | 站内没有相关内容 | “推荐 Kubernetes 文章”但无内容 | 明确说明没有找到，不用无关文章凑数 |
| 可解释推荐 | 推荐标题不明显但标签匹配 | 某文章标题不含 Docker，但标签含 Docker | 卡片理由显示“标签包含 Docker” |

## 4. 功能范围

### 4.1 必须实现

- 抽离独立文章发现服务，统一处理搜索、主题推荐、当前文章相关推荐和泛化推荐。
- 明确区分搜索与推荐：
  - 搜索：用户目标是“找某个关键词”。
  - 主题推荐：用户目标是“围绕某主题推荐内容”。
  - 泛化推荐：用户没有给主题时才推荐最新/热门文章。
- 对主题推荐必须先提取主题，再调用站内查询能力。
- 对候选文章进行相关性评分，至少支持标题、标签、分类、摘要维度。
- 每篇推荐结果必须返回推荐理由和匹配字段。
- 推荐结果必须返回稳定策略字段，至少区分 `topic_recommendation`、`search`、`related`、`general_latest`、`general_hot`、`empty`。
- 推荐结果必须返回可调试字段：`score`、`matchedFields`、`strategy`，前端可选择不展示 `score`，但类型契约必须保留。
- 如果用户指定主题但没有相关结果，不允许直接 fallback 到最新文章；必须诚实说明没有找到。
- 后端返回结构化契约，前端可直接渲染可点击卡片。
- 推荐和搜索工具调用必须记录在 Agent 工具调用审计中。
- 保持现有 Web 聊天和 Admin 侧边栏的对接兼容。
- 当前文章相关推荐必须支持并明确前端上下文字段：`postId`、`title`、`summary`、`categoryName`、`tagNames`，并排除当前 `postId`。
- 多主题输入必须有可预测处理规则：本期只选最高置信主题，其他主题进入 `secondaryQueries`，不同时混合无关结果。

### 4.2 可选增强

- 结合当前文章正文做相似推荐。
- 增加学习路径推荐，例如“Docker 入门 -> 部署实践 -> Nginx 反代”。
- 增加热度、发布时间、阅读量、点赞数作为排序辅助。
- 后续接入向量检索/RAG，用语义相似度替代部分关键词规则。

### 4.3 本次不做

- 不接入外部搜索引擎。
- 不引入向量数据库。
- 不重写主后端文章搜索体系。
- 不让大模型直接决定最终推荐列表。
- 不改变文章发布、草稿、上下架等管理流程。

## 5. 非目标范围

- 不解决博客内容不足的问题；如果站内没有相关文章，应诚实反馈。
- 不保证推荐一定符合所有用户偏好；本期以主题相关性和可解释性为第一目标。
- 不把推荐逻辑散落在前端；核心判断必须在后端完成。
- 不依赖自然语言解析文章卡片；前端只消费结构化字段。
- 不把 `score` 当成用户可见价值判断；它主要服务调试、排序和审计，UI 默认展示自然语言 reason。
- 不把文章发现能力做成新的万能服务；它不负责管理员写操作、不负责 LLM 聊天、不负责 SSE 发送、不负责权限认证，只负责文章发现相关决策。

## 5.1 AI 架构防臃肿原则

本功能必须遵守以下边界，避免 AI 模块继续向巨型服务演化：

- `AgentOrchestrator` 只负责编排：识别意图、创建任务、调用专用能力、组装响应；不继续承载推荐评分、主题提取、候选排序等细节。
- 文章发现能力必须拆成小职责：
  - Query/Context 解析：从用户消息和页面上下文得到主查询、辅助查询、当前文章信息。
  - Candidate Retrieval：调用公开文章工具获取候选文章。
  - Ranking：对候选文章打分、去重、过滤。
  - Explanation：生成 `reason`、`matchedFields`、`score`、`strategy`。
  - Contract Mapping：把内部结果映射成前端稳定 DTO。
- `PublicArticleTool` 只负责工具调用和缓存，不负责业务排序。
- `BlogApiClient` 只负责跨服务 HTTP 调用和 DTO 解析，不负责推荐策略。
- `ArticleResultItem` / `ArticleResultsPayload` 只作为响应契约，不承载业务方法。
- 任何单个 application 类超过 250 行，或同时出现“解析、检索、排序、响应文案、审计”三类以上职责时，必须拆分。
- 本期不引入 LangChain/LangGraph 这类重框架；当前问题是服务边界和推荐管线，不是缺少框架。
- 后续接入 RAG 时，只能作为新的候选召回源加入 Candidate Retrieval，不允许推翻现有结构化契约。

## 6. 用户流程

主题推荐流程：

```text
1. 用户输入“我在学习 Docker，有推荐吗”。
2. 前端判断为 Agent 任务，携带 token 和页面上下文请求 AI 服务。
3. AI 服务识别为主题推荐。
4. 文章发现服务提取主题“docker”。
5. 文章发现服务调用站内查询接口获取候选文章。
6. 文章发现服务计算候选文章相关性分数和匹配字段。
7. 系统返回文本说明和结构化文章卡片。
8. 前端展示标题、摘要、分类、标签、推荐理由和跳转入口。
```

无结果流程：

```text
1. 用户输入明确主题。
2. 文章发现服务查询不到相关结果。
3. 系统返回“我没有找到和该主题直接相关的文章”。
4. 系统可建议换关键词或查看泛化分类，但不能自动混入无关最新文章。
```

当前文章相关推荐流程：

```text
1. 用户在文章详情页询问“有没有类似文章”。
2. 前端携带当前 postId、title、category、tags。
3. 文章发现服务优先基于当前文章标签和分类生成查询主题。
4. 返回排除当前文章后的相关文章。
```

## 7. 业务规则

- 主题优先规则：用户输入中存在明确主题时，推荐必须围绕主题执行。
- 无主题规则：只有无法提取主题且没有当前文章上下文时，才走最新/热门文章。
- 不凑数规则：指定主题无匹配时，不用无关文章补满数量。
- 可解释规则：每个推荐项必须说明至少一个推荐原因。
- 排序规则：标题、标签、分类、摘要命中应有明确权重；热度和时间只能作为同分辅助，不能让弱相关文章压过强相关文章。
- 去重规则：多路召回的文章按文章 ID 去重，只保留最高分和最清晰的 reason。
- 排除规则：当前文章相关推荐必须排除当前文章自身。
- 阈值规则：主题推荐必须设置最低相关性阈值；低于阈值的文章不进入 `article-results`。
- 可点击规则：每个推荐项必须包含前端可跳转路径。
- 权限规则：公开推荐只返回已发布文章；管理员视角可在后续扩展草稿/管理入口，但本次默认公开可见结果。
- 审计规则：Agent 工具调用必须记录 query、strategy、结果数量、耗时、成功/失败。
- 代码边界规则：推荐、搜索、相关推荐的业务逻辑不得直接写在 Controller、SSE Publisher 或前端组件中。

## 8. 交互与体验要求

- 前台看板娘对主题推荐应明确说“我按 Docker 帮你找了相关内容”。
- 如果推荐项标题不明显，应展示理由，例如“标签包含 Docker”。
- 无结果时应避免尴尬兜底，文案应自然但诚实。
- 前端卡片沿用当前文章卡片体验，不新增复杂 UI。
- 管理后台侧边栏如复用文章推荐，也应使用同一结构化契约。

Then 推荐结果应优先来自当前文章的标签、分类或主题，并排除当前文章。

AC6：
Given 推荐/搜索返回文章卡片
When 前端渲染
Then 每项至少包含 `id/title/summary/status/url/reason/source/score/matchedFields`，用户可点击跳转。

AC7：
Given Agent 执行推荐工具
When 工具执行完成

AC8：
Given 用户在文章详情页询问“有没有类似文章”

Then 推荐结果不得包含当前文章自身。

AC9：
Given 用户输入“推荐 Docker 和 Nginx 相关内容”
When 系统执行主题推荐
Then 系统应选择一个主查询并在响应中保留 `secondaryQueries`，不得把两个主题的低相关结果混合成不可解释列表。

AC10：
Given 主题推荐候选文章只在正文弱命中且标题/标签/分类/摘要均不匹配
When 已存在强匹配文章
Then 弱匹配文章不应进入推荐卡片。

Given 后续实现文章发现推荐引擎

AC12：
Given 后续扩展 RAG 或语义搜索
When 新增候选召回能力
Then 不应改变前端 `article-results` 基础契约，只能扩展 `source/strategy/matchedFields` 等兼容字段。

## 10. 安全、性能与合规边界

- 推荐属于 AI/跨服务调用核心链路，需要限制接口超时和结果数量。
- 不记录 JWT、API Key、完整正文或敏感用户信息。
- 公开推荐仅返回公开文章。
- 主题提取和评分应可测试，避免完全依赖模型不可控输出。
- 对常见查询可继续使用短 TTL 缓存。
- 缓存 key 必须包含 strategy、query、上下文 postId 和 limit，避免不同推荐场景互相污染。
- 工具审计日志只记录输入摘要、策略、数量和耗时，不记录完整文章正文。
- 目标首包体验：Agent 应先返回计划/开始事件，再执行查询；纯工具查询应尽量在 1 秒内完成。

## 11. 约束与假设

- 假设主后端已有 `/posts/search`、`/posts/latest`、`/posts/hot` 等基础公开接口。
- 假设文章列表数据中可获得标题、摘要、分类、标签、状态、跳转路径。
- 假设本期不新增全文索引或向量索引，只在 AI 服务侧做候选排序和解释。
- 假设前端已支持 `article-results` 事件并能展示文章卡片。
- 假设主后端搜索可能返回“正文弱命中”的候选文章，因此 AI 服务侧仍需要二次评分和阈值过滤。

## 13. 需求审查记录

### 13.1 与当前代码一致的部分

- 当前 Web 已能基于关键词触发 Agent，并消费 `article-results` 事件。
- AI 服务已有 `PublicArticleTool`、`BlogApiClient`、`ArticleResultItem`、工具调用审计和短 TTL 缓存。
- 已验证主题推荐可以通过 `query=docker` 调用站内搜索，并返回结构化文章结果。

### 13.2 与当前代码或架构冲突的部分

- 当前 `AgentOrchestrator` 仍承担推荐、关键词抽取、排序和文案职责，长期会膨胀。
- 当前推荐结果缺少正式的 `strategy`、`score`、`matchedFields` 契约。
- 当前前端 `PostSummaryDTO` / `ArticleResultItem` 类型还没有 `score`、`matchedFields`、`strategy`、`secondaryQueries` 字段。
- 当前 `ArticleResultsPayload` 后端响应还没有 `strategy`、`secondaryQueries`、`totalCandidates`、`filteredCount` 等调试字段。
- 当前关键词抽取仍是轻量规则，不能覆盖复杂中文表达和多主题请求。

### 13.3 安全与性能风险

- 如果继续在编排器里堆规则，推荐质量会越来越难验证。
- `AgentOrchestrator` 当前已经约 500 行，是首要膨胀点；文章发现实现必须从其中迁出推荐相关细节。
- `AiChatServiceImpl` 当前已经约 700 行，是历史膨胀点；本功能不得继续向旧聊天服务追加文章发现逻辑。
- `BlogApiClient` 当前同时包含文章、分类、作者资料等公开 API 访问，后续可拆 `PublicBlogClient`，但本期重点是不要再把推荐策略写进去。
- 如果无结果时 fallback 最新文章，会损害用户信任。
- 如果前端只能看到自然语言原因，后续调试推荐质量会困难。

### 13.4 需要用户决策的问题

- 是否确认本期把 `ArticleDiscoveryService` 作为独立模块实现。
- 是否确认文章发现模块按 QueryParser / CandidateRetriever / Ranker / ExplanationBuilder / Mapper 拆分，而不是做成一个大服务类。
- 是否确认返回 `score/matchedFields/strategy` 字段。
- 是否确认主题无结果不混入最新文章。
- 是否确认多主题输入本期采用主主题优先，不做复杂混合推荐。

### 13.5 调整结论

- 保持原智能看板娘需求，但将搜索/推荐升级为独立文章发现能力。
- 推荐的核心目标从“有文章可展示”调整为“相关、可解释、可点击、可审计”。
- RAG/向量搜索继续放入后续扩展。
