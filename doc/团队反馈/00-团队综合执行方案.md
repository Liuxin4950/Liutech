## 一、团队结论汇总

### 1.1 项目定位（项目主管）
在校生作品里属第一梯队：双后端微服务 + 双前端 + Docker 编排 + SSE 流式 + AI MCP + 熔断限流，500+ 提交。技术广度达标，但**半成品多、风格不统一**是面试致命伤。

### 1.2 lead 亲验的高影响结论（10 项全部属实）
1. CLAUDE.md 引用的 `doc/记录/当前架构.md`、`LiuTech/API文档.md` 均不存在（坏链）
2. PostsController(web) 在 `/posts` 下混入 5 个 ADMIN 写操作，与 PostsAdminController 重叠
3. ChatRequest 无 `draft` 字段；WritingTools 仅 2 工具，无读取/修改文章能力
4. StreamingChatService 实发 6 种 SSE 事件，前端期望的 field-update/writing-draft/tool-start/tool-result/agent-plan/confirmation 全不发--admin 写作协议断裂
5. 前端 inferFieldScope 关键词匹配推断意图（脆弱），quickPrompts 有"保存为草稿/发布"但后端无落库链路
6. BaseAdminController.handleException 与 GlobalExceptionHandler 职责重复
7. GlobalExceptionHandler 完善兜底（业务/参数/HTTP/上传/DB/权限/兜底全链路），**Controller 去 try-catch 安全可行**
8. docker-compose 所有服务端口暴露公网（MySQL/8080/8081/3000/3001）
9. AI 服务 actuator 全量暴露 permitAll（prometheus 暴露指标，health show-details 暴露 DataSource）
10. DB 用 root 账户连接

## 二、lead 裁决（交叉质疑关键决策）

| 议题 | 裁决 | 理由 |
|------|------|------|
| AI 写作：补后端 vs 砍前端 | **补后端，端到端打通核心链路**；plan/tool/confirmation 等高级事件后置 | 架构师有完整方案，PM 评估 3 天，是项目最大差异化亮点；砍前端浪费已写 UI。但分阶段，先打通"读草稿→给修改→写表单"主链路 |
| UserController 下沉 | 下沉到 UserAuthService，**不独立 PasswordService**（避免过度拆分） | 现有 UserAuthService 已处理认证，resetPassword/emailLogin 同属认证编排，归一处；依赖可通过构造器注入管理，未过载 |
| AI 隔离 | 采纳架构师 ToolRegistry + ToolGroup 方案，三层防御纵深 | 当前按 ChatMode 硬编码分派缺防御纵深 |
| 积分测试 | 优先 Testcontainers + MySQL（保真），H2 兼容性风险高 | 待测试核实 Mapper XML 后定，但倾向 Testcontainers |
| 重构顺序 | Controller 瘦身 → AI 写作端到端 → 安全加固 → 测试 CI → 文档 | 先低风险高收益热身，再核心亮点，再加固 |

## 三、分阶段执行方案

### P0-A：Controller 瘦身（低风险高收益，立即实施）

**目标**：消除分层污染，统一异常处理风格，Controller 回归"接收参数→调 Service→返回 Result"。

| 文件 | 改动 | 风险 |
|------|------|------|
| `PostsAdminController` | 删 14 处 try-catch，异常直接抛出由 GlobalExceptionHandler 兜底 | 低 |
| `BaseAdminController` | 删 `handleException`/`handleOperationResult`，保留或改造 `checkResourceExists` | 低 |
| `PostsController` | 删 5 处 try-catch + 9 处冗余 `getCurrentUserId()==null`；ADMIN 写操作(createPost/updatePost/deletePost/publishPost/unpublishPost)迁移到 PostsAdminController | 中（路由变化，需同步前端） |
| `UserController` | resetPassword/emailLogin 业务逻辑下沉到 UserAuthService；删手动 BeanUtils+脱敏 | 中（认证敏感，需测试覆盖） |
| `AnnouncementsController` | admin 接口拆分到 AnnouncementsAdminController；5 个内部 DTO 独立到 req/ | 中 |
| `FileUploadController` | 7-8 个 @RequestParam 封装为 DTO；内部 DTO 独立 | 低 |

**安全前提**（已验证）：GlobalExceptionHandler 完善兜底；`@PreAuthorize` 保证认证。无 `@PreAuthorize` 但依赖 userId 的接口（如 toggleLike）**不删 null 检查**，改在 SecurityConfig 或 service 层处理。

### P0-B：admin 写作端到端打通（核心亮点）

**目标**：AI 能读取当前文章草稿，制定修改（标题/摘要/正文/分类/标签），结构化回写表单。

后端改动：
1. `ChatRequest` 加 `draft` 字段（`AdminArticleDraftSnapshot`：postId/title/content/summary/categoryId/tagIds）
2. `PromptService` 处理 `admin-post-editor` 上下文，将 draft 注入为**不可信上下文**（包裹边界防注入）
3. 新增写作专用系统提示词（角色=写作助手，输出格式=field-update JSON），与聊天模式隔离
4. 新增 `AdminPostTools`（@ToolGroup ADMIN）：`getArticleDetail`/`listCategories`/`listTags`
5. `StreamingChatService` 写作分支：解析 AI 输出的 `---field-update---` JSON 标记，发 `field-update` SSE 事件
6. ToolRegistry 按 ADMIN 角色注册 AdminPostTools + WritingTools

前端改动：
7. `AdminAgentSidebar` quickPrompts 补"读取并优化当前文章"
8. field-update diff 预览（正文改动确认后再应用，DOMPurify 已有）
9. 清理空转的 plan/tool/confirmation handler（暂不发的事件标注 TODO 或移除，避免面试官看到空壳）

### P0-C：安全加固

1. `docker-compose.yml`：生产仅暴露 80/443/81，其余去 ports 映射
2. AI 服务 `application.yml`：actuator exposure 限 health，`show-details: when-authorized`
3. SQL 初始化脚本：创建 `liutech_app`/`liutech_ai_app` 非 root 用户，最小权限
4. nginx：加安全 headers（X-Frame-Options/X-Content-Type-Options/HSTS），Admin 81 端口上 TLS
5. JWT_SECRET/TTS_PROXY_INTERNAL_TOKEN 加 `:?required` 必填校验

### P1：测试与 CI

1. 新增 `.github/workflows/ci.yml`：PR/push 跑 `mvn test`（后端）+ `npm run build`（前端），deploy 依赖 ci 通过
2. UserController 下沉后补 `UserAuthService` 单测（resetPassword/emailLogin 编排）
3. 积分乐观锁集成测试（Testcontainers + MySQL）
4. Web 前端补 `stores/user.ts`、`services/agent.ts` SSE 解析单测（vitest 已配好，补 setup.ts）

### P1：文档与架构隔离

1. 修复 CLAUDE.md 坏链（补 `doc/记录/当前架构.md` 或删引用）
2. AI 服务 ToolRegistry + ToolGroup 按角色过滤（P0-B 第 6 项）
3. 统一两份 docker-compose（部署脚本从仓库读取，不内联生成）
