**1. 工程基础设施扎实**

## 最大短板（面试视角，按致命程度排序）

### 1. Controller 层异常处理风格严重不统一（最致命）

这是面试官翻代码时最先看到的东西，也是最容易暴露问题的地方：

- `PostsController`（web 端）：每个方法自己写 try-catch，手动返回 `Result.fail(ErrorCode.SYSTEM_ERROR)`，日志大量 `log.info` 堆在每个方法里
- `PostsAdminController`（admin 端）：用 `BaseAdminController` 的 `handleException()` 统一处理，但本质还是在 Controller 层 try-catch
- 同时项目已经有 `GlobalExceptionHandler`（`@RestControllerAdvice`）做了全局异常兜底

**问题是**：你已经有全局异常处理器了，Controller 层就不该再写 try-catch。现在等于做了两层异常处理，而且风格不一致——一个 Controller 用 `@Autowired` 字段注入，另一个用 `@RequiredArgsConstructor` 构造器注入；一个手动 catch，一个走基类。面试官会问"为什么同一个项目两套风格"，如果你答不上来，就会暴露对架构一致性缺乏把控。

### 2. AI 写作助手是半成品，但前端已经写了大量 UI 代码

`AdminAgentSidebar.vue` 有 590 行，定义了完整的 Agent 交互流程：plan steps、tool events、field updates、writing draft、confirmation，类型定义（`agent.ts`）也很完整。但后端 `WritingTools` 只有两个工具（`listCategories`、`listTags`），且写作助手的前端期望的事件类型（`agent-plan`、`agent-start`、`tool-start`、`tool-result`、`writing-draft`、`field-update`、`confirmation-required`）在后端 SSE 事件中并没有全部实现。【待质疑：此结论基于静态代码分析。`StreamingChatService.subscribeStream` 只发送 start/data/avatar-cue/audio/article-results/complete 等标准事件，未发现生成 agent 专属事件的代码路径。但可能存在我没读到的中间件或拦截器层，需与架构师确认前端 agent.ts 的事件 handler 是否有实际被触发的路径。】

**面试风险**：面试官如果点开这个组件问"这个 Agent 能做什么"，你展示的是一个看起来很完整的 UI，但实际跑起来 AI 返回的事件和前端期望的对不上。这是作者自述的"做了一半"的部分，但前端 UI 的完成度会给人"已经做完了"的错觉，反而更危险。

### 3. 过度设计的痕迹明显

作者自己已经意识到这个问题。具体表现：

- `AdminArticleDraftSnapshot`、`WritingDraftPayload`、`FieldUpdatePayload` 等类型定义了大量字段（`suggestedCategoryName`、`suggestedTagNames`、`coverPrompt`、`notes`、`checks`、`htmlSafe`），但后端 WritingTools 连基本的"读取当前文章内容让 AI 修改"都没实现
- `AiChatController` 里的 `markLegacyRoute` 方法在每个接口都调，但注释说"后续如引入 v2 版本可用来区分"——这是提前设计了用不到的东西
- `AdminAgentSidebar.vue` 的 `inferFieldScope` 方法用关键词匹配推断用户意图（`hasAny('写一篇', '生成一篇', '新文章'...)`），这种设计脆弱且不可维护

### 4. 日志规范混乱

`PostsController` 里每个方法开头都有 `log.info("查询文章列表 - 页码: {}, 大小: {}, ...")`，结尾又一条 `log.info("查询文章列表成功 - 总数: {}, ...")`，成功路径大量 info 日志会污染生产日志。而 `PostsAdminController` 又几乎没日志。应该统一用 `log.debug` 记录正常流程，`log.warn` 记录业务异常，`log.error` 记录系统异常。

### 5. 前端零测试

0 个前端测试文件。后端有 45 个测试文件，前端一个都没有。如果面试官问"前端怎么保证质量"，目前只能靠手动测试。至少核心的 API service 层（`agent.ts` 的 SSE 事件解析、`api.ts` 的请求封装）应该有单元测试。

### 6. PostsController 职责过重

`PostsController` 放在 `controller/web` 包下，但同时承担了用户端功能（列表、详情、搜索、点赞、收藏、草稿箱、我的文章、收藏列表）和管理端功能（创建、更新、删除、发布、下线——全部加了 `@PreAuthorize("hasRole('ADMIN')")`）。而 `PostsAdminController` 也有创建、更新、删除、发布、下线。**两个 Controller 的功能重叠了**，同一个"创建文章"操作有两个入口（`POST /posts` 和 `POST /admin/posts`），逻辑分叉容易出 bug。【待质疑：未验证前端 Admin 实际调用的是 `/posts` 还是 `/admin/posts`。如果 Admin 前端只调用 `/admin/posts`，那 PostsController 里的 ADMIN 写操作接口就是死代码，严重程度从"逻辑分叉"降为"残留死代码"。需与测试同事确认前端路由实际调用情况。】

## 学习路线建议（按优先级）

### P0：分层架构思想（最急需）

你目前的代码暴露出对"Controller 层该做什么、Service 层该做什么"的边界不够清晰。Controller 层应该只做三件事：接收参数、调用 Service、返回结果。异常处理交给 `@RestControllerAdvice`，日志交给 AOP 或 Service 层。

**具体补习**：
- 重读 Spring MVC 的 `@RestControllerAdvice` + `@ExceptionHandler` 机制，理解全局异常处理的优先级链
- 学习"瘦 Controller / 胖 Service"模式，Controller 不应该有 try-catch、不应该有业务判断逻辑
- 对比 `PostsController`（web，手动 catch）和 `PostsAdminController`（admin，走基类），理解为什么不统一是问题

### P1：设计模式与过度设计的辨别

你已经有意识在用一些模式（`BaseAdminController` 模板方法、`ChatServiceHelper` 提取公共逻辑、策略模式 `AiModelPolicy`），但还缺乏"什么时候不该用模式"的判断力。

**具体补习**：
- 读《重构》第 8 章"重新组织数据"和第 11 章"简化函数"，理解"过早抽象比不抽象更危险"
- 实践 YAGNI 原则（You Aren't Gonna Need It）：`markLegacyRoute` 这种"以后可能用到"的代码就是典型的反例
- 对比 `AdminAgentSidebar.vue` 的 `inferFieldScope` 和简单的"让 AI 自己判断要改哪些字段"，理解为什么后者更好

### P2：测试思维

后端测试做得不错（45 个文件），但存在两个问题：一是前端完全没测试，二是后端测试主要集中在 Controller 层的 mock 测试，Service 层和 Mapper 层的集成测试缺失。

**具体补习**：
- 学习 Vitest（Vue 3 生态首选），给 `agent.ts` 的 SSE 事件解析逻辑写测试
- 学习 `@SpringBootTest` + `@Transactional` 的集成测试模式，至少给 `PostsService` 的核心方法写几个集成测试
- 理解测试金字塔：单元测试（Controller mock）-> 集成测试（Service + Mapper）-> E2E 测试（目前缺失）

### P3：安全意识深化

你已经做了不少安全相关的工作（JWT、白名单、SecureRandom、密码强度），但还有一些需要加强：

**具体补习**：
- 学习 OWASP Top 10，特别是 SSRF（AI 服务调用外部 API）、IDOR（越权访问，如 `/posts/{id}/drafts` 是否校验了作者身份）【待质疑：从代码看 `PostsController.getDrafts` 会设置 `req.setAuthorId(authorId)` 做过滤，且 SecurityWhitelist 把 `/posts/drafts` 列入 AUTHENTICATED_PATHS 需登录。但未验证是否存在路径匹配绕过的可能性（如 `/posts/drafts/` 带尾斜杠），需与架构师深入审查 SecurityWhitelist 的 startsWith 匹配逻辑是否严谨。】
- 理解 CORS 配置的安全性：`setAllowedOriginPatterns` 用具体域名而不是 `*` 是对的，但 `setAllowCredentials(true)` + `setAllowedHeaders("*")` 组合在生产环境需要审视
- 学习 API 限流：你已经有 `AiRateLimitInterceptor`，但主后端没有限流

### P4：DevOps 和可观测性

Docker 部署做得不错，但可观测性几乎为零。

**具体补习**：
- 学习 Spring Boot Actuator 的健康检查、指标暴露（你已经有 `/actuator/health`，但没有用到 `/actuator/metrics`）
- 学习结构化日志（JSON 格式），便于 ELK/Loki 采集
- 理解容器化下的日志收集策略（stdout -> 日志驱动 -> 集中收集）

## 面试话术建议

### 加分故事（主动讲这些）

**故事 1：AI 服务的 SSE 流式响应踩坑**
"做 AI 聊天流式响应时，我遇到过 SSE 连接被 Nginx 缓冲导致前端收不到流式数据的问题。排查后发现 Nginx 默认开启了 `proxy_buffering`，需要显式关闭并提高 `proxy_read_timeout`。另外还遇到 SSE 流式输出后 Spring Security 的 `SecurityContextHolder` 被清空，导致认证异常处理器试图在已提交的 event-stream 上写 JSON，破坏了响应格式。我用 `RequestAttributeSecurityContextRepository` 替换默认的上下文存储，并在认证异常处理器里判断 SSE 请求是否已提交来跳过写入。"
——这个故事展示了真实的问题排查能力和对 HTTP/Security 底层的理解。

**故事 2：从单体到微服务的拆分决策**
"最初 AI 聊天功能在主后端里，后来发现 AI 调用耗时长、需要独立的数据库（聊天记录和模型配置），而且熔断/限流策略和主后端的业务逻辑耦合在一起不好维护。我把 AI 功能拆成独立服务，通过 Nginx 路径前缀 `/ai/` 做路由隔离，两个服务共享 JWT_SECRET 做统一认证。"
——这个故事展示了架构决策的思考过程。

**故事 3：Caffeine 缓存替代 Redis 的技术选型**
"博客是单人运营的，QPS 很低，引入 Redis 会增加运维成本。我用 Caffeine 本地缓存 + 多级 TTL 策略，对文章列表、热门文章、标签、分类分别设置不同的过期时间。写操作时用 `@CacheEvict(allEntries=true)` 清除相关缓存。"
——这个故事展示了"不盲目选热门技术"的务实思维。

### "AI 帮你写了多少"怎么答

这个问题几乎所有用 AI 辅助开发的应届生都会被问到。建议这样回答：

"我用了 AI 辅助开发，但方式是在不断变化的。早期我自己写核心架构和业务逻辑，AI 主要帮我生成重复性的 CRUD 代码和写注释。中期我让 AI 参与了一些功能模块的开发，但后来发现代码风格不统一、部分设计过度复杂——这正是我这次重构要解决的问题。现在我的做法是：核心架构和安全相关的代码我自己写，AI 辅助生成测试用例和文档，功能代码写完后我逐行 review 再合入。这个项目让我学到最重要的一课是：AI 是很好的代码生成工具，但架构决策和代码一致性必须由人把控。"

这个回答的优点：诚实（承认用了 AI）、有反思（说出了具体问题）、有成长（讲了现在的做法变化）、有技术深度（把 AI 使用策略和工程实践联系起来）。

## 如果时间有限的最终取舍（最该做的 3 件事）

> 【待质疑（与 PM 互校）：以下 3 件事的核心立场是"不加新功能，先打磨现有代码一致性"。如果 PM 的 P0 路线图包含新功能开发（如完善 AI 写作助手端到端），则我的第 2 件事与 PM 可能存在优先级冲突。我的判断是：先砍 UI 到匹配后端能力，再逐步补功能；如果 PM 认为写作助手端到端是 P0，则需重新评估第 2 件事的策略选择（策略 A vs 策略 B）。】

### 第 1 件：统一 Controller 层异常处理风格（1-2 天）

这是 ROI 最高的一件事。具体操作：

1. 删掉 `PostsController` 所有方法里的 try-catch，让异常直接抛出，交给 `GlobalExceptionHandler` 统一处理
2. 删掉 `BaseAdminController` 的 `handleException` 方法，admin Controller 也不再 try-catch
3. 把 `PostsController` 里的 `log.info` 降级为 `log.debug`，或者干脆删掉（异常日志交给 GlobalExceptionHandler 和 Service 层）
4. 统一依赖注入方式：全部用 `@RequiredArgsConstructor` 构造器注入，删掉所有 `@Autowired` 字段注入
5. 把 `PostsController` 里的 ADMIN 写操作接口（createPost/updatePost/deletePost/publishPost/unpublishPost）移到 `PostsAdminController`，消除功能重叠

做完这件事后，面试官翻任何一个 Controller 都能看到一致的风格——这就是"架构把控力"的直接证据。

### 第 2 件：给 AI 写作助手定一个明确的"最小可用"边界（2-3 天）

当前 `AdminAgentSidebar.vue` 的前端 UI 远超后端能力。有两种策略：

**策略 A（推荐）：砍前端 UI 到匹配后端能力**
- 保留：文本输入、流式回复展示、快捷指令
- 去掉：plan steps 进度条、tool events 展示、confirmation 流程、field-update 自动写入
- 后端 `WritingTools` 增加 `getPostDetail` 工具（让 AI 能读取当前编辑的文章内容），增加 `suggestTags` 工具【待质疑：WritingTools 当前复用 BlogApiClient 的公开 API（GET /tags、GET /categories）。如果加 `getPostDetail`，需要确认 BlogApiClient 是否已有此方法（BlogMcpTools 中有 `getPostDetail` 但走的是公开接口 GET /posts/{id}），还是需要新增管理员级别的文章读取接口。需与架构师确认接口复用策略。】
- 面试时讲："写作助手目前支持 AI 读取当前文章内容并给出修改建议，用户手动复制到编辑器。下一步计划是做字段级别的自动回写，但目前在 SSE 事件协议设计阶段。"

**策略 B：补完后端 SSE 事件协议**
- 后端实现 `agent-plan`、`tool-start`、`tool-result`、`writing-draft`、`field-update` 等事件
- 这个工作量大，风险高，如果时间紧张不建议

无论选哪个策略，关键是**不要让面试官看到一个看起来完整但实际跑不起来的 UI**。

### 第 3 件：写一个 README 级别的"架构决策记录"（半天）

在 README 或单独文件中，用 3-5 段话讲清楚以下决策的"为什么"：

1. 为什么拆成两个后端服务而不是单体
2. 为什么用 Caffeine 而不是 Redis
3. 为什么用户 AI 和管理员 AI 的工具要分开
4. 为什么 AI 服务要做熔断限流
5. 安全白名单为什么抽成独立常量类

面试官看到这些会认为你有架构决策能力。而且这些内容你在面试中也要讲，写下来相当于提前准备了话术。

## 给学生的话

刘鑫，看完你的代码我想说几句实在话。
