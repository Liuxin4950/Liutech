## 2. nginx 配置评估

**架构说明：** 三层 nginx -- 容器内 nginx（Web/Admin 各一个）做 SPA 路由 + 本地代理，根 nginx（`nginx/conf.d/default.conf`）做统一反向代理/HTTPS/SSE。

**做得好的部分：**
- HTTPS 配置完整：TLS 1.2/1.3、HSTS-grade cipher suite、HTTP->HTTPS 301 重定向
- SSE 配置正确：`proxy_buffering off`、`proxy_request_buffering off`、`proxy_read_timeout 3600s`
- CORS 处理分场景：API 用 `cors.include`（通配 `*`），AI 服务用动态 `$http_origin`（因需 `Allow-Credentials: true`）
- gzip 配置合理，`client_max_body_size 100M` 与后端 multipart 限制一致
- 上传文件路径有 30 天长缓存 + `immutable`，减少回源
- 已修复的 406 问题（移除强制 `Accept: text/event-stream`）有注释说明，体现了踩坑后的经验沉淀

**问题清单：**

| # | 严重度 | 问题 | 位置 |
|---|--------|------|------|
| 1 | **高** | Admin 后台走明文 HTTP（端口 81） | `default.conf` L131-211 | Admin 管理后台监听 81 端口，无 TLS。管理员登录凭据、JWT token 全部明文传输。应在 81 端口也配 SSL，或用不同 server_name + 443。【待质疑→PM：Admin 加 HTTPS 是否影响现有访问方式？端口 81 是否有外部依赖（如书签、监控告警）需同步更新】 |
| 2 | **中** | API 的 CORS 配置为 `Access-Control-Allow-Origin *` | `cors.include` L2 | API 接口允许任意来源跨域，虽然不带 credentials（`Allow-Credentials` 未在 cors.include 中设置），但通配源仍增加了攻击面。建议限制为已知域名 |
| 3 | **中** | SSL 配置缺少 HSTS | `default.conf` L30-39 | 缺少 `Strict-Transport-Security` header。加上 HSTS 可防止首次访问的中间人降级攻击 |
| 4 | **中** | 缺少安全 headers | `nginx.conf` / `default.conf` | 缺少 `X-Content-Type-Options nosniff`、`X-Frame-Options DENY`、`X-XSS-Protection` 等基础安全头 |
| 5 | **低** | upstream 无容错配置 | `default.conf` L6-20 | `upstream backend_servers { server backend:8080; }` 只有单节点，没有 `max_fails`、`fail_timeout`、`backup` 等配置。单节点场景影响不大，但加上 `max_fails=3 fail_timeout=30s` 可更快感知故障 |
| 6 | **低** | AI 服务 CORS 重复定义 | `default.conf` L73-106 和 L157-190 | 443 server 和 81 server 的 `/ai/` location CORS 配置完全相同，应抽取为 include 文件复用 |

## 4. 部署流程评估与坑点

**两套部署链路对比：**

| 维度 | 方式 A（离线打包） | 方式 B（DockerHub CI/CD） |
|------|-------------------|-------------------------|
| 可靠性 | 高，全程离线，不依赖网络 | 中，依赖 DockerHub 可达性 |
| 可复现性 | 中，两份 compose 有偏差 | 高，compose 从仓库同步 |
| 安全性 | 中，需手动管理 .env | 中，secrets 在 GitHub |
| 适用场景 | 国内服务器 | 海外/有代理 |

**主要坑点：**

1. **两份 docker-compose.yml 偏差**：仓库根目录的 `docker-compose.yml` 和 `服务器部署脚本.sh` 内联生成的是两份不同配置。脚本版本有 `SPRING_PROFILES_ACTIVE=prod` 但缺 healthcheck 和 resource limits；仓库版本有 healthcheck 但缺 `SPRING_PROFILES_ACTIVE=prod`。实际生产用的是脚本版本。应消除偏差，只用一份。

2. **本地打包脚本 `快速打包文件.bat` 直接 `docker build`，不走 Docker BuildKit 缓存优化**：每次全量构建。对于学生项目影响不大，但可以加 `DOCKER_BUILDKIT=1` 提速。

3. **`deploy.yml` 的部署步骤有服务中断**：`docker compose down` -> `docker compose pull` -> `docker compose up -d`，期间所有服务停机。正确做法：先 `pull` 再 `up -d --force-recreate`，docker 会逐个重建容器，中断窗口更小。

4. **镜像导出脚本无错误处理**：`镜像导出脚本.bat` 没有 `set -e` 等效机制，某个 `docker save` 失败后继续执行，可能产出不完整的 tar 包。

5. **SSL 证书路径硬编码**：nginx 配置中证书路径 `liuxin.chat_bundle.crt` 和 `liuxin.chat.key` 是硬编码的。换域名需要改配置文件。可接受，但值得注意。

## 5. 可观测性现状

**健康检查：**
- MySQL：有 healthcheck（`mysqladmin ping`），配置合理
- Backend：有 healthcheck（`/actuator/health`），最近 commit `a64ac815` 修复了 healthcheck 误报（放行 `/actuator/health`），说明踩过坑并解决了
- AI：有 healthcheck（`/actuator/health`），同上
- Nginx/Web/Admin：**无 healthcheck**

**日志：**
- 后端：`logging.level` 配置在 `application.yml` 中，root=INFO，aspect=DEBUG。日志写入文件路径 `logs/` 但容器内无日志卷挂载，容器重启日志丢失
- AI 服务：日志写 `logs/liutech-ai.log`，同样无持久化卷
- Nginx：access.log / error.log 在容器内，无持久化

**监控：**
- AI 服务配置了 Prometheus 端点（`/actuator/prometheus`），但后端没有。即便有，也没有 Prometheus/Grafana 采集端
- 无告警机制

**结论：** 健康检查覆盖不全，日志无持久化，监控只有端点暴露但无采集。对于面试项目来说，能说到"我知道这些缺失并知道怎么补"就足够了。

## 6. 面试加分运维实践建议

以下按"投入产出比"排序，前几项改动小、面试加分明显。【待质疑→PM：以下优先级排序是否与产品迭代计划对齐？哪些可以安排在当前 refactor/blog-polish 分支，哪些放到后续】

1. **修复端口暴露（S1）**：生产 compose 只暴露 80/443/81，其余服务去掉 ports。面试时说"我做了网络分层，只有 nginx 暴露公网，内部服务走 Docker 内网通信"，直接体现安全意识。

2. **给后端加 management 配置 + 限制 actuator 暴露**：后端 `application.yml` 加 `management.endpoints.web.exposure.include: health`，AI 服务把 `show-details: always` 改为 `show-details: when-authorized`。面试说"我控制了 actuator 端点暴露范围，health 详情需要认证才能看"。

3. **加安全 headers**：nginx 加 `X-Frame-Options`、`X-Content-Type-Options`、`Strict-Transport-Security`。一行配置，面试聊 HTTPS 安全时能展开说。

4. **日志持久化**：给 backend 和 ai 加日志卷挂载（`./logs/backend:/app/logs`）。面试说"容器日志挂载到宿主机，重启不丢失"。

5. **创建非 root 数据库用户**：SQL 初始化脚本中创建 `liutech_app` 用户，只授 `liutech` 库权限；`liutech_ai_app` 只授 `liutech_ai` 库权限。面试说"数据库最小权限原则，应用不用 root 连接"。

6. **统一两份 compose**：让部署脚本从仓库读取 `docker-compose.yml` 而非内联生成。消除配置偏差。面试说"部署配置单一可信来源"。

7. **加 GitHub Actions CI 测试门禁**：在 `deploy.yml` 的 build 步骤前加 `mvn test`，测试不过不构建。面试说"CI 流水线包含测试门禁，测试不过不允许部署"。

8. **（加分项，非必须）Docker 网络隔离**：定义 `frontend` 和 `backend` 两个网络，web/admin/nginx 在 frontend，backend/ai/mysql 在 backend，nginx 跨两个网络。面试时画网络拓扑图，体现架构设计能力。

## 7. 给学生的话

你的部署方案在在校生中属于上游水平：离线打包链路设计、`${VAR:?}` 必填校验、部署脚本防呆检测、SSE 代理配置、actuator healthcheck 踩坑修复，这些都说明你有实际部署经验且会反思。这些经验在面试中讲出来，比"我用了 Docker"有说服力得多。

最需要优先修的是**端口暴露**和**actuator 端点过度暴露**，这两个是面试官如果懂运维一定会问的点。修法很简单（删掉 ports 映射、限制 exposure），但修不修体现的是你的安全意识。

建议按第 6 节的顺序逐项修，每修一项就在 commit message 里写清楚"为什么改、怎么验证"，这些 commit 本身就是面试素材。
