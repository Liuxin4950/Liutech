## 1. 问题 / 需求概述

- 背景：原 AI 模块更接近一次问答助手，缺少 Agent 任务、工具、确认和审计链路。
- 用户目标：把博客 AI 升级为智能看板娘，普通用户可聊天、总结、搜索和推荐文章；管理员可在写文章时获得辅助，并在确认后创建草稿、发布或下架文章。
- 本次要解决的问题：落地首版 Agent 领域包、结构化 SSE 契约、管理员确认流、Admin 编辑器侧边栏和数据库审计表。
- 本次不解决的内容：删除文章、RAG/向量检索、长期记忆、多 Agent 框架、完整 Python/LangChain 重构。

## 2. 原因定位

- 现象：旧 AI 服务已有聊天、推荐、模型配置和 SSE，但缺少多步任务状态、工具调用审计、写操作确认和前后端统一结果契约。
- 根因 / 缺口：功能按通用 `controller/service/dto` 累积，Agent 能力继续堆叠会让文件命名和职责边界变乱。
- 证据：实现 PRD 审查了 `AiChatServiceImpl`、`BlogApiClient`、`AiRecommendController`、`PostsAdminController` 和 `PostsManagement.vue` 等路径。
- 涉及模块：`LiuTech-AI`、`LiuTech`、`Admin`、`Web`、`sql`。

## 5. 实现内容

### 5.1 后端

- 新增 `/ai/agent/chat` 和 `/ai/agent/stream`，统一由 `AgentOrchestrator` 判断意图、生成计划、调用工具并返回结果。
- 新增 `/ai/agent/actions/{actionId}/confirm`，管理员确认后才执行写操作。
- Agent 新生成文章首次强制 `status=draft`；发布和下架必须先创建 `PENDING` action。
- 结构化搜索/推荐结果统一为 `ArticleResultsPayload` 和 `ArticleResultItem`，包含 `id/title/summary/status/url/adminUrl/reason/source`。
- `AdminBlogClient` 只通过主后端管理 API 写文章，并透传当前管理员 Bearer Token，不直写主库。
- 主后端文章发布、下架、状态更新改为读取当前登录用户 ID，避免审计操作者写死。
- `PublicArticleTool` 对搜索、最新、热门文章结果做短 TTL 缓存，降低连续对话重复查询主后端的开销。
- `AgentToolCallRecorder` 将只读工具和确认后的管理员工具执行写入 `ai_agent_tool_call`，记录成功、失败、耗时和压缩后的输入输出。
- `BlogApiClient` 与 `AdminBlogClient` 使用带超时的 `RestTemplate`，避免主后端异常时 Agent 请求长时间悬挂。

### 5.2 前端

- Admin 文章编辑弹窗右侧新增 `AdminAgentSidebar`。
- 侧边栏读取当前编辑器标题、正文、摘要、分类、标签和文章 ID，作为 Agent 草稿上下文。
- SSE 客户端按事件类型处理 `agent-plan`、`data`、`article-results`、`confirmation-required`、`action-result` 和 `complete`。
- 管理员可将 Agent 结果追加到正文、写入摘要、应用草稿预览或确认写操作。
- 前台 AI 文章摘要类型补齐结构化跳转字段。
- Web 聊天在推荐、搜索、总结等站内任务中走 `/ai/agent/stream`，普通闲聊仍走旧聊天流，保留既有 TTS/会话体验。
- Web 聊天可消费 `article-results` 事件，将后端结构化推荐/搜索结果渲染成可点击文章卡片。
- Admin AI 模型管理接口增加 `/ai/admin/models` 兼容路径，保证生产环境以 `/ai` 作为统一前端入口时不会 404。

### 5.3 数据库 / 配置 / 部署

- 新增 `ai_agent_task`，记录 Agent 任务、意图、输入、状态、结果摘要和错误。
- 新增 `ai_agent_action`，记录待确认和已执行的管理员写操作。
- 新增 `ai_agent_tool_call`，为后续工具调用审计和性能分析预留。
- 根目录 `sql/sql.sql` 为当前权威 SQL；已有环境按该文件与线上库差异补齐 Agent 表结构。
- Docker/Nginx 路由不新增入口，沿用 `/ai/` 转发 AI 服务。

## 6. 安全与性能处理

- 安全影响：涉及管理员写文章、发布、下架和 AI 生成富文本，属于高风险变更。
- 性能影响：Agent 会增加模型调用、主后端文章查询和 SSE 长连接。
- 已采取措施：写操作只允许管理员确认后执行；新文章第一次只能创建草稿；AI 服务不直连主库写文章；草稿快照增加长度限制；SSE 先发任务开始和计划，降低首包等待感；公开文章工具增加短 TTL 缓存；主后端调用增加超时；工具调用写入审计表。
- 遗留风险：当前意图识别仍是轻量规则，推荐仍基于现有文章列表接口；后续如要语义搜索和更强多步推理，需要引入 RAG 或更完整的 Agent 工作流。

## 8. 问题记录

| 问题 | 原因 | 处理方式 | 状态 |
| --- | --- | --- | --- |
| SSE 首包不够快 | 原实现先执行完整 Agent，再发送事件 | 改为流式入口先创建任务并发送 start/plan | 已处理 |
| `Map.of` 不能携带 null | 任务 ID 或会话 ID 可能为空 | 使用 `eventPayload` 过滤 null | 已处理 |
| 草稿请求缺少大小边界 | 管理端可能携带整篇正文 | 对标题、正文、摘要、标签和图片地址增加校验 | 已处理 |
| Agent 结果类型存在 `any` | 前端事件 payload 契约不够明确 | 增加 `ArticleResultsPayload`、`AgentCompletePayload`、`AgentErrorPayload` | 已处理 |
| Admin 构建首次 `spawn EPERM` | Windows 沙箱限制 Vite/esbuild 子进程 | 提权重跑 `npm run build` | 已确认通过 |
| 主后端测试首次临时目录清理失败 | Windows 沙箱限制 JUnit 清理临时目录 | 提权重跑 `mvn test` | 已确认通过 |
| 工具调用表未真正写入 | 首版先建了表，编排层未接入记录器 | 新增 `AgentToolCallRecorder` 并接入只读工具和管理员确认执行 | 已处理 |
| 连续推荐/搜索重复查询主后端 | 只读工具没有缓存 | `PublicArticleTool` 增加短 TTL 内存缓存和单次结果上限 | 已处理 |
| 跨服务调用可能长时间等待 | `RestTemplate` 没有显式超时 | `BlogApiClient` 和 `AdminBlogClient` 增加连接/读取超时 | 已处理 |
| AI 前端入口路径不一致 | 聊天使用 `/ai/**`，模型管理使用 `/admin/**`，生产前端统一从 `/ai` 代理进入时可能 404 | 模型管理增加 `/ai/admin/models` 兼容路径，Nginx HTTPS `/ai/` 保留前缀 | 已处理 |
| MySQL 8.0.44 不支持 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` | 迁移脚本使用了不兼容语法 | 改为 `information_schema` 检查 + prepared statement | 已处理 |
| “只保存草稿，不发布” 被识别成发布 | 意图识别先匹配了“发布”关键词，没有处理否定语义 | 调整分类规则并补测试 | 已处理 |
| 草稿内容已完整仍等待模型生成 | `mergeGeneratedDraft` 总是尝试模型补全文本 | 当前编辑器已有正文时只补标题/摘要并跳过模型调用 | 已处理 |
| 确认后 task/action 审计不闭环 | 确认服务只更新 action 结果，没有回填真实目标 ID 和 task 终态 | 确认成功后回填 `target_id`，同步 task 为 `COMPLETED`；失败或过期同步失败状态 | 已处理 |
| Windows PowerShell 5.1 执行脚本不稳定 | 中文路径/脚本编码在旧 PowerShell 下容易乱码或解析异常 | 本地开发改用 PowerShell 7 `pwsh` 或直接后台启动 Maven | 已确认 |
| “我是啥身份”回答成访客 | 前端将身份类问题走旧聊天流，模型没有使用 AI 服务已解析的 JWT 上下文 | 新增 `IDENTITY` Agent 意图，前端身份问题路由到 Agent，后端基于 JWT 上下文直接返回 `guest/user/admin` | 已处理 |
| Agent 普通闲聊响应偏慢 | 普通文本生成没有限制 maxTokens，短问题也可能等待较长模型输出 | Agent 文本生成增加 maxTokens 上限；身份、推荐、搜索等确定性任务不调用模型 | 已处理 |
| “学习 Docker，推荐文章”返回最新文章 | 推荐分支固定调用 `latestArticles`，没有使用用户消息中的主题关键词 | 推荐分支先提取主题，带主题时调用搜索工具；仅泛泛推荐才走最新文章 | 已处理 |
| 主题推荐理由不可解释 | 主后端搜索可能命中标签或摘要，但卡片只显示泛化理由，用户看标题会觉得不相关 | AI 服务侧增加相关性排序和理由细化，卡片显示“标题包含/标签包含/摘要提到” | 已处理 |
