## 1. 背景

当前 LiuTech-AI 已具备基础聊天、文章上下文注入、文章搜索推荐、会话记忆、SSE 流式输出和 TTS 能力，但整体更接近“一次问答式 AI 助手”。用户希望把它升级为博客中的智能看板娘，既能陪普通访客聊天、理解文章、推荐和搜索内容，也能在识别管理员身份后承担写作辅助、草稿生成、文章发布、上下架管理等复杂任务。

现有体验的主要不足：

- 一次对话只能生成回答，缺少“思考、计划、调用工具、执行、回看结果”的 Agent 流程。
- 普通用户能力和管理员能力尚未形成清晰的权限隔离。
- 文章查询、推荐、总结、写作、发布和管理没有统一的任务状态和执行反馈。
- AI 服务目录与职责已有膨胀趋势，后续继续加 Agent 能力会影响维护性和性能。
- 当前数据库脚本和实体存在版本漂移风险，需要在升级前统一数据模型边界。

## 2. 用户目标

作为普通访客，我希望博客看板娘能理解我当前所在页面和阅读内容，帮助我总结文章、解释概念、搜索文章、推荐相关内容，并进行自然聊天，以便更快找到和理解博客内容。

作为登录用户，我希望看板娘能记住同一会话上下文，在后续追问中延续上下文，以便获得更连贯的辅助体验。

作为管理员，我希望看板娘在确认我具备管理员权限后，可以辅助写博客、润色内容、生成标题摘要标签、创建草稿、发布文章、管理文章上下架，并在高风险操作前向我确认，以便提高内容生产和管理效率。

## 3. 用户场景

| 场景 | 触发条件 | 用户行为 | 期望结果 |
| --- | --- | --- | --- |
| 文章总结 | 用户在文章详情页 | 询问“这篇文章讲了什么” | 看板娘基于当前文章内容总结，不凭空编造 |
| 概念解释 | 用户阅读技术文章 | 询问文章中的概念或代码 | 看板娘结合文章上下文解释，并指出与文章相关的位置或主题 |
| 文章搜索 | 用户想找内容 | 输入“找一下 JWT 相关的文章” | 看板娘调用真实文章搜索能力，返回匹配文章和简短推荐理由 |
| 个性推荐 | 用户想继续阅读 | 输入“推荐几篇类似文章” | 看板娘基于当前文章、最近推荐结果或关键词推荐真实文章 |
| 日常聊天 | 用户无明确站内任务 | 与看板娘聊天 | 看板娘保持站内第一人称、温和自然的角色气质 |
| 写作辅助 | 管理员在编辑器或 AI 面板 | 输入主题、提纲或草稿 | 看板娘生成大纲、标题、摘要、标签建议或文章正文 |

| 多步任务 | 用户提出复杂目标 | 例如“帮我找旧文并写一篇总结” | 看板娘拆解任务，展示计划，逐步调用工具并汇报进度 |

## 4. 功能范围

### 4.1 必须实现

- 保留并优化现有普通聊天、流式聊天、会话管理、TTS 开关、文章上下文注入能力。
- 将 AI 模块整理为清晰的领域目录，避免聊天、TTS、模型选择、工具执行继续堆在一个服务类中。
- 统一 AI 数据库脚本与实体模型，明确会话、消息、模型配置、Agent 任务和工具调用记录的边界。
- 提供普通用户可用的看板娘能力：
  - 当前文章总结。
  - 当前文章问答。
  - 文章搜索。
  - 文章推荐。
  - 分类、标签、作者和站点信息问答。
  - 普通聊天。
- 提供管理员专属能力：
  - 写作选题、提纲、标题、摘要、标签建议。
  - 文章草稿生成和编辑辅助。
  - 创建草稿。
  - 发布文章。
  - 文章上下架。
  - 查询和管理文章状态。
- Agent 生成的新文章首次必须保存为草稿；管理员审查或明确同意发布后，Agent 才能将草稿发布为正文。
- 本期不开放文章删除能力。
- 实现 Agent 执行模式：
  - 识别用户意图。
  - 判断权限和可用工具。
  - 生成任务计划。
  - 调用查询或写入工具。
  - 对高风险写操作进行确认。
  - 返回执行结果和失败原因。
- 对普通用户和管理员使用不同工具集，普通用户不能看到或调用写入类管理工具。
- 管理员写操作必须具备审计记录，至少记录发起人、任务类型、目标资源、执行结果和时间。
- 性能优化必须覆盖：
  - 常用站点信息、分类、标签和热门/最新文章缓存。
  - 模型调用超时和降级提示。
  - SSE 心跳与任务进度事件。
  - Agent 工具调用次数和最大步骤限制。

### 4.2 可选增强

- 长期记忆摘要，用于跨会话记住管理员写作偏好。
- 文章质量检查，包括错别字、SEO、结构、摘要、标签完整性检查。
- 定时任务或发布计划辅助。
- 多模型路由，例如总结走快速模型，写作走质量模型。
- RAG/向量检索，用于更精准的全站文章语义搜索。
- 看板娘前端动画状态与 Agent 执行状态联动。

### 4.3 本次不做

- 不接入外部搜索引擎作为默认事实来源。
- 不让 AI 绕过主后端权限和业务校验直接写数据库。
- 不支持普通用户执行任何文章写入、发布、上下架或删除操作。
- 不默认自动发布 AI 生成内容；首次生成必须为草稿，发布前必须由管理员审查或明确同意。
- 不在未确认范围内重做整站 UI。

## 5. 非目标范围

- 不改变主博客的核心文章数据归属规则。
- 不改变现有 JWT 登录体系和管理员角色定义。
- 不替代 Admin 后台，AI Agent 是辅助入口，不是唯一管理入口。
- 不承诺 AI 输出完全正确，所有写入操作必须保留用户确认与失败回滚路径。
- 不把 TTS 作为 Agent 能力的强依赖，TTS 是可关闭的体验增强。

## 6. 用户流程

普通用户文章问答流程：

```text
1. 用户进入文章详情页。
2. 前端向 AI 请求中携带 page、postId、最近推荐等上下文。
3. 用户询问总结、解释或推荐。
4. 看板娘读取当前文章和必要站内数据。
5. 看板娘以站内第一人称返回答案。
6. 如涉及推荐，返回真实文章列表和推荐理由。
```

管理员写作辅助流程：

```text
1. 管理员登录后进入文章编辑页或 AI 面板。
2. 管理员提出写作需求，例如“帮我写一篇 Spring AI Agent 实战草稿”。
3. 看板娘识别管理员身份，展示任务计划。
4. 看板娘生成标题、摘要、正文、分类和标签建议。
5. 管理员确认是否创建草稿。
6. 确认后看板娘调用主后端文章创建能力。
7. 系统返回草稿 ID 和可编辑入口。
8. 管理员审查草稿后，可明确要求 Agent 发布该草稿。
```

管理员发布或上下架流程：

```text
1. 管理员提出“把某篇文章发布/下架”。
2. 看板娘先查询并展示目标文章，避免误操作。
3. 如果是 Agent 新生成的文章，系统必须确认它已经先保存为草稿。
4. 系统要求管理员明确确认。
5. 管理员确认后执行状态变更。
6. 看板娘返回执行结果；失败时返回原因和可重试建议。
```

复杂 Agent 任务流程：

```text
1. 用户提出多步目标。
2. 看板娘判断任务类型、权限、所需工具和风险等级。
3. 看板娘输出简短计划。
4. 对只读工具直接执行；对写入工具先停在确认点。
5. 工具执行过程通过 SSE 返回 progress/tool/result/error 事件。
6. 看板娘汇总结果，并保存任务轨迹。
```

异常路径：

```text
1. 当用户未登录或权限不足时，看板娘只提供公开只读能力。
2. 当工具调用失败时，看板娘返回具体失败阶段，不假装执行成功。
3. 当目标文章不唯一时，看板娘要求用户选择具体文章。
4. 当模型输出缺少必要字段时，看板娘应要求补充或重新生成，不直接写入。
```

## 7. 业务规则

- 权限规则：
  - 游客可聊天、总结公开文章、搜索公开文章、查看公开推荐。
  - 登录普通用户可拥有会话记忆，但不能执行管理工具。
  - 管理员可使用写作辅助和文章管理工具。
  - 管理员身份必须以主后端 `/user/current` 的当前角色校验结果为准。
- 工具规则：
  - 普通工具只允许读公开内容。
  - 管理工具必须通过主后端 API 执行，不允许 AI 服务直写主库。
  - 写入类工具必须有确认步骤。
  - Agent 新生成文章的首次写入只能创建草稿。
  - 草稿发布必须由管理员审查或明确同意后执行。
  - 删除类能力本期不开放。
- Agent 规则：
  - 每个 Agent 任务必须有最大步骤数。
  - 每个任务必须有可见状态：规划中、等待确认、执行中、完成、失败、取消。
  - Agent 不能把模型猜测当作工具结果。
- 内容规则：
  - AI 生成文章必须先作为草稿。
  - 发布前需要管理员审查或明确确认标题、正文、分类、标签和状态。
  - 推荐和搜索结果必须返回结构化数据，包含文章 ID、标题、摘要、状态、跳转路径等字段，保证前端可识别并支持点击跳转。
  - AI 总结文章必须基于真实文章内容。
- 数据规则：
  - 会话消息、Agent 步骤、工具调用结果应能追踪。
  - 高风险操作需要记录审计日志。

## 8. 交互与体验要求

- 页面入口：
  - Web 前台保留看板娘聊天入口。
  - 文章详情页可直接询问当前文章。
  - Admin 后台或编辑器中提供管理员 Agent 入口。
- 操作反馈：
  - 流式输出文本。
  - Agent 多步执行时显示当前步骤和工具调用状态。
  - 写入操作前显示确认卡片。
- 加载状态：
  - 普通聊天显示生成中。
  - Agent 任务显示规划中、执行中、等待确认等状态。
- 空状态：
  - 无相关文章时给出替代搜索建议。
  - 无权限时说明当前只能做只读辅助。
- 错误提示：
  - 区分模型失败、工具失败、权限失败、参数缺失、目标不唯一。
- 移动端要求：
  - 普通看板娘入口需要兼容移动端。
  - 管理员写作能力优先放在 Admin 文章编辑器侧边栏，并优先保证桌面端体验。
- 兼容性要求：
  - 沿用当前项目交互风格，由实现 PRD 结合现有页面确定。

## 9. 验收标准

AC1：文章总结
Given 用户位于已发布文章详情页
When 用户询问“总结这篇文章”
Then 看板娘应基于该文章真实内容返回摘要，不引用不存在的内容。

AC2：文章搜索
Given 用户输入“找一下 JWT 相关文章”
When AI 判断这是搜索意图
Then 系统应调用真实文章搜索能力，并返回文章标题、摘要或推荐理由。

AC3：普通用户权限隔离
Given 当前用户不是管理员
When 用户要求“帮我发布文章”
Then 看板娘应拒绝执行写入操作，并说明需要管理员权限。

AC4：管理员创建草稿
Given 当前用户是管理员
When 管理员要求生成文章草稿并确认创建
Then 系统应创建草稿并返回草稿 ID 或编辑入口。

AC5：管理员发布确认
Given 当前用户是管理员
When 管理员要求发布某篇文章
Then 系统应先展示目标文章和发布动作，确认该文章不是未经审查的新生成内容，等待管理员确认后再执行。

AC6：目标不唯一
Given 管理员要求“下架最新那篇文章”但系统无法唯一定位
When Agent 查询到多个可能目标
Then 系统应要求管理员选择具体文章，不直接执行。

AC7：Agent 进度
Given 用户发起多步任务
When Agent 执行查询、生成、写入等步骤
Then 前端应收到可区分的计划、进度、工具结果、完成或失败事件。

AC8：性能边界
Given 普通文章总结或搜索推荐请求
When 后端和 AI 提供商正常
Then 首个流式响应应尽快返回，工具查询类数据应避免重复远程请求。

AC9：审计记录
Given 管理员执行创建草稿、发布、上下架等写操作
When 操作完成或失败
Then 系统应记录操作者、动作、目标、结果和时间。

AC10：失败处理
Given AI 模型或主后端工具调用失败
When Agent 无法继续执行
Then 看板娘应说明失败阶段和原因，不保存虚假的成功状态。

AC11：结构化推荐和搜索结果
Given 用户要求搜索或推荐文章
When AI 返回推荐或搜索结果
Then 后端响应中应包含前端可识别的结构化文章数据，至少包含 id、title、summary、status、url/path 和 reason，前端可据此渲染可点击跳转项。

## 10. 安全、性能与合规边界

- 涉及登录态、管理员角色、JWT、主后端权限校验。
- 涉及富文本文章内容生成与发布，需遵守现有富文本消毒和展示边界。
- 涉及第三方 AI 接口调用，不能在日志中泄漏 API Key、JWT、用户隐私或完整敏感请求。
- 写入类工具必须走主后端 API，继承主后端权限校验和业务校验。
- AI 服务需要限制 Agent 最大步骤数、工具调用次数、单次输入长度、单次输出长度。
- 对高频只读数据应设置缓存或短 TTL，降低主后端和模型调用压力。
- SSE 需要支持心跳、超时、取消和错误事件。
- 管理员写操作必须审计，便于追踪误操作。

## 11. 约束与假设

- 假设主后端已有或可补充文章创建、更新、发布、下架、查询管理接口。
- 假设 AI 服务继续通过主后端 `/user/current` 校验用户角色。
- 假设普通看板娘和管理员 Agent 可以共用基础聊天 UI，但管理员能力需要额外确认交互。
- 假设本期优先实现工具调用式 Agent，不先引入复杂多 Agent 协作框架。
- 假设发布操作前必须人工确认，不做全自动发布。
- 假设 Admin 文章编辑器侧边栏是本期管理员 Agent 的主要入口。
- 假设推荐和搜索结果以结构化 action/result 字段返回，不能只依赖模型自然语言文本解析。

## 13. 需求审查记录

### 13.1 与当前代码一致的部分

- AI 服务已有普通聊天、SSE 流式聊天、会话管理、模型配置、站点/文章上下文、工具查询和 TTS 基础能力。
- 当前架构已明确 AI 服务通过主后端 `/user/current` 校验当前用户状态和角色。
- 主后端已有文章、分类、标签、作者资料等公开查询能力，也存在管理员文章/公告管理能力。
- 当前 Web 前台和 Admin 后台分别承担用户阅读和管理写作入口，适合区分普通看板娘与管理员 Agent。

### 13.2 与当前代码或架构冲突的部分

- AI 模块当前更偏一次问答，没有 Agent 任务、步骤、工具调用审计和确认状态。
- AI 数据库脚本存在多版本漂移，实体字段与模块内 SQL 不完全一致。
- `AiChatServiceImpl` 当前承载聊天、SSE、TTS、模型选择、参数解析等多种职责，继续加入 Agent 会显著增加维护风险。
- 当前工具包命名为 `mcp`，但实际是 Spring AI Tool，并非 MCP Server，长期命名可能误导。

### 13.3 安全与性能风险

- 管理员写入类工具如果缺少确认和审计，可能误发布、误下架文章。
- 如果 Agent 每轮都远程查询主后端和模型，首包延迟和主后端压力会明显升高。
- 如果工具调用结果与模型输出边界不清，AI 可能把猜测内容当作真实执行结果。
- 如果权限判断只依赖前端或 token claim，会造成越权风险；必须以后端当前角色为准。

### 13.4 需要用户决策的问题

- 是否允许 Agent 直接发布文章。
- 是否开放删除能力。
- 首期是否引入完整 Agent 框架，还是先做轻量状态机。
- 是否首期做语义搜索/RAG。
- 管理员写作入口优先放在 Admin 编辑器还是独立 AI 工作台。
- 推荐/搜索结果必须设计结构化响应契约，避免前端解析自然语言。

### 13.5 调整结论

- 保持原需求：看板娘应支持聊天、文章总结、推荐、搜索，管理员应支持写作和文章管理辅助。
- 调整后的需求：所有写入类管理员动作必须先确认；Agent 新生成文章首次必须先创建草稿；管理员审查或明确同意后才能发布；首期做草稿/发布/上下架，不开放删除；推荐/搜索结果必须返回结构化数据契约。
- 暂缓或拆分的内容：语义搜索/RAG、长期记忆、多模型复杂路由、定时发布建议放入二期。
