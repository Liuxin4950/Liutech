## 1. 需求摘要

- 用户目标：把 LiuTech-AI 从一次问答助手升级为博客智能看板娘 Agent，支持文章总结、搜索、推荐、聊天，以及管理员写作、草稿、发布、上下架辅助。
- 必须实现：普通用户只读能力、管理员写作管理能力、轻量 Agent 状态机、结构化推荐/搜索响应契约、Admin 编辑器侧边栏、AI 后端文件架构整理。
- 本次不做：文章删除、RAG/语义搜索、长期记忆、多模型复杂路由、完整多 Agent 框架。
- 关键验收：Agent 新生成文章首次必须创建草稿；管理员审查或明确同意后才可发布；推荐/搜索结果必须返回前端可识别并可跳转的结构化数据。

## 4. 影响范围

### 4.1 业务影响

- 普通用户会看到更稳定的文章总结、搜索、推荐卡片。
- 管理员可在文章编辑时通过侧边栏让 Agent 生成草稿、润色、补摘要标签，并在确认后发布。
- 写入操作引入确认和审计，不允许静默发布或删除。

### 4.2 前端影响

- Web：扩展 AI 流事件类型，支持结构化推荐/搜索卡片渲染。
- Admin：文章编辑弹窗或页面新增 Agent 侧边栏，支持写作建议、插入到表单、保存草稿、发布确认。

### 4.3 后端影响

- LiuTech-AI：新增 Agent 编排、工具、审计、结构化响应；重构 AI 目录。
- LiuTech：原则上复用现有 admin posts API；如 operatorId 写死影响审计，应修正为当前用户。

### 4.4 数据库影响

- 统一 `sql/ai_chat_tables.sql` 为权威脚本。
- AI 服务新增 Agent 任务表和工具调用日志表。
- 可能补充会话消息 metadata 字段，保证结构化事件可追踪。

### 4.5 部署与配置影响

- 新增 Agent 最大步骤数、工具超时、缓存 TTL 配置。
- Docker/Nginx 路由沿用 `/ai/`，无需新增路由类型。
- SSE 超时与心跳配置继续沿用并扩展事件类型。

## 5. 总体实现方案

整体路线：先整理 AI 后端包结构和 SQL 契约，再引入轻量 Agent 状态机。普通只读任务直接执行工具并返回结构化卡片；管理员写入任务先生成计划和预览，首次保存为草稿，发布/上下架必须等待确认。

```text
用户/Admin 输入
-> Web 看板娘或 Admin 编辑器侧边栏
-> LiuTech-AI /ai/agent/stream
-> AgentOrchestrator 判断身份、意图、工具、风险
-> 只读工具或管理员工具调用主后端 API
-> SSE 返回文本、计划、工具结果、推荐卡片、确认请求、完成事件
-> 前端按事件类型渲染文本/卡片/确认按钮/跳转链接
```

关键设计取舍：

- 方案 A：直接把 Agent 加进 `AiChatServiceImpl`。
- 方案 B：新增 `agent` 领域包，旧聊天只做兼容调用。
- 选择：方案 B。
- 原因：用户非常在意后端文件名称和架构规整，且 Agent 会持续扩展，必须从第一版就有清楚边界。

### 6.2 结构化响应契约

SSE 事件类型：

| event | payload | 前端用途 |
| --- | --- | --- |
| `agent-start` | `{ taskId, conversationId, mode, role }` | 初始化任务 |
| `agent-plan` | `{ steps: AgentPlanStep[] }` | 展示执行计划 |
| `data` | `{ content }` | 流式文本 |
| `article-results` | `{ source, query, items: ArticleResultItem[] }` | 渲染可点击文章卡片 |
| `tool-start` | `{ toolName, displayName }` | 展示工具执行中 |
| `tool-result` | `{ toolName, success, summary }` | 展示工具结果 |
| `confirmation-required` | `{ actionId, actionType, title, description, preview, riskLevel }` | 渲染确认卡片 |
| `action-result` | `{ actionId, success, target }` | 展示写操作结果 |
| `complete` | `{ taskId, conversationId }` | 结束 |
| `error` | `{ code, message, stage }` | 错误提示 |

## 11. 安全影响

- 认证与授权：管理员工具只允许 `ROLE_ADMIN`，身份以后端回查结果为准。
- 输入校验：限制 message、title、summary、content 长度；校验 postId/categoryId/tagIds。
- XSS：AI 生成富文本最终仍走现有文章展示消毒；Admin 预览不直接信任 HTML。
- SQL 注入：新增 mapper 使用 MyBatis-Plus 参数化查询，不拼接用户输入。
- SSRF：AI 工具只能调用配置好的主后端 base URL，不允许模型提供任意 URL。
- CSRF：继续使用 Bearer Token。
- 敏感日志：不记录 JWT、API Key、完整富文本大内容。

安全风险等级：高。
必须修复项：写操作确认、管理员权限校验、工具白名单、审计记录。
可接受风险：AI 文案质量不稳定，通过草稿和人工确认缓解。

## 12. 性能影响

- 列表分页：文章搜索和管理查询必须分页。
- 数据库索引：Agent 任务按 user/status/created_at 查询需索引。
- N+1：推荐结果尽量由主后端聚合返回，AI 侧不循环查详情。
- 大对象传输：文章正文只在必要时拉取，列表只返回摘要。
- 缓存策略：分类、标签、作者资料、最新/热门文章短 TTL 缓存。
- 线程池：SSE 和 TTS 不应每请求无限创建线程；TTS 默认管理员 Agent 关闭。
- 首包：Agent 先发 `agent-start` 和 `agent-plan`，再执行较慢工具。

性能风险等级：中到高。
预估瓶颈：LLM 调用、主后端文章详情查询、TTS 并发。
缓解方案：短 TTL 缓存、步骤上限、工具超时、管理员默认关闭 TTS。

## 15. 回滚方案

- 代码回滚：回退 AI 服务 Agent 相关提交，旧 `/ai/chat` 和 `/ai/recommend` 保持可用。
- 配置回滚：关闭 Agent 入口开关，只保留普通聊天。
- 数据回滚：保留 Agent 表不影响旧功能；必要时执行 drop 表回滚 SQL。
- 前端回滚：隐藏 Admin Agent 侧边栏和 Web 文章卡片事件渲染。
- 用户影响：回滚后失去 Agent 写作/管理能力，普通聊天不受影响。
