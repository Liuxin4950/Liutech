# 项目经理审查报告：LiuTech 全栈博客平台

## 1. 一句话总评

项目架构完成度和工程量已经超出在校学生的平均水平，但 admin 写作助手功能存在前后端协议断裂的硬伤——前端精心设计的 agent 交互协议在后端完全没有对应实现，导致这个"亮点功能"实际上是个空壳。

> **交叉评审准备**：我将在以下环节参与质疑——(1) 评估架构师"AI隔离方案"和"AI读取内容并制定修改"设计的产品可行性与优先级；(2) 接受项目主管对我的 P0/P1/P2 路线图做取舍校验。报告中以【待质疑】标注的结论是我认为需要其他专家校验或存在争议的点。

## 2. 项目整体健康度评估

**规模数据**：主后端 185 个 Java 文件（32 个 Controller），AI 服务 56 个，Admin 前端 82 个，Web 前端 102 个。主后端 40 个测试文件，AI 服务 5 个。这个体量作为在校学生作品集是扎实的。

**做得好的**：
- 分层清晰，controller/admin 和 controller/web 分包，service -> mapper -> model 层次分明
- SSE 生命周期管理完善：心跳保活、超时处理、线程池关闭、异常兜底都有（`StreamingChatService`）
- 容错设计到位：Resilience4j 熔断/限流 + Spring Retry 重试链（`SiliconFlowChatClient`）
- 安全意识强：prompt injection 防护（不可信内容边界包裹）、JWT 跨服务校验 + 60s 缓存、SecurityConfig 端点分级
- 文档和注释充分，Javadoc 覆盖率高
- Docker Compose 编排完整，生产部署流程（离线打包 -> 导出 tar -> 上传 -> 部署脚本）考虑了国内服务器实际网络限制

**需要警惕的**：
- **前后端协议断裂**：admin agent 前端定义了 12 种 SSE 事件类型，后端只发 5 种，7 种事件完全是空转。这说明前端是在没有和后端对齐协议的情况下"先行设计"的，或者后端实现计划了但没做完
- **控制器偏胖**：`PostsController` 520 行、`UserController` 408 行，有业务逻辑渗透到 controller 层的迹象（如点赞/收藏逻辑直接写在 controller 里而不是纯委托 service）。【待质疑】这个判断基于行数和粗略浏览，需架构师确认 controller 中哪些逻辑确实应该下沉、哪些属于 controller 合理职责
- **测试覆盖不均**：AI 服务只有 5 个测试文件，对于承担核心 AI 功能的服务来说偏少。【待质疑】文件数不等于覆盖率，需测试专家评估实际覆盖率和关键路径覆盖情况
- **文档指针失效**：`CLAUDE.md` 引用的 `doc/记录/当前架构.md` 和 `LiuTech/API文档.md` 都不存在，说明文档维护和代码演进脱节

## 3. 功能完整度盘点

### 3.1 用户聊天（完整度：高，可面试演示）

端到端链路完整：Web 前端 `AiChat.vue`(694行) + `stores/chat.ts`(751行) -> Nginx `/ai/` -> AI 服务 `/ai/chat/stream` -> `AiChatController` -> `AiChatServiceImpl` -> `StreamingChatService` -> `SiliconFlowChatClient`(CHAT mode, `BlogMcpTools`)

SSE 事件链完整：start -> data* -> avatar-cue* -> audio*|audio-skip* -> article-results? -> complete -> audio-complete?

功能齐全：游客模式、登录用户会话持久化、历史记录、记忆清除、TTS 语音合成、Live2D 表情提示、文章推荐（工具调用）、多模型配置、限流。这是项目的核心亮点，面试时可以完整演示。

### 3.2 Admin 写作助手（完整度：极低，不可演示）

详见第 4 节。当前实际体验是：管理员输入指令 -> AI 返回一段纯文本 -> 没有任何结构化字段写入。前端精心设计的 plan 步骤追踪、工具调用展示、字段高亮/撤销、分类标签建议创建等 UI 全部空转。

### 3.3 TTS 语音合成（完整度：高）

AI 服务通过 `TtsClient` 调用 SiliconFlow 云端 TTS，分段合成（`TtsSegmenter`），通过 SSE `audio` 事件带 seq 推送。主后端有 `/tts/speech` 代理端点和 `/tts/status` 状态查询。`TTS_PROXY_INTERNAL_TOKEN` 两服务一致约束在 CLAUDE.md 和 README 中都有文档。完整可用。

### 3.4 其他功能（完整度：中高）

主后端 32 个 Controller 覆盖：文章 CRUD、分类标签、评论留言、签到积分、资源下载、轮播公告、音乐、图片上传、缓存管理、日志、用户管理、系统设置、Sitemap。功能面广，是标准的全栈博客平台该有的。Admin 后台以 Ant Design Vue 表格/表单 CRUD 为主，中规中矩。

### 4.2 六个核心缺口

**缺口 1：ChatRequest 没有 draft 字段**

`Admin\src\types\agent.ts` 的 `AgentChatRequest` 包含 `draft: AdminArticleDraftSnapshot`（postId, title, content, summary, categoryId, tagIds 等），前端 `agent.ts` 通过 `JSON.stringify(request)` 发送。但后端 `LiuTech-AI\...\dto\ChatRequest.java` 只有 message, mode, model, temperature, maxTokens, context, tempMessages, conversationId, ttsEnabled——没有 draft 字段。Jackson 反序列化时默认忽略未知字段，draft 数据被丢弃。

**影响**：AI 完全不知道当前文章草稿的内容。用户说"帮我润色当前文章"，AI 不知道当前文章是什么。

**缺口 2：PromptService 不处理 admin-post-editor 页面**

`PromptService.buildContextPrompt()` 只处理 `"post-detail"` 页面上下文（拉取文章详情注入）。前端传的 context 是 `{ page: 'admin-post-editor', postId, requestedFields, appendTags }`，page 值不匹配，不会触发任何上下文注入。`requestedFields` 和 `appendTags` 也被忽略。

**影响**：即使修复了缺口 1 让 draft 到达后端，PromptService 也没有逻辑把草稿内容注入到 AI 的消息序列中。

【待质疑】这里有两个可选方案需要架构师定夺：(A) 在 ChatRequest 增加 draft 字段，PromptService 直接将草稿内容注入 system/user prompt；(B) 不传 draft，而是让 AI 通过工具调用（getArticleDetail）按需读取。方案 A 简单但每次都传全文（token 浪费），方案 B 灵活但依赖 AI 主动调用工具。我倾向 A+B 结合：草稿摘要注入 prompt + 完整正文通过工具按需读取。但具体设计应看架构师的"AI读取内容并制定修改"方案。

**缺口 3：后端不发送前端期望的 7 种 SSE 事件**

前端 `AdminAgentSidebar.vue` 监听 12 种事件，后端 `StreamingChatService.subscribeStream()` 只发送 6 种（start, data, avatar-cue, audio, article-results, complete）。缺失的 7 种：agent-start, agent-plan, tool-start, tool-result, writing-draft, field-update, confirmation-required, action-result。

**影响**：
- plan 步骤 UI 永远空转（onPlan 从不触发）
- 工具调用追踪永远不显示（onToolStart/onToolResult 从不触发）
- 字段写入永远不发生（onWritingDraft/onFieldUpdate 从不触发）——这是最严重的，AI 的输出不会写入表单
- 确认流程永远不出现（onConfirmation 从不触发）
- 前端 `inferFieldScope()` 的字段范围推断逻辑完全无效

【待质疑】补全这些事件的优先级排序需要产品视角确认。我的判断是 writing-draft / field-update（字段写入）是 P0 核心，tool-start / tool-result（工具追踪）是 P1 增强，agent-plan / agent-start（计划展示）是 P2 体验。但架构师可能有不同优先级判断，特别是如果架构师的方案采用不同的 Agent 架构（如不用 plan 事件改用其他方式展示进度）。

**缺口 4：没有写作专用系统提示词**

`PromptService.buildSystemPrompt()` 始终返回"纳西妲看板娘"角色提示词 + 能力边界规则 + 安全规则。写作模式和聊天模式用完全相同的系统提示词。AI 不知道自己应该输出结构化的标题/摘要/HTML内容/分类ID/标签ID，也不知道有 `writing-draft` 或 `field-update` 这样的输出格式约定。

**影响**：即使补全了 SSE 事件，AI 也不知道应该按什么格式输出来触发这些事件。需要设计写作专用的系统提示词，定义结构化输出协议（如 JSON 格式的草稿载荷），后端解析后转换为 SSE 事件。

【待质疑】结构化输出协议的设计方案需要架构师确认。两个方向：(A) 让 AI 输出 JSON（如 `{"title":"...","summary":"...","contentHtml":"...","categoryId":1,"tagIds":[1,2]}`），后端解析后发 field-update 事件；(B) 让 AI 输出带特定标记的文本（如 `<<<WRITING_DRAFT>>>json...<<<END>>>`），后端正则提取。方案 A 更规范但 JSON 输出对 LLM 来说不稳定（尤其长 HTML 内容中的引号转义），方案 B 更鲁棒但不优雅。这个设计决策直接影响 P0-2 和 P0-3 的实现方式。

**缺口 5：WritingTools 缺少"读取当前文章"工具**

`WritingTools` 只有 `listCategories()` 和 `listTags()` 两个工具。`BlogMcpTools` 中有 `getPostDetail(Long postId)`，但写作模式不注册 BlogMcpTools（`SiliconFlowChatClient.resolveTools` 按 ChatMode 二选一）。AI 在写作流程中无法通过工具调用读取当前文章的完整内容。

**影响**：即使通过缺口 1/2 注入了草稿摘要，AI 也无法获取文章的完整正文来做润色/改写。对于"帮我润色当前文章"这样的核心需求，AI 没有足够的信息。

【待质疑】这与缺口 1/2 的方案选择相关。如果选择方案 A（draft 注入 prompt），缺口 5 的紧迫性降低；如果选择方案 B（工具按需读取），则缺口 5 是 P0 前置。需架构师的"AI读取内容"方案来确定。另外，写作模式是否应该共用 BlogMcpTools 的部分工具（而非完全二选一），这是隔离方案的范畴，需架构师定夺。

**缺口 6：写作模式没有落库链路**

`StreamingChatService.processWritingStream()` 的 onComplete 回调是空实现（`fullResponse -> {}`），不落库、不写回主后端。前端 `handleAgentActionDone` 期望 `action-result` 事件带 `target.postId` 和 `target.status`，但后端不发送这个事件。文章保存完全依赖用户手动点击"保存"按钮（`PostsManagement.vue` 的 `handleOk` -> `PUT /admin/posts/{id}`）。

**影响**：这本身不一定是问题（让用户确认后手动保存是合理设计），但前端 `handleAgentActionDone` 和 `quickPrompts` 中的"保存为草稿""发布这篇文章"按钮暗示了 AI 直接操作文章的意图，这些功能没有后端支撑。

【待质疑】从产品角度，我认为"AI 生成内容 -> 用户确认 -> 手动保存"是更安全的设计，AI 直接落库的风险（幻觉写入、格式错误）不值得为了少点一次按钮来承担。但前端 quickPrompts 中的"保存为草稿"/"发布这篇文章"暗示作者想要 AI 直接操作。这个产品取舍需项目主管确认方向。

### 4.3 链路总结

当前 admin 写作助手的实际体验：管理员在侧边栏输入指令 -> AI 用"纳西妲"身份返回一段纯文本回复 -> 管理员看完回复后手动编辑文章。这和打开一个新标签页用 ChatGPT 没有本质区别，没有任何"集成"价值。前端 590 行的 `AdminAgentSidebar.vue` 中约 70% 的逻辑（plan 追踪、工具展示、字段写入、撤销、分类标签建议创建）处于空转状态。【待质疑】"70% 空转"是基于代码行数的粗估，实际需架构师确认哪些逻辑确实空转、哪些可能通过其他路径间接生效。

## 5. 用户 agent vs 管理员 AI 隔离现状

### 5.1 做得好的部分

1. **端点级隔离**：`SecurityConfig` 中 `/ai/chat` 和 `/ai/chat/stream` 是 `permitAll`（支持游客），`/ai/writing` 和 `/ai/writing/stream` 是 `hasRole('ADMIN')`。配置层直接限制，不依赖业务层补判。这是正确的做法。

2. **工具级隔离**：`SiliconFlowChatClient.resolveTools(ChatMode)` 按模式分派——CHAT 注册 `BlogMcpTools`（搜索文章、分类文章、最新/热门文章、文章详情、作者资料），WRITING 注册 `WritingTools`（分类列表、标签列表）。用户聊天不会加载写作工具，写作助手不会加载博客搜索工具。作者提到的"用户agent不能加载管理员AI的tools"在工具层面已经做到。

3. **JWT 跨服务校验**：`JwtAuthenticationFilter` 调用主后端 `/user/current` 验证 token 有效性 + 用户角色 + 账号状态，60s 缓存。角色信息映射为 `ROLE_USER` / `ROLE_ADMIN`，供 Spring Security 授权层使用。

4. **限流分级**：`AiRateLimitInterceptor` 对 guest/user/admin 有不同的限流阈值（20/60/120 次/分钟）。

### 5.2 未完成的部分

1. **系统提示词未隔离**：写作模式和聊天模式用同一套"纳西妲看板娘"系统提示词。AI 在写作模式下仍然自称"纳西妲"、仍然遵守看板娘的行为规范。应该有一套独立的写作助手系统提示词，定义不同的角色身份、输出格式和工具使用策略。【待质疑】隔离到什么程度需架构师确认：是完全不同的 system prompt，还是在同一 prompt 中加 mode 分支？完全隔离更干净但维护两套 prompt；分支复用更省事但边界模糊。我倾向完全隔离（写作模式不走 PromptService.buildSystemPrompt，而是走独立的 WritingPromptService），但这是架构决策。

2. **前端 agent 协议设计但未实现**：`agent.ts` 中的 `AgentStartPayload` 有 `role: 'guest' | 'user' | 'admin'` 字段，暗示前端设计了角色区分，但后端 `start` 事件只发 `mode: "guest"/"user"/"writing"`，不发 `role`。

3. **admin 端点路由混用**：`AiModelAdminController` 的 `@RequestMapping` 是 `{"/admin/models", "/ai/admin/models"}`，两个路径前缀都映射。这本身不是安全问题（有 `@PreAuthorize("hasRole('ADMIN')")`），但路径不统一会增加 Nginx 配置和维护的复杂度。

4. **WritingTools 工具集不完整**：当前只有 listCategories 和 listTags。缺少写作流程需要的核心工具：读取当前文章内容、生成写作 HTML（前端 plan 中有 `admin.generateWritingHtml` 步骤映射，但没有对应的后端工具）、保存草稿等。【待质疑】"生成写作 HTML"是否应该是一个独立的工具（AI 调用它来格式化输出），还是应该通过 system prompt 指导 AI 直接输出 HTML？前者更可控（可以加 sanitize 逻辑），后者更灵活。需架构师的隔离方案和工具设计来定。

### P1：提升工程质量与可维护性（重要）

| 序号 | 任务 | 预计工作量 | 面试加分点 |

## 7. 给学生的话

**先说批评。** admin 写作助手这个功能，前端写了 590 行的侧边栏组件，定义了 12 种 SSE 事件类型的 TypeScript 接口，设计了 plan 步骤追踪、工具调用展示、字段高亮写入、撤销栈、分类标签建议创建——这些代码的工程量和设计思考是实打实的。但后端完全没有对应的实现。`ChatRequest` 连 `draft` 字段都没有，`PromptService` 不处理写作页面上下文，`StreamingChatService` 不发送 `writing-draft` 和 `field-update` 事件。这意味着前端大部分代码在运行时是空转的。

这不是"做了一半"，这是"前端做了 80%，后端做了 20%，中间的协议层是断裂的"。如果你拿着这个项目去面试，面试官点开 `AdminAgentSidebar.vue` 会觉得"这个学生很厉害，设计了完整的 agent 交互协议"；然后翻到后端发现事件根本不发，会立刻质疑你对自己代码的理解程度。**空转的代码比没有代码更扣分**，因为它暗示你要么不理解自己的代码，要么在故意包装。【待质疑】这个面试观是基于一般情况的判断，具体取决于面试官风格和面试方向。如果面试偏重前端能力展示，空转的前端代码至少能证明设计能力；如果偏重全栈/后端，则确实是减分项。

**再说做得好的。** 作为一个在校学生，你能独立完成 185 + 56 个 Java 文件的后端、184 个前端文件的全栈项目，Docker Compose 编排 5 个服务，Nginx SSE 代理、HTTPS、离线部署流程都想到了，Resilience4j 熔断/限流 + Spring Retry 重试链、prompt injection 防护、JWT 跨服务校验都做了——这个工程量和工程意识已经超过绝大多数同龄人。用户聊天链路是真正端到端完善的，SSE + TTS + Live2D + 文章推荐，完整可演示。

**学习建议。**

1. **先对齐再实现**。前后端协作（即使是你一个人写）最常见的问题是前端先行设计了一套协议，后端没跟上。下次先写接口契约（事件类型、payload 结构），再前后端同步实现。这也是为什么 API 文档和架构文档很重要——你 CLAUDE.md 里引用的两个文档都不存在了，说明文档和代码演进脱节了。

2. **删掉空转代码**。面试前，`AdminAgentSidebar.vue` 里那些不触发的 handler 和 `agent.ts` 里不发送的事件类型，要么标注 `// TODO: 待后端实现`，要么先删掉。P0 做完后再加回来。一个"小而完整"的功能比一个"大而空壳"的功能有说服力得多。

3. **理解你的每一行代码**。面试官会问"这个 `onWritingDraft` 什么时候触发"，你需要能回答"当前后端不发送 writing-draft 事件，这个 handler 不会触发，我计划在 P0 阶段实现"。诚实 + 有计划，远好于"呃...应该是 AI 返回写作草稿时触发吧"。

4. **把 P0 做完**。3 天的工作量，让 admin 写作助手从空壳变成可演示。面试时现场演示"输入一句'帮我润色当前文章' -> AI 读取草稿 -> 返回修改后的标题/摘要/正文 -> 字段高亮写入 -> 用户确认保存"，这个演示的冲击力远超任何 README 描述。

5. **测试意识要补**。AI 服务 56 个 Java 文件只有 5 个测试文件。面试官会问"你怎么保证 SSE 事件序列的正确性"。至少把核心链路（提示词组装、工具注册、SSE 事件发送）的单元测试补上。
