## 2. 高风险未覆盖模块清单

按风险从高到低排序：

### P0 - 认证流程中的 controller 内联业务逻辑（已测 service，未测 controller 编排）

`UserController` 的两个方法在 controller 层做了多步骤认证编排，**没有被任何测试覆盖**：

1. **`resetPassword()`**（第336-353行）：验证码校验 -> 查用户 -> 密码加密 -> 更新用户 -> 标记验证码已使用。5步编排散在 controller 里，任何一步出 bug 就可能导致密码重置漏洞或验证码被复用。
2. **`verifyEmailLogin()`**（第377-401行）：验证码校验 -> 查用户 -> 检查状态 -> 生成 JWT -> 更新登录时间 -> 标记验证码已使用。同样是多步编排无测试。

风险：验证码重放攻击（`markUsed` 调用时机不对）、账户状态绕过、JWT 生成参数错误。

现有测试 `UserControllerSecurityTest` 只通过反射检查 `@PreAuthorize` 注解是否存在，不验证业务逻辑正确性。

### P1 - 无集成测试，SQL/MyBatis 映射错误不可见

所有测试都是纯 Mock，Mapper 的行为是 `when().thenReturn()` 假设的。真实的 SQL 语句、MyBatis-Plus 查询条件、乐观锁 SQL 是否正确，完全没有验证。

高风险点：`deductPointsWithVersion` 的乐观锁 SQL 如果写错（比如 WHERE 条件少了 version 字段），Mock 测试全绿但生产环境积分被刷。

### P2 - 前端零测试

Web 前端配了 vitest 但没写一行测试。stores（user token 管理）、services（API 调用层）、composables 这些纯逻辑层最该测，也最容易测。

Admin 前端连测试框架都没装。

### P3 - TTS 代理调用链

`TtsSpeechService` 的测试只覆盖了缓存清理逻辑（过期删除、容量淘汰、节流），但**TTS 语音合成的实际调用链**（后端 -> AI 服务 -> 返回音频）没有测试。CLAUDE.md 提到 `TTS_PROXY_INTERNAL_TOKEN` 跨服务一致性是高风险点，但无相关测试。

【待质疑：TTS 调用链涉及跨服务通信，单元测试难以覆盖。是否值得投入集成测试需与架构师确认 TTS 在产品中的定位--如果是核心卖点应补测，如果是边缘功能可降级处理】

### P4 - SSE 流式响应

AI 聊天的 SSE 流式响应是端到端最复杂的路径，但 `AiChatServiceImplTest` 只测了模型解析和 TTS 分段逻辑，没有测 SSE 流的组装和推送。这个确实不好测（需要 Mock SSE 通道），可以理解为低优先级。

## 3. 可测试性评估

### 好的方面

大部分 controller 已经做到了**薄委托**——接收参数、调 service、包装 Result 返回。例如：
- `PostsController`：所有方法都是 `userUtils.getCurrentUserId()` + `postsService.xxx()` + `Result.success()`
- `ResourceDownloadController`：3个方法，每个都是单行调 service
- `PostsAdminController`：继承 `BaseAdminController`，用 `handleException()` 统一异常处理

这些 controller 的测试（已存在的 10 个 controller test）主要验证"参数传递是否正确"和"异常是否被正确捕获"，定位合理。

### 需要改进

**`UserController.resetPassword()` 和 `verifyEmailLogin()` 是可测试性最差的代码**。它们把以下逻辑揉在 controller 里：
- 验证码校验（`verificationCodeService.verifyCode`）
- 用户查询（`userManagementService.findUsersByEmail`）
- 密码加密（`passwordEncoder.encode`）
- 用户更新（`userManagementService.updateUser`）
- 验证码标记（`verificationCodeService.markUsed`）

这5个依赖注入到 controller 里，如果要测这两个方法，得 Mock 5个依赖 + 构造 HTTP 请求上下文。而如果把这些逻辑下沉到 `UserAuthService`，只需要 Mock 2-3 个 Mapper 就能用现有的测试模式覆盖。

**建议**：把 `resetPassword` 和 `verifyEmailLogin` 的编排逻辑移入 `UserAuthService`，controller 只负责调用。这样既能用现有的 Mockito 模式补测试，又能让 controller 回归薄委托。

【待质疑：此重构建议涉及架构调整，需与架构师交叉评审确认下沉方案。具体问题：1) UserAuthService 当前已有 5 个依赖，再加 UserManagementService + BCryptPasswordEncoder 会不会过载；2) resetPassword 涉及密码加密，是否应独立为 PasswordService】

### PostsController 的 try-catch 模板

`PostsController` 的 `createPost`/`updatePost`/`deletePost`/`publishPost` 等方法都有相同的 try-catch 结构：
```java
try {
    Long authorId = userUtils.getCurrentUserId();
    if (authorId == null) return Result.fail(ErrorCode.UNAUTHORIZED);
    // ...
} catch (Exception e) {
    return Result.fail(ErrorCode.OPERATION_ERROR, "xxx失败: " + e.getMessage());
}
```
而 `PostsAdminController` 用 `BaseAdminController.handleException()` 消除了这个模板。两套异常处理风格并存，建议统一到 `BaseAdminController` 模式。

## 4. 务实测试策略

### 必须测（高风险，面试会被追问）

【待质疑：以下优先级排序需项目主管校验是否合理，特别是"必须测"与"应该测"的边界划分】

| 优先级 | 目标 | 类型 | 理由 |
|---|---|---|---|
| 1 | `UserController.resetPassword` / `verifyEmailLogin` 下沉到 service 后补单测 | 单元测试 | 认证流程无测试 = 面试致命伤 |
| 2 | `PointsService` 乐观锁 SQL | 集成测试（H2 或 Testcontainers） | 积分系统是金融类逻辑，Mock 不够 |
| 3 | `ResourceDownloadService` 路径穿越 | 已有单测，补一个集成测试验证真实文件系统 | 安全漏洞必须端到端验证 |

### 应该测（中风险，性价比高）

| 优先级 | 目标 | 类型 | 理由 |
|---|---|---|---|
| 4 | Web 前端 `stores/user.ts`（token 管理/登出清理） | 单元测试 | 前端认证状态管理，bug 会导致未登录访问 |
| 5 | Web 前端 `services/*.ts`（API 请求拦截/错误处理） | 单元测试 | 纯逻辑层，vitest 已配好，写起来快 |
| 6 | `JwtUtil` token 生成与解析 | 单元测试 | JWT 是认证核心，当前完全没测 |
| 7 | `VerificationCodeService` 验证码生成/校验/过期 | 单元测试 | 验证码是认证流程关键环节 |

### 可以不测（低风险或 ROI 低）

【待质疑：以下"可以不测"清单需项目主管校验是否过于激进。尤其 Admin 前端和 SSE 项】

- CRUD controller 的列表查询/分页（已有 controller 测试覆盖参数传递，足够）
- Admin 前端（CRUD 表单为主，逻辑简单，测试 ROI 低）
- SSE 流式响应（Mock 成本高，端到端测试更合适但投入大）
- Nginx 配置（运维域，用 curl 手动验证即可）
- Docker Compose 编排（部署域）

### 集成测试引入建议

不建议一步到位上 Testcontainers（CI 跑 MySQL 容器慢）。务实方案：

1. 加一个 `@SpringBootTest` + H2 内存数据库的集成测试，只覆盖 `PointsService` 的乐观锁 SQL
2. H2 和 MySQL 语法差异小，乐观锁的 `UPDATE ... WHERE version = ?` 语句能在 H2 上验证
3. 如果发现 H2 兼容性问题，再升级到 Testcontainers

【待质疑：H2 与 MySQL 兼容性需验证。MyBatis-Plus 的 `deductPointsWithVersion` 是自定义 XML SQL 还是 LambdaUpdateWrapper？如果是 XML 自定义 SQL，H2 可能有函数/语法不兼容。需确认 Mapper XML 实际内容后才能判断 H2 方案是否可行。如果 H2 不可行，备选方案是 Testcontainers + MySQL 镜像（CI 增加约 30 秒启动时间）】

## 5. CI 集成建议

当前 CI 是纯 CD（push main -> build -> deploy），没有任何质量门禁。建议加一个轻量 CI workflow：

### 方案：新增 `.github/workflows/ci.yml`

```yaml
name: CI
on:
  pull_request:
    branches: [main]
  push:
    branches: [main, refactor/**]

jobs:
  backend-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '21'
          cache: 'maven'
      - name: Run LiuTech tests
        run: mvn -f LiuTech/pom.xml test
      - name: Run LiuTech-AI tests
        run: mvn -f LiuTech-AI/pom.xml test

  frontend-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          cache-dependency-path: Web/package-lock.json
      - name: Install & build Web
        working-directory: ./Web
        run: |
          npm ci
          npm run build
      # 前端测试目前跑不起来（setup.ts 不存在），暂不加 npm test
      # 等前端测试文件写好后再加: npm test
```

### 关键设计决策

1. **PR 和 push 都触发**：PR 阶段就能看到测试结果，不必等到合入 main
2. **不加覆盖率门禁**：学生项目不需要卡覆盖率，先把"测试能跑"这个底线建起来
3. **前端暂不跑 test**：vitest 配置引用的 `setup.ts` 不存在，`npm test` 会报错。等补上测试文件后再开
4. **不改 deploy.yml**：deploy.yml 保持 `-DskipTests`，因为它只负责打包镜像；测试在 ci.yml 里跑，deploy 依赖 ci 通过（可在分支保护规则里设置 required status check）

【待质疑：1) 分支触发策略中 `refactor/**` 是否符合团队实际工作流，需与项目主管确认；2) "不加覆盖率门禁"是否过于宽松，项目主管可能要求至少加一个底线（如核心 service 不允许覆盖率下降）；3) deploy 依赖 CI 通过需要配置 GitHub branch protection rules，需运维确认仓库权限是否支持】

## 6. 给学生的话

你的后端测试已经做得很好了，这不是客套。45个测试文件，覆盖了认证、积分、签到、文件上传、资源下载、TTS 缓存、AI 限流这些高风险模块，而且测试质量在线——Mock 用法正确，异常路径覆盖充分，甚至用反射验证了 `@PreAuthorize` 注解。大多数在校学生的项目是零测试的。

但有几个认知需要建立：

**测试不是越多越好，而是越早越好。** 你现在的问题不是测试不够多，而是测试来得太晚——代码已经写完了才补测试，所以 controller 层有漏网业务逻辑（`resetPassword` / `verifyEmailLogin`），因为它们不在 service 层，你补测试时自然没覆盖到。如果写代码时就想着"这个方法要怎么测"，你自然不会把5步编排塞进 controller。

**Mock 测试和集成测试是两回事。** 你现在的测试全是 Mock——假设 Mapper 返回什么，然后验证 service 的处理逻辑。这能测出"逻辑写错了"的问题，但测不出"SQL 写错了"的问题。积分系统的乐观锁 SQL 如果 WHERE 条件写错，你的 Mock 测试全绿但生产被刷。至少给积分系统加一个用真实数据库的集成测试。

**CI 跑测试比写测试更重要。** 你有 45 个测试文件，但 CI 里 `mvn -DskipTests` 全跳过了。测试写了不跑等于没写。加一个 ci.yml，让每次 PR 都自动跑测试，这个动作的工作量是 30 分钟，但它的价值是让你的 45 个测试文件真正发挥作用。

**前端测试从 stores 开始。** vitest 已经配好了，`src/__tests__/setup.ts` 创建一个空文件就能跑起来。先写 `stores/user.ts` 的测试——token 存储、登录状态、登出清理，这些是纯逻辑，不需要 Mock DOM，10 分钟能写 3 个测试。面试时说"前端也写了关键 store 的单元测试"，比"配了 vitest 但没写测试"强太多。

**面试谈测试的思维框架**：不要说"我写了 XX 个测试"，要说"我按风险排序，认证和积分这种出 bug 就是安全事故的模块优先覆盖，CRUD 查询接口用 controller 测试验证参数传递就够了"。这比覆盖率数字更能体现工程判断力。
