# 当前架构

> 本文档描述 LiuTech 当前生效的总体架构，供开发与 AI 协作参考。
> 历史团队分析报告见 `Docs/团队反馈/`（当前未纳入版本控制）；本文以当前代码与架构模块索引为准。

## 顶层模块

| 路径 | 角色 | 端口 |
| --- | --- | --- |
| `Web/` | 用户前台博客（Vue3 + TS + Vite） | 3000 |
| `Admin/` | 管理后台（Vue3 + Ant Design Vue） | 3001 |
| `LiuTech/` | 主后端 REST API（Spring Boot 4.1.0 + MyBatis-Plus） | 8080 |
| `LiuTech-AI/` | AI 服务（聊天/写作/TTS/推荐） | 8081 |
| `nginx/` | 反向代理、CORS、SSE | 80/443/81 |
| `Docs/SQL/sql.sql` | MySQL 唯一初始化脚本（`liutech` + `liutech_ai` 两库） | 3306 |

容器内服务名通信：`backend:8080`、`ai:8081`、`mysql:3306`。完整编排见 `docker-compose.yml`。

## 后端分层（LiuTech）

`controller/{admin,web}` -> `service` -> `mapper` -> `model`，横切关注点在 `common/`、`config/`、`aspect/`、`filter/`。

- **Controller**：只做"参数接收 -> 调 Service -> 返回 Result"。异常由 `GlobalExceptionHandler` 统一兜底，认证由 `@PreAuthorize` 保证，方法内不再 try-catch 与冗余 null 检查。
- **Service**：业务逻辑所在地。
- 管理端 Controller（`/admin/**`）类级 `@PreAuthorize("hasRole('ADMIN')")`，认证在方法体执行前由 Spring Security 拦截。

## AI 服务架构（LiuTech-AI）

`controller/{,admin}` -> `service`，横切 `common/{client,mcp,tts,monitor,utils}`、`infra/{config,security,filter,exception,aspect}`。

- **聊天模式**（`/ai/chat`，permitAll 支持游客）：注册 `BlogMcpTools`（公开博客查询/搜索/推荐）
- **写作模式**（`/ai/writing`，hasRole('ADMIN')）：注册 `WritingTools`（分类/标签/读文章）
- **写作助手**：前端传 `draft`（`AdminArticleDraftSnapshot`：标题/正文/摘要/分类/标签），`PromptService` 注入为不可信上下文，使用写作专用系统提示词（与看板娘人设隔离）
- **SSE 流式**：`StreamingChatService`，事件 `start`/`data`/`avatar-cue`/`audio`/`article-results`/`complete`
- **TTS**：分段合成，`/tts/speech` 代理（`TTS_PROXY_INTERNAL_TOKEN` 跨服务一致）
- **安全**：prompt injection 防护（不可信内容边界包裹）、JWT 跨服务校验（调主后端 `/user/current`，60s 缓存）、Resilience4j 熔断 + 限流 + Spring Retry

## 跨服务集成约束

- `JWT_SECRET`：backend 与 ai **必须完全一致**
- `TTS_PROXY_INTERNAL_TOKEN`：backend 与 ai **必须一致**
- `BLOG_API_URL`：Docker 内 `http://backend:8080`，本地 `http://localhost:8080`
- JDBC URL 必须含 `allowPublicKeyRetrieval=true`（兼容 MySQL 8 认证）
- 文件上传：容器内 `/app/uploads` 绑定宿主机 `/liuxin/uploads`；**不要**用 `docker compose down -v`（清空 `mysql_data` 卷）
- SSE：Nginx 必须 `proxy_buffering off;` 并提高 `proxy_read_timeout`；**不要**给非 SSE 路径加 `Accept: text/event-stream`（破坏 JSON 响应 406）

## 文件上传与静态资源 URL

**URL 策略：两种形态，数据库统一存逻辑路径**
- 本地磁盘（默认）：`LocalFileStorage.generateUrl` 返回相对路径 `/uploads/...`，**不拼** `serverBaseUrl`，由前端代理（vite proxy / nginx）转发到后端
- 腾讯云 COS（`COS_ENABLED=true`）：`CosFileStorage.generateUrl` 返回 COS 默认域名完整 URL（`https://liutech-1341692466.cos.ap-chongqing.myqcloud.com/...`），前端 img 直出，流量不过服务器
- 两种形态下 `images.file_url` 存 `generateUrl` 输出（本地=相对路径 /uploads/...，COS=完整 URL），`file_path` 列单独存逻辑路径（`images/...`），零迁移切换；`FileUtil.extractRelativePath` / `normalizeToRelativePath` 同时兼容相对路径、站内完整 URL、COS 直出 URL（解析新旧数据用），删除/引用计数/对账统一走它们，不在调用方散落前缀判断
- 切换步骤与 COS 配置见 [Docs/架构/后端/图片管理/存储抽象.md](../架构/后端/图片管理/存储抽象.md)；COS 密钥只放本地 .env（gitignore）

**访问路径（反向代理统一转发）**
- 开发环境：`Web/vite.config.ts` 与 `Admin/vite.config.ts` 配 `proxy['/uploads'] -> http://localhost:8080`
- 生产环境：`nginx/conf.d/default.conf` 已配 `location /uploads/ -> http://backend_servers/uploads/`
- 前端 `img :src` 直接用后端返回的相对路径，浏览器拼接当前域名后由反代转发到 backend

**SERVER_BASE_URL（.env）**：仅供 `extractRelativePath` 解析历史完整 URL 使用，新生成的 URL 不再依赖它。不要为"开发环境图片显示不了"去改它--应走相对路径 + vite proxy。

**历史数据**：早期 `serverBaseUrl` 配置不一致曾产生绝对 URL（`http://localhost:8080/...`、`https://www.liuxin.chat/...`）。2026-08-03 已将 `images.file_url`、`carousels.image_url`、`posts.cover_image` 中的绝对 URL 全部迁移为相对路径，全库零残留。新上传统一相对路径，不再产生此问题。

## 前后端错误响应与提示约定

**后端响应**：
- 业务异常抛 `BusinessException`，由 `GlobalExceptionHandler` 统一返回 `{code, message, data}` + HTTP 400
- `message` 必须面向用户可读（如"邮箱已被其他用户使用"），不要暴露 SQL/堆栈等技术细节
- 参数校验失败返回 HTTP 400 + `data` 为字段错误 map；权限不足返回 403；未认证返回 401

**前端提示**（Web 与 Admin 共用同一套约定）：
- 响应拦截器对业务错误（HTTP 4xx/5xx 且 `response.data.message` 存在）统一提示后端 message，并标记 `error.isBusiness = true`
  - Web：`Web/src/services/api.ts`（SweetAlert2 Toast）
  - Admin：`Admin/src/services/httpClient.ts`（ant-design-vue `message`；主后端与 AI 两个实例共用这一个工厂，仅 `normalizeResponse` 取值不同）
- 401：清 token 跳登录（Web 弹全局登录弹窗、停留当前页；Admin 跳 `/login`）；403：静默或跳 `/403`；其他错误：提示后端 message
- 调用方 `catch` 里对 `isBusiness` 错误**不要**再弹通用文案（如 `message.error('更新失败')`），避免重复/覆盖；只有非业务错误（网络等）才弹通用提示，写法为 `if (!error?.isBusiness) { ... }`
- **禁止直接展示 `error.message`**：axios 错误的 message 是 `Request failed with status code 400` 这类英文原文，对用户无意义；提示一律用业务文案（后端具体原因由拦截器负责展示）。2026-09-09 曾因 27 处 `message.error(error?.message || '...')` 导致登录失败弹两条（后端原文 + axios 原文）
- Web 用 `handleFormSubmit`（`useErrorHandler`）的调用方已内置此逻辑；Admin 页面直接 `try/catch` 的地方需手动判断 `isBusiness`
- 提示封装：Web 是 `Web/src/utils/errorHandler.ts`（SweetAlert2 + 5 秒去重）；Admin 只保留 `Admin/src/utils/globalErrorHandler.ts` 的全局兜底（antd message + 5 秒去重），页面/store 统一直接用 antd `message`
- Admin 的 token 读写统一走 `Admin/src/utils/auth.ts`（`getToken`/`setToken`/`removeToken`），不要在业务代码里直接访问 localStorage

## 部署

- Docker Compose 编排 6 服务（mysql/backend/ai/web/admin/nginx）
- 生产仅暴露 nginx 的 80/443/81，其余服务走 Docker 内网；开发态的端口映射在 `docker-compose.override.yml`（本地专用，生产不上传该文件）
- 主域名 `liuxin.chat` 走腾讯云 CDN（HTTPS 回源）；后台 `admin.liuxin.chat` 直连源站 443（独立 server 块，复用证书）；81 端口保留为 admin 备用入口
- HTTPS 证书（生产）：`/opt/liutech/nginx/liuxin.chat_bundle.crt` 与 `liuxin.chat.key`（SAN 含 liuxin.chat、www.liuxin.chat，不含 admin 子域名）
- 域名/CDN/证书/部署细节与已踩坑见 [部署运维/总览.md](../架构/运维/部署运维/总览.md)
- 环境变量从根目录 `.env` 注入；`.env.example` 是模板，生产替换为强密钥
