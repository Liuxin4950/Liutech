> 状态：待处理清单。本文只记录当前代码能够证明的问题，不以“文件长”“写法不同”作为单独重构理由。

## 1. 结论

项目主体已经具备稳定运行的基础，但当前最大的维护风险不在功能数量，而在以下四类问题：

1. **存在多个事实源**：生产 Compose、写作端、富文本样式、技术栈说明都有重复实现，并且部分副本已经发生漂移。
2. **错误被伪装成空数据**：分类和标签请求失败后被 Store 吞掉，页面可能显示“暂无数据”而不是失败状态。
3. **自动化门禁不完整**：Web 已有测试但 CI 不运行；Admin 没有测试；主后端测试当前在本机无法完整通过。
4. **代码与数据中仍有“看起来像真的”静态信息**：后台技术栈、关于页初始化数据、AI 创建分类的说明会写入不准确内容。

建议先解决 P0/P1，再进行 UI/CSS 和包体积减法。不要先做大范围目录重组。

## 2. 优先级说明

| 级别 | 含义 |
| --- | --- |
| P0 | 可能造成安全事故、部署事故或生产不可用，应最先处理 |
| P1 | 已能复现的 Bug、测试失效或持续产生错误数据，应尽快处理 |
| P2 | 明确的重复、性能浪费或维护成本，可按模块逐步清理 |
| P3 | 文档与低风险一致性问题，可随对应模块修复 |

验收：

- 仓库中只有一份生产服务定义。
- 修改任意服务环境变量后，无需同步修改另一个 heredoc。
- 文档、部署脚本和生产实际路径均指向同一 Compose。

### P0-03 数据库迁移依赖人工记忆，没有执行台账

**状态：部分缓解。历史 SQL 已于 2026-09-07 聚合为一个初始化脚本；迁移执行台账仍未处理。**

证据：

- 文章系列、读者成就和关于页历史变更已经折叠进该文件，`Docs/SQL` 不再保存多个历史迁移副本。
- 现有数据库仍没有迁移版本表或自动执行器，生产是否已升级仍依赖操作者与部署记录。
- 完整初始化脚本包含初始化数据，并且 `CREATE TABLE IF NOT EXISTS` 不会为旧表补新增列，因此不能作为已有生产库的迁移脚本反复执行。
- 本次关于页结构升级曾出现“代码先上线、旧 JSON 未迁移，接口反序列化失败”的实际故障。

影响：

- 是否迁移取决于操作者记忆，代码版本与数据库版本没有机器可验证关系。
- 漏跑会导致新代码直接读取旧结构；误重跑又可能覆盖真实运营数据。

建议：

- 优先采用成熟迁移工具（Flyway/Liquibase）；如果暂不引入依赖，至少建立 `schema_migrations(version, checksum, executed_at)` 台账和统一执行脚本。
- 部署前自动列出“未执行迁移”，执行后写入版本和校验和；禁止只凭文件名或人工记忆判断。
- `Docs/SQL/sql.sql` 只负责全新环境；已有环境的最小增量 SQL 在对应发布中生成、审核和执行，完成后折叠进初始化脚本，不长期保留重复副本。

验收：

- 任意环境都能查询当前数据库迁移版本。
- 同一迁移不会重复执行，缺失迁移会在启动/发布前被阻止。
- 数据结构升级不会依赖 Java 静默兼容或人工修改 JSON。

### P1-01 分类/标签 Store 吞掉异常，页面把失败显示成空数据

**状态：未处理**

证据：

- [`category.ts`](../../Web/src/stores/category.ts#L47) 捕获异常后直接返回 `[]`，不抛出也没有 `error` 状态。
- [`Categories.vue`](../../Web/src/views/Categories.vue#L118) 外层使用 `handleAsync` 期待通过 `onError` 设置错误提示，但 Store 已吞掉异常，因此该分支不会执行。
- [`tag.ts`](../../Web/src/stores/tag.ts#L55) 同样在失败时返回 `[]`/`null`。
- [`Tags.vue`](../../Web/src/views/Tags.vue#L39) 只有加载态和空态，没有错误态。

影响：

- API 500、网络中断和“数据库确实没有数据”被表现为同一种空页面。
- 分类页还会把 Store 返回的 `[]` 写入页面局部状态，短暂缓存也无法继续展示。
- 这类错误容易被误判为 CSS、路由或数据丢失问题。

建议：

- Store 负责维护 `data/loading/error/lastSuccessfulAt`，请求失败不要返回伪造的空数组。
- 列表为空只表示请求成功且真实返回空集合。
- 统一分类、标签、公告 Store 的失败语义，避免各页面各写一套。

验收：

- 断开 API 后分类/标签页显示可重试错误，不显示“暂无分类/标签”。
- 有旧缓存时明确展示“缓存数据 + 刷新失败”，不清空为假空态。

- 保证缓存测试不创建网络客户端、不访问 loopback。

验收：

- Windows/JDK 21 与 CI Linux 均可运行根 `mvn test`。
- 缓存测试失败只可能来自缓存逻辑，而非网络栈初始化。

### P1-06 Controller 异常处理仍与项目权威规范冲突

**状态：未处理**

静态统计：主后端 Controller 中仍有 16 个 `catch`，40 个 `Result.fail(...)`。

典型问题：

- [`MessagesController`](../../LiuTech/src/main/java/chat/liuxin/liutech/controller/web/MessagesController.java#L45) 捕获所有异常，并把 `e.getMessage()` 拼进用户响应。
- [`CategoriesController`](../../LiuTech/src/main/java/chat/liuxin/liutech/controller/web/CategoriesController.java#L58) 和 [`TagsController`](../../LiuTech/src/main/java/chat/liuxin/liutech/controller/web/TagsController.java#L106) 在 Controller 重复处理业务异常和系统异常。
- [`ResourceDownloadController`](../../LiuTech/src/main/java/chat/liuxin/liutech/controller/web/ResourceDownloadController.java#L49) 使用魔法数字并返回底层异常消息。
- 这些写法与 [`跨服务规范`](../架构/跨服务规范.md#L20) 的“业务异常交给 GlobalExceptionHandler、Controller 不 try-catch”冲突。

影响：

- 同类错误可能返回 HTTP 200 + 失败 code，也可能返回 HTTP 4xx；前端必须兼容多套语义。
- 底层异常消息存在泄漏实现细节的风险。
- 每个 Controller 都在复制日志和错误文案。

建议：

- 先处理会暴露 `e.getMessage()` 的入口，再按领域逐步清理，不做一次性机械替换。
- “未找到/未认证/业务违反”统一抛 `BusinessException(ErrorCode...)`；系统异常由全局处理器记录堆栈并返回固定用户文案。

验收：

- Controller 只接参、调 Service、返回成功结果。
- 同一种错误拥有稳定的 HTTP 状态、业务 code 和用户文案。

### P2-04 动效没有统一边界，基础按钮迫使页面写反向覆盖

**状态：未处理**

证据：

- Web 中扫描到 53 个包含 transition/animation/transform 的样式文件，仅 5 个包含 `prefers-reduced-motion` 处理。
- [`styles.scss`](../../Web/src/assets/styles/styles.scss#L348) 的全局 `.btn-primary` 默认 `translateY(-2px)`。
- [`About.vue`](../../Web/src/views/About.vue#L637) 为禁止移动，只能再写 `.btn-primary:hover, .btn-primary:active { transform: none; }`。
- 全局 Lenis [`useLenis.ts`](../../Web/src/composables/useLenis.ts#L17) 始终启动 `requestAnimationFrame` 平滑滚动，没有 reduced-motion 或关闭策略。

这正是“通用类定义过重，页面再覆盖”的维护反模式。

建议：

- 基础按钮只保留颜色、边框、阴影等稳定反馈，不默认位移。
- 特殊动效必须是显式 modifier，不让所有页面继承后再抵消。
- 建立统一 motion token，并对全局平滑滚动、无限动画和页面过渡支持 `prefers-reduced-motion`。
