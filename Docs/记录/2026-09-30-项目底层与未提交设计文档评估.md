## 1. 结论

需要优化底层，优先统一**数据访问的语义和边界**。已有 MyBatis-Plus、Hikari、主服务身份权威、存储接口和前端流式解析，不需要重新建设一套数据库工具层，也没有证据支持进一步拆分微服务。

现有设计比较适合个人维护：博客核心与 AI 分进程、分库，AI/TTS 故障边界清楚；父 POM 管理后端依赖；主后端已有 Result/ErrorCode/异常处理；Web/Admin 保持各自产品体验，并对公共 SSE 模块做镜像校验。这些边界可以保留。

最大的缺口是：业务读出的实体被直接写回、SQL 对软删除和属主的解释不一致、分页方式混用、外部 IO 混进事务、数据库升级没有执行台账。目录一致只是后续维护手段，不是本轮最高收益。

## 3. 优先处理的实际问题

### 3.1 P0：缓存 Users 整实体写回会覆盖积分和认证字段

证据：`UserUtils.java:39` 缓存完整可变 `Users` 5 分钟；`UserProfileService.java:72` 取得该对象，`:121` 直接 `userMapper.updateById(currentUser)`。`Users.java:42,47` 含 `points/version`，没有 `@Version`。`UserAuthService.java:359,429,548` 也有整实体写回。

这不只是“并发时可能丢更新”。例如：先加载用户缓存 → 签到把数据库积分加上 → 更新昵称。旧缓存里的积分与 version 会随昵称一起写回，顺序操作也可能覆盖新值。修改登录时间同样不应覆盖积分、角色或密码字段。缓存对象还会在数据库提交之前被原地修改。

建议：所有资料/密码/登录时间更新只 SET 所需列；积分只能通过积分业务入口修改，余额更新与流水处于同一个短事务。认证缓存存不可变快照，不把缓存中的实体作为写入对象；写后提交成功再失效。不能仅补 `@Version` 而忽略 0 行结果。

验收：缓存命中后“签到→改昵称”积分不回退；并发加积分/改资料流水可核对；资料更新 SQL 不包含 points/version/password_hash/role；失败或回滚不污染缓存快照。

### 3.2 P0：AI 异常落库绕过会话属主检查

证据：`MemoryService.java:77,100` 两个保存方法不校验属主；`ChatServiceHelper.java:91` 的错误记录直接调用 `saveAssistantMessage`。`StreamingChatService.java:163` 先装配历史，`:207` 在 catch 中记录错误。同步路径 `AiChatServiceImpl.java:76,103` 也如此。

需要纠正未提交文档的影响描述：默认 `chat-history-limit=14` 时，`PromptService.java:121` → `listLastMessagesAsPromptMessages` → `getConversationOwnedByUser` 会先阻止正常用户消息写入别人的会话。因此不能断言默认配置下一定能把任意输入正文写进去。

**实际漏洞仍然存在**：属主检查抛出异常后，catch 会向传入会话写一条 `content=null/status=3` 的助手消息，并修改该会话计数。若历史长度设为 0，两个历史方法提前 return，正文写入路径才也失去这个校验。错误处理不应产生被拒绝访问对象的副作用。

建议：在业务入口解析会话时校验一次；在 MemoryService 的所有写入口再次保证 userId/conversationId 一致；授权失败不记入目标会话；会话检查不依赖历史长度。组合外键可作第二阶段兜底，需要先检查存量数据。

验收：A 使用 B 的 id，不论历史长度 0 或 14、同步或流式、正常或异常，B 的消息数、内容和更新时间全部不变。

### 3.3 P1：分片任务路径未限制，合并还会递归清理

证据：`FileUploadService.java:317,363` 只检查 uploadId 非空与长度；`:335,374` 直接拼到 tmp 下；`:406,416` 合并后递归删除该目录。`FileUploadController.java:134,162` 的接口要求 ADMIN。

这是有管理员权限前提的路径边界漏洞，不是匿名任意写。含 `..` 或路径分隔符的标识可使读写/清理越出预期任务目录，合并路径比单纯写分片更危险。当前以 uploadId 共享目录，没有任务属主绑定。

建议：服务端生成任务 id，绑定用户；若短期保留客户端 id，严格限制字符集合，并对规范化后路径检查仍在任务根目录内；清理只允许已登记任务目录。流式合并是随后独立的内存优化。

### 3.4 P1：AI 的三个 LIMIT 没有生效

证据：`MemoryService.java:207,248,263` 都是 `.last(false, "LIMIT ...")`。MyBatis-Plus 3.5.15 的 `AbstractWrapper.last(boolean, String)` 仅在 condition=true 时追加 SQL，false 是不执行，不是关闭检查。[官方源码](https://raw.githubusercontent.com/baomidou/mybatis-plus/v3.5.15/mybatis-plus-core/src/main/java/com/baomidou/mybatisplus/core/conditions/AbstractWrapper.java)。

导致会话列表/会话消息分页失效，历史上下文查询也先拉全量数据。另有 offset 在 size 钳制前计算的问题：即使恢复 LIMIT，也要用归一化后的 page/size 计算偏移并防溢出。

建议：普通页码查询用 MP Page/IPage（AI 需补本服务的分页配置），末尾 N 条用绑定参数的 Mapper SQL；不要在 Service 拼 LIMIT。分页计数保留现有 total 契约，游标分页另作协议演进。

### 3.5 P1：软删除、恢复、状态和计数口径不一致

证据：文章删除级联软删互动行；`PostsAdminService.java:274,292` 恢复只调 posts 的恢复 SQL。`PostsMapper.xml:700,707` 只恢复文章。`PostLikesMapper.xml:23` 计数过滤 deleted_at，`:36` 状态不过滤，`:43` upsert 不清 deleted_at；收藏有同类问题。

因此恢复后的文章可显示“已点赞”，但该记录不计入点赞数，再切换也不能恢复可见性。文章冗余 like_count 是否立刻归零取决于后续重算，不能简单说恢复语句本身把它设成 0。

建议：先定义恢复是否恢复原互动；按该语义同时修复单条/批量恢复、状态查询、upsert 与计数。自定义 XML/注解 SQL 必须显式写软删条件；恢复和物理删除允许明确绕过 MP 的自动软删条件。

### 3.6 P1：并发更新策略混用，没有统一事务模型

证据：`PointsService.java:146` 在一个事务中重复普通 SELECT/version UPDATE；`UserMapper.xml:145,155` 手写 version；主配置注册乐观锁插件，但 Users 无 `@Version`。`MemoryService.java:120` 会话计数先读后加一再整实体 UPDATE，`:131` 取 MAX(seq)+1；`sql.sql:622` 序号索引非唯一。

在默认 RR 的并发冲突场景，同一事务的普通读重试可能一直看到旧快照。AI 两条消息并发保存可能拿相同序号、丢计数。单测 mock 返回值无法证明这些语义。

建议：余额和计数优先条件/原子 SQL，处理影响行数；确需 retry 时重试整个独立事务并限制次数。AI 取号在已校验会话的串行点下完成，增加计数用原子 SET；序号唯一约束前先去除存量重复。为积分流水 balance_after 明确定义取值与锁定方式。

### 3.7 P1：外部副作用与数据库事务混在一起

证据：`ImagesService.java:47,68` 的事务覆盖文件保存；`UserManagementService.java:650,661` 与 `:692,703` 在事务中请求 AI 数据清理。

不只连接持有时间长：AI 删除成功后主库回滚，也无法自动还原 AI 数据。简单把 HTTP 改成 afterCommit 可以缩短事务，但仍有进程退出/重试丢失的窗口。

建议：图片保存与短 DB 事务分段，失败有清理补偿；跨服务用户清理使用主库持久化待处理任务/outbox，提交后执行、幂等重试。普通同库 CRUD 不需要因此套上任务框架。

### 3.8 P1：初始化与迁移仍缺机器可验证的边界

证据：Compose 挂载 `Docs/SQL/sql.sql` 到首启目录；仓库无 Flyway/Liquibase/执行版本台账。额外 `LiuTech-AI/src/main/resources/sql/ai_chat_tables.sql:14` 仍 DROP 三张 AI 表，且缺当前 context_window/ai_tts_config。

旧脚本未发现自动执行引用，不是当前启动必然清库；它是一个过期且危险的手工入口。`CREATE TABLE IF NOT EXISTS` 不会升级已有表；反复初始化还可能覆盖运营种子数据。

建议：保留 sql.sql 作为完整新库快照；旧 AI 初始化脚本移出可执行入口或删除；两库各有迁移版本/校验和/执行台账，由部署使用独立迁移权限执行。版本化迁移发布后保持不可变，不能折叠进初始化后删除唯一的升级历史。可采用成熟工具，重点是执行规则而非自造 SQL 执行框架。

## 5. 数据库连接与 SQL 应统一到什么程度

### 5.1 连接配置

两服务已经都用 Boot 自动数据源 + Hikari + MyBatis-Plus；未找到另一套手工 DriverManager/JdbcTemplate 业务访问。数据库和运行账号应继续隔离。

Compose 的 `SPRING_DATASOURCE_URL` 覆盖 prod.yml，而两处参数集不同。建议 yml 定义完整模板，Compose 只传主机/端口/库/账号等环境值，或反过来明确整 URL 是唯一真源；不要两处独立维护一串参数。

共同规则：保留项目要求的 allowPublicKeyRetrieval=true、统一时区和字符集，区分连接池等待/建连/SQL/事务超时，池容量参数化。不要把两服务 TTL/池配置强行设成相同数字。

不建议为了“参数补齐”重新加 autoReconnect。Connector/J 明确不推荐它，已有连接池负责坏连接淘汰，事务失败要由业务决定能否重试。[官方说明](https://dev.mysql.com/doc/connector-j/en/connector-j-usagenotes-troubleshooting.html)。

主配置 `configuration-properties.helperDialect/reasonable/...` 是 PageHelper 风格，目前实际分页入口为 MP PaginationInnerInterceptor，未发现 PageHelper 调用。可验证无引用后删去误导配置；AI 真正使用 Page 时建立本服务拦截器。

### 5.2 SQL 分工规则（建议写入现有跨服务规范）

| 场景 | 推荐入口 | 必须统一的行为 |
| --- | --- | --- |
| 单表简单 CRUD/过滤 | BaseMapper + LambdaWrapper | 不用字符串列名拼业务参数；只读实体不直接整体写回 |
| 关联列表、聚合、动态条件 | Mapper XML | #{参数} 绑定，明确 DTO/列清单/软删/排序；公共片段只在真正重复时提取 |
| 很短的固定查询/原子更新 | Mapper 注解可以保留 | 参数绑定；多分支或较长 SQL 移到 XML；同一查询只有一个实现入口 |
| 修改资料/密码/状态 | 字段级 UPDATE | 禁止把查询实体全字段写回；不修改无关余额/角色 |
| 积分/库存/派生计数 | 专用 Mapper 方法 | 条件更新、影响行数检查、流水事务、明确快照与重试策略 |
| 页码分页 | Page/IPage 或绑定 offset/limit 的 Mapper | 统一 page>=1、size 上限、排序白名单、稳定 id 次序；Service 不拼 LIMIT |
| 末尾 N 条历史 | 绑定 LIMIT 的专用查询 | 会话属主先校验，倒序读取后按约定恢复顺序 |
| 软删/恢复/物理删除 | 明确命名的 Mapper 方法 | 主后端以 deleted_at IS NULL 为基线；例外操作明确标记；AI status=9 是另一业务语义 |
| 批量操作 | foreach/executeBatch/CASE 按需选择 | 绑定参数、单批上限、重复 id/URL 的含义、提交与失败语义明确 |

没有理由把所有 SQL 一刀切成 XML，也没有理由因为 Wrapper 更短就把复杂关联藏进 Service。项目目前 XML 值参数扫描未发现 `${...}`；现存 `.last` 是分页设计问题，不能直接误报成字符串输入 SQL 注入。

主服务真实软删列是 deleted_at，但 `跨服务规范.md` §7 写成 deleted。应纠正文档；AI 的归档 status=9 不应为了列名统一被改成主服务软删除。

## 6. 项目结构建议

保留 Web / Admin / LiuTech / LiuTech-AI / nginx 顶层。先在主后端已有 service/mapper 结构内按职责整理，不立即搬全仓包路径。

- 文章：读列表/详情/搜索形成明确查询服务；写文章与互动保留各自业务入口。先解开 PostsService 与交互、缓存、附件之间的耦合，再决定是否迁入 post 领域目录。
- 用户：把认证、资料、积分各自允许写的列明确化；统一身份快照，减少 UserUtils 完整实体缓存与 DB 当前状态两条事实源的交叉。
- AI：优先拆 MemoryService 的“授权与持久化事务”和 StreamingChatService 的“流生命周期”。已存在 ChatServiceHelper、PromptBudget、BackendApiTransport，继续复用。
- 前端：`usePostEditor.ts` 当前 1042 行，包含自动草稿、附件、分类、上传、AI 应用及提交。可以先提取独立可测试的草稿/附件/AI 草稿更新模块；不按行数等分。
- 公共前端：3 对镜像模块本次校验通过。长期可迁到 npm workspace 共享包，但要同时调整 Docker build context、锁文件、CI 与 Vite 引用。两个 Vite 根并不代表技术上永远不能共享，只是现部署方式需要配套修改。
- Admin 的 CRUD 数据存在 composable 本地 ref 很合理，不因 Store 数少就引入全局状态。Web/Admin 的提示 UI 不同，也无需为了一致把两套交互全部合并。
- 不新增通用 BaseRepository/万能 BaseService，不把两后端实体和业务 Mapper 抽进公共 jar。跨服务统一编码规则不等于统一运行时状态。
