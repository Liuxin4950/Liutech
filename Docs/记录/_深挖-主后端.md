## 2. 安全链路（逐层）

整条链路：**HTTP 请求 → RequestTraceFilter（traceId）→ JwtAuthenticationFilter（无状态认证）→ SecurityFilterChain 授权规则 → Controller 层 @PreAuthorize → GlobalExceptionHandler（401/403 JSON）**。

### 2.1 SecurityConfig

`config/SecurityConfig.java:36-38` 三注解：`@Configuration @EnableWebSecurity @EnableMethodSecurity`。`@EnableMethodSecurity` 是让 `@PreAuthorize` 生效的关键开关（大白话：不加它，写在 Controller 上的权限注解就是摆设）。

过滤器链 `filterChain(HttpSecurity)`（`SecurityConfig.java:59-140`）顺序与规则：

1. `csrf(disable)`（:69）——REST + JWT 无 Cookie 会话，关 CSRF。
2. `cors(configurationSource(corsConfigurationSource()))`（:70）。
3. 异常处理（:71-86）：`authenticationEntryPoint`（未认证 → **401** + `Result.fail(ErrorCode.UNAUTHORIZED, "未登录或Token已失效")`）、`accessDeniedHandler`（权限不足 → **403**）。都用 `tools.jackson.databind.ObjectMapper`（Boot 4 的 Jackson 3 包名）手写 JSON，与全局异常格式一致。
4. `SessionCreationPolicy.STATELESS`（:87）——无状态会话，每次请求都靠 JWT。
5. 授权规则（:89-134），**顺序即优先级**（Spring Security 按声明顺序匹配第一个命中的规则）：
   - `OPTIONS /**` permitAll（:91，CORS 预检）；
   - `FULLY_PUBLIC` 全放行（:94-96）；
   - `AUTHENTICATED_PATHS` 的 **GET** 强制认证（:99-101，即在公开前缀下又要登录的特殊路径，如 `/posts/my`）；
   - GET/HEAD/POST 公开精确路径与公开前缀（:104-119）；
   - `DENY_PREFIXES` 的 GET/HEAD `denyAll()`（:122-125）：`/resources/`、`/uploads/resources/` 直接 403，堵死付费文件静态直出；
   - `/admin/**` `hasRole("ADMIN")`（:128）——**URL 层的第一道管理端防线**；
   - `POST /upload/**` authenticated（:131）；
   - `anyRequest().authenticated()`（:133）兜底。
6. 过滤器注册（:136-137）：
   ```java
   .addFilterBefore(requestTraceFilter, UsernamePasswordAuthenticationFilter.class)
   .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
   ```
   注意：`requestTraceFilter` 在前、`jwtAuthenticationFilter` 在后（后 add 的排在更前执行？不——两个都是 `addFilterBefore` 同一锚点，后添加者插到更靠前位置，实际执行序为 jwt → trace 反了。此处从代码看两者都注册在 UsernamePasswordAuthenticationFilter 之前，`requestTraceFilter` 先 add、`jwtAuthenticationFilter` 后 add，因此链上 `JwtAuthenticationFilter` 在 `RequestTraceFilter` **之前**执行——traceId 绑定晚于 JWT 解析，JWT 过滤器内的日志没有 traceId。这是一个可以写进“可改进点”的细节）。

CORS（`SecurityConfig.java:148-186`）：`allowedOriginPatterns` 用 **pattern**（`http://localhost:*`、`http(s)://liuxin.chat(:*)`、`www/admin.liuxin.chat` 等，:152-166）而非精确 origin，解决前端跑在任意端口的问题；`allowedHeaders: *` + `allowCredentials: true`（:174-177），预检缓存 `maxAge: 3600`（:180）。注意 `allowCredentials(true)` 与 `*` 头共存依赖 `allowedOriginPatterns`（Spring 的约束：凭据模式下 origin 不能用 `*`，pattern 合法）。

密码编码器：`BCryptPasswordEncoder` Bean（`SecurityConfig.java:190-193`）。

### 2.2 白名单单点维护：SecurityWhitelist

`config/SecurityWhitelist.java:20-101` 把白名单集中成常量：`FULLY_PUBLIC`（注册/登录/找回密码等 8 条）、`PUBLIC_GET_PREFIXES`（`/posts/`、`/categories/`、`/uploads/images/`、`/tts/audio/` 等 13 条）、`PUBLIC_GET_EXACT`（含 `/actuator/health`，给 docker compose healthcheck 探针，:63）、`PUBLIC_POST_EXACT`（`/messages`、`/tts/speech`）、`DENY_PREFIXES`、`AUTHENTICATED_PATHS`（`/posts/my`、`/posts/drafts`、`/posts/favorites`、`/posts/view-history`、`/posts/recommendations`，:95-101）。

配套静态方法 `shouldSkipAuthentication(uri, method)`（`SecurityWhitelist.java:112-156`）供 JWT 过滤器复用——**SecurityConfig 和 JwtAuthenticationFilter 共享同一份白名单**，避免两处维护不一致（这正是注释强调的设计意图）。

### 2.3 JwtAuthenticationFilter

`filter/JwtAuthenticationFilter.java:33-35`：`@Component` + 继承 `OncePerRequestFilter`（保证单次请求只执行一次）。

`doFilterInternal`（:49-68）四步：
1. `shouldSkipAuthentication` 公开接口直接放行（:54-58）；
2. `extractTokenFromRequest`（:85-91）——**只从 `Authorization: Bearer xxx` 头取 token**（`authHeader.substring(7)` 截掉 "Bearer "），不做 Cookie/query 参数回退；
3. `processValidToken`（:98-115）：
   - `jwtUtil.validateToken(token)`（弱校验：签名 + 未过期，:99）；
   - 取出 `username`、`userId`；
   - **查库二次校验**：`userAuthLookupService.selectById(userId)` → `isCurrentUserTokenValid`（`service/UserAuthLookupService.java:41-54`）：用户存在且未软删除、用户名与 token 一致、`status==1`（未禁用）、token 中的 `passwordHash` 摘要与数据库 `passwordHash` 再哈希后一致。**角色与账号状态以数据库当前值为准**——降权/禁用/改密后旧 token 立即失效，这是比“纯 JWT 无状态”更严的做法；
4. `setAuthenticationContext`（:124-136）：构造 `UsernamePasswordAuthenticationToken(username, null, authorities)`，**把 `userId` 塞进 `details`**（:131，后续 `UserUtils`、`MyMetaObjectHandler` 都从这里取），再 `SecurityContextHolder.getContext().setAuthentication(...)`。

权限构建 `buildUserAuthorities`（:143-152）：默认加 `ROLE_USER`，数据库角色为 `admin` 时再加 `ROLE_ADMIN`。任何异常都被 catch 后继续放行（:64-66）——认证失败不在此处拒绝，由后续授权链决定 401/403。

### 2.4 JwtUtil（`utils/JwtUtil.java`）

- 签名：HS256 对称签名，密钥来自 `jwt.secret`，`getSigningKey()` 用 `Keys.hmacShaKeyFor(secretKey.getBytes())`（:46-48）；创建时 `.signWith(getSigningKey(), Jwts.SIG.HS256)`（:112）。
- Claims（`generateToken` :80-87）：`userId`、`username`、`role`、`passwordHash`——其中 `passwordHash` 是 **BCrypt 哈希再 SHA-256 摘要**（`sha256()` :55-69），避免把 BCrypt 值明文放进 JWT payload；subject 放 username。
- 有效期：`expiration = now + expirationTime`（:103-114），30 天由配置注入。
- 解析（:184-196）：`Jwts.parser().verifyWith(key).build().parseSignedClaims(token)`，任何 `JwtException` 都统一返回 null，调用方只感知“无效”。
- 双校验方法：`validateToken(token)` 弱校验（签名+未过期，:230-233）；`validateToken(token, username)` 强校验（加用户名匹配，:216-222）。
- `refreshToken`（:241-260）：沿用旧 claims 重新签发，注意它把已是 SHA-256 的 passwordHash **原样**写入新 claims 不再二次哈希（:252-258 注释专门说明）。

### 2.5 @PreAuthorize 类级鉴权

方法级：`controller/web/PostsController.java:151-188` 上，创建/更新/删除/发布/下线文章各自标 `@PreAuthorize("hasRole('ADMIN')")`（如 :151、:159、:168、:176、:184）。

类级：`controller/admin/**` 全部在类上挂 `@PreAuthorize("hasRole('ADMIN')")`，例如：
- `PostsAdminController.java:31`、`PointsAdminController.java:32`、`CacheAdminController.java:21`、`CategoriesAdminController.java:25`、`DashboardController.java:18`、`AboutPageAdminController.java:24` 等（20 个 admin 控制器一致）。
- 与 URL 规则 `/admin/** hasRole("ADMIN")`（SecurityConfig.java:128）形成**双层防御**：URL 层先拦，方法注解再兜底（防止有人把 Controller 挪出 /admin 前缀后失去保护）。

管理端控制器继承 `BaseAdminController`（`controller/admin/BaseAdminController.java:17-49`），提供 `handleOperationResult(boolean→Result)` 与 `checkResourceExists` 两个模板方法，减少重复样板。

### 2.6 MyMetaObjectHandler（审计字段自动填充）

`config/MyMetaObjectHandler.java:24-57`：实现 MP 的 `MetaObjectHandler`。`insertFill`（:34-42）填 `createdAt/updatedAt`（new Date）和 `createdBy/updatedBy`（`userUtils.getCurrentUserId()`，从 SecurityContext 的 details 取）；`updateFill`（:49-57）只填 `updatedAt`，`updatedBy` 仅在能拿到用户时填（匿名场景不填 null 覆盖）。`strictInsertFill`/`strictUpdateFill` 只在字段为 null 时才填充（严格模式，不覆盖业务显式设置的值）。配合 `BaseEntity` 上的 `@TableField(fill = FieldFill.INSERT / INSERT_UPDATE)`（`model/BaseEntity.java:23-42`）。

`UserUtils.getCurrentUserId()`（`utils/UserUtils.java:51-85`）的取值优先级：Authentication.details 里的 userId（JWT 过滤器写入）→ principal 用户名查 Caffeine 缓存/查库。内置 5 分钟/200 条的用户缓存（:39-42）。

## 4. 缓存（Caffeine）

`config/CacheConfig.java:29-69`：`@EnableCaching` + 手工组装 `SimpleCacheManager`，为每个名字建独立 `CaffeineCache`。**全部缓存清单**（:35-52）：

|---|---|---|---|
| `postList` | 5 分钟 | 200 | 文章分页列表 |
| `hotPosts` | 5 分钟 | 50 | 热门文章 |
| `latestPosts` | 5 分钟 | 50 | 最新文章 |
| `hotTags` | 10 分钟 | 100 | 热门标签 |
| `allTags` | 10 分钟 | 10 | 全部标签 |

统一 `buildCache(name, ttlMinutes, maxSize)`（:63-69）：`expireAfterWrite` + `recordStats()`（开启统计，便于后续监控命中率）。

**实际用法示例 1（Posts）**：
- 读：`PostsService.getPostList(req, userId)` 上 `@Cacheable(value = "postList", key = "#req.page + ':' + #req.size + ':' + ... + #userId", unless = "#result == null")`（`service/PostsService.java:107-109`）——SpEL 拼出复合 key，**连 userId 都进 key**（不同用户看到的点赞收藏状态不同，不能共享缓存，这是易错点）；`getHotPosts`（:224-226）与 `getLatestPosts`（:317-319）以 `#limit` 为 key，且 `unless` 排除空结果防穿透。
- 写：`createPost`（:396-398）、`updatePost`（:466-468）、`updatePostForAdmin`（:515-517）、`deletePost`（:573-575）、`publishPost`（:621-623）、`unpublishPost`（:638-640）全部 `@CacheEvict(value = {"hotPosts","latestPosts","postList","postSeries","allTags"}, allEntries = true)`——因为文章变更会影响多个列表的任意组合，直接全清（博客体量下代价可接受）。

**实际用法示例 2（Announcements / Categories）**：

### 5.2 Points（积分）链路

积分是博客的虚拟货币：签到/成就赚分，下载付费资源花分。

**前台入口**：`controller/web/CheckinController.java`（`@RequestMapping("/user")`，:26-27）——`POST /user/checkin` 签到（:38-46，带 `@OperationLog(action="checkin")`）、`GET /user/checkin/status`、`/calendar`、`/months`（:53-92）。

**CheckinService**（`service/CheckinService.java`）：
- `checkin(userId)`（:47-113）`@Transactional`：查用户 → `calculateConsecutiveDays`（连续签到天数）→ `calculatePointsEarned`（基础 1 分 + 连续奖励）→ 插 `user_checkins` 记录 → 调 `pointsService.addPoints(...)`（原子加积分 + 流水，失败包装成 `SYSTEM_ERROR`）→ 回读最新积分组装 `CheckinResp`（:80-107）。
- 只读接口无事务注解：`getCheckinStatus`（:117-151）、`getCheckinCalendar`（:159-184）、`getCheckinMonths`（:189-194）。

**PointsService**（`service/PointsService.java`）——积分的唯一写入口：
- 类型常量（:31-52）：交易类型 `checkin/consumption/refund/admin_adjust`，来源 `resource_download/admin_manual/system_reward`。
- `deductPoints`（:71-119）`@Transactional`：校验金额 > 0 → 读用户拿 `points` 和 `version`（乐观锁版本号，大白话：每次修改前先记下数据版本，修改时带条件 `version = 旧值`，别人改过就更新 0 行，说明有并发冲突）→ 积分充足性检查 → `userMapper.deductPointsWithVersion`（**SQL 双保险**，见下）→ 0 行即乐观锁冲突抛“系统繁忙”→ 插入 `points_transactions` 流水（amount 存负数，balanceAfter 存余额）。
- `addPoints`（:131-181）`@Transactional`：与扣减不同，**加了 3 次重试循环**（`MAX_RETRY_COUNT = 3`，:53-54），每次冲突重读最新 version 再试（:146-159）。
- `refundPoints`（:191-194）：转发 `addPoints(TYPE_REFUND)`。

**关键 SQL** `mapper/UserMapper.xml:133-151`：
```sql
UPDATE users SET points = points - #{amount}, version = #{newVersion}, updated_at = NOW()
WHERE id = #{userId} AND version = #{currentVersion} AND points >= #{amount}
```
扣减在 WHERE 里同时带 `version` 和 `points >= amount` 两个条件——数据库层面保证“不超扣 + 不覆盖并发修改”，返回 0 行即冲突。

**管理端**：`controller/admin/PointsAdminController.java:31-34`（类级 `@PreAuthorize("hasRole('ADMIN')")`，继承 BaseAdminController）——流水分页 `GET /admin/points/transactions`（:39-50，时间参数用 `@DateTimeFormat(pattern="yyyy-MM-dd HH:mm:ss")`）、`POST /admin/points/adjust` 手动调分（:65-72，`@OperationLog`）、签到记录查询（:75-97）、`GET /admin/points/stats` 汇总（:100-103）。所有分页参数经 `ValidationUtil.validateRange(size, 1, 100)`（:48）。
`PointsAdminService.adjustPoints`（:107-176）`@Transactional`：正数调 `addPointsWithVersion`、负数调 `deductPointsWithVersion`，同样 3 次重试，成功后插 `admin_adjust` 流水。

**消费方**：`service/ResourceDownloadService.purchaseResource`（:68-127）`@Transactional`——查资源 → 免费/上传者免购 → **先插入 `download_logs` 购买记录（唯一索引防重复购买，`DuplicateKeyException` 转“已购买”）→ 再 `pointsService.deductPoints`**（先插记录后扣分，配合事务回滚保证“扣了分但没记录”不会发生）→ 失败回滚。

**DTO**：`req/PointsAdjustReq`、`resp/PointsTransactionResp`（流水+用户名）、`resp/CheckinResp/CheckinStatusResp/CheckinCalendarItemResp/CheckinMonthResp`、`resp/PageResp<T>`。

## 8. 分页、参数校验、MyBatis-Plus 使用模式

### 8.1 分页插件

`config/MybatisPlusConfig.java:22-34`：`MybatisPlusInterceptor` 注册两个内部拦截器——`PaginationInnerInterceptor(DbType.MYSQL)` 且 **`setMaxLimit(500L)`**（单页最大 500 条，防 `size=999999` 打爆数据库）和 `OptimisticLockerInnerInterceptor`（乐观锁插件，配合实体 `@Version` 字段用；注意本项目的 users.version 是手工 SQL 更新，插件兜底）。

用法（`service/PostsService.java:111,117`）：`new Page<PostListResp>(page, size)` → mapper 方法首参传 `IPage` → 插件自动改写 SQL 追加 `LIMIT` 并执行 count；返回 `IPage.getRecords()/getTotal()/getCurrent()/getSize()` → 组装 `resp/PageResp<T>`（`resp/PageResp.java:47-57`，构造器里算好 `pages/hasNext/hasPrevious`）。

yml 里 `application.yml:67-71` 的 `configuration-properties: helperDialect...` 是 PageHelper 风格的遗留配置，对 MP 分页无效（无害，但属于可清理项）。

### 8.2 参数校验（两条路线并存）

1. **JSR303**（`spring-boot-starter-validation`）：`req/PostCreateReq.java:19-39` 典型用法——`@NotBlank(message="文章标题不能为空")` + `@Size(max=200)` 的 title、`@NotBlank` 的 content、`@NotNull` 的 categoryId；Controller 侧 `@Valid @RequestBody PostCreateReq req`（`PostsController.java:153`）触发，失败由 `GlobalExceptionHandler.handleMethodArgumentNotValidException` 收（§3.4）。
2. **手工校验工具** `utils/ValidationUtil.java:17-162`：`validateId/validateRange/validateNotBlank/validateEmail/validateUsername/validatePassword`（正则：用户名 4-20 位字母数字下划线 :29-31、邮箱 :22-24），抛 `BusinessException(PARAMS_ERROR)`。管理端查询参数用它（如 `PointsAdminController.java:47-48`），因为 query 参数校验 `@Validated` 需要类级注解，团队选择了更直白的手工方式。

### 8.3 MyBatis-Plus 使用模式

- **BaseMapper 继承**：所有 mapper 接口 `extends BaseMapper<T>`（如 `mapper/PostsMapper.java:23-24`），拿到 CRUD；复杂 SQL 自定义方法 + XML（`resources/mapper/PostsMapper.xml` 等 22 个 XML），映射用 `resultMap`（`PostListRespMap` :26-66 是典型：association 组装嵌套对象）。
- **Service 层继承**：`PostsService extends ServiceImpl<PostsMapper, Posts>`（:61）获得 `save/updateById/getById/update(Wrapper)`。
- **Wrapper 两种风格**：`LambdaQueryWrapper`（类型安全，`new LambdaQueryWrapper<UserViewHistory>().select(...).eq(...)`，PostsService.java:349-352）和 `LambdaUpdateWrapper`（`updateWrapper.eq(Posts::getId, id).setSql("view_count = IFNULL(view_count, 0) + 1")`，:194-197；`updateSeriesAssignment` 用显式 `.set` 绕过 null 不更新策略，:295-308）。
- **软删除**：全局配置 + `@TableLogic`（`model/BaseEntity.java:47-48`）——select 自动拼 `deleted_at IS NULL`、deleteById 自动变 UPDATE；但 PostsService.deletePost 用自定义 SQL 覆盖（XML:718），额外带 `deleted_at = #{deletedAt}` 和操作人。
- **批量插入**：`postTagsMapper.batchInsert(postTags)` 自定义 foreach 批量（PostsService.java:700-703）。
- **审计填充**：`MyMetaObjectHandler` + `@TableField(fill=...)`（§2.6）。

## 10. 架构亮点与可改进点

### 亮点

1. **白名单单点维护**（SecurityWhitelist）——SecurityConfig 与 JWT 过滤器同源，不会出现“过滤器跳过了但授权没放行”的漂移。
2. **JWT + 数据库状态校验**（`UserAuthLookupService.isCurrentUserTokenValid`，UserAuthLookupService.java:41-54）：token 内嵌 passwordHash 摘要，改密/禁用/降权即失效；角色以库为准。
3. **401/403 与业务异常全部走统一 Result 结构**，前端只有一种解析逻辑；Spring Security 6 新老授权异常（AuthorizationDeniedException/AccessDeniedException）显式映射 403 而非 500（GlobalExceptionHandler.java:265-270）。
4. **积分系统的并发正确性**：`UPDATE ... WHERE version = ? AND points >= ?` 数据库级 CAS + 重试 + 流水表 + 事务回滚（PointsService/PointsAdminService/UserMapper.xml:133-151）；购买资源“先插记录靠唯一索引挡重复，再扣分，异常回滚”（ResourceDownloadService.java:88-126）。
5. **存储抽象 + 逻辑路径**：本地/COS 双实现共享 `StoragePathUtil` 生成路径，切 COS 数据库零迁移；付费文件不走静态映射，只走购买校验的下载接口；COS 签名直链 + 本地流式转发双回退（FileStorage.java:51-72）。
6. **图片资产全生命周期**：哈希去重（ImagesService.java:49-54）→ 引用计数（ImageReferenceService）→ 定时对账/孤儿清理（两个 cron 任务）→ 10 分钟重复上传幂等兜底（FileUploadService.saveResourceFile）。
7. **防 N+1 与缓存键细节**：标签批量 IN 查询填充（PostsService.fillTags :248-268）；`postList` 缓存 key 带上 userId（不同用户交互状态不同，:108）；空结果不进缓存（`unless`）。
8. **对外部依赖的防御性超时**：AI 聚合 1s/1.5s 超时、TTS 状态探测 800ms/1200ms + 5s 结果缓存，外部服务故障不影响主接口。
9. **可观测性**：RequestTraceFilter 的 traceId 贯穿 MDC + 响应头 + 慢请求告警；OperationLogAspect 全自动审计（SpEL 描述、IP 链回退、失败也记录）。

### 可改进点（按优先级）

1. **RestTemplate 无超时配置**（TtsSpeechService.java:68）：默认 `SimpleClientHttpRequestFactory` 的 connect/read timeout 是**无限**，SiliconFlow 挂起会拖住线程。应改 `RestTemplateBuilder` 配 connectTimeout/readTimeout。
2. **过滤器顺序与 traceId 覆盖不全**：SecurityConfig.java:136-137 两个 `addFilterBefore` 同一锚点，后注册的 JwtAuthenticationFilter 实际先执行，其日志没有 traceId；建议显式 `addFilterBefore(jwt, RequestTraceFilter.class)` 让 trace 最先。
3. **积分扣减/增增加的重试不对称**：deductPoints 无重试直接失败（PointsService.java:95-101），addPoints 有 3 次重试——扣减冲突时用户体验更差；且重试上限、`selectById` 双读可提取公共方法。
4. **多处 RuntimeException 裸抛**（如 ResourceDownloadService 的“资源不存在”等）：绕过 ErrorCode 体系，前端拿到的是 500“系统异常”；建议统一换 `BusinessException(ErrorCode.xxx)`。
5. **application.yml:67-71 的 `helperDialect` 等 PageHelper 遗留配置**对 MP 无效，易误导后来者，建议删除。
6. **JWT secret 强制 `${JWT_SECRET}` 无默认值**是好的，但 token 无黑名单/refresh 轮换机制（refreshToken 只是重新签一份同样的 claims），被盗后 30 天内无法主动吊销（只能靠改密码触发 passwordHash 失效）。
7. **`postList` 缓存 key 拼接 10 个维度**，维度多了以后命中率低且 key 冗长；量大了可考虑按 `page:size` 分桶 + 服务内二次过滤，或上 Redis 集中缓存。
8. `BaseAdminController.handleOperationResult` 把 boolean 失败转成 `Result.fail` 而非抛异常，与“异常统一兜底”的风格不统一，新代码容易两种写法混用。
