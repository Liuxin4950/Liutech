## 2. Web 网络封装（重中之重）

### 2.1 多服务 axios 实例（`Web/src/services/api.ts`）

**大白话**：axios 实例 = 一个配置好"默认地址、超时时间、拦截器"的 HTTP 客户端。这个项目有两个后端（主服务 8080 和 AI 服务 8081），所以建了两个实例。

1. **统一响应壳**（:9-13）：
   ```ts
   export interface ApiResponse<T = any> { code: number; message: string; data: T }
   ```
2. **实例工厂**（:21-33）：
   ```ts
   const instances: Record<ServiceType, AxiosInstance> = {} as Record<ServiceType, AxiosInstance>
   Object.values(ServiceType).forEach(serviceType => {
     const config = getServiceConfig(serviceType)
     instances[serviceType] = axios.create({ baseURL: config.baseURL, timeout: config.timeout })
   })
   ```
   注意 :24-26 的注释——**故意不预设 Content-Type**：让 axios 按 data 类型自动判断（普通对象→JSON，FormData→multipart+boundary）。注释记录了历史事故："曾因默认 application/json 覆盖 FormData 检测，导致 TinyMCE 粘贴图片上传 400"。

3. **服务配置**（`Web/src/services/serviceConfig.ts`）：
   - `ServiceType` 是值对象 + 类型别名（:10-14），注释说明"避免 enum 引发 TS1294"（TS 编译器对 const enum 跨模块引用的报错）。
   - `getBackendURL()`（:27-33）：优先 `VITE_API_BASE_URL`，兜底 dev `http://127.0.0.1:8080` / prod `/api`。
   - `getAiBaseURL()`（:36-42）：dev 兜底 `http://127.0.0.1:8081/ai`。
   - 超时：主服务 30000ms，**AI 服务 60000ms**（:48,:53）——AI 推理慢，超时单独放宽。

4. **请求拦截器**（:43-57）——每个实例都挂同一套：
   ```ts
   const token = localStorage.getItem('token')
   if (token) config.headers.Authorization = `Bearer ${token}`
   ```
   token 直接读 localStorage，**不经过 Pinia store**（这是刻意设计：拦截器要避免循环依赖 store）。

5. **响应拦截器——双格式归一化**（:60-96）。这是全项目最核心的设计：
   ```ts
   // 标准业务响应：{ code:number, message:string, data:any }
   const isStandard = data && typeof data.code === 'number' && 'message' in data && 'data' in data
   // AI 服务响应：{ success:boolean, ... }
   const isAi = data && typeof data.success === 'boolean'
   ```
   - **标准格式分支**（:69-78）：`code !== 200` → `showErrorToast(data.message)`，然后构造一个 Error，打上 `err.isBusiness = true` 标记后 `throw err`。这个标记的含义见 2.3。
   - **AI 格式分支**（:80-91）：`success !== true` 同样 Toast + isBusiness 抛错；成功则把 AI 响应**包装成标准格式** `response.data = { code: 200, message, data }`（:89）——上层所有 API 函数拿到的永远是 ApiResponse，类型一致。
   - **未知结构分支**（:94）：直接包成 `{code:200, message:'ok', data}`，兼容 AI 服务的裸数组响应。

6. **错误分支**（:97-126）：
   - **401**（:105-113）：先看请求 URL——`requestUrl.includes('/user/')` 时是"登录/注册/验证码等业务失败"，只提示后端消息（防御性处理，:107-108）；否则执行"会话失效"流程：`Swal.close()` 清弹窗 → `localStorage.removeItem('token')` → `useAuthModalStore().show('登录状态已失效，请重新登录。')`。**注意：不跳转登录页，原地弹全局登录框**。
   - **403**（:114-117）：只 `Swal.close()` 清理弹窗（注释：避免弹窗残留），重新抛出由调用方处理。
   - **4xx 其他**（:117-121）：有 `bizMessage` 就 `showErrorToast(bizMessage)` 并给 error 打上 `error.isBusiness = true`——**业务错误已在拦截器弹过 Toast，调用方不能再弹一遍**。
   - 最后统一 `throw error`（:124），保持错误传播链。

7. **get/post/put/del 四件套**（:130-197）：全部 `async` 包装，签名如 `post<T>(url, data, config)`；从 config 里解构出 `serviceType`（不传给 axios），选实例发请求，返回 `response.data`（即 ApiResponse）。catch 里只 console.error 再原样 throw。

8. 导出（:200-206）：`getAxiosInstance(serviceType)`、默认 `axiosInstance`（主服务），供特殊场景直接拿裸实例。

### 2.3 SSE 流式请求封装（`Web/src/services/aiStream.ts`）——逐段解析

**大白话**：SSE（Server-Sent Events，服务器推送事件）= 服务器把一条回复拆成很多小片段，通过一条长连接陆续推过来。原生 `EventSource` 只能发 GET、不能带自定义请求头和 body，所以这里用 `fetch` + `ReadableStream`（流式读取器）手动实现，代码注释原话："由于EventSource不支持自定义请求头和POST方法，我们使用fetch流式读取作为替代方案"（:167-168）。

**Envelope 协议**（:10-22）：服务端 2026-05 升级了协议，每个事件不是裸 JSON，而是统一信封：

```ts
const CONTRACT_VERSION = 1
interface SseEnvelope<T> {
  contractVersion: number   // 协议版本，前端据此判断如何解析
  event: string             // 事件类型
  taskId: number
  conversationId: number
  timestamp: string
  payload: T                // 真正的数据
}
```

**streamChat 完整流程**（:111-295）：

1. **重连状态机**（:118-147）：`userCancelled`（用户主动取消）、`isCompleted`（收到 complete）、`serverError`（收到 error）三个标志决定要不要重连。`wrappedOnEvent`（:127-135）拦截两件事：`start` 事件更新 `currentConversationId`；任何带 `seq` 的事件记录 `lastSeq`——重连时把这俩带给后端"去重/续传"。
2. **doStream 单次请求**（:152-231）：
   - 先 `cleanup()` 清掉上一个 AbortController，再 `new AbortController()`（:157）——取消请求的句柄，`cancel()` 里调 `abort()` 让 fetch 立刻中断。
   - URL 选择（:163-165）：`chatType === 'writing' ? '/writing/stream' : '/chat/stream'`（看板娘和写作助手共用一套 SSE 基建）。
   - fetch 配置（:169-185）：POST、`Accept: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`、条件带 `Authorization: Bearer`，body 带上 `conversationId` 和 `lastSeq`。
   - `!response.ok` → 抛 `StreamError('HTTP xxx', 'HTTP_ERROR', status)`（:187-193）。
   - **流读取核心**（:195-225）：
     ```ts
     const reader = response.body?.getReader()
     const decoder = new TextDecoder()
     let buffer = ''
     while (true) {
       const { done, value } = await reader.read()
       if (done) break
       const chunk = decoder.decode(value, { stream: true })  // stream:true 防止半个多字节 UTF-8 汉字被截断
       buffer += chunk
       const events = buffer.split('\n\n')   // SSE 协议：事件之间用空行分隔
       buffer = events.pop() || ''           // 最后一段可能是不完整事件，留到下一轮拼接
       for (const event of events) { if (event.trim()) this.handleSSEEvent(...) }
     }
     ```
     这是教科书式的"分帧缓冲"写法：`decoder.decode(..., {stream:true})` 处理跨 chunk 的多字节字符，`buffer.split('\n\n') + pop()` 处理跨 chunk 的半个事件。
3. **指数退避重连**（:247-294）：`delay = min(1000 * 2^retryCount, 30000)`，即 1s/2s/4s/8s，最多 4 次（:90）。`retryDelay`（:236-245）把 setTimeout 包成可取消的 Promise——`cancel()` 时 resolve 掉 `retryResolve`，立即解除等待，不等定时器。若流读完但没收到 complete（:276-290），同样按退避重连，用尽则抛 `STREAM_INCOMPLETE`。
4. **handleSSEEvent 解析**（:305-415）：
   - 按行解析 `event:` 和 `data:`（:313-323），`JSON.parse(data)`（:330）。
   - **新旧格式兼容**（:336-343）：`parsedData.contractVersion === 1` 就拆信封（eventType 取 `envelope.event`，数据取 `envelope.payload`，记下 `envelopeConversationId`），否则当旧版裸 payload 处理。
   - switch 分发（:345-407）：
     - `start` → `onEvent('start', {conversationId})`，上层立即更新 store（:346-349）。
     - `data` → 取 `payload.content` 调 `onChunk(content)`；payload 是纯字符串则兼容旧格式（:351-361）。
     - `audio` / `audio-skip` / `audio-complete` / `avatar-cue` / `heartbeat` → 原样透传（:363-370），由 store 侧分发到 TTS 队列和表情队列。
     - `article-results` → 透传文章推荐列表（:372-376）。
     - `complete` → `onComplete(payload)`（:378-382）。
     - `error` → 构造 `StreamError(code, message)` 给 `onError`（:384-392）。
     - default 兜底：字符串直接当内容；有 `content` 字段当内容；有 `error` 字段当旧格式错误（:394-406）。
   - 整个解析 try/catch 包住，解析失败抛 `SSE_PARSE_ERROR`（:408-414）。
5. **取消**（:420-433）：`cancel()` 置 `userCancelled=true`（与网络中断区分，避免误重连）、清重连定时器、resolve 等待、`cleanup()` abort 请求。`isStreaming` getter（:448-450）用 `abortController !== null` 判断是否在连。

### 2.4 SSE 事件在前端怎么消费（`Web/src/stores/chat.ts`）

`sendStreamMessage`（:400 起）的回调注册是理解数据流的关键：

- **发消息前**（:402-407）：`ttsCancelCounter++`（旧音频全部作废）、清空 TTS 和表情队列、`audioGeneration = ttsCancelCounter` 记下"代际号"，`ttsAwaitingAudio = true`，插入一条 `isStreaming: true, isThinking: true` 的空 AI 消息。
- **onChunk**（:414-416）：`updateStreamingMessage(chunk)` → `streamingMsg.content += content`（:307-313）。前端不缓存 HTML，只在消息上追加纯文本，渲染交给 MarkdownRenderer 的 computed（见 4.3）。
- **onEvent**（:417-470）：
  - `start`：拿到 conversationId 立即写 store（:421-427）——注释说"避免后续请求用旧 id 或 null"。
  - `article-results`：`aiMessage.articleResults = payload.items`，存 `reason` 文案，结束思考状态（:428-435）。
  - `avatar-cue`：`aiThinking = false`（表情提示到达说明 AI 开始输出）+ `enqueueAvatarCue({seq, expression, motion, intensity, durationMs, text, ...})`（:437-449）。
  - `audio-complete`：`audioGeneration === ttsCancelCounter` 才置 `ttsAwaitingAudio = false`（:450-455）——**代际校验**，旧流迟到的事件被丢弃。
  - `audio`：校验代际 + TTS 开关后 `enqueueTtsAudio({seq, audioUrl, text, ...})`（:458-466）；`audio-skip`：入队 `status:'skipped'` 的空项（:467-477）——skipped 项的作用是**占住 seq 位**，让有序缓冲区的游标能推进（见 2.5）。
- **onComplete**（:480-494）：`completeStreamingMessage()`（`isStreaming=false, renderedContent=undefined`，:315-324）、更新 conversationId。
- **onError**（:496-516）：把半截流式消息从数组里 splice 掉，插入 `addErrorMessage` 的 ❌ 消息。
- 错误文案细化在 `handleError`（:564-611）：`StreamError` 显示 code；HTTP 429/500/503 分别给友好中文提示；错误消息 5 秒后自动清除。

普通（非流式）模式 `sendNormalMessage`（:533-...）走 `Ai.chat()`（`services/ai.ts:76-84`，chatType=writing 时打 `/writing`），一次拿完整响应。

### 2.5 TTS/表情的有序队列（`Web/src/composables/useSequencedBuffer.ts` + `chatTts.ts`）

**大白话**：SSE 事件按到达顺序触发，但 TTS 音频必须按 seq（序号）顺序播放。乱序到达怎么办？用一个"序号→数据"的哈希桶 + 一个游标：

- `buffer = ref<Record<number, T>>({})`，`nextSeq` 游标从 1 开始（:16-17）。
- `enqueue(item)`（:21-24）：seq 无效或小于游标直接丢弃。
- `shift()`（:27-33）：只取 `buffer[nextSeq]`，取到就删并推进游标；没有就返回 null（等下一段入队）。
- `shiftBySeq(seq)`（:36-45）：跨队列绑定用（avatar-cue 与 audio 按 seq 配对），并把游标推进到 seq+1，防止卡住。
- `clear()`（:48-51）：清空并重置游标。

`chatTts.ts` 是队列的使用层：

```ts

  message.destroy()                          // 清残留 message
```

## 6. 构建产物与部署方式

### 6.1 构建

- 两个项目都是 `vue-tsc -b && vite build`，产物在各自 `dist/`。
- Web dist 结构：`index.html + assets/（页面级 chunk：PostDetail-*.js、AiChat-*.js、About-*.js...）+ live2d/（模型与脚本）+ tinymce/ + robots.txt + 洛天依.png`。**路由懒加载 → 每个页面独立 chunk，文件名带 hash**（缓存友好）。
- Admin dist：同构，页面 chunk 按管理页命名（`AiModelsManagement-*.js` 等）。
- Admin vite.config 有 `define` 注入 `__APP_VERSION__/__BUILD_TIME__/__ANTDV_VERSION__` 等（`vite.config.ts:17-25`），用于设置页展示版本信息。

### 6.2 Dockerfile（两项目相同模式，`Web/Dockerfile` / `Admin/Dockerfile`）

**两阶段构建**（大白话：第一个容器只用来编译，第二个容器只装运行时的东西，最终镜像没有 node_modules 垃圾）：

1. `FROM node:20-alpine as builder` → `npm ci`（锁文件安装，可复现）→ `npm run build`。
2. `FROM nginx:alpine` → `COPY --from=builder /app/dist /usr/share/nginx/html` → 覆盖 nginx.conf → `EXPOSE 80`。

### 6.3 容器内 Nginx（`Web/nginx.conf` / `Admin/nginx.conf`）

- history 模式兜底：`try_files $uri $uri/ /index.html`（Web :41-43）。
- 缓存分层（Web :46-60）：`/assets/` 带 hash → `immutable` 1 年；`index.html` → no-cache；其他静态 1h。
- 容器内也自带反向代理（Web :62-90）：`/api/ → backend:8080`、`/tts/ → backend:8080/tts/`、**`/ai/ → ai:8081` 时 `proxy_buffering off; proxy_request_buffering off; proxy_read_timeout 3600s; add_header Cache-Control no-cache`（Web nginx.conf :82-90）——SSE 必须关缓冲，否则事件会被 nginx 攒成一大块才吐出来，"流式"变"卡死"**。
- gzip 全开（:24-39）。

### 6.4 根 Nginx（`nginx/conf.d/default.conf`）——生产拓扑

- upstream：`backend:8080`、`ai:8081`、`web:80`、`admin:80`（:5-20）。
- 域名：`liuxin.chat`（Web，80→301→443）+ `admin.liuxin.chat`（443）+ **`:81` 备用入口**（证书不覆盖 admin 子域名期间的直连方案，:171 注释）。
- 安全头：X-Frame-Options DENY、nosniff、HSTS（主站开，admin 子域**故意不开**，:108 注释解释证书错误会被 HSTS 硬拦截）。
- `sitemap.xml` 直接代理给后端（:46-52，注释"避免被 SPA 路由吞掉"）。
- `/api/` 代理、`/uploads/` 30 天 immutable 缓存、`/upload/` 上限 `client_max_body_size 100M`（:89-99）。
- `ai-proxy.include` / `tts-proxy.include` 提取共用片段，两站共用。
- docker-compose（`docker-compose.yml:129-142`）：`web: liutech-web:latest`、`admin: liutech-admin:latest`，均 depends_on backend。

## 8. 亮点与可改进点

### 亮点（值得学的地方）

1. **双格式响应归一化 + isBusiness 标记**（`api.ts:65-96`）：主服务 `{code,message,data}` 和 AI 服务 `{success}` 统一成一个出口；`isBusiness` 标记贯穿"拦截器已弹过 → 调用方不再弹"，杜绝双重弹窗，这是很多项目没想清楚的点。
2. **SSE 用 fetch + ReadableStream 自研**（`aiStream.ts`）：跨 chunk 缓冲分帧、envelope 协议版本化、conversationId+lastSeq 断点重连、指数退避 + 可中断的等待 Promise、取消与网络中断语义分离——写得很教科书。
3. **seq 有序缓冲区**（`useSequencedBuffer.ts`）：用 40 行解决"SSE 乱序 vs 播放有序"的经典问题，比维护排序数组干净。
4. **音频图生命周期**（`useAudioLipSync.ts:1-3` 注释）：AudioContext 归页面、模型只持旁路 analyser，销毁模型不断声音；destination 只连一次。
5. **流式 Markdown 补全 + DOMPurify 白名单**（`useMarkdown.ts:80-98`）：AI 输出未闭合标记也能渲染，且消毒在渲染前——安全与体验都覆盖。
6. **错误去重**（`utils/errorHandler.ts:167-181`）：5 秒同消息只弹一次，并发失败不轰炸用户。
7. **CustomEvent 跨组件解耦**（`PostDetail.vue:423-433` → `AiChat.vue:219`）："问 AI"功能页面只发事件，不 import 聊天组件。
8. Admin 的 **composables 三件套**（useTablePage/useCrudActions/useModalForm）把 18 个管理页的样板代码压缩到每页几十行；草稿自动保存 + field-update 回写带 undoStack + 字段高亮，AI 写作助手的交互闭环完整。

### 可改进点（按性价比排序）

1. **SSE 解析器三份重复**：`aiStream.ts` / `adminAgent.ts`（Web）/ `agent.ts`（Admin）各自实现了一遍"分帧 + envelope 拆包"，协议升级要改三处。建议抽一个共享的 `parseSseStream(response, dispatch)` 模块。
2. **token 读写散落**：`localStorage.getItem('token')` 出现在拦截器、路由守卫、上传服务、SSE、工具函数至少 6 处，无单一事实来源；建议收敛到 `utils/auth.ts` 或 user store 暴露的纯函数。
3. **Web 401 两条路径**：守卫和拦截器都会触发"登录失效"弹窗流程，边界情况（如登录页本身发请求 401）靠 `requestUrl.includes('/user/')` 的字符串判断兜底，较脆弱；建议用 config 标记（如 `skipAuthModal: true`）替代 URL 匹配。
4. **聊天历史存 localStorage 无上限**：长会话 + 流式每 chunk 触发防抖保存，易逼近 5MB 配额；建议改 IndexedDB 或后端历史为准、本地只存草稿。
5. **AiStream 是静态类**：全局单例 abortController，无法同时开两条独立流（写作助手 + 聊天），也不利于单测；建议改成工厂函数返回实例。
6. `playwright` 放在 dependencies（`Web/package.json`），应移入 devDependencies。
7. Admin `upload.ts:18` 生产兜底硬编码 `https://liutech.com`，与 api.ts 的 `/api` 策略不一致，域名变更时会漏改。
8. Admin 菜单是静态 computed（`TheSidebar.vue:36-84`），若未来引入"运营/编辑"等次级角色，需要改成按角色过滤 + 后端下发的菜单树。
9. 两个前端 nginx 容器内都保留 `proxy_pass http://backend:8080` 等容器内网段，直接暴露容器端口（3000/3001）时可用，但等于维护两套代理配置（容器内 + 根 Nginx），规则容易漂移；建议容器只做静态托管，代理统一收口根 Nginx。
