# 2026-09-10 AI 模型配额与写作链路修复

> 起因：管理端配置模型时没有「上下文上限」可配；用写作智能体读长文后模型卡住且没有任何提示。
> 本文记录排查到的全部问题、修复方式与验证结果，作为后续排查同类问题的参照。
>
> 涉及模块：`LiuTech-AI`（模型配置、Prompt 预算、SSE 事件）、`Admin`（模型管理页）、`Docs/SQL`（表结构）。

## 1. 结论

问题不是单点 Bug，而是**大模型端只有"输出上限"、没有"输入预算"这个概念**：

1. 表 `ai_model_config` 只有 `max_tokens`（单次输出上限），无处配置上下文窗口；
2. 组装好的 prompt 不做任何总量检查就发给模型；
3. AI 读取整篇文章的工具（写作 `getArticleDetail`、看板娘 `getPostDetail`）返回完整 HTML 正文，**完全不截断**；
4. 历史消息只按**条数**限制（14 条），不按 token；
5. 超限之后本地没有任何处理，只能等上游报错或 SSE 超时（默认 5 分钟），而超时路径**不发 error 事件**。

## 2. 问题清单（含当时未发现的）

### 2.1 配置层

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | 无上下文窗口配置项 | `ai_model_config` 表结构、`ModelConfigRequest` | 输入侧无法约束，也无从排查 |
| 2 | **管理端配置被静默夹取** | `AiModelPolicy` 旧实现用 `model-policy-max-tokens-ceiling: 8192` 直接 `Math.min` | 填 16384 / 32768 都不生效，界面上毫无提示 —— 「配了不生效」的根源 |
| 3 | `writing-max-tokens: 32768` 与上面的 8192 互相矛盾 | `AiChatServiceImpl.writingParameters` 旧实现 | 注释说"尽量取大"，实际被锁死在 8192 |
| 4 | 死配置 | `spring.ai.agent.max-context-chars`、`tool-cache-ttl-ms`、`max-article-results`、`persona.title-suffix` 均 0 处 Java 引用；`PromptService` 里 6000 是硬编码 | 改了 yml 没有任何效果 |

### 2.2 执行层

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| 5 | 读全文工具无截断 | `WritingTools.getArticleDetail`、`BlogMcpTools.getPostDetail` | 直接顶穿上下文窗口，本次故障的直接原因 |
| 6 | prompt 无总量检查 | `ChatServiceHelper.prepareMessages` 旧实现 | 只能靠上游拒绝 |
| 7 | 历史按条数不按 token | `chat-history-limit: 14` + AI 长回复原样入库 | 多轮之后看板娘也会超限 |
| 8 | 工具调用轮次无上限 | Spring AI 2.0 `DefaultToolCallingManager` 内部循环（反编译确认无迭代上限） | AI 反复读文章可一轮轮撑爆上下文 |

### 2.3 可观测与提示层

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| 9 | **SSE 超时无提示** | `StreamingChatService` 的 `emitter.onTimeout` 只 `complete()` | 上游卡住时前端只能显示"连接中断"，看板娘还会重连 4 次，最长拖 20 分钟以上 |
| 10 | 写作入口异常口径不一致 | 入口 catch 用 `e.getMessage()`（原始技术文案），流中错误用 `toUserFriendlyError` | 同一链路两种提示风格 |
| 11 | 熔断降级冒充正文 | `SiliconFlowChatClient.fallbackChat/fallbackStreamChat` 返回降级文案字符串 | 前端当正文展示、进 TTS、同步版还会**落库成 assistant 消息** |
| 12 | 友好文案只认英文关键词 | `toUserFriendlyError` 匹配 timeout/context/token/length/maximum | 上游返回中文时漏判，把原始错误丢给用户 |
| 13 | 输入侧零观测 | `AiMetrics`/`estimateTokens` 只统计输出 | 出问题只能靠猜 |

### 2.4 写作助手的"假进度"

前端（`AdminAgentSidebar.vue` 与 `AdminWritingAssistant.vue`）自行编造了进度展示：

- `ensurePlan()` 硬编码 5 个步骤，与 AI 实际行为无关（AI 可能一个工具都没调）；
- `processPercent()` 里"只要有步骤在跑就白送 0.55"凑百分比；
- `TOOL_STEP_MAP` 只映射 3 个工具名，其余靠 `inferStepKey` 用中文关键词猜；
- 后端 `tool-result` 的 `durationMs` **恒为 0**：`WritingToolEventSink` 用 `ThreadLocal` 记录开始时间，而 Spring AI 的工具执行在响应式线程上，跨线程取不到（假耗时）。

## 3. 修复方式

### 3.1 表结构与配置（`Docs/SQL`）

- `ai_model_config` 新增 `context_window INT`（输入 + 输出总 token 上限）；
- 初始化脚本 `Docs/SQL/sql.sql` 同步表结构与种子数据（GLM-4.6 205000、Qwen2.5-7B 32768、DeepSeek-V2.5 128000）；
- 已有库增量脚本：`Docs/SQL/migration_ai_model_context_window.sql`（幂等，含已知模型回填，末尾打印校验结果）。

### 3.2 服务端（`LiuTech-AI`）

| 能力 | 实现 |
| --- | --- |
| 生效限制解析 | 新增 [`PromptBudget`](../../LiuTech-AI/src/main/java/chat/liuxin/ai/infra/security/PromptBudget.java)：token 估算（中文 1 字≈1 token）、`resolveLimits`（上下文 / 输出 / 输入预算）、`trimHistory`、`assertMandatoryFits`、`toolResultCharBudget` |
| 参数策略 | [`AiModelPolicy`](../../LiuTech-AI/src/main/java/chat/liuxin/ai/infra/security/AiModelPolicy.java) 重写：以模型配置为权威，请求只能更小；被全局上限夹小时打 WARN 并标记，不再静默 |
| 预算执行 | [`ChatServiceHelper.prepareMessages`](../../LiuTech-AI/src/main/java/chat/liuxin/ai/service/ChatServiceHelper.java)：必需内容超预算→立刻报错（给出占用/预算/建议）；历史从最旧整条丢弃；每次请求记 INFO 预算日志 |
| 工具结果控制 | 新增 [`ToolResultBudget`](../../LiuTech-AI/src/main/java/chat/liuxin/ai/common/mcp/ToolResultBudget.java)，两个读全文工具按预算截断并显式标注"正文过长已截断" |
| 草稿注入 | `PromptService` 的硬编码 6000 改为读 `spring.ai.agent.max-context-chars` |
| 失败可见 | `onTimeout` 发 error 事件说明等待超时；写作入口异常改用友好文案；熔断 fallback 改为抛异常 / `Flux.error` |
| 保存时校验 | `AiModelConfigService.validateLimits`：输出上限超全局上限、上下文 ≤ 输出上限时**保存即报错**，并给出修改建议 |
| 真实事件数据 | `WritingToolEventSink` 改为按工具名维护开始时间栈（修复跨线程取不到导致的假 0 耗时），`tool-start` 带 `startedAt`、`tool-result` 带真实 `durationMs`/`finishedAt`；`field-update` 新增 `fields`（本次真实写入的字段名列表） |
| 配置清理 | 删除 `writing-max-tokens`（与全局上限重复且矛盾）、`tool-cache-ttl-ms`、`persona.title-suffix`；接上 `max-context-chars`、`max-article-results`、新增 `max-tool-result-chars`；`model-policy-max-tokens-ceiling` 由 8192 提到 65536，并新增 `model-policy-default-context-window: 32768`、`model-policy-max-input-tokens: 96000` |

### 3.3 管理端（`Admin`）

- 模型表单新增「上下文窗口」，并在「最大 Token」下补说明（单次输出上限）；
- 新增**预设下拉**（仅新增态）：GLM-4.6 / DeepSeek-V3.2 / DeepSeek-R1 / Qwen2.5-7B / DeepSeek-V2.5，一键填充模型名、显示名、上下文窗口、最大 Token、温度；
- 表单校验：上下文窗口必须大于最大 Token，否则提交即提示"否则没有输入预算"；
- 表格参数列展示「上下文窗口 / 输出上限 / 输入预算 / Temperature」，并在被全局上限或成本护栏限制时显式提示，不再让管理员面对"配了不知道为什么"。

### 3.4 写作助手的真实进度（`Admin` + `Web`）

- 删除 `ensurePlan`（硬编码 5 步）、`processPercent`（假百分比）、`TOOL_STEP_MAP`/`inferStepKey`（猜步骤）、`fallbackPlan` 等一整套编造逻辑；
- 改为真实事件驱动的时间线：`tool-start` → 运行中条目（带真实入参摘要），`tool-result` → 就地更新为成功/失败 + **真实耗时** + 结果摘要，
  `field-update` → 「已写入：标题、标签」（取 `fields` 真实字段名），`data` → 累计真实字数，`error` → 展示后端友好文案；
- 状态行改为真实动作与真实汇总（调用工具 N 次 / 写入 M 个字段 / 生成 X 字），不再出现百分比。

## 4. 验证

- `LiuTech-AI` 单元测试：**58 个通过**（新增 `PromptBudgetTest` 20 个，覆盖估算、预算解析、历史裁剪、超限报错文案、工具结果预算；`AiModelPolicyTest` 扩到 6 个，含"数据库配置不再被夹成 8192"的回归用例）。
- `Admin` / `Web` 构建（`vue-tsc -b && vite build`）通过。
- SQL：初始化脚本与增量脚本保持一致字段与注释；增量脚本幂等（重复执行不报错）。

## 5. 仍未覆盖的两点（已知边界）

1. **工具调用轮次仍由 Spring AI 内部循环控制**（`DefaultToolCallingManager` 无迭代上限，反编译确认）。本轮通过"单个工具结果按预算截断"把单轮膨胀压住了，但没有在每一轮工具调用之间重新校验输入预算。
   彻底解决需要关闭 Spring AI 的内部工具执行（`ToolCallingChatOptions`），改成自己写「模型 → 工具 → 再问模型」的循环并逐轮校验预算与轮次上限。属于结构性改动，本轮未做。
   当前后果：极端情况下仍可能顶到上游上限，但**不会再"静默卡住"**——会返回可读的错误提示（关键词映射已支持中英文上下文超限文案）。
2. **输入 token 只进日志、未进指标**：`AiMetrics` 仍只统计输出 token（`recordSuccess(model, responseTime, tokenCount)` 语义未变）。现在每次请求都会打一条 INFO 日志记录「上下文 / 输出上限 / 输入预算 / 本次实际占用」，排查够用；若要接监控面板需另开一轮改指标维度。

## 6. 上线注意

1. **先跑增量 SQL**（`Docs/SQL/migration_ai_model_context_window.sql`），否则新代码读取不到的 `context_window` 会走默认 32768 兜底（功能可用，但大上下文模型会被低估）。
2. 新增配置项都有默认值，`application.yml` 已带注释；如需调整单次请求输入上限，改 `spring.ai.security.model-policy-max-input-tokens`。
3. 行为变化：输入超限不再"卡住"，而是**快速失败并给出可读提示**（含模型名、本次占用、可用预算）；管理端配置超过全局上限时**保存即报错**而不是静默夹取。
