# 系统设置死配置清理与配置归属梳理

> 日期：2026-09-22
> 触发：管理员在 Admin「系统设置」页关闭"语音推理全局开关"后 TTS 行为无变化；同一开关在「AI 设置」页又存在一份。
> 范围：Admin 伪配置页下线、主后端通用设置 CRUD 删除、初始化种子与生产死数据清理；复核主服务 / AI 服务隔离。
> 前置阅读：[2026-09-13-AI服务解耦实施总结.md](2026-09-13-AI服务解耦实施总结.md)、[当前架构.md](当前架构.md)

## 1. 结论

「系统设置」页在 2026-09-14 TTS 解耦（提交 `dfbdb90`）后成为**整页伪配置**：页面上所有可保存项均无任何代码消费，保存只提示成功、不改变任何行为。其中 9 个 `tts.*` 项**在解耦前是真配置**，消费方随解耦被删而前端页面漏删；其余 `site.*` / `comment.need_review` / `upload.max_size_mb` 自播种起就没有消费方。

TTS 的唯一全局开关在「AI 设置」页 → AI 库 `liutech_ai.ai_tts_config.enabled`，真实拦截点见下文第 3 节。

## 2. 配置归属总表（单一事实源）

| 配置域 | 唯一维护入口 | 事实源 | 消费方 |
| --- | --- | --- | --- |
| TTS 开关/引擎/音色/格式/采样率/语速 | Admin「AI 设置」 | AI 库 `liutech_ai.ai_tts_config`（单行 id=1） | `TtsSpeechService` / `StreamingChatService` |
| 聊天模型、配额（max_tokens/context_window）、默认模型 | Admin「AI 模型管理」 | AI 库 `ai_model_config` | `AiModelPolicy`、`PromptBudget` |
| 作者资料与关于页内容 | Admin「关于页管理」 | 主库 `system_settings` 的 `author.*`、`about.content` | `AboutPageService`（Caffeine `aboutPage`）、`UserProfileService` |
| 主题/密度/侧栏/语言（本机偏好） | Admin 右上角设置抽屉 | 浏览器 localStorage | Admin `stores/settings.ts`（UI 偏好，非服务端配置） |
| 站点名/URL/备案号 | 无后台页面 | [`Web/src/config/site.ts`](../../Web/src/config/site.ts) + `VITE_*` 构建变量 | Web `usePageSeo`、`TheFooter` |
| 上传大小上限 | 无后台页面 | Spring 配置 `spring.servlet.multipart.*`、`file.upload.*` | [`LiuTech/src/main/resources/application.yml`](../../LiuTech/src/main/resources/application.yml) |
| 评论审核 | 不存在该能力 | —— | 评论直发，无审核逻辑 |
| 邮箱/COS/JWT/内部令牌/限流等 | 运维配置 | `.env` + `application*.yml` | 两服务启动注入 |

原则：**每个页面只维护自己域内的配置；跨域配置不另设第二份可写入口。**

## 3. 证据链（git + 代码 + 数据库权限）

### 3.1 旧开关曾经是活的

- 解耦前主后端存在 `LiuTech/.../service/TtsConfigService.java`（`dfbdb90^` 版本可查），从主库 `system_settings` 读写 9 个 `tts.*` 键：
  - `KEY_ENABLED = "tts.enabled"`，`getConfig()` 内 `systemSettingService.getBoolean(KEY_ENABLED, true)`。
- 提交 `dfbdb90`（2026-09-14「完成主服务与AI服务边界解耦」）：
  - 删除主后端该消费类（HEAD 中 `git cat-file -e HEAD:LiuTech/.../TtsConfigService.java` 返回"路径不在 HEAD 中"）；
  - 同一提交把 `SystemSettingsAdminService` 的 9 个 `PREDEFINED_SETTINGS.put("tts.*", ...)` 与 tts 分组逻辑删空；
  - **但 Admin 前端 `SystemSettings.vue` 漏删**，硬编码的开关、字段标签、选项仍在页面上。
- 解耦时按回滚方案在生产主库保留 9 行旧 `tts.*` 七天（见 [2026-09-13-AI服务解耦实施总结.md](2026-09-13-AI服务解耦实施总结.md) 第 5、118 行），回滚窗口 2026-09-21 到期。

### 3.2 当前零消费（HEAD 实测）

- 全仓搜索 `tts.enabled` / `tts.provider` / `tts.baseUrl`：主后端 Java 读取代码为 0；`SystemSettingService.getBoolean(...)` 全仓无调用方。
- `system_settings` 表的读取方只有 `AboutPageService`（`author.*`/`about.content`）与 `UserProfileService`（`author.*`）。
- 物理隔离：AI 服务数据源只连 `liutech_ai` 库（[`LiuTech-AI/src/main/resources/application-prod.yml`](../../LiuTech-AI/src/main/resources/application-prod.yml)），MySQL 账号 `liutech_ai_app` 仅有 `liutech_ai.*` 权限（[`mysql/init-users.sh`](../../mysql/init-users.sh) 第 25 行），即使想读主库那行也被数据库拒绝。

### 3.3 真正生效的开关链路

- 写：`PUT /ai/admin/tts/config` → `TtsConfigService.updateConfig` → `liutech_ai.ai_tts_config`。
- 读与拦截（两处，均在 AI 服务内）：
  1. 主动合成：`TtsSpeechService.synthesize` 开头校验 `config.getEnabled()`，关闭抛"语音功能已关闭"。
  2. 流式聊天：`TtsSpeechService.inferSingleAudioUrl` 先查 `getStatus()`，`!enabled || !online` 返回 null；`StreamingChatService` 据此发 `audio-skip`，不产生音频。
- 全 AI 服务无第二个 enabled 来源（无环境变量旁路）。

### 3.4 顺带确认的其他死配置

- `resilience4j-config.yml` 的 `ratelimiter aiService` 实例全仓无 `@RateLimiter` 引用；真实限流是自定义滑动窗口 `AiRateLimitInterceptor`（读 `spring.ai.security.rate-limit.*`）。改 yml 该段不会生效，本次未清理，留待专项处理。
- `CacheAdminController`（`/admin/cache/clear`）无 Admin 前端入口，属纯运维 API，保留。

## 4. 主服务 / AI 服务隔离复核

AI 服务故障**不会**导致 Admin 及与 AI 无关的功能失效：

- 主后端出站调 AI **仅 1 处**：`AiUserDataClient`（connect 3s / read 8s），且仅在管理员「彻底删除用户」前调用；AI 不可用时该操作刻意中止并提示（fail-closed，防 AI 侧孤儿数据）。软删/禁用用户、登录、文章、评论、资源、积分、上传等日常链路零 AI 调用；主服务启动与健康检查不依赖 AI。
- AI → 主服务：身份走 `/internal/auth/introspect`（结果按 token 摘要缓存 60s），主服务不可用时带 token 请求显式 503，不静默降级游客；MCP 博客工具调主服务失败吞异常返回空结果。
- Admin 前端触 AI 的位置仅：AI 设置、AI 模型管理、文章编辑器内的写作助手侧边栏（主动发消息才请求）。AI 设置页用 `Promise.allSettled` 容错，AI 离线只影响本页卡片。
- Nginx `/api/`（backend upstream）与 `/ai/`（ai upstream）独立代理；`/internal/**` 公网 404 屏蔽。

## 6. 生产操作手册（开发机连云生产执行）

> 生产 compose 目录 `/opt/liutech`，容器名 `liutech-mysql`/`liutech-backend`/`liutech-ai`/`liutech-admin`/`liutech-nginx`；国内服务器离线镜像（build → save tar → scp → load → force-recreate），重建 backend/admin 后必须 restart nginx。

### 6.1 提交代码并构建镜像（开发机）

1. 在开发机拉取本工作区改动，commit 后按既有离线流程构建镜像：`liutech-backend`、`liutech-admin`（本次不涉及 ai/web/nginx 镜像与 MySQL 卷结构变更）。
2. 本次只需部署 backend + admin 两个新镜像；`sql.sql` 的改动**不影响已有库**（初始化脚本只在全新数据卷执行），生产数据清理走 6.3 的迁移脚本。

### 6.2 备份（必做）

```bash
cd /opt/liutech
mkdir -p /liuxin/backups/manual-20260922
docker exec liutech-mysql sh -c \
  'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction liutech' \
  > /liuxin/backups/manual-20260922/liutech.sql
# 校验备份非空且含 system_settings
grep -c "system_settings" /liuxin/backups/manual-20260922/liutech.sql
```

（若容器内无 `MYSQL_ROOT_PASSWORD` 环境变量，从 `/opt/liutech/.env` 取 `DB_PASSWORD` 交互输入。）

### 6.3 执行死配置清理

把 `Docs/SQL/migration_remove_dead_settings.sql` 拷到服务器后执行（脚本幂等，只删 18 个明确键，不碰 `author.*`/`about.content`）：

```bash
docker exec -i liutech-mysql mysql -uroot -p"$DB_PASSWORD" liutech \
  < /opt/liutech/migration_remove_dead_settings.sql
```

执行后核对（前两条应返回 0 / 空集，第三条应返回 author.* 4 行与 about.content 1 行）：

```sql
SELECT COUNT(*) FROM system_settings WHERE setting_key LIKE 'tts.%';            -- 0
SELECT COUNT(*) FROM system_settings
 WHERE setting_key LIKE 'site.%' OR setting_key IN ('comment.need_review','upload.max_size_mb');  -- 0
SELECT setting_key FROM system_settings ORDER BY id;                            -- 仅 author.* / about.*
```

顺序说明：数据清理与镜像部署无强依赖——旧后端在数据删除后只会读到空列表，新后端在旧数据上也不暴露这些行。建议先清理数据再部署。

### 6.4 部署镜像并验证

```bash
cd /opt/liutech
docker load -i liutech-backend-<tag>.tar
docker load -i liutech-admin-<tag>.tar
# 在 .env 固定 BACKEND_IMAGE_TAG / ADMIN_IMAGE_TAG 后：
docker compose up -d --force-recreate backend admin
docker compose restart nginx
docker compose ps
```

验证清单：

1. `docker compose logs --tail=50 backend` 启动无异常；`curl -s http://localhost:8080/actuator/health` 为 UP。
2. 浏览器登录 Admin：侧栏「系统管理」下只剩操作日志；访问旧路径 `/settings` 走 404 兜底页；命令面板 `g s` 已消失。
3. AI 设置页 TTS 全局开关拨动能保存并生效：关闭后前台聊天收 `audio-skip` 无音频；`curl https://<域名>/ai/runtime` 的 `tts.enabled` 随开关变化。
4. 关于页管理仍可正常保存（验证 `system_settings` 保留键链路未受影响）。
5. 「彻底删除用户」前 AI 清理链路保持原状（本次未改动）。

### 6.5 回滚

- 数据：死配置行删除后无代码再读，无需回滚；确需恢复，从 6.2 备份中按 `setting_key` 导回（`tts.*` 也不会再被消费，回滚只在整组回退到 `dfbdb90` 之前镜像时才有意义）。
- 镜像：用旧 tag 重新 `docker load` + `docker compose up -d --force-recreate backend admin` + `docker compose restart nginx`。
