## 1. 结论

## 3. 证据链（git + 代码 + 数据库权限）

### 3.1 旧开关曾经是活的

- 解耦前主后端存在 `LiuTech/.../service/TtsConfigService.java`（`dfbdb90^` 版本可查），从主库 `system_settings` 读写 9 个 `tts.*` 键：
  - `KEY_ENABLED = "tts.enabled"`，`getConfig()` 内 `systemSettingService.getBoolean(KEY_ENABLED, true)`。
- 提交 `dfbdb90`（2026-09-14「完成主服务与AI服务边界解耦」）：
  - 删除主后端该消费类（HEAD 中 `git cat-file -e HEAD:LiuTech/.../TtsConfigService.java` 返回"路径不在 HEAD 中"）；
  - 同一提交把 `SystemSettingsAdminService` 的 9 个 `PREDEFINED_SETTINGS.put("tts.*", ...)` 与 tts 分组逻辑删空；
  - **但 Admin 前端 `SystemSettings.vue` 漏删**，硬编码的开关、字段标签、选项仍在页面上。
- 解耦时按回滚方案在生产主库保留 9 行旧 `tts.*` 七天（见 [2026-09-13-AI服务解耦实施总结.md](2026-09-13-AI服务解耦实施总结.md) 第 5、118 行），回滚窗口 2026-09-21 到期。

### 3.2 当前零消费（HEAD 实测）

- 全仓搜索 `tts.enabled` / `tts.provider` / `tts.baseUrl`：主后端 Java 读取代码为 0；`SystemSettingService.getBoolean(...)` 全仓无调用方。
- `system_settings` 表的读取方只有 `AboutPageService`（`author.*`/`about.content`）与 `UserProfileService`（`author.*`）。
- 物理隔离：AI 服务数据源只连 `liutech_ai` 库（[`LiuTech-AI/src/main/resources/application-prod.yml`](../../LiuTech-AI/src/main/resources/application-prod.yml)），MySQL 账号 `liutech_ai_app` 仅有 `liutech_ai.*` 权限（[`mysql/init-users.sh`](../../mysql/init-users.sh) 第 25 行），即使想读主库那行也被数据库拒绝。

### 3.3 真正生效的开关链路

- 写：`PUT /ai/admin/tts/config` → `TtsConfigService.updateConfig` → `liutech_ai.ai_tts_config`。
- 读与拦截（两处，均在 AI 服务内）：
  1. 主动合成：`TtsSpeechService.synthesize` 开头校验 `config.getEnabled()`，关闭抛"语音功能已关闭"。
  2. 流式聊天：`TtsSpeechService.inferSingleAudioUrl` 先查 `getStatus()`，`!enabled || !online` 返回 null；`StreamingChatService` 据此发 `audio-skip`，不产生音频。
- 全 AI 服务无第二个 enabled 来源（无环境变量旁路）。

### 3.4 顺带确认的其他死配置

- `resilience4j-config.yml` 的 `ratelimiter aiService` 实例全仓无 `@RateLimiter` 引用；真实限流是自定义滑动窗口 `AiRateLimitInterceptor`（读 `spring.ai.security.rate-limit.*`）。改 yml 该段不会生效，本次未清理，留待专项处理。
- `CacheAdminController`（`/admin/cache/clear`）无 Admin 前端入口，属纯运维 API，保留。

## 4. 主服务 / AI 服务隔离复核

AI 服务故障**不会**导致 Admin 及与 AI 无关的功能失效：

- 主后端出站调 AI **仅 1 处**：`AiUserDataClient`（connect 3s / read 8s），且仅在管理员「彻底删除用户」前调用；AI 不可用时该操作刻意中止并提示（fail-closed，防 AI 侧孤儿数据）。软删/禁用用户、登录、文章、评论、资源、积分、上传等日常链路零 AI 调用；主服务启动与健康检查不依赖 AI。
- AI → 主服务：身份走 `/internal/auth/introspect`（结果按 token 摘要缓存 60s），主服务不可用时带 token 请求显式 503，不静默降级游客；MCP 博客工具调主服务失败吞异常返回空结果。
- Admin 前端触 AI 的位置仅：AI 设置、AI 模型管理、文章编辑器内的写作助手侧边栏（主动发消息才请求）。AI 设置页用 `Promise.allSettled` 容错，AI 离线只影响本页卡片。
- Nginx `/api/`（backend upstream）与 `/ai/`（ai upstream）独立代理；`/internal/**` 公网 404 屏蔽。

## 6. 生产执行记录（2026-09-22 已完成）

> 生产 compose 目录 `/opt/liutech`，容器名 `liutech-mysql`/`liutech-backend`/`liutech-ai`/`liutech-admin`/`liutech-nginx`。以下为实际执行步骤，可直接作为同类「只改 backend + admin」发布的复用手册。

### 6.1 构建路径（与标准离线流程的差异）

标准流程是「本地 `docker build` → `docker save` tar → scp → `docker load`」。本次执行机为 **aarch64 且无 Docker**，改用**本地编译架构无关产物 → 上传 → 服务端 x86_64 构建镜像**：

1. 本地（执行机）出产物，只编译不打包镜像：
   - backend：`mvn -f LiuTech/pom.xml clean package -DskipTests` → `LiuTech/target/liutech-0.0.1.jar`（约 77MB）
   - admin：`cd Admin && npm run build` → `Admin/dist/`
2. 上传到服务端 `/tmp/liutech-build/`：jar 放 `backend/target/`，`Admin/dist/` + `Admin/nginx.conf` 放 `admin/`，另传 `LiuTech/Dockerfile`。
3. 服务端构建（基础镜像 `eclipse-temurin:21-jre-alpine`、`nginx:alpine` 已在本地缓存，无需联网拉取）：
   - backend 复用仓库原 `LiuTech/Dockerfile`（其 `apk add tzdata` 实测可达）
   - admin 用等价于 `Admin/Dockerfile` 生产段的临时 Dockerfile（`FROM nginx:alpine` + `COPY dist` + `COPY nginx.conf`），跳过容器内 `npm ci`（国内 CDN 易 idle timeout）

产物本身跨架构，故该路径与标准流程等价；仅当执行机无 Docker 时使用。

### 6.2 备份（已执行）

```bash
cd /opt/liutech
PW=$(grep -E '^DB_PASSWORD=' .env | cut -d= -f2)   # 必须先赋值，否则下面 -p"" 会连不上
docker exec liutech-mysql mysqldump -uroot -p"$PW" --default-character-set=utf8mb4 \
  --databases liutech > /opt/liutech/backups/liutech-before-settings-cleanup-20260922.sql
gzip -f /opt/liutech/backups/liutech-before-settings-cleanup-20260922.sql
```

产物：`/opt/liutech/backups/liutech-before-settings-cleanup-20260922.sql.gz`（约 130KB），内容为 `--databases liutech` **整库** dump。

### 6.3 执行死配置清理（已执行）

清理前实测生产库 `system_settings` 共 24 行，其中命中删除清单 **19 行**（9 个 `tts.*` + 8 个 `site.*` + `comment.need_review` + `upload.max_size_mb`）。

### 6.5 回滚

**镜像回滚**（回退到本次发布前的 `dfbdb90` 镜像）。回滚 tag 已指向旧镜像，实测：`liutech-backend:rollback-before-settings-cleanup-20260922 → 240815b7011d`、`liutech-admin:rollback-before-settings-cleanup-20260922 → 4b6cb8341dc9`：

```bash
docker tag liutech-backend:rollback-before-settings-cleanup-20260922 liutech-backend:dfbdb90
docker tag liutech-admin:rollback-before-settings-cleanup-20260922  liutech-admin:dfbdb90
cd /opt/liutech && docker compose up -d --no-deps --force-recreate backend admin && docker compose restart nginx
```

- **回滚可逆**：新镜像同时挂着 `release-6ae35fa` tag，前滚回去只需把该 tag 再指回 `dfbdb90` 并重复上面两条命令，无需重新构建。
- **回滚的已知副作用**：回退后 Admin 的「系统设置」伪配置页会重新出现（该页正是本次修复对象），后端通用设置 CRUD 也随之恢复，页面上保存会重新写入已删除的死键行。即回滚 = 回到"开关保存成功但无效果"的旧行为。
- **验证**：`docker inspect liutech-backend --format '{{.Image}}'` 应回到 `240815b7011d…`。

**数据回滚**：**不需要，且不建议整份重放**。

- 删除的 19 个键在新代码中零消费方；即使把镜像回滚到 `dfbdb90`，旧页面保存的仍是同样的死数据，恢复与否不改变任何行为。
- 6.2 备份是 `--databases liutech` **整库** dump，**不能**直接 `mysql < 备份` 重放（会覆盖生产全库，同仓库既有约定"不要把 sql.sql 整份重放到已有生产库"）。
- dump 用 extended-insert：`system_settings` 全部 24 行压在同一条 `INSERT INTO \`system_settings\` VALUES (...),(...);` 里（单行超长，实测在备份第 798 行）。挑行恢复需先把整条取出来再手工保留所需元组：

```bash
zcat /opt/liutech/backups/liutech-before-settings-cleanup-20260922.sql.gz \
  | grep "INSERT INTO \`system_settings\`" > /tmp/system_settings-restore.sql
# 编辑该文件，只保留需要恢复的元组，确认后再导入：
# docker exec -i liutech-mysql mysql -uroot -p"$PW" --default-character-set=utf8mb4 liutech < /tmp/system_settings-restore.sql
```

> 主键不冲突（实测）：现存 5 行 id 为 20–24（删除后未重排），备份中被删的 19 行 id 为 1–19，空间已空出，按原 `id` 导回即可；仅当 `id` 被手工占用时才需去掉首列 `id` 让自增分配。
