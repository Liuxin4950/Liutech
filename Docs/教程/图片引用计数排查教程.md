# 图片引用计数为 0 的排查与修复（完整教程）

> 这是一次真实的线上 bug 排查记录，整理成教程。适合面试时讲：问题现象 → 排查思路 → 根因 → 修复方案 → 背后的设计思想。
> 读完你能讲清楚：引用计数的双层机制、URL 归一化、脏数据容错、以及"为什么显示正常、溯源正常、计数却是 0"。

---

## 1. 业务背景：图片引用计数是什么

### 1.1 场景

博客系统里，用户上传图片、写文章时在正文里引用图片。系统需要知道**每张图片现在被多少个地方引用**（usage_count）。

这个数字有三个用途：

| 用途 | 说明 |
| --- | --- |
| 删除保护 | 删除有引用的图片时警告「被 N 篇文章引用」，防止删了文章还在用的图 |
| 孤立图片清理 | `usage_count = 0` 的图视为无人引用，可以物理删除释放空间 |
| 引用溯源 | 点开图片详情，列出具体被谁引用（哪篇文章的哪个位置） |

### 1.2 计数规则（引用点）

**usage_count 不是"上传次数"，是"引用点数"**：

- 文章封面 1 点、缩略图 1 点、正文里每个 `<img src="...">` 1 点（同一张图出现 N 次计 N）
- 用户头像、音乐封面、轮播图、系列封面各 1 点
- 上传本身不计数（图还没被任何内容引用）

### 1.3 类比

把 `images` 表想象成**图书馆的图书登记表**，`usage_count` 就是"这本书现在被几个人借走"。

- 上传图片 = 新书入库（还没人借，计数 0）
- 文章引用 = 借书（计数 +1）
- 文章删图 = 还书（计数 -1）
- 但借书人可能会**忘记还**，所以图书馆每天晚上要**盘点**（对账）

## 2. 核心概念一：双层机制（增量维护 + 每日对账）

这是整个设计的灵魂，面试官最爱问"为什么这么设计"。

### 2.1 增量维护（日常记账）

所有"内容里出现图片 URL"的写操作，都会调用统一的 `ImageReferenceService`：

| 方法 | 场景 |
| --- | --- |
| `addReferences(urls)` | 新增引用（创建文章、改头像） |
| `removeReferences(urls)` | 移除引用（删除音乐、清封面） |
| `syncReferences(oldUrls, newUrls)` | 编辑替换（按差量增减） |
| `countByPath(urls)` | 对账统计用 |

内部流程：**URL → 归一化成逻辑路径 → 查 images 记录 → `usage_count ± delta`**。

### 2.2 每日对账（保险丝）

每天凌晨 02:55 跑一次全量对账：

1. 把所有 `usage_count` 清零
2. 扫描全库引用源（文章封面/缩略图/正文、头像、音乐/轮播/系列封面），重新统计每个逻辑路径被引用次数
3. 按统计结果逐条重建计数

### 2.3 为什么需要对账（面试重点）

增量记账**一定会出错**，常见原因：

- 业务方漏调了计数方法（比如某次新功能加了图片字段但忘了登记）
- URL 格式变化导致归一对不上（就是这次的问题）
- 软删除不减计数导致虚高（可恢复，故意不减）

所以设计哲学是：**增量保证及时性，对账保证正确性**。增量记错了不要紧，第二天自动修正——对账是"保险丝"，让任何偷懒/遗漏都成为安全设计。

类比：平时记账 + 月底盘点。账算错了不慌，盘点会拉平。

## 3. 核心概念二：URL 归一化

### 3.1 问题：同一张图有多种写法

一张图片 `images/2026/08/04/xxx.png`，在不同地方可能以不同形态出现：

```
/uploads/images/2026/08/04/xxx.png              相对路径
https://www.liuxin.chat/uploads/images/...       站内完整 URL
https://static.liuxin.chat/images/2026/08/04/xxx.png   COS 直出 URL
```

如果直接拿字符串去比对，这 3 种写法互不相等，计数就会各算各的——同一张图被算成"3 张不同的图"。

### 3.2 解决方案：统一归一化口径

`FileUtil.normalizeToRelativePath(url)`：不管什么形态，都提取出**逻辑路径**（`images/2026/08/04/xxx.png`），这是全项目唯一口径，所有引用计数/对账/溯源都必须走它。

- 数据库里存的就是逻辑路径（`file_path` 字段）
- URL 经过归一化后和 `file_path` 精确比对

**这是"口径统一"的经典案例**：多系统协作时，各写各的解析逻辑必然不一致，收敛到一个入口函数。

## 4. 问题现象

线上管理后台（admin）图片管理页：一张图 `image.png` 明明被最新一篇文章引用了，**引用次数显示 0**。

奇怪的是，用户观察到另外两个"正常"：

1. 图片在管理页能正常显示
2. 点开"引用溯源"也能查到"文章正文"这条引用

三个功能，两个正常，唯独计数是 0。

---

## 5. 排查过程（方法论：先读代码，再上服务器验证，不靠猜）

### 5.1 第一步：读代码，把计数链路完整走一遍

先理解"计数是从哪算出来的"，两个入口：

- 增量入口：`ImageReferenceService.addReferences` → `normalizeToRelativePath`
- 对账入口：`ImageUsageReconcileService.reconcileUsageCount` → 收集所有 URL → `countByPath`（内部也是 `normalizeToRelativePath`）

**两个入口共用同一个归一化函数**。这说明：只要归一化失败，增量和对账都会数不到。**嫌疑集中在 `normalizeToRelativePath`。**

### 5.2 第二步：服务器实测（关键！不要凭本地推断下结论）

登录生产服务器查三样东西：

1. 生产 `.env` 的配置（COS 是否启用、自定义域名是什么）
2. `images` 表里这张图的 `file_path`、`file_url`
3. 最新文章的 `content` 里图片 URL 的真实形态

结果：

```
.env:     COS_ENABLED=true, COS_BASE_URL=https://static.liuxin.chat
images:   file_path = images/2026/08/04/xxx.png
          file_url  = https://static.liuxin.chat/images/2026/08/04/xxx.png
文章正文:  src="https://liuxin.chathttps://static.liuxin.chat/images/2026/08/04/xxx.png"
```

**正文里的 URL 是畸形的双前缀**：`https://liuxin.chat` + `https://static.liuxin.chat/...` 拼接在一起。

### 5.3 第三步：用浏览器标准解析验证（Node 实测）

`new URL('https://liuxin.chathttps://static.liuxin.chat/...')` 的结果：

```
host:     liuxin.chathttps      ← 一个不存在的域名
pathname: //static.liuxin.chat/images/2026/08/04/xxx.png
```

浏览器会去请求 `https://liuxin.chathttps/...`，DNS 解析必然失败。**所以在 Web 端这篇文章里，这张图其实是裂的**（加载失败，走了兜底图）。

### 5.4 第四步：确认脏数据来源

看这个 img 标签的上下文，后面跟着 `md-hr`、`--tw-*` 这类 CSS 变量 class——这是外部 Markdown 渲染器（Tailwind 风格）的产物，**说明文章是从别处复制粘贴进来的富文本，粘贴源里就带着这个畸形 URL**。不是当前系统代码拼出来的。

### 5.5 第五步：三套口径对照分析（为什么"看起来正常"）

| 环节 | 处理方式 | 结果 |
| --- | --- | --- |
| admin 图片显示 | 读 `images.file_url`（存的是正常 COS URL），不读文章正文 | 正常 |
| 引用溯源 | 用 `file_path` 做 **LIKE 模糊匹配**扫五张表 | 畸形 URL 里恰好包含正确路径子串，能匹配上 → 正常 |
| 引用计数 | `normalizeToRelativePath` **精确归一化**整段 URL | 畸形 URL 归一无解 → null → 计数 0 |

**关键洞察：三个功能用了两种口径（LIKE 模糊 vs 精确归一化），所以结果不一致。**

---

## 6. 根因总结

- 直接原因：文章正文里存了畸形双重前缀 URL，`normalizeToRelativePath` 对含 `://` 且匹配不上任何已知前缀的 URL 直接返回 null
- 根本原因：**数据不干净（粘贴脏数据）+ 归一化策略过于严格（宁可漏，不误判）**

严格策略本身是对的——防止把外部网站的图片 URL 误认成系统图片。问题在于**系统内已经产生的脏数据没有兜底**。

---

## 7. 修复方案（三层：容错 + 治理 + 验证）

### 7.1 第一层：代码容错（防再犯）

给 `normalizeToRelativePath` 加畸形双重前缀容错：

1. 常规归一化失败、且 URL 含 `://` 时，取**最后一个 `://` 后面的 host 段**
2. 校验这个 host 是否属于**系统已知域名**（`SERVER_BASE_URL` / `COS_BASE_URL` 的 host 及 www 变体）
3. 是 → 从该 host 之后提取路径继续归一化；否 → 保持返回 null

**为什么必须是"系统域名白名单"**：否则 `https://example.com/images/a.jpg` 这种外部 URL 会被剥掉域名后误认成 `/images/a.jpg`——把外部图片算进系统计数。白名单保证：只救系统自己人（双前缀里至少一段是系统域名），不碰外部站点。

### 7.2 第二层：数据修复（治存量）

直接改数据库（先备份该行，再替换）：

```sql
-- 备份
CREATE TABLE posts_backup AS SELECT * FROM posts WHERE id=25;
-- 修复
UPDATE posts SET content = REPLACE(content,
  'https://liuxin.chathttps://static.liuxin.chat',
  'https://static.liuxin.chat')
WHERE id=25;
```

修复后：Web 端裂图恢复，计数也能数到了。

### 7.3 第三层：验证（对账）

部署新代码后，手动触发一次全量对账（管理页的「引用对账」按钮 = 手动重数），`usage_count` 从 0 恢复为 1。

**为什么修复后还要对账**：修了归一化代码，只是让"下次对账能数对"；存量计数还是错的，必须重数一遍。代码修复和数据修复是两回事。

## 8. 顺带的知识点：怎么在服务器上安全地调用管理接口验证

对账接口是 admin 接口，需要带 JWT。在服务器上直接生成 token（密钥不出服务器）：

- JWT = Header + Payload + Signature 三段 base64url
- Payload 里带 `userId` / `username` / `role` / `passwordHash`（passwordHash 是数据库中 BCrypt 哈希再做一次 SHA-256，防止 token 里明文暴露哈希）
- Signature = HMAC-SHA256(header.payload, JWT_SECRET)

然后 `curl -X POST /api/admin/images/reconcile-usage -H "Authorization: Bearer <token>"`。

**安全细节**：JWT_SECRET 只存在于服务器 `.env`，不进代码仓库；验证接口只在服务器上执行，密钥不经过本地。

## 9. 设计思想总结（面试加分点）

### 9.1 双层保险：增量 + 对账

- 增量：及时、代价小，但可能错
- 对账：全量、正确，但慢
- 组合 = 及时 + 最终正确。**"最终一致"的典型工程实践**

### 9.2 口径统一

所有 URL 解析收敛到一个入口函数（`normalizeToRelativePath`），杜绝各处各写一套。**多系统协作的第一原则：先统一口径，再谈功能。**

### 9.3 严格校验 + 白名单容错

- 对外部 URL 严格（不误判）
- 对系统内脏数据容错（白名单 host 才救）
- **安全与可用性的权衡：宁可少救，不可误伤**

### 9.4 LIKE 模糊匹配 vs 精确归一化

两个功能口径不同，结果就不同。排查这类"部分正常部分不正常"的 bug，**先找出每个功能各自的处理口径**，对照差异往往直接命中根因。

### 9.5 先验证服务器再下结论

本地代码推断再合理，也要到生产环境实测（配置、真实数据、真实 URL 形态）。"生产环境的数据和配置，才是最终事实"。

## 10. 面试问答预案

**Q: 为什么不用 Redis 做计数？**
A: 计数规模小（几百张图），Caffeine 本地多级 TTL 缓存足够；计数正确性靠每日对账保证，不需要分布式组件。引入 Redis 反而增加部署和运维成本。

**Q: 增量计数为什么会出错？你们怎么兜底？**
A: 业务方可能漏调、URL 格式变化归一对不上（这次就是）、软删除不减计数导致虚高。兜底是每日全量对账——清零重数，与增量无关，错了也能拉平。

**Q: 容错会不会把外部图片误算成系统图片？**
A: 不会。只对"最后一个 `://` 后的 host 属于系统域名白名单"的 URL 做剥离，外部站点的绝对 URL 不在白名单，直接返回 null。

**Q: 为什么对账要全量清零而不是增量修正？**
A: 全量清零重建简单可靠，不依赖历史增量的正确性；增量只负责两次对账之间的及时性。数据量小（几百上千条），代价可忽略。

**Q: 计数和溯源为什么结果不一致？**
A: 两个功能口径不同：溯源用 LIKE 模糊匹配（只要路径子串在就行），计数用精确归一化（整段 URL 必须能解析成逻辑路径）。口径差异就是这次 bug 的暴露面。

**Q: 修复为什么分三层？**
A: 容错防再犯（系统内脏数据无法杜绝）、数据修复治存量（现有错误数字必须纠正）、对账验证闭环（确认修复真正生效）。

## 11. 给面试官讲的话术（30 秒版）

"我们线上图片管理页出现一个 bug：一张被文章引用的图片，引用次数显示 0，但图片显示和引用溯源都正常。我查了计数链路，发现增量和每日对账共用同一个 URL 归一化函数，而这篇文章的正文是从外部粘贴的富文本，里面图片 URL 被拼了双重前缀（`https://站点域名 + https://COS域名 + 路径`），归一化函数对这种 URL 直接返回 null，所以计不到。溯源正常是因为它用 LIKE 模糊匹配，碰巧能匹配上路径子串。

修复分三层：一是归一化函数加容错，只对系统域名白名单内的双前缀做剥离，外部站点 URL 不受影响；二是修正存量脏数据（备份后 REPLACE）；三是部署后手动触发全量对账，计数恢复为 1。

这件事也验证了系统的设计：增量计数保证及时，每日对账保证最终正确，所以即使出现这种数据问题也能自愈。"
