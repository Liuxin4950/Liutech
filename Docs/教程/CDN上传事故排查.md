# 一次 CDN 大文件上传事故的排查与解决（面试教程）

> 本文档把一次真实生产事故的完整排查过程写成教程，重点讲**排查方法论**和**根因分析**——面试时讲清楚「怎么一步步定位」比讲「最后怎么改的」更值钱。

## 一句话概述

用户在前台博客上传 21MB 的 RAR 附件反复失败，浏览器报 `ERR_HTTP2_PROTOCOL_ERROR`。经过分层验证，最终定位到**腾讯云 CDN 边缘节点对回源请求有约 10 秒的加载超时、对与浏览器的连接有约 30 秒的空闲超时**，而 21MB 文件回源到源站需要约 28~33 秒——超时被掐断。并且「后端其实每次都上传成功了，只是响应回不来」，导致用户反复重试产生 6 份重复数据。最终用**分片上传 + 幂等查重**根治。

## 项目背景

- 全栈博客平台：Vue 3 前端 + Spring Boot 后端 + MySQL + 腾讯云 COS 对象存储
- 访问拓扑：**浏览器 → 腾讯云 CDN（liuxin.chat）→ 源站 Nginx → 后端**，静态文件存在 COS，走 `static.liuxin.chat` 域名
- 附件上传：编辑器里传 RAR/ZIP 等资源文件，后端校验后存入 COS

## 问题现象

1. 浏览器上传 21MB 的 `adb工具.rar`，等 10 多秒后报 `ERR_HTTP2_PROTOCOL_ERROR`，前端 axios 报 `Network Error`
2. 用户以为是失败，反复重试
3. 本地 `127.0.0.1:8080` 直连后端上传**成功**（说明后端没问题）

## 排查过程（核心：分层验证法）

面试讲这一段。核心方法论：**遇到链路问题，先从源头往末端逐层验证，用「谁通谁不通」把问题范围不断缩小**。

### 第 1 步：确认后端和文件本身没问题

用户本地直连后端 `127.0.0.1:8080/upload/resource` 上传成功 → 后端代码、文件本身、数据库都没问题。**问题在公网链路上**。

### 第 2 步：从服务器上绕过 CDN 直测源站

在源站服务器上 `curl https://localhost/api/upload/resource` 上传同样 21MB：

```bash
http_code=401 time=0.07s   # 请求完整到达后端（401 是没带 token 被安全拦截）
```

0.07 秒收到 401 → **Nginx 和后端链路完全正常**，21MB 上传毫秒级完成。

### 第 3 步：服务器上走 CDN 域名复现

```bash
curl https://liuxin.chat/api/upload/resource   # 21MB
http_code=401 time=28s     # 通了！但花了 28 秒
```

走 CDN 时 21MB 要 28 秒（回源链路慢），但**能通**。curl 能通、Chrome 不通 → 差异只剩浏览器。

### 第 4 步：看源站 Nginx 日志（关键证据）

用户再次重试时，源站 Nginx 日志出现：

```
"POST /api/upload/resource" 499 0  Chrome/148   ← 关键
```

**HTTP 499 是 Nginx 特有的状态码：客户端在请求未完成时就主动断开了连接**。并且从日志看，请求确实穿过了 CDN 到达源站（回源 IP 是 CDN 边缘节点的 IP），但 body 接收开始约 15 秒后 CDN 边缘节点主动断开。

**结论：不是被防火墙/WAF 拦截（拦截会返回 403/445），是 CDN 边缘节点主动掐断了连接。**

### 第 5 步：查 CDN 控制台配置

CDN 控制台「回源配置」里有：

- 回源加载时间：**10 秒**（默认）← 就是这个！

**回源加载时间**的意思是：CDN 边缘节点向源站发起回源请求后，等待源站响应的超时时间。21MB 回源要 28 秒 > 10 秒 → 超时掐断。

### 第 6 步：调大后还不行？再挖一层

把回源加载时间调到 60 秒后，上传「成功」了，但**前端还是报 Network Error**。看日志：

```
10:32:29 开始接收 body（回源开始）
10:33:02 200 OK  ← 后端其实成功返回了！
```

后端返回 200、响应就 424 字节（成功 JSON），但浏览器还是报网络中断 → **响应丢失发生在 CDN 边缘 → 浏览器这一段**。

原因：用户上传 21MB 用了约 8 秒，回源又花了 33 秒——这 33 秒里浏览器和 CDN 边缘节点之间没有任何数据传输，**CDN 边缘节点约 30 秒的空闲超时把与浏览器的连接掐了**，响应发不回去。

**这是配置层解决不了的**：回源加载时间只管回源段，边缘节点与浏览器的连接超时是另一段。

## 衍生问题（面试亮点：一个事故引出四个问题）

### 问题 1：重复上传 6 份

后端其实每次**都上传成功**（COS 里有 6 个 21MB 的完整对象），只是响应没回来 → 前端误报失败 → 用户重试 → 重复上传。

前端失败弹窗写着「上传失败，请重试」——**这就是引导用户重试的元凶**。

### 问题 2：查重失效

响应体里有 `isDuplicate` 字段（图片上传有查重），但**资源上传压根没有查重逻辑**。补上查重后第一版按「用户 + 文件名 + 草稿键 + 10 分钟」查重——但**用户刷新页面后草稿键（draftKey）会重新生成**，查不到旧草稿键的记录，防不住刷新后重传。

改法：查重条件去掉草稿键，改为「同用户 + 同名 + 时间窗口」。

### 问题 3：文章保存后附件丢失

查重命中时直接返回了已有资源，但**没有创建附件关联记录**（页面显示附件是前端自己 push 的假象），保存文章时按草稿键绑定附件发现查无记录 → 绑定 0 行 → 文章详情查不到附件。

改法：查重命中时也要**幂等创建附件关联**（同一草稿键 + 同一资源已有关联则不重复建）。

### 问题 4：下载的文件只有 15 字节

下载链路完全正常（后端 200、21MB 完整到浏览器），但保存的文件只有 15 字节、打开提示损坏。

**15 字节正好是 `[object Object]` 的长度**。根因：前端 axios 全局响应拦截器会把非标准响应包装成 `{ code, message, data }` 对象，blob（二进制）响应也被包进去了；前端 `new Blob([response.data])` 把对象转成了字符串 `[object Object]`。

改法：`new Blob([response.data.data ?? response.data])`。

### 附加发现：COS 对象整目录被清空

排查中发下 COS 的 `resources/` 目录**整个空了**（数据库记录还在）。代码里没有任何批量删除逻辑，判断是在 COS 控制台手动删「重复文件」时误删了全部。恢复方式：把原文件补传到**原对象 key**（数据库存的就是这个 key），下载立即恢复。

**教训：COS 控制台手动删对象不会同步数据库，会造成下载 400。**

## 解决方案：分片上传（核心设计）

配置层解决不了边缘节点空闲超时，最终方案是**分片上传**：

```
原文件 21MB ──切分──> [5MB][5MB][5MB][5MB][1MB] ──逐片上传──> 后端收片存临时目录 ──合并──> 校验完整性 ──> 存 COS + 入库
```

**为什么单片 5MB？** 单片请求的完整周期 = 上传（约 2 秒）+ 回源（约 7 秒）≈ 9 秒，**远低于 30 秒的空闲超时阈值**，响应必定正常返回。

为什么选分片而不是绕开 CDN（比如直连域名）？分片不动域名拓扑、不加证书运维负担、顺带能传更大的文件，是改动收益比最高的方案。

后端两个新接口：

- `POST /upload/resource/chunk`：收单片，落临时目录（`uploads/tmp/{uploadId}/{index}.part`），校验单片 ≤5MB、序号合法
- `POST /upload/resource/merge`：校验分片完整（片数齐全、总大小 ≤100MB），按序拼文件，清理临时目录，然后走与普通上传**完全相同**的保存逻辑（含幂等查重）

## 技术点清单（面试可以展开讲）

1. **HTTP 499 状态码**：Nginx 特有的「客户端提前断开」标志，排障时比浏览器报错信息更有用
2. **CDN 回源超时 vs 边缘空闲超时**：两段独立超时，配置层只能调前者
3. **HTTP/2 的 `ERR_HTTP2_PROTOCOL_ERROR`**：浏览器侧的表现，本质是连接被 RST/GOAWAY
4. **幂等设计**：查重 + 复用已有资源 + 幂等建关联，让「重试」变成安全操作
5. **时区错位**：MySQL 会话时区是 UTC、应用按本地时间写入，导致查重「10 分钟窗口」实际约 8 小时——副作用是防重窗口更长，反而有利
6. **axios 拦截器与 blob**：全局响应拦截器会把非标准响应包装成对象，二进制下载要解包 `.data`

## 面试问答预演

**Q：为什么不用 CDN 直连上传？**
A：上传本身就是要经过 CDN 的（域名解析到 CDN），问题是 CDN 边缘节点对大请求的两段超时。配置层调大回源超时只能解决回源段，边缘与浏览器的空闲超时调不了。分片是让整个请求周期缩短到超时阈值内。

**Q：分片大小怎么定的？**
A：反推。边缘节点空闲超时约 30 秒，回源速度实测约 750KB/s，单片要在 30 秒内完成「上传 + 回源」全周期，5MB 单片约 9 秒，留了 3 倍余量。太小（如 1MB）请求次数太多，太大（如 20MB）又回到超时问题。

**Q：分片断了怎么办？**
A：前端重试时重新生成 uploadId 从头传（临时目录按 uploadId 隔离，互不污染）；merge 时校验分片完整性，缺片直接报「分片不完整，请重新上传」。因为单片很小，重传成本低。生产上没做断点续传，权衡后不值得（单片 9 秒完成，失败概率极低）。

**Q：怎么保证合并后的文件没错？**
A：merge 时校验片数齐全、每片存在、总大小与预期一致、上限 100MB；验证时上传后从 COS 下载回来做 md5 对比，完全一致。

**Q：为什么查重不按文件内容 hash？**
A：resources 表没有 hash 字段，加字段要迁移。用「同用户 + 同名 + 时间窗口」在真实场景下足够——同名同用户短时间内重传，几乎必然是重试。想传新版同名文件就先删旧附件（删了旧记录查重就不命中）。

**Q：这个事故你最大的收获是什么？**
A：三点。第一，链路问题要分层验证，用「谁通谁不通」缩小范围，而不是瞎猜——这次靠的是源站直连、CDN 复现、Nginx 日志三组证据。第二，**「失败」不代表「没成功」**——响应丢失会让前端误判，所以后端要有幂等设计让重试安全。第三，任何一层代理（CDN、网关）都可能有你没配置过的超时，出问题先看中间层的日志和配置，再怀疑自己的代码。

## 附录：排查时用到的命令

```bash
# 服务器上绕过 CDN 直测源站（验证后端链路）
curl -sk -X POST --data-binary @big21m.bin -H "Content-Type: multipart/form-data" \
  https://localhost/api/upload/resource -w "%{http_code} %{time_total}s"

# 走 CDN 复现（对比耗时）
curl -sk -X POST --data-binary @big21m.bin -H "Content-Type: multipart/form-data" \
  https://liuxin.chat/api/upload/resource -w "%{http_code} %{time_total}s"

# 看 Nginx 日志里的 499（客户端提前断开）
docker logs liutech-nginx 2>&1 | grep "upload/resource"

# 本机 Node 模拟 HTTP/2 上传（复现 Chrome 行为）
node -e "const h=require('http2'),fs=require('fs');const c=h.connect('https://liuxin.chat',{rejectUnauthorized:false});const r=c.request({':method':'POST',':path':'/api/upload/resource','content-type':'multipart/form-data; boundary=x','content-length':String(fs.statSync('f.rar').size)});r.on('response',h=>console.log(h[':status']));r.on('error',e=>console.log('ERR',e.code));r.end(fs.readFileSync('f.rar'))"
```
