## 1. 什么才算"优秀的高并发"

### 判据 1：并发占用是算出来的，不是猜出来的

Little's Law 的准确形式：

```
L = λ × W        平均在途请求数 = 到达率(QPS) × 平均驻留时间(秒)
```

两点必须说清，否则公式会被滥用：

1. **`W` 是平均值，不是 P99。** 用 P99 代入得到的是**偏保守的设计余量**，不是 Little's Law 本身；本套文档一律写作"按 P99 估算的保守槽位需求"。
2. **该式只对"同一资源被请求独占"成立**（DB 连接、Tomcat 线程、流式配额）。内存（整文件入堆）与带宽是**另一种量纲**，不能与"槽位"混列在同一张表里相加比较。

按此重算（**W 全部是估测，需 `06` §2/§3 实测替换**）：

| 场景 | 估 W（持有 DB 连接） | λ=500 QPS 需要连接 | 现状 | 判定 |
| --- | --- | --- | --- | --- |
| 只读列表，缓存命中 | ≈ 0 | ≈ 0 | 20 | 无瓶颈 |
| 只读列表，未命中（4 条 SQL） | 估 20~40 ms | 10~20 | 20 | 临界，取决于实测 |
| `GET /posts/{id}`（≥5 条含 1 次行锁 UPDATE） | 估 30~60 ms + 锁等待 | 15~30 | 20 | 临界，且**同一篇文章并发时因行锁退化** |
| `GET /admin/dashboard/stats`（约 25 条独立借还） | 估 150~300 ms | — | 20 | 单个后台页可占池 15 %（**估**） |

结论：天花板不是"缺 Redis"，而是**每请求持有连接/线程的时间**。但**任何具体倍数都要等实测**。

### 判据 2：请求不占用它用不到的资源

请求同时占用 **Tomcat 线程**、**Hikari 连接**、**行锁**、**堆内存**。每项持有时间应只覆盖真正需要它的代码段。已核实的违反点：网络/文件 IO 在事务内（`02` §4）、读接口持写锁（`PostsService.java:193-197`）、BCrypt/图片压缩在事务内。

### 判据 3：过载时优雅降级，而不是塌陷

要求：等待队列**有界** + **显式拒绝策略** + 入口**限流** + 慢接口**舱壁隔离**。现状：主后端零限流；AI 侧 `Executors.newFixedThreadPool(16)` 无界队列；Nginx 无 `limit_req`/`limit_conn`（全量 grep 0 命中）。

## 2. 五个降载杠杆（严格按序）

| 级别 | 杠杆 | 本项目最高频用法 |
| --- | --- | --- |
| **L0 别做** | 缓存命中、静态化、边缘缓存 | Nginx 微缓存 + Caffeine；`sitemap.xml` |
| **L1 别同步做** | 移出请求线程：异步、批处理、攒批 flush | 浏览量增量、操作日志、SMTP |
| **L2 别占连接做** | IO 出事务、流式代替整文件入堆、及时归还连接 | 上传/下载/COS |
| **L3 少做** | 索引可用、列裁剪、免 COUNT、N+1 改批量、验签一次 | `01`/`03` 的 SQL 与索引清单 |
| **L4 排队别塌陷** | 有界队列 + 拒绝策略 + 限流 + 配额 | `04` §3.2、`05` §3 |

> **反模式**：多数人先做 L4 或先加 Redis。L0~L3 是**免费的容量提升**，通常 10~100 倍；L4 只保证"超出容量时不死得难看"。

## 4. 容量基线台账（事实与推导分列）

| 项 | 事实（可核） | 推导（**待实测**） |
| --- | --- | --- |
| Tomcat 线程 | 未配 `server.tomcat.*` → Boot 默认 200 | 200 : 20 = 10:1 错配 |
| HikariCP | 两服务各 20 | 只读吞吐随"每请求 SQL 数"线性变化 |
| MySQL | 无 `my.cnf` 挂载（`mysql/` 下仅 `init-users.sh`）；`command:` 只设认证插件 → 取镜像默认（**外部事实，需 `06` V-2 实测**） | 热数据超默认 buffer pool 即落盘 |
| 应用账号权限 | `mysql/init-users.sh:20,25` 仅 `SELECT,INSERT,UPDATE,DELETE` → **无 DDL、无 PROCESS、无 performance_schema/sys** | 所有 `ALTER`/`SHOW ENGINE`/`sys.*` 必须 root；见 `03` §4 双写规则 |
| JVM 堆 | Dockerfile 无 `-Xmx`、compose `memory: 2G` → 约 512 MiB（依赖 limits 真生效，`06` V-10） | 5 × 100 MB 上传即逼近上限（整文件入堆） |
| 缓存 | `CacheConfig.java:37-51` 声明 10 个命名缓存，**`userStats` 无任何 `@Cacheable`（只有 `@CacheEvict`）→ 实际生效 9 个**；`carousels`/`music`/`sitemap`/`/posts/{id}` **今日未缓存** | 命中率取决于键基数 |
| AI 流式 | `streamExecutor` = `newFixedThreadPool(16)` 无界队列（`StreamingChatService.java:79,89`） | 第 17 条流静默等到 emitter 超时（V-5） |
| TTS | `${TTS_CONCURRENCY:1}` + `Math.max(1,·)` + compose `:-1` → 默认全站并发 1 | 阻塞 acquire 无超时 |
| 定时任务 | 仅 `@EnableScheduling`，无 `TaskScheduler` bean → **单线程** | 主后端两个夜间镜像任务会与新 flush 任务互斥（AI 侧只有 1 个 `@Scheduled`，无饿死对象） |
| 观测 | 主后端有 actuator 但**无 `micrometer-registry-prometheus`、无任何 `management.*` 配置**；AI 有依赖但 `exposure.include: health` | **当前拿不到 Hikari/Tomcat 指标**，先做 `06` §1 |
| 限流 | Nginx 无 `limit_req`/`limit_conn`；主后端无拦截器；AI 有 `AiRateLimitInterceptor`（已注册生效，含 SSE） | `POST /messages` 匿名可写且无入口限制 |

**断点预测**（需实测确认）：① `GET /posts/{id}` 读时行锁写；② 认证管线每请求 1 次无缓存 `SELECT`；③ SSE 无配额 + `Disposable` 丢弃；④ 后台报表约 25 条语句无缓存；⑤ 上传整文件入堆。

## 5. 与"不引入 Redis"约束的边界

`跨服务规范.md:86` 禁止建议/编写 Redis 代码，本套文档全部方案在 Caffeine + MySQL + Nginx + Compose 内。约束的**后果**必须说清：

| 能力 | 替代做法（已核） | 天花板 |
| --- | --- | --- |
| 跨实例缓存失效 | 当前**有意单副本**（6 个服务全部固定 `container_name`；Nginx upstream 各 1 成员）。**"缓存键拼全局版本号"已被推翻**：版本号要跨实例一致就得放共享存储（DB 一行）→ 每请求又回到一次读，退化成 TTL（`05` §8） | 无 Redis 就**没有**真正的跨实例精确失效；正解是短 TTL + 接受陈旧窗口 |
| 分布式锁 | 唯一索引 + ODKU + 捕获重复键（`UserAuthService.java:155-165`）；真互斥 `SELECT … FOR UPDATE`（`UserAchievementMapper.java:10`）；单次作业 `GET_LOCK()` | `FOR UPDATE` 锁整行 `users`，会串行化同用户其他写 |
| 限流 | **Nginx 层**（按 IP，零 Java、不占应用线程）+ AI 侧按用户桶 | 共享出口 IP 会误伤，需 `set_real_ip_from` |
| 计数缓冲 | Caffeine 累加 + 定时 flush（正确性细节 `03` §1a） | 崩溃丢 ≤1 个 flush 窗口 |
| Token 撤销 | token 内嵌 `sha256(passwordHash)`（`UserAuthLookupService.java:41-54`）——**但该处有 fail-open（`:53`），且改密路径不清用户缓存**，见 `05` §1.3 | 端到端陈旧上限 **300 s**（`UserUtils.java:39-42` 的 5 min 缓存），不是内省那段的 60 s |

**何时必须破约束**：只读 QPS 长期突破连接池极限，或需要 ≥3 副本高可用。破约束要连 `跨服务规范.md` 一起修订，不允许代码里偷偷加依赖。

### 关于"优先级"与"实施顺序"不一致的说明

`§6` 是**风险分级**，`06` §5 是**实施顺序**，二者刻意不同，理由必须写明以免被当成矛盾：

## 8. 陷阱与约束

- **协议不可动**：SSE 的 `start/data/audio/complete` 与 `response.isCommitted()` 分支是刻意设计（`跨服务规范.md:45`）；AI 非流式接口沿用 `{success,message,code}`（前端 `api.ts` 已双格式归一化）。改 SSE 还要同时改两端镜像客户端文件（`04` §9）。
- **审计日志不可降级**（`跨服务规范.md:71`）：异步化只能改执行线程，不能改"是否记录"，且切面内所有 `RequestContextHolder`/`SecurityContextHolder` 取值必须在提交任务前完成。
- **DDL 双写**：`sql.sql` 只在 MySQL 首启执行 → 迁移脚本 + 回填 `sql.sql`，**一次变更两处修改**；且应用账号无 `ALTER`/`INDEX`，必须 root。详见 `03` §4。
- **CI 绿 ≠ 并发已验证**：本机实测 **595 个测试全绿**（主后端 499 + AI 96，按 surefire 产物核对而非退出码），但 67 个测试类里 `@SpringBootTest` 为 **0**，控制器直接 `new` + Mockito（`PostsControllerTest.java:36`）→ `@Cacheable`/`@Transactional`/SQL/索引/行锁**全不经过代理与数据库**。但 CI 确实守着行为契约（如 `toggleLike` 返回 `liked`/`unliked` 的断言）。三层门禁见 `06` §7。
- **不要 `docker compose down -v`**（清空 `mysql_data`，`AGENTS.md`）；压测在隔离环境做。
- 固定 `container_name` 阻止 `--scale` 是**有意的护栏**，不是待修 bug。
