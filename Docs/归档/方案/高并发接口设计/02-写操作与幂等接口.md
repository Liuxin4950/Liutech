## 1. 写并发的四种冲突与四种解法

| 冲突模式 | 症状 | 正确解法（按优先级） | 本项目实况（已核） |
| --- | --- | --- | --- |
| **① 重复执行**（双击/重试/重放） | 本应唯一的多行 | **唯一索引 + 捕获 `DuplicateKeyException` → 抛 `BusinessException`（业务码）** | ✅ 唯一键模式对：`UserAuthService.java:155-165`；⚠️ `ResourceDownloadService.java:101` 模式对但抛裸 `RuntimeException`→500；❌ `CheckinService.java:79` 完全没捕获 |
| **② 丢失更新**（read-modify-write） | 计数偏小、余额错 | 单条原子 SQL；派生值绝不"读→算→绝对覆盖" | ❌ `UserProfileService.java:120` 整实体 `updateById`；❌ `MemoryService.java:119-127`；⚠️ `PostInteractionService.java:53-63` |
| **③ check-then-act 窗口**（TOCTOU） | 超卖、重复领、窗口绕过 | 悲观锁把 check 与 act 关进同一锁域，或**把 check 下推为 WHERE 条件** | ✅ `UserAchievementMapper.java:10`（锁粒度偏大）；❌ `MessagesService.java:84-95` |
| **④ 状态切换竞态**（先读后翻） | 并发两次点击落到同一态 | **客户端提交目标状态，服务端写绝对值** | ❌ `PostInteractionService.java:53-57` |

**四条铁律**：① 幂等靠 **DB 约束**不靠应用判断；② 能用一条 SQL 完成的绝不用三步；③ **重试必须在新快照里**（`PointsService.java:146-159` 在 RR 快照内重试必然再失败）；④ 带外部副作用的写接口必须有**客户端幂等键**（DB 约束防重复行，幂等键防重复副作用）。

## 2. 类型 D：点赞/收藏

### 2.1 事实（逐条核实）

```sql
-- 列名是 is_like / is_favorite（sql.sql:151 / :168），TINYINT UNSIGNED NOT NULL DEFAULT 1
-- deleted_at 可空（:154 / :171）；uk_user_post(user_id, post_id) 唯一键（:155 / :172）
-- 现状 SQL（PostLikesMapper.xml:43-49）：
INSERT INTO post_likes (user_id, post_id, is_like, created_at, updated_at) VALUES (?,?,?,NOW(),NOW())
ON DUPLICATE KEY UPDATE is_like = #{status}, updated_at = NOW();   -- ★ 从不写 deleted_at
-- 计数（:23-27）：… WHERE post_id=? AND is_like=1 AND deleted_at IS NULL
-- 状态（:36-40）：SELECT is_like … WHERE user_id=? AND post_id=?   -- ★ 不过滤 deleted_at
```

上一版我建议的 `is_liked = NOT is_liked` 有**两处致命错误**：列名不存在（MySQL 1054，语句跑不起来）；且"DB 内翻转"本质非幂等（重试两次 = 点赞后取消）。

### 2.2 正确设计

```sql
-- ① 绝对状态 upsert（幂等：重放写同一个值）
--   已核实：裸 @Insert/XML 完全绕开 MP 逻辑删除，deleted_at = NULL 写得进去；6 列全存在，
--   除 is_like 外无 NOT NULL 缺默认
INSERT INTO post_likes (user_id, post_id, is_like, deleted_at, created_at, updated_at)
VALUES (#{userId}, #{postId}, #{status}, NULL, NOW(), NOW())
ON DUPLICATE KEY UPDATE is_like = #{status}, deleted_at = NULL, updated_at = NOW();

-- ② 计数：三种形态的取舍见 §2.2 末尾的结论表（子查询方案并未被否定，它的代价只是间隙锁）
```

**②的两种可选形态（第三轮更正）**：

```sql
-- 形态 A（推荐）：把"串行点"显式化，再做一致性读 + 传值写入
-- 形态 A（可用，但有两条硬前置，见 §2.2 末尾）
SELECT id FROM posts WHERE id = #{postId};                    -- ✗ 不能作为串行点
SELECT id FROM posts WHERE id = #{postId} FOR UPDATE;         -- ★ 必须是本事务【第一条】语句
SELECT COUNT(*) FROM post_likes WHERE post_id = #{postId} AND is_like = 1 AND deleted_at IS NULL;
UPDATE posts SET like_count = #{count}, updated_at = updated_at WHERE id = #{postId};
```

```text
形态 B（并发更高时）：posts.like_count 不落请求路径，由 03 的定时对账任务从 post_likes 重算，
请求只写 ① 的 upsert。代价：计数短暂滞后。需要 03 先补"计数落列对账"任务（目前只有 usage_count 有）。
```

> **为什么不能用"一条 UPDATE + 相关子查询"**（上一版的写法）：InnoDB 对 `UPDATE` 语句里的子查询，会按更新语句的规则给**扫描到的 `post_likes` 索引记录加 S 锁 + next-key（含间隙）**。它与并发 `INSERT … ODKU` 的插入意向锁互斥 → ① 同一热帖的点赞被**串行化**；② "T1 持有自己行的 X 锁并请求某区间 S 锁 / T2 反之"构成经典**死锁（1213）**。上一版"这样终值正确"的论证忽略了这一点。
> `updated_at = updated_at` 抑制列级 `ON UPDATE CURRENT_TIMESTAMP` 成立；`AND deleted_at IS NULL` 是**必须**的（裸 XML 不受 MP 逻辑删除过滤）；Connector/J 默认返回 matched 行数，因此"值未变化"不会被误判成 0 行。

**为什么不改 `like_count = like_count ± 1`（第二版建议，已删）**：`like_count`/`favorite_count` 是 `INT UNSIGNED`（`sql.sql:112-113`），在 0 上减 1 报 **1690**；加 `WHERE … >= 0` 守卫又会**静默 0 行**、与"文章不存在"不可区分；绝对重算对软删级联/批量/回滚全部自愈，`±1` 反而新造漂移。
**结论（第四轮定论，依据 MySQL 8.0 手册 §17.7.2.3/17.7.2.4 原文）**

三条被文档明确表述的规则：① RR 下 `Consistent reads within the same transaction read the snapshot established by the first read`；② 加锁读 `reads the latest available data` 且**不建立快照**，手册同时警告"非锁读用 read view、锁读用最新状态，两者互不一致、难以解读"；③ `UPDATE … SELECT` 里的 SELECT 部分**表现为 READ COMMITTED**（每次一致性读自建新快照）。

由这三条推出我前两版都没说清的结论：

| 形态 | 正确性 | 代价 | 何时用 |
| --- | --- | --- | --- |
| **① 一条 `UPDATE … SET like_count = (子查询)`** | ✅ **被文档正面保证**（子查询按 READ COMMITTED 取新快照） | 对扫描到的 `post_likes` 记录加 S + next-key（含间隙）锁 → 热帖串行化、与并发 `INSERT … ODKU` 的插入意向锁可能死锁（1213） | 冷/中热文章，图一条语句必然正确 |
| **② 形态 B：计数不落请求路径**，由 `03` 的对账任务刷新，请求只做 ① 的 upsert | ✅ 无竞态（列只由单一反向任务写） | 计数滞后一个刷新周期；需 `03` 先补"计数落列对账"（现只有 `usage_count` 有） | **热帖/高并发场景选它** |
| **③ 形态 A：`FOR UPDATE` → 普通 `COUNT` → 传值 `UPDATE`** | ⚠️ **有条件成立** | 3 条语句、1 次额外往返 | 只有下面两条前置都满足才可用 |

**形态 A 的两条硬前置（缺一条就真的会丢别人的赞）**：

1. `SELECT … FOR UPDATE` **必须是本事务的第一条语句**。现状代码违反：`PostInteractionService.java:47`（`getById`）与 `:53`（`getLikeStatus`）都是**锁之前的一致性读** → 快照被钉在旧值上，随后的 `COUNT` 看不见并发已提交的赞，绝对重算会把它抹掉。**这才是"自愈被亲手破坏"的真实成因**，不是形态 A 本身错。
2. 串行点**不能带 `AND deleted_at IS NULL`**：帖子已软删时该 `FOR UPDATE` 匹配 0 行 = 根本没有串行点（软删文章的互动另有 `§2.3` 的专门处理）。

另外两点更正：`SELECT COUNT(*) … FOR UPDATE` **不要用** —— 文档未授权该写法且会锁 `post_likes` 区间，等于把形态 ① 的代价叠加到形态 A 上；`±1` 增量仍不可取（`INT UNSIGNED` → 1690）。

补索引（让计数读走 index-only，形态 ①/②/③ 都受益）：`ALTER TABLE post_likes ADD INDEX idx_post_like (post_id, is_like, deleted_at);`（现状 `idx_post_id` 在 `sql.sql:157` 不覆盖 `is_like/deleted_at`，要回表）。

> 上述"RR 快照 vs 加锁读"的推导来自手册原文，但**本项目尚未实测复现**。落地前用 `06` V-22 关掉它：两个并发用户同时对同一文章点赞，比较三种形态下 `like_count` 与真实行数是否一致。

### 2.3 恢复文章丢点赞（真实缺陷，修法已修正）

| 事实 | 证据 |
| --- | --- |
| 软删文章时级联把 `post_likes.deleted_at`、`post_favorites.deleted_at` 置值，**共三处写入点** | `PostsService.java:593`、`PostsAdminService.java:185`（单条）、`PostsAdminService.java:249`（批量删） |
| 恢复只碰 `posts` | `PostsAdminService.java:274-286` → `PostsMapper.xml:700-704`（仅 `posts.deleted_at = NULL`） |
| 状态查询与计数查询过滤条件不一致 | `PostLikesMapper.xml:36-40` 不过滤 `deleted_at`，`:23-27` 过滤 |

**影响**：恢复后 `countLikesByPostId` 恒 0（点赞永久丢失）；用户 UI 显示"已赞"而计数为 0，点一下取消（写 0）、再点一下（写 1 但 `deleted_at` 仍非空）→ 该赞**永久不可见**。

**修法（三步，必须一起做）**：

1. `restorePost` / `batchRestorePosts` 内补两条恢复语句 —— **必须用裸 `@Update`/XML**：
   ```sql
   UPDATE post_likes     SET deleted_at = NULL WHERE post_id = #{postId} AND deleted_at IS NOT NULL;
   UPDATE post_favorites SET deleted_at = NULL WHERE post_id = #{postId} AND deleted_at IS NOT NULL;
   ```
   > ⚠ 若按项目常见写法用 `LambdaUpdateWrapper`（如 `PostsService.java:591-594` 那样），MP 会自动追加 `AND deleted_at IS NULL` → **匹配 0 行、静默无效**。同仓库已有"绕过 `@TableLogic`"的先例可参照：`PostsMapper.xml:700-704`、`ImagesMapper.xml:70-71`、`CarouselService.java:266-267` 的注释。
2. `getLikeStatus` 补 `AND deleted_at IS NULL`，与计数口径对齐。
3. upsert 补 `deleted_at = NULL`（§2.2①）。

`post_favorites` 的等价过滤列是 `is_favorite`（`sql.sql:168`）。补 `deleted_at IS NULL` 后，`is_like = 0` 的历史行永不复活 —— 行为自洽（那本就是"未点赞"）。

## 3. 事务边界（写接口的第一性能杀手）

> **事务生命周期只覆盖 DB 操作。** 事务内任何非 DB 动作都在独占一条 Hikari 连接并持有行锁。现状 195 处 `@Transactional`、**无一处设 `timeout`/`isolation`**。

| 违规动作 | 证据（行号已按代码修正） | 持有时长 |
| --- | --- | --- |
| COS `putObject` | `ImagesService.java:47` 的 `@Transactional` 覆盖 `:61` 压缩与 `:69` `fileStorage.save`；`FileUploadService.java:210→248` | 秒级（`CosFileStorage.java:53` 未设超时） |
| COS `deleteObject` | `FileUploadService.java:711→734` | 秒级 |
| 跨服务 HTTP（删用户） | `UserManagementService.java:650→660`（单次 connect 3 s + read 8 s ≈ 11 s）；`:692→703`（每 100 用户一次**串行**调用 → 1000 用户可达分钟级**单事务**） | **分钟级** |
| SMTP 发信 | `VerificationCodeService.java:71` 插码 + `:74` 发信同事务同线程。`:114` 的 `REQUIRES_NEW` 是 `incrementAttemptCount`，**只隔离尝试计数**（第二版说它"隔离了插码"是错的） | 秒级 |
| BCrypt | `UserAuthService.java:134,427,545` | 50~300 ms CPU |
| Caffeine 清理 | `UserProfileService.java:66-67` 在提交前失效 → 改 `afterCommit` | 短但语义错 |

纪律：新增只读方法一律 `@Transactional(readOnly = true)`（现状 76 处已做对，`getPostDetail` 是反例）。
**注意 MP 的双重性**：`ServiceImpl` 的 `this.save/update/list` 自身带事务，从非事务方法调用会各开一个短事务 → 判断"某条 SQL 是否在某事务内"必须看**调用方有没有注解**，不能只看有没有 `@Transactional` 字样。

## 4. 类型 E：余额与派生计数

### 4.1 积分

```sql
-- users.points 是 DECIMAL(12,2) 有符号（sql.sql:42）→ 无 1690 风险，条件扣减安全
UPDATE users SET points = points - #{amount}, version = version + 1, updated_at = NOW()
 WHERE id = #{userId} AND deleted_at IS NULL AND points >= #{amount};
```

现状需要改的量比"方向一致"大：`PointsService.deductPoints` 返回 **void**、失败**抛裸 `RuntimeException`**（`:100`）→ 500；重试耗尽后才抛，且流水插入在 `:113-116`（确在扣减之后，顺序对）。改造要点：① **影响行数 0 必须识别为业务码分支**（"余额不足"，`ErrorCode` 需补对应项），而不是重试信号；② **删掉 `:47-100` 的乐观锁重试循环**（RR 快照内重试必然再失败）；③ 硬约束保持"行数≠1 先于流水插入抛出"。

### 4.2 整实体更新（资损级）

`Users.java:47` 的 `version` 无 `@Version` → `MybatisPlusConfig.java:32` 的乐观锁插件永不介入。`UserProfileService.java:120`、`UserAuthService.java:359,548` 的 `updateById(entity)` 会 ① 把 `points` 按旧快照写回（覆盖并发签到所得）；② **把 `version` 也写回旧值，直接抵消 `addPointsWithVersion`（`UserMapper.xml:155-163`）的递增**。

两条路选一：**推荐**改用字段级 `LambdaUpdateWrapper`（只 `SET` 真正要改的列，范式见 `PostsAdminService.java:142`）；或补 `@Version` 并处理"0 行需重试"分支 —— 后者保留了"整实体更新"这个语义陷阱。

### 4.3 AI 会话计数与 seq_no（更正）

```text
message_count：现状 selectById → Java +1 → updateById（MemoryService.java:119-127）
  → UPDATE ai_conversation SET message_count = message_count + #{n}, last_message_at = NOW() WHERE id = ?
seq_no：idx_conv_seq 是【非唯一 KEY】（sql.sql:622，第二版误写 :620）
```

**第二版那句"MySQL 1093，必须派生表包装"是错的**：官方规则是**更新目标表不能出现在同一语句的子查询 FROM 中**，而 `INSERT … SELECT … FROM 同表` 是**允许**的（内部用临时表实现）。真正要防的两个坑是：

1. 我上一版字面写的 `SELECT MAX(seq_no)+1 FROM ai_chat_message` **漏了 `WHERE conversation_id = ?`** → 会取全表最大值（跨会话串号，比 1093 严重得多）；
2. `seq_no INT NOT NULL DEFAULT 0`（`sql.sql:611`）→ 空集合时 `MAX+1 = NULL` → **1048 非空违反**。

现状是 Java 侧读改写（`MemoryService.java:100-113` + `:131-140`），所以**"先锁会话行再取号"才是正解**：`SELECT … FROM ai_conversation WHERE id=? FOR UPDATE` → `COALESCE(MAX(seq_no),0)+1`（带 `WHERE conversation_id=?`）→ 插入。会话内串行本就是期望语义。

### 4.4 派生计数

`PostInteractionService.java:59-63` 的绝对 `COUNT(*)` 重算**保留**（自愈），但按 `§2.2` 的形态 A/B 执行；绝对 `SET` 只应出现在请求路径的**加锁串行段**内或对账任务里。

## 6. 批量写与后台 CRUD

1. **一次多行，不要 N 次单行**：全仓 JDBC URL 无 `rewriteBatchedStatements`。注意它**只重写 INSERT**；UPDATE/DELETE 批处理的可行做法见 `03` §3.1（`ExecutorType.BATCH` 单独用仍要 N 次往返，正解是单条 `CASE` 多行 UPDATE）。
2. **⚠ 但"逐条改批量"不总等价 —— 已发现一处会算错**（第二版的建议错）：`/admin/posts/batch/permanent` 的图片计数递减在 `PostsAdminService.java:339-341`、`:379-381` **按 URL 循环**调 `decrementImageUsageCountByUrl`（`ImagesService.java:186`，每次 1 SELECT + 1 UPDATE）。改成 `WHERE url IN (…)` 一条**会造成 `usage_count` 当日不归零 + 孤儿文件与 COS 存储暂留**（**不是"永久"**：`02:55` 的 `ImageUsageReconcileService.java:47` 夜间 reset+重扫会自愈 —— 但依赖对账兜底不等于批量化写对，且对账前孤儿窗口真实存在），因为 `collectPostImageUrls`（`:391-401`）**不去重** —— cover==thumbnail、正文同图两次、批量删多篇共用一张图，都会让同一 URL 出现 N 次，循环减 N 次而 `IN` 只减 1 次；且 SELECT 侧还带 `status = 1` 过滤（`ImagesService.java:172`）会静默跳过。
   **正解是复用已有实现**（`跨服务规范.md` 铁律"先复用，再造"）：`ImageReferenceService.removeReferences(urls)`（`service/ImageReferenceService.java:49-56`，内部 `countUrls` **按出现次数聚合** —— 注意 `applyDelta` 仍是逐 URL 循环，所以复用它的收益是**计数正确**，不是减少往返）。若必须自己写批量 UPDATE，要按 `path → delta` 逐条 `CASE`，不能 `IN` 一刀切。
3. **分批提交**：每 200~500 行一个事务，别一整个大事务。
4. **失效按批次一次**（配合 `§5` 的 `afterCommit`）；**不要指望"版本号键"简化这件事** —— 该方案已在 `05` §8 被推翻。
5. **上限钳制**：`ids.size() ≤ 500`，超出返回 400（在 `ErrorCode` 对应区间加项）。
6. **不可逆操作与外部调用解耦**：`05` §5 的 outbox（需新建表，仓库无任何 job/task/outbox 表可复用，已 grep 确认）。

## 8. 陷阱与约束

- **`POST` 改 `PUT` 是契约变更，影响面已量化**：后端 `PostsControllerTest.java:189,200,231` 断言返回 `"liked"`/`"unliked"`/`"favorited"`，且用 `new PostsController(...)`（`:36`）手工构造；前端调用点**只有 2 处** —— `Web/src/services/post.ts:391`（like）与 `:405`（favorite），`Admin` 侧**零调用**（`Admin/src/services/posts.ts:227` 是后台"谁收藏了这篇文章"的另一个端点，不受影响）。前端 http 封装已有 `put`（`Web/src/services/api.ts:168`），所以改造成本比预想的低：**2 个前端函数 + 3 条测试断言**。三层门禁见 `06` §7。
- **MP 会悄悄改写你的 UPDATE**：`@TableLogic`/全局 `logic-delete-field` 使 Wrapper 类语句自动追加 `deleted_at IS NULL`（`application.yml:63-65`、`BaseEntity.java:47-48`）→ **任何"要写 `deleted_at` 本身"的操作都必须走裸 XML**，否则静默无效（§2.3 就是实例）。反过来说，裸 XML 也不自动过滤，`AND deleted_at IS NULL` 要自己写（§2.2）。
- **`INT UNSIGNED` 列禁止做减法增量**：`like_count`/`favorite_count`/`usage_count` 都是无符号（`sql.sql:112-113,502`）→ 1690；`users.points` 是 `DECIMAL(12,2)` 有符号，条件扣减才安全。
- **`checkinDate` 的"今日"依赖时区**：JDBC URL 写死 `serverTimezone=GMT+8`（`docker-compose.yml:32`），MySQL 容器未设 TZ。改并发方案前先确认日期来自 DB `CURDATE()` 还是 JVM `LocalDate.now()`，否则并发修复会顺带改变业务边界。
- 物理删除类端点不可逆；并发重复物理删除可能因外键顺序报 500（`GlobalExceptionHandler` 的 DB 异常分支返回 500 而非业务码）。
- **不要在开发分支上直接对生产库跑 §6 的批量删除回归** —— 它们是 `permanent` 语义，且会连带删评论/点赞/收藏（`PostsAdminService.java:314-381`）。
