## 统一事件

写作只发送 `event: writing-event`。`data` 中是版本信封，不是正文字符串：

```json
{"version":1,"requestId":"本轮唯一ID","sequence":1,"timestamp":1791000000000,"type":"started","data":{"model":"deepseek-ai/DeepSeek-V3.2","mode":"writing","baseRevision":"原稿SHA256","contentMode":"patch"}}
```

`sequence` 从 1 开始，每帧严格加 1；写作活动、正文、心跳和终态共用序号，同一发送临界区保证线序。`requestId` 隔离请求，`baseRevision` 是完整原稿 UTF-8 的 SHA-256。写作不启用聊天表情或 TTS。聊天接口仍使用原有事件。

| type | data | 语义 |
| --- | --- | --- |
| `started` | `model/mode/baseRevision/contentMode` 等 | 请求受理、实际模型与原稿版本 |
| `activity` | `activityId/stage/status/message/startedAt`，结束时 `finishedAt/durationMs`，可有 `toolName` | 服务端真实操作 |
| `delta` | `content` | 模型可见回复增量；不直接修改正文 |
| `proposal` | 字段建议，可有 `fields` | 仅暂存预览 |
| `references` | `items/reason` | 核验后的文章引用 |
| `heartbeat` | `timestamp` 等 | 保活，不证明模型已经完成 |
| `completed` | `responseLength/mode` 等 | 整轮成功，仍需管理员明确采纳 |
| `failed` | `error` 或 `message` | 失败终态，本轮不可采纳 |

客户端校验版本、请求 ID、序号、事件结构及成功终态。坏 JSON、漏帧、跨请求混入、断流、取消、错误后迟到成功均不能使建议变为可采纳。终态或协议错误立即取消读流并释放连接，不等待EOF，不自动重发 POST。客户端保留旧事件解析兼容，同一请求不得混用两种协议；新版本新增contentMode和严格信封，后端、Web、Admin应共同更新。

## 真实活动

活动状态为 `running/completed/failed/cancelled`；同名工具每次有独立 `activityId`，不再按工具名推测配对。时长来自单调时钟，开始/结束时间为 Unix 毫秒。

| stage | 触发点 |
| --- | --- |
| `reading_draft` | 准备完整草稿和配置预算 |
| `thinking` | 每轮真实模型调用 |
| `reading_article` | 文章资料工具起止 |
| `reading_categories` | 分类列表工具起止 |
| `reading_tags` | 标签列表工具起止 |
| `editing_content` | 收到正文修改工具名开始准备参数；工具实际生成补丁 |
| `updating_fields` | 生成标题、摘要、分类、标签建议 |
| `validating` | 完整结束后校验模式、结果与原稿定位 |
| `ready` | 本轮结果就绪或检查后无需修改 |

`thinking` 表示模型请求处理中，不是内部思维内容，也没有虚构的独立“理解已完成”步骤。AI 只提出新分类/标签建议；用户确认后的真实创建由父编辑器执行，在同一界面追加本地创建活动，不声称模型已经创建或保存文章。

## 正文两种模式

页面上下文 `contentMode` 仅接受 `patch/replace`。未提供时，有正文默认 `patch`，空稿默认 `replace`。`requestedFields` 仍约束修改范围；`check` 禁止修改工具。标题、摘要等仍用 `applyArticleUpdate`。

```text
patch：完整原稿 → 模型只生成需要修改的 before/after → editArticleContent
       → 原子校验 → 成功终态前 proposal.contentPatch → 段落前后对照 → 明确采纳
replace：完整原稿或空稿 → 模型输出完整 HTML → 完整结束和 HTML 校验
         → proposal.contentHtml → 整文预览 → 明确采纳
```

局部建议形态：

```json
{"contentPatch":{"baseRevision":"原稿SHA256","edits":[{"before":"<p>原错误段落</p>","after":"<p>修正后的段落</p>"}]},"fields":["content"]}
```

- `before` 必须从本轮原稿逐字复制完整 HTML 段落，唯一匹配。重复段落可带相邻段落消除歧义，不进行模糊定位。
- 每轮最多 32 处；多次工具调用仍基于同一原稿，不能重叠。单次任意一处无效，整次不记录部分补丁。
- `after=""` 删除对应片段；续写以最后一段为锚点，替换内容保留它并追加新段落。
- 完整标签和安全片段分别校验，禁止半截标签、属性内部定位、脚本或改动既有媒体为未知资源。局部编辑不重新净化原稿其他片段。
- `editArticleContent(edits=[])` 明确表示已检查且无须修改，成功结束但不生成空补丁预览。
- `contentHtml` 与 `contentPatch` 互斥。局部模式不把普通文本或模型误输出的全文当成正文替换。
- 总正文仍受 200000 字符及配置模型输入预算限制；局部编辑节省的是模型输出，不免除读取原稿的输入成本。

## 前端采纳与撤销

`writingSession.ts` 在两个 Vite 根镜像，Web/Admin 页面只提供草稿、请求封装和应用回调。历史最多末 7 轮（14 条），成功轮次保存简短操作摘要，不把整篇 HTML 重复放入历史；仅工具结果无自然语言也记录该轮。

补丁按请求前快照定位，`baseRevision` 与开始事件一致；片段唯一、无重叠，`after` 先净化再精确拼合原稿。父编辑器再次从原始快照验证，避免仅凭补丁标记跳过安全边界。未修改的原稿片段、空白、格式和媒体保留；只预览改动段落。

采纳需完整成功、存在修改、尚未采纳、当前草稿完整签名仍等于原稿。用户中途编辑、换文章、停止或卸载时不接受旧结果。采纳仅更新编辑器；最近一轮原稿供整轮/字段撤销，实际保存和发布仍使用业务按钮。详见[后台管理](../../前端/后台管理/总览.md#写作助手)。

## 陷阱与约束

- 首次“读取草稿”只说明服务器准备了输入；只有实际模型调用可展示模型处理中。
- 结构化字段建议可早于模型终态，但只暂存。正文补丁仅在整轮正常完成后下发。
- 相同内容的多处段落必须扩展唯一锚点，不能随意猜第几处。
- 创建分类/标签成功不代表文章已经保存；撤销草稿字段不删除已创建的数据库分类/标签。
- 镜像校验包含 `sse.ts/writingStream.ts/writingReview.ts/writingSession.ts` 四对，运行 `node scripts/check-mirrored-modules.mjs`。
