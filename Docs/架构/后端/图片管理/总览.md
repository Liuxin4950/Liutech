# 图片管理架构总览

> 图片的上传、去重、压缩、存储、引用计数与清理。读完本文能看懂一张图从「粘贴进编辑器」到「被 N 篇文章引用」再到「无人引用被清理」的完整生命周期。

## 模块职责

图片是博客最重的资源类型：TinyMCE 粘贴上传、跨文章复用、管理端统计与清理。本模块解决三件事：

1. **存得下**：上传 → 校验 → 压缩 → 存入存储层（`FileStorage` 双实现：本地磁盘默认 / 腾讯云 COS 按 `cos.enabled` 切换，详见[存储抽象](存储抽象.md)）
2. **不重复**：按文件内容哈希（SHA-256）去重，相同图片全局只存一份，跨用户共享
3. **数得清**：每张图维护引用计数 `usage_count`（多少篇文章/封面/头像在用它），每日定时全量对账纠偏，管理端可凭计数安全清理

## 核心机制一图流

```
TinyMCE 粘贴/选择图片
  └→ FileUploadController.uploadImageForTinyMCE（ADMIN 校验）
      └→ FileUploadService.uploadImage（用户/类型/大小校验）
          └→ ImagesService.uploadImage【去重 + 压缩 + 入库】
              ├─ 哈希命中已有图片 → 直接返回旧记录（不存新文件）
              └─ 未命中 → 压缩 → FileStorage.save → DB 插入（usage_count=0）

文章发布/编辑/删除
  └→ PostsService → ImageReferenceService【引用计数唯一入口】
      └→ images.usage_count ±N

每日 02:55
  └→ ImageUsageReconcileService.reconcileUsageCount【对账：全量重数一遍】

管理端
  └→ ImagesAdminService（软删/物理删/孤立清理/引用溯源，都看 usage_count）
```

## 陷阱与约束

- 数据库 `file_path` 存**逻辑路径**（`images/2026/08/05/xxx.jpg`），`file_url` 存 `generateUrl` 输出（本地=`/uploads/...` 相对路径，COS=完整 URL），两种形态 `FileUtil` 归一化后等价
- `usage_count` 是**软计数**：日常增量维护，每日 02:55 全量对账兜底——不要依赖它在两次对账之间绝对精确
- 软删除文章/图片**不**减 usage_count（对账会修正），物理删除才需要计数为 0
- 图片去重按文件内容哈希，跨用户共享同一文件；删除时影响所有引用者（管理端有引用警告）
- 孤立清理排除最近 24 小时上传的图片，避免误删"粘贴了还没保存"的图
- 跨服务约束（上传路径绑定、URL 策略）见 [Docs/记录/当前架构.md](../../../记录/当前架构.md)，不在此重复
