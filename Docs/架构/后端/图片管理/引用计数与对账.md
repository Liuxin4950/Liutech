# 引用计数与对账

> 每张图片的 `usage_count` =「现在有多少个地方在用它」。机制分两层：**日常增量维护**（谁引用谁增减）+ **每日全量对账**（凌晨重数一遍，纠偏兜底）。对账是本设计的保险丝——增量记错了不要紧，第二天自动修正。

## 计数怎么记

`usage_count` 不是"上传次数"，是**引用点数**：

- 文章封面 = 1 点，文章缩略图 = 1 点，正文里每个 `<img src="/uploads/...">` = 1 点（同一张图出现 N 次计 N）
- 用户头像 / 音乐封面 / 轮播图 / 系列封面各计 1 点
- 上传/去重本身不计数（图还没被任何内容引用）

所有增减**必须**走 [\`ImageReferenceService\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/service/ImageReferenceService.java)，业务方只传 URL 列表：

| 方法 | 场景 |
| --- | --- |
| `addReferences(urls)` | 新增引用（如创建文章、改头像） |
| `removeReferences(urls)` | 移除引用（如删除音乐、清封面） |
| `syncReferences(oldUrls, newUrls)` | 编辑替换（按差量增减，如编辑文章换图） |
| `countByPath(urls)` | 对账统计（URL → 逻辑路径 → 次数，多种 URL 写法归并） |

内部流程：URL → `FileUtil.normalizeToRelativePath` 归一成逻辑路径（全项目唯一口径，三份重复实现已收敛）→ 查 `images` 记录 → `usage_count ± delta`（`GREATEST(0, ...)` 防负）。

**畸形双重前缀容错**：粘贴来源可能带 `https://系统域https://COS域/...` 的脏 URL（外部复制内容），归一化时若常规提取失败，仅当尾段 host 属于系统域名（SERVER_BASE_URL/COS_BASE_URL 的 host 及 www 变体）才剥离前缀继续提取，外部站点绝对 URL 不受影响。见 `FileUtil.normalizeToRelativePath` 与 `extractPathFromMalformedUrl`。

**哪些地方在调它**（都是"内容里出现图片 URL"的写操作）：

- 文章：创建/编辑时收集封面+缩略图+正文图片（[\`PostsService.java:377\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/service/PostsService.java)）
- 音乐封面、轮播图、用户头像、系列封面：增删改时

## 每日对账：保险丝

`ImageUsageReconcileService.reconcileUsageCount`（每天 02:55，cron 可配）：

1. `resetUsageCount`：全部 `usage_count` 清零
2. 扫描全库引用源（文章封面/缩略图/正文、头像、音乐/轮播/系列封面），用 `countByPath` 统计每个逻辑路径被引用的次数
3. 按统计结果逐条重建计数（500 条一批）

对账的存在让「软删除不减计数」这种偷懒成为安全设计：即使日常计数算错了、漏了，第二天全量重建。

## 管理端操作（都看 usage_count）

| 操作 | 行为 |
| --- | --- |
| 软删除 | 有引用时警告「被 N 篇文章引用」；只标 `deleted_at`，不删文件、不改计数 |
| 物理删除 | 删文件 + 删记录（需自行确认无人引用） |
| 孤立图片列表 | `usage_count=0` 且未删除的图 |
| 孤立清理 | 物理删除孤立图；**排除最近 24h 上传的**（保护粘贴后还没保存的图） |
| 引用溯源 | 按图片路径 LIKE 扫五张表（文章/用户/轮播/音乐/系列），列出具体引用位置 |

入口：[\`ImagesAdminService.java\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/service/ImagesAdminService.java)（软删 `:110`、物理删 `:192`、清理 `:252`、溯源 `:305`）。

## 陷阱与约束

- 软删除文章/图片不减计数——`usage_count` 可能在两次对账之间虚高，管理端的引用警告数字是"上次对账/上次操作后"的值
- `GREATEST(0, usage_count + delta)` 会静默钳制负数：如果某次多减了，计数失真，靠对账修正
- 对账只统计已落库的内容；「上传了但文章没保存」的图计数为 0，会被孤立清理盯上（24h 保护已挡住窗口期）
- 路径归一化必须走 `FileUtil.normalizeToRelativePath`，新写统计逻辑不要自己解析 URL
