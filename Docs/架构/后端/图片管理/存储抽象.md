# 存储抽象

> 为未来接入对象存储（OSS）预留的插槽。核心思想一句话：**业务代码只认逻辑路径（`images/2026/08/05/xxx.jpg`），不碰文件系统；存哪、URL 长什么样，由存储实现决定。**

## 接口

[\`FileStorage.java\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/FileStorage.java) 四个方法，正好覆盖一个文件的完整生命周期：

| 方法 | 做什么 | 调用方 |
| --- | --- | --- |
| `save(data, subPath, filename)` | 存文件，返回**逻辑路径**（目录结构由实现决定） | 上传图片/文档/资源/音频 |
| `delete(relativePath)` | 删文件（不存在视为成功） | 删除附件/音乐/清理孤立图 |
| `exists(relativePath)` | 判断是否存在 | 备用 |
| `generateUrl(relativePath)` | 生成访问 URL | 上传响应、引用计数 |

**约定**：数据库存逻辑路径，**URL 永远现场生成、不落库**。这样换存储后端时数据库零迁移。

## 当前实现：本地磁盘

[\`LocalFileStorage.java\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/LocalFileStorage.java)：

- 路径结构：`<subPath>/yyyy/MM/dd/<timestamp>_<uuid>.<ext>`（按天分目录）
- `generateUrl` 返回相对路径 `/uploads/...`，由前端代理（dev vite proxy / 生产 nginx）转发到后端——数据库记录与环境无关（详见 [Docs/记录/当前架构.md](../../../记录/当前架构.md)）
- 根目录：`FILE_UPLOAD_BASE_PATH` 环境变量 > `file.upload.base-path` 系统属性 > 默认 `./uploads`

## 未来接 OSS

新写一个 `OssFileStorage implements FileStorage`，替换 Bean 即可：

- `save` → 上传对象（subPath + 日期目录作为对象键前缀）
- `delete` → 删除对象
- `generateUrl` → 返回 CDN 完整 URL（如 `https://cdn.liuxin.chat/images/...`）

数据库里的逻辑路径不变，前端拿到什么 URL 由 `generateUrl` 决定，引用计数/对账/溯源全部无感。唯一注意：`extractRelativePath` / `normalizeToRelativePath` 解析 URL 时依赖 `SERVER_BASE_URL` 前缀（见 [\`FileUtil.java:161\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/utils/FileUtil.java)），接 OSS 后需确认该配置与新 URL 形态匹配。

## 陷阱与约束

- 不要在业务代码里直接用 `Files`/`Paths` 读写上传文件——必须走 `FileStorage`，否则切 OSS 时会漏
- URL 生成只有存储层一处，`FileUtil.generateFileUrl` 已废弃（历史代码如已迁移）
- 音频/文档/资源也走同一个 `FileStorage`（OSS 后全部一起切）
