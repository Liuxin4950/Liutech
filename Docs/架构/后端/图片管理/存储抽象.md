# 存储抽象

> 为未来接入对象存储（OSS）预留的插槽。核心思想一句话：**业务代码只认逻辑路径（`images/2026/08/05/xxx.jpg`），不碰文件系统；存哪、URL 长什么样，由存储实现决定。**

## 接口

[\`FileStorage.java\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/FileStorage.java) 四个方法，正好覆盖一个文件的完整生命周期：

| 方法 | 做什么 | 调用方 |
| --- | --- | --- |
| `save(data, subPath, filename)` | 存文件，返回**逻辑路径**（目录结构由实现决定） | 上传图片/文档/资源/音频 |
| `delete(relativePath)` | 删文件（不存在视为成功） | 删除附件/音乐/清理孤立图 |
| `exists(relativePath)` | 判断是否存在 | 备用 |
| `generateUrl(relativePath)` | 生成访问 URL | 上传响应、引用计数 |
| `open(relativePath)` | 打开文件内容（返回流） | 付费资源下载（鉴权后由后端转发，不直出） |

**约定**：`images` 表 `file_url` 列存的是 **generateUrl 的输出（访问 URL）**——本地模式为相对路径 `/uploads/...`，COS 模式为完整 URL；`file_path` 列单独存**逻辑路径**（如 `images/2026/08/05/xxx.jpg`），与环境无关，换存储后端时零迁移。所有 URL 解析统一走 `FileUtil` 归一化，两种形态等价。

## 当前实现：本地磁盘

[\`LocalFileStorage.java\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/LocalFileStorage.java)：

- 路径结构：`<subPath>/yyyy/MM/dd/<timestamp>_<uuid>.<ext>`（按天分目录）
- `generateUrl` 返回相对路径 `/uploads/...`，由前端代理（dev vite proxy / 生产 nginx）转发到后端——数据库记录与环境无关（详见 [Docs/记录/当前架构.md](../../../记录/当前架构.md)）
- 根目录：`FILE_UPLOAD_BASE_PATH` 环境变量 > `file.upload.base-path` 系统属性 > 默认 `./uploads`

### `/uploads/` 是什么：反代挂载点，不是文件路径

`/uploads/images/2026/08/05/xxx.jpg` 拆开看是两段：

```
/uploads/ ─────────────── 反代挂载点
   浏览器请求它 → nginx/vite proxy 转发到后端 → 后端按后续路径读磁盘文件
images/2026/08/05/xxx.jpg ── 逻辑路径（数据库存的就是这段）
```

关键认知：数据库的 `file_url` 列存的是 `generateUrl` 的**输出**——本地模式是 `/uploads/images/...`（相对路径），COS 模式是完整 URL；**真正的逻辑路径 `images/2026/08/05/xxx.jpg` 单独存 `file_path` 列**。`/uploads/` 只是"本地磁盘需要后端代理来喂文件"这个部署形态的产物——浏览器不能直接读服务器磁盘，必须经后端。所以：

- 换存储后端（OSS）时逻辑路径一个字不变，数据库零迁移
- 接 OSS 后 CDN 直接出文件，`uploads` 挂载点自然消失（不再需要后端转发）
- 想让 URL 保持 `/uploads/...` 形式也可以：CDN 域名映射 `/uploads/*` 即可，`generateUrl` 是唯一决定 URL 形态的地方

## 当前实现二：腾讯云 COS（已落地）

[\`CosFileStorage.java\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/CosFileStorage.java) 实现 `FileStorage`，与本地磁盘**二选一**：

- `cos.enabled=true`（环境变量 `COS_ENABLED`）→ 注册 `CosFileStorage`
- 否则（默认）→ 注册 `LocalFileStorage`（`@ConditionalOnProperty` 互斥）

| 方法 | COS 实现 |
| --- | --- |
| `save` | `putObject`，对象键 = 逻辑路径（[\`StoragePathUtil\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/StoragePathUtil.java) 生成，目录结构与本地一致，**数据库零迁移**） |
| `delete` | `deleteObject`（COS 删除不存在的对象不报错，符合约定） |
| `exists` | `doesObjectExist` |
| `generateUrl` | `https://<bucket>.cos.<region>.myqcloud.com/<逻辑路径>`（COS 默认域名直出，流量不过服务器） |

配置走环境变量（.env）：`COS_ENABLED` / `COS_SECRET_ID` / `COS_SECRET_KEY` / `COS_REGION` / `COS_BUCKET`，真实密钥只放本地 .env（gitignore），不入库。

**URL 解析兼容**：`FileUtil.extractRelativePath` / `normalizeToRelativePath` 已支持 COS 直出 URL（[`FileUtil.java:119`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/utils/FileUtil.java)）；`extractImageUrls` 的图片归属判断统一走「能归一化为逻辑路径 = 系统图片」这一口径（`isSystemImageUrl`），引用计数/对账/溯源对两种存储形态无感，不再散落前缀判断。

**桶权限**：需设为**公有读**（只读，写入仍需密钥签名）。以后要 CDN 加速：配好 CDN 域名后改 `CosStorageProperties.getBaseUrl()` 一处即可。

### 切换与迁移（CosMigrateRunner）

顺序不能乱，先迁后切：

1. `.env` 设 `COS_MIGRATE=true` 重启 → [\`CosMigrateRunner\`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/storage/CosMigrateRunner.java) 把本地 uploads 全量传 COS（对象键 = 相对路径，与数据库一致；已存在自动跳过，失败可重跑）
2. 日志出现「COS 迁移完成」，确认 COS 文件齐全
3. `COS_ENABLED=true` 正式切换，移除 `COS_MIGRATE` 再重启
4. 旧本地文件保留兜底（nginx `/uploads` 代理仍在），稳定后可手动清理

## 陷阱与约束

- 不要在业务代码里直接用 `Files`/`Paths` 读写上传文件——必须走 `FileStorage`，否则切 COS 时会漏
- **读文件内容也走 `FileStorage.open`**：付费资源下载（[`ResourceDownloadService`](../../../../LiuTech/src/main/java/chat/liuxin/liutech/service/ResourceDownloadService.java)）已改为经存储层读流，COS 后资源仍在后端鉴权转发，不直出 URL；若从磁盘直读会 404
- URL 生成只有存储层一处，`FileUtil.generateFileUrl` 已废弃（历史代码如已迁移）
- 音频/文档/资源也走同一个 `FileStorage`（切 COS 后全部一起切）
- 切 COS 前必须先跑迁移（`COS_MIGRATE`），否则旧文件仍只在本地磁盘
- COS 桶须设公有读；私有桶 + 签名 URL 会过期，不适合博客图片
