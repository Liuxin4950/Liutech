# 上传与去重

> 图片从「粘贴进 TinyMCE」到「落盘 + 入库」的过程。核心是两个机制：**内容哈希去重**（相同图片只存一份）和**压缩/格式处理**（省空间 + 兼容性）。

## 上传链路

```
TinyMCE 粘贴/选择图片（blob，文件名如 blobid0.png 不可靠）
  → FileUploadController.uploadImageForTinyMCE     校验 ADMIN 角色
    → FileUploadService.uploadImage                校验用户存在/扩展名白名单/大小 ≤10MB
      → ImagesService.uploadImage                  去重 + 压缩 + 入库（核心）
```

一次上传最终产生三件事：文件进了存储层（`FileStorage.save`）、一条 `images` 记录（`usage_count=0`）、返回给前端相对路径 URL。

## 去重：内容指纹

思路和 Git 的对象存储一样：**文件内容就是身份**。

1. `fileUtil.calculateFileHash` 算整个文件的 SHA-256（流式，不占内存）
2. `imagesMapper.selectByHash` 查是否已有同哈希图片（条件：未软删 + `status=1`）
3. 命中 → 直接返回已有记录（`isDuplicate=true`），**不存新文件、不建新记录**——相同图片跨用户、跨文章全局共享

去重的代价是**删除影响面变大**：删一张图会同时影响所有引用它的人。所以管理端删除有引用警告（见[引用计数与对账](引用计数与对账.md)）。

## 压缩与格式处理

`ImageCompressService.compress` 按扩展名分三路：

| 输入 | 处理 | 说明 |
| --- | --- | --- |
| GIF | 原样保存 | 不压缩，避免丢动画 |
| 宽 > 1920px | 等比缩放 → JPEG | 控制大图体积 |
| PNG / BMP | 转 JPEG | 通常比 JPEG 大很多 |
| JPEG/WebP 等 | 原样保存 | 已是压缩格式 |
| 无法解码的图 | 降级原样保存 | 不阻塞上传（fail-open） |

### 两个关键坑（都修过）

**坑 1：RGBA 透明 PNG 转 JPEG 报 "Bogus input colorspace"**

JDK 的 JPEG 编码器不支持 alpha 通道。Word 文档里粘贴出来的图常是 RGBA PNG，`encodeJpeg` 直接写会抛 `Bogus input colorspace`（注意：报错在**编码端**，不是解码端）。修复：写 JPEG 前先把带 alpha 的图合成到白底 RGB（`ImageCompressService.java:108` 的 `encodeJpeg`）。

**坑 2：TinyMCE blob 文件名不可靠 + 解码失败中断上传**

- blob 名（`blobid0.png`）与实际字节可能不符（如字节是 JPEG）；保存前用 `FileUtil.detectImageFormat` 按文件头探测真实格式，扩展名以探测结果为准
- `ImageIO.read` 对 CMYK 等色彩空间的图会抛异常——已改为捕获后降级原样保存（浏览器本身能正常显示 CMYK JPEG）
