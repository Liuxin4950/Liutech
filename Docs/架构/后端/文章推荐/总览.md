# 文章推荐架构总览

> 首页右侧「推荐阅读」的个性化推荐链路：登录用户按浏览历史做分类+标签相似推荐，未登录/失败回退热门。读完能定位接口、打分 SQL 与前端回退逻辑。

## 模块职责

首页推荐文章的服务端能力。核心设计是**「浏览历史 → 兴趣画像 → 相似推荐」**：取用户浏览过的文章的分类与标签作为兴趣信号，给未读文章打分排序；数量不足用全局热门补足，保证推荐位永远有内容。接口需登录（个性化依赖用户数据），未登录由前端直接走热门，不产生额外请求。

数据源在 `LiuTech/`（复用 `user_view_history` 表，建表与记录链路见 [浏览历史](../浏览历史/总览.md)），消费方在 `Web/` 首页。

## 数据流概览

```
首页挂载 → loadRecommendedPosts
  │
  ├─ 未登录 → getHotPosts(5)                          ← 全局热门，无个性化
  │
  └─ 已登录 → GET /posts/recommendations?limit=5（Bearer token）
       │    接口失败（401/网络）→ .catch(() => null) → 回退 getHotPosts(5)
       ▼
  PostsService.getPersonalizedRecommendations(limit, userId)
       │  ① selectList(user_view_history)：取该用户已读文章 ID 集合（补足去重用）
       │  ② selectRecommendedPostListResp(limit, userId)：
       │       候选 = 已发布、未删除、未读过的文章
       │       得分 = 分类命中(+2) + 标签重合数(每命中一个 +1)
       │       排序 = 得分降序 → 热度(浏览量*0.3+点赞*0.4+收藏*0.3)降序 → 创建时间降序
       │       取前 limit 条（SQL 内子查询统计兴趣分类/标签）
       │  ③ 结果不足 limit → 查热门补足，跳过已读和已推荐（HashSet 去重）
       ▼
  List<PostListResp> → 首页右侧「推荐阅读」卡片（RecommendedPosts）
```

无浏览历史时：兴趣子查询为空集，所有候选得分为 0，② 退化为按热度排序 ≈ 热门；③ 兜底同样生效，推荐位不空。

## 陷阱与约束

- **认证白名单必须同步**：`/posts/recommendations` 落在 GET 公开前缀 `/posts/` 下，必须进 `SecurityWhitelist.AUTHENTICATED_PATHS`（99 行），否则主后端过滤器对公开路径跳过 JWT 验证、拿不到登录用户而永远返回 401。同类坑与机制详见 [浏览历史](../浏览历史/总览.md)、[认证授权](../认证授权/总览.md)
- **路由冲突**：`/posts/recommendations` 若后端未部署该接口，会被 `GET /posts/{id}` 吞掉，`id="recommendations"` 转 Long 失败报 400「参数[id]类型错误」。新接口上线必须同步部署主后端镜像（2026-08-16 曾因只部署前端漏掉 backend 踩坑）
- **补足必须去重**：热门补足时跳过「已读」（viewedIds 集合）和「已推荐」（existingIds 集合），否则推荐位出现用户刚看过的文章
- **回退静默**：前端个性化失败不回显错误（首页推荐是装饰位，失败静默回退热门，避免打扰阅读）
- **未登录不发请求**：`UserService.isLoggedIn()` 判断在前端完成，未登录直接走热门，不给后端发注定 401 的请求
- **缓存策略**：个性化结果按 userId 维度且随浏览行为实时变化，刻意不加 `@Cacheable`；热门兜底走既有 `hotPosts` 缓存
