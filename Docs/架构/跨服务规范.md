# 跨服务开发规范（LiuTech）

> 本文件是 LiuTech 两个后端服务（主后端 `LiuTech/`、AI 服务 `LiuTech-AI/`）**统一编码规范**的权威来源。
> 目的：消除「重复造轮子」「方法不统一」，让新代码、AI 协作改代码都能**遵循同一套约定**，不各搞一套。
> 所有规范点均标注权威实现文件，改代码前请先核对这些文件，**优先复用既有实现，不另起炉灶**。
> 与《Docs/记录/当前架构.md》（总体架构）、《Docs/架构/README.md》（模块导航）互补；本文档专注"**怎么写才对**"。

---

## 0. 两条铁律（所有代码必须遵守）

1. **先复用，再造**：实现任何横切能力（响应封装、异常、缓存、JWT、分页、错误码、日志）前，先搜索仓库里是否已有统一实现。**禁止**新建第二套同名/同职责的实现。
2. **两服务保持同一风格**：主后端已完成治理的规范，AI 服务新代码必须跟随主后端约定（构造器注入、Result/ErrorCode、声明式缓存），不要因"微服务隔离"就另起炉灶。**微服务隔离的是进程与数据库，不是编码风格。**

## 1. 响应统一规范（Response）

### 1.1 主后端（权威实现）

- **成功/失败统一用 `Result<T>`（不可用裸 Map / Object 返回）**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/common/Result.java`
  - 返回格式：`{ code, message, data }`
  - 成功：`Result.success(data)`、`Result.success()`、`Result.success(message, data)`
  - 失败：由业务抛 `BusinessException`，交给全局异常处理器统一返回，不要在 Controller 手拼错误响应。

- **错误码统一用 `ErrorCode` 枚举，不放魔法数字**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/common/ErrorCode.java`
  - 分段规范：
    - `200` 成功
    - `400-499` 客户端（参数/权限）
    - `500-599` 系统
    - `1000-1099` 用户、`1100-1199` 博客文章/分类/标签/系列、`1200-1299` 评论、`1300-1399` 点赞收藏、`1400-1499` 公告、`1500-1599` 留言、`1600-1699` 邮箱
  - 新增业务错误时，在本枚举内追加对应区间项，**不要**在 Service 里 `new Result(4001, "xxx")`。

- **所有异常统一由 `GlobalExceptionHandler` 兜底，Controller/Service 里不 try-catch 业务异常**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/common/GlobalExceptionHandler.java`
  - 已知处理：业务异常(400)、参数校验(400)、JSON格式错(400)、类型转换(400)、方法不支持(405)、404、上传超限(400)、数据库异常(500)、权限不足(403)、兜底(500)。

### 1.2 AI 服务（差异与边界）

- **现状（差异点）**：AI 服务返回 `{ success, message, code }`（code 为 HTTP 状态码），与主后端 `{ code, message, data }` **不一致**。
  - 权威实现：`LiuTech-AI/src/main/java/chat/liuxin/ai/infra/exception/GlobalExceptionHandler.java`
  - 前端已在 `Web/src/services/api.ts`（第 64-95 行）做了**双格式归一化**：检测到 `code/message/data` 走标准分支，检测到 `success` 走 AI 分支。所以前端层是通的。
- **边界裁定（刻意保留，不改）**：AI 服务是 **SSE 流式** 服务，其 `start/data/audio/complete` 流式事件协议、以及 SSE 异常处理（`response.isCommitted()` 时跳过 JSON 写入）是**刻意设计**，涉及前端 `AiChat.vue` 大量依赖，**不要一刀切改造成 Result**。
- **新规**：AI 服务的**非流式**接口（会话管理、模型列表等，非 SSE）优先沿用 AI 服务 `{success,message,code}` 约定（因为前端已适配），但**不要再增加第三种**响应结构。若未来要统一，走一次专项治理并同步 `api.ts`，禁止零散改动。

## 2. 依赖注入规范（构造器注入）

> ⚠️ 本节的基线『主后端全部构造器注入』**最初被我误报**。经逐点核验纠正如下（真实事实）：

- **普通业务层（Service）统一用构造器注入**：`@RequiredArgsConstructor` + `private final` 字段。
  - 依据：主后端 `PostsService:55`、`CategoriesService:29`、`TagsService:33`、`PointsService:29`、`CommentsService:38` 等均为该写法。**这是两服务业务层都要遵循的基线。**
  - 好处：依赖不可变、可 mock、无循环依赖隐患。**新增 Service 一律用构造器注入。**

- **例外（两服务共同惯例，不算违规）**：`@Autowired` 字段注入**仅允许**出现在安全/过滤器配置与需打破循环依赖的场景，且通常配 `@Lazy`：
  - 主后端：`config/SecurityConfig.java:45,48`、`filter/JwtAuthenticationFilter.java:42,45`、`config/MyMetaObjectHandler.java:26(@Lazy)`、`service/VerificationCodeService.java:43(@Lazy)`、`utils/UserUtils.java:32(@Lazy)`
  - AI 服务：`infra/config/SecurityConfig.java:44,47`、`infra/filter/JwtAuthenticationFilter.java:49`
  - 这类写法发生在 Security 过滤器链/配置注入点，两服务一致。

- **一个真正的改进点（非循环依赖的普通字段注入）**：AI 服务 `infra/config/SecurityConfig.java:47` 的 `ObjectMapper` 字段注入**并非** filter/循环依赖场景，本可构造器注入。**新代码不要在普通字段上再用 `@Autowired`**（指可构造器注入的普通依赖）。

## 3. 异常与日志规范

- **业务逻辑违反**：主后端抛 `BusinessException`（`common/BusinessException.java`）；AI 服务抛 `AIServiceException` 多级子类（连接/超时/模型/请求），语义不同但角色一致。**不要**在一个服务里混合使用对方服务的异常类型。
- **日志级别（两服务一致）**：
  - `log.info`：安全审计（登录/注册/改密/验证码/邮箱）、资产变动（积分增减/资源购买）、数据删除/不可逆操作、AI 模型增删改。**审计日志不可降级或删除。**
  - `log.debug` 或不打：高频读（首页/列表/查询/sitemap）、请求链路/认证。
  - `log.warn`：业务异常、慢请求(>1s)。
  - `log.error`：系统异常、数据库异常，附堆栈。
  - 生产 `root: INFO`，不要给业务包整体开 `DEBUG`（Spring AI 的 DEBUG 会打 prompt 明文，IO 开销大）。
- 用户可读错误消息：不暴露 SQL/堆栈等技术细节（见 `当前架构.md` 错误响应约定）。

## 4. 缓存规范

- **缓存统一用 Caffeine，声明式注解 `@Cacheable`/`@CacheEvict`/`@CachePut`**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/config/CacheConfig.java`（集中管理 9 个缓存：postList/hotPosts/latestPosts 5min、hotTags/allTags/announcements/userStats 10min、categories/postSeries 15min，均带 TTL 与容量）。
  - 新增数据缓存时：**先在 `CacheConfig` 里补一个缓存实例，再用注解**。禁止在 Service 里手写 `ConcurrentHashMap`/`Caffeine.newBuilder` 做数据缓存（登录失败计数等**有状态业务缓存**除外，如 `UserAuthService` 的 `LOGIN_FAILURE_COUNTS`）。
  - 变更数据后记得 `@CacheEvict` 失效对应缓存，避免脏读。
- **未引入 Redis，不要建议/编写 Redis 代码。**

## 5. JWT / 安全规范

- **两服务各自维护一份 `JwtUtil`，但签名逻辑必须一致**：
  - 主后端：`LiuTech/src/main/java/chat/liuxin/liutech/utils/JwtUtil.java`
  - AI 服务：`LiuTech-AI/src/main/java/chat/liuxin/ai/common/utils/JwtUtil.java`
  - 两者都使用 `Keys.hmacShaKeyFor(secretKey.getBytes())` + `Jwts.SIG.HS256`，`JWT_SECRET` 两服务必须完全一致。
  - **禁止**在其中一方复制对方的全套逻辑后改造成不同签名 key 来源；改动密钥解析方式必须两服务同步。

- **认证风格差异（合理但需知晓）**：
  - 主后端：纯 Spring Security 过滤器链 + `@PreAuthorize`（类级 `hasRole('ADMIN')`）。
  - AI 服务：`AiModelPolicy` + `AiRateLimitInterceptor` + `AiSecurityWebConfig`（filter + 限流拦截器），认证额外经 `AiModelPolicy` 限制可用模型。
  - 新增接口权限判断：主后端用 `@PreAuthorize`，AI 服务遵循其现有 filter/策略方式。**不要**在主后端手写 filter 做权限，也不要在 AI 服务里伪造 `@PreAuthorize` 语义。

## 6. 分层与包结构规范

### 6.1 主后端（权威）
- 包路径：`chat.liuxin.liutech.{controller/{admin,web}, service, mapper, model, common, config, aspect, filter, exception, req, resp, vo, storage, utils}`
- 调用链：`controller → service → mapper → model`
- Controller 只做「参数接收 → 调 Service → 返回 `Result`」，不写业务逻辑、不 try-catch、不手拼错误。
- DTO 区分：`req/`（入参）、`resp/`（出参）、`vo/`（视图）；`model/` 放实体。**不要**把 `req/resp/vo` 混进 model。
- Service 用 `@Transactional` 管理事务边界；`final` 字段。

### 6.2 AI 服务（差异点）
- 包路径：`chat.liuxin.ai.{controller/{,admin}, service/{,impl}, mapper, entity, dto, common/{client,mcp,tts,monitor,utils}, infra/{config,security,filter,exception,aspect}}`
- **差异点**：AI 服务用 `service/impl`（有 `AiChatServiceImpl` 等），主后端无 `impl` 后缀。这是既成差异，新增 AI 服务时**沿用现有 `impl` 约定**，不要混用两种风格一致化（避免无意义重构）。核心约束是「一个功能只有一个实现入口」，而非「必须/diss 用 impl」。

## 7. 命名规范

- **Java**：类/接口/枚举 PascalCase；方法/字段 camelCase；常量 `UPPER_SNAKE`；boolean 用 `is/has/can` 前缀。
- **SQL 表/列**：`snake_case`，主键 `id`，时间 `created_at/updated_at`，软删 `deleted`。
- **API 路径**：小写、`-` 或 `/` 分层，语义化；主后端管理接口带 `/admin/` 前缀。
- **前端**：组件 PascalCase、目录 kebab 或扁平按 `views/components/stores/services/router/composables/utils` 分层。

## 8. 改代码前置检查清单（AI 协作强制项）

> 这组检查是对「AI 不了解架构就动手、重复造轮子」的直接约束。任何改代码任务开始前，依次确认：

```text
[  ] 1. 搜索仓库：我要实现的能力是否已有统一实现？（Result/ErrorCode/缓存配置/JwtUtil/GlobalExceptionHandler…）
[  ] 2. 分层归位：改动落在正确层次？Controller 不写业务，Service 不拼响应，DTO 进 req/resp/vo。
[  ] 3. 注入方式：用构造器注入，不新增 @Autowired/@Resource 字段注入。
[  ] 4. 缓存：数据缓存走 CacheConfig + 注解，不手写本地 Map 缓存，不引入 Redis。
[  ] 5. 异常与错误：业务违反抛项目异常（主后端 BusinessException / AI AIServiceException），不 try-catch 业务异常，不改用对方服务异常类型。
[  ] 6. 日志：按第 3 节级别打日志，审计日志不删不降级。
[  ] 7. 跨服务密钥：JWT_SECRET / TTS_PROXY_INTERNAL_TOKEN 两服务一致；改密钥解析要两服务同步。
[  ] 8. 文档：改动触达模块，需同步《Docs/架构/README.md》索引或对应模块「总览.md」。
```

## 9. 当前差异与待办清单（2026-08 核验）

| 项 | 主后端 | AI 服务 | 状态 |
|---|---|---|---|
| 响应结构 | `{code,message,data}` `Result` | `{success,message,code}` SSE/Map | 边界内，保留 |
| 错误码 | `ErrorCode` 枚举分段 | `AIServiceException` 多级 | 合理隔离 |
| 注入方式 | 业务层构造器注入；安全/配置处 `@Lazy` 字段注入 | 同主后端（业务层构造器注入；安全/配置处字段注入） | 一致 ✅ |
| 缓存 | 9 个 Caffeine 声明式 | 无缓存配置 | 边界内（AI 少读缓存） |
| JWT | `utils/JwtUtil.java` | `common/utils/JwtUtil.java` | 逻辑一致，各自维护 |
| Service 分层 | 无 impl 后缀 | `service/impl` | 既成，沿用 |
| 认证 | Spring Security 链 | filter+策略+限流 | 合理隔离 |

> 原「注入方式待统一」结论**经复核为误报**：两服务普通业务层都用构造器注入，安全/过滤器配置处都用 `@Lazy` 字段注入，风格一致。唯一改进点是 AI 服务 `SecurityConfig:47` 的 `ObjectMapper` 属非循环依赖的普通字段注入，可顺手改构造器注入，但不紧急。
