# 跨服务开发规范（LiuTech）

> 本文件是 LiuTech 两个后端服务（主后端 `LiuTech/`、AI 服务 `LiuTech-AI/`）**统一编码规范**的权威来源。
> 目的：消除「重复造轮子」「方法不统一」，让新代码、AI 协作改代码都能**遵循同一套约定**，不各搞一套。
> 所有规范点均标注权威实现文件，改代码前请先核对这些文件，**优先复用既有实现，不另起炉灶**。
> 总体关系见[架构总览](总览.md)，模块实现见[架构索引](README.md)。本文件定义编码与边界规范；已知存量差距见[维护清单](../维护清单.md)。

---

## 0. 两条铁律（所有代码必须遵守）

1. **先复用，再造**：实现任何横切能力（响应封装、异常、缓存、JWT、分页、错误码、日志）前，先搜索仓库里是否已有统一实现。**禁止**新建第二套同名/同职责的实现。
2. **两服务保持同一风格**：主后端已完成治理的规范，AI 服务新代码必须跟随主后端约定（构造器注入、Result/ErrorCode、声明式缓存），不要因"微服务隔离"就另起炉灶。**微服务隔离的是进程与数据库，不是编码风格。**

## 1. 响应统一规范（Response）

### 1.1 主后端（权威实现）

- **成功/失败统一用 `Result<T>`（不可用裸 Map / Object 返回）**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/common/Result.java`
  - 返回格式：`{ code, message, data }`
  - 成功：`Result.success(data)`、`Result.success()`、`Result.success(message, data)`
  - 失败：由业务抛 `BusinessException`，交给全局异常处理器统一返回，不要在 Controller 手拼错误响应。

- **错误码统一用 `ErrorCode` 枚举，不放魔法数字**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/common/ErrorCode.java`
  - 分段规范：
    - `200` 成功
    - `400-499` 客户端（参数/权限）
    - `500-599` 系统
    - `1000-1099` 用户、`1100-1199` 博客文章/分类/标签/系列、`1200-1299` 评论、`1300-1399` 点赞收藏、`1400-1499` 公告、`1500-1599` 留言、`1600-1699` 邮箱
    - `1700-1799` 社区 AI 角色、上下文版本、额度、链路与冷却
  - 新增业务错误时，在本枚举内追加对应区间项，**不要**在 Service 里 `new Result(4001, "xxx")`。

- **所有异常统一由 `GlobalExceptionHandler` 兜底，Controller/Service 里不 try-catch 业务异常**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/common/GlobalExceptionHandler.java`
  - 已知处理：业务异常(通常400，通用NOT_FOUND为404)、参数校验(400)、JSON格式错(400)、类型转换(400)、方法不支持(405)、404、上传超限(400)、数据库异常(500)、权限不足(403)、兜底(500)。

### 1.2 AI 服务（差异与边界）

- **现状（差异点）**：AI 错误 JSON 通常返回 `{ success, message, code }`；成功响应按既有 Controller 保留对象、数组、文本或空体，不统一假定含 `data`。完整契约见[接口参考](后端/AI服务/接口参考.md)。
  - 权威实现：`LiuTech-AI/src/main/java/chat/liuxin/ai/infra/exception/GlobalExceptionHandler.java`
  - 前端已在 `Web/src/services/api.ts`（第 64-95 行）做了**双格式归一化**：检测到 `code/message/data` 走标准分支，检测到 `success` 走 AI 分支。所以前端层是通的。
- **边界裁定（刻意保留，不改）**：AI 服务是 **SSE 流式** 服务，其 `start/data/audio/complete` 流式事件协议、以及 SSE 异常处理（`response.isCommitted()` 时跳过 JSON 写入）是**刻意设计**，涉及前端 `AiChat.vue` 大量依赖，**不要一刀切改造成 Result**。
- **新规**：AI 非流式接口沿用对应领域的既有成功与失败契约，不另建通用包裹。若要统一，需专项治理并同步 `api.ts` 与接口参考。

## 2. 依赖注入规范（构造器注入）

普通业务层以构造器注入为基线；安全装配与循环依赖边界按下列例外处理。

- **普通业务层（Service）统一用构造器注入**：`@RequiredArgsConstructor` + `private final` 字段。
  - 依据：主后端 `PostsService:55`、`CategoriesService:29`、`TagsService:33`、`PointsService:29`、`CommentsService:38` 等均为该写法。**这是两服务业务层都要遵循的基线。**
  - 好处：依赖不可变、可 mock、无循环依赖隐患。**新增 Service 一律用构造器注入。**

- **例外（两服务共同惯例，不算违规）**：`@Autowired` 字段注入**仅允许**出现在安全/过滤器配置与需打破循环依赖的场景，且通常配 `@Lazy`：
  - 主后端：`config/SecurityConfig.java:45,48`、`filter/JwtAuthenticationFilter.java:42,45`、`config/MyMetaObjectHandler.java:26(@Lazy)`、`service/VerificationCodeService.java:43(@Lazy)`、`utils/UserUtils.java` 的 @Lazy 构造器参数
  - AI 服务：`infra/config/SecurityConfig.java` 的安全过滤器装配
  - 这类写法发生在 Security 过滤器链/配置注入点，两服务一致。

- **一个真正的改进点（非循环依赖的普通字段注入）**：AI 服务 `infra/config/SecurityConfig.java:47` 的 `ObjectMapper` 字段注入**并非** filter/循环依赖场景，本可构造器注入。**新代码不要在普通字段上再用 `@Autowired`**（指可构造器注入的普通依赖）。

## 3. 异常与日志规范

- **业务逻辑违反**：主后端抛 `BusinessException`（`common/BusinessException.java`）；AI 服务抛 `AIServiceException` 多级子类（连接/超时/模型/请求），语义不同但角色一致。**不要**在一个服务里混合使用对方服务的异常类型。
- **日志级别（两服务一致）**：
  - `log.info`：安全审计（登录/注册/改密/验证码/邮箱）、资产变动（积分增减/资源购买）、数据删除/不可逆操作、AI 模型增删改。**审计日志不可降级或删除。**
  - `log.debug` 或不打：高频读（首页/列表/查询/sitemap）、请求链路/认证。
  - `log.warn`：业务异常、慢请求(>1s)。
  - `log.error`：系统异常、数据库异常，附堆栈。
  - 生产 `root: INFO`，不要给业务包整体开 `DEBUG`（Spring AI 的 DEBUG 会打 prompt 明文，IO 开销大）。
- 用户可读错误消息不暴露 SQL/堆栈等技术细节，错误响应遵循本文件第 1 节，前端提示规则见[网络封装](设计/网络封装/总览.md)。

## 4. 缓存规范

- **缓存统一用 Caffeine，声明式注解 `@Cacheable`/`@CacheEvict`/`@CachePut`**
  - 权威实现：`LiuTech/src/main/java/chat/liuxin/liutech/config/CacheConfig.java`（集中管理业务缓存与 userIdentity 身份映射：postList/hotPosts/latestPosts 5min、hotTags/allTags/announcements/userStats/aboutPage 10min、categories/postSeries 15min，均带 TTL 与容量）。
  - 新增数据缓存时：**先在 `CacheConfig` 里补一个缓存实例，再用注解**。禁止在 Service 里手写 `ConcurrentHashMap`/`Caffeine.newBuilder` 做数据缓存（登录失败计数等**有状态业务缓存**除外，如 `UserAuthService` 的 `LOGIN_FAILURE_COUNTS`）。
  - 变更数据后记得 `@CacheEvict` 失效对应缓存，避免脏读。
  - CacheManager 由 `TransactionAwareCacheManagerProxy` 包装：事务内 put/evict/clear 在提交后执行，回滚不生效。不要用 evictIfPresent/invalidate 绕过提交边界。
  - UserUtils 的安全身份映射使用现有 CacheManager API，其它业务数据缓存继续使用注解。UserUtils 只缓存 username → Long ID；完整 Users 直接查当前数据库，禁止缓存可变实体作为写入对象。事务感知缓存不再外套手工 afterCommit 回调，避免重复延迟注册。
- **未引入 Redis，不要建议/编写 Redis 代码。**

## 5. JWT / 内部服务安全规范

- **主后端是唯一身份权威**：只有 `LiuTech/utils/JwtUtil.java` 负责签发和解析 JWT，`JWT_SECRET` 只注入 backend。
- **AI 服务禁止复制 JWT 逻辑**：`RemoteAuthenticationFilter` 把 bearer token 交给主后端 `GET /internal/auth/introspect`；身份成功结果按 token SHA-256 摘要缓存 60 秒。
- **失败必须显式**：无 token 的公开聊天是游客；带无效 token 返回 401；身份权威离线返回 503，不能静默降级成游客。
- **内部接口令牌**：`LIUTECH_INTERNAL_TOKEN` 在两服务一致，使用 `X-LiuTech-Internal-Token` 传递并以常量时间比较；Nginx 对公网屏蔽两组 `/internal/**` 路径。
- **权限来源**：AI 的 `ROLE_USER/ROLE_ADMIN` 只由身份内省响应建立；模型策略和限流读取该认证上下文，不信任前端字段。

## 6. 分层与包结构规范

### 6.1 主后端（权威）
- 包路径：`chat.liuxin.liutech.{controller/{admin,web}, service, mapper, model, common, config, aspect, filter, exception, req, resp, vo, storage, utils}`
- 调用链：`controller → service → mapper → model`
- Controller 只做参数接收、认证身份提取和协议转换；聚合、分页校验、存在性判断由 Service 执行，业务失败交给全局异常处理。
- 首页聚合入口为 HomeService，返回 HomeDashboardResp / SiteStatsResp，Controller 不组装业务 Map。资源下载 Service 返回 DownloadFile（名称、长度、流）；Controller 设置 HTTP 下载头。文件流打开前的失败同样由全局异常处理返回 JSON。
- TinyMCE 上传保留 `{location}` / `{error:{message}}` 的插件协议，SSE 保留事件协议；这类协议适配是明确例外，不照搬到普通业务接口。
- DTO 区分：`req/`（入参）、`resp/`（出参）、`vo/`（视图）；`model/` 放实体。**不要**把 `req/resp/vo` 混进 model。
- Service 用 `@Transactional` 管理事务边界；`final` 字段。

### 6.2 AI 服务（差异点）
- 包路径：`chat.liuxin.ai.{controller/{,admin}, service/{,impl}, mapper, entity, dto, common/{client,tools,tts,monitor,utils}, infra/{config,security,filter,exception,aspect}}`
- **差异点**：AI 服务用 `service/impl`（有 `AiChatServiceImpl` 等），主后端无 `impl` 后缀。这是既成差异，新增 AI 服务时**沿用现有 `impl` 约定**，不要混用两种风格一致化（避免无意义重构）。核心约束是「一个功能只有一个实现入口」，而非「必须/diss 用 impl」。

## 7. 命名规范

- **Java**：类/接口/枚举 PascalCase；方法/字段 camelCase；常量 `UPPER_SNAKE`；boolean 用 `is/has/can` 前缀。
- **SQL 表/列**：`snake_case`，主键 `id`，时间 `created_at/updated_at`，主服务软删 `deleted_at`（NULL 表示有效）；AI 会话 `status=9` 表示归档，不套用主服务软删列。
- **API 路径**：小写、`-` 或 `/` 分层，语义化；主后端管理接口带 `/admin/` 前缀。
- **前端**：组件 PascalCase、目录 kebab 或扁平按 `views/components/stores/services/router/composables/utils` 分层。

## 8. 改代码前置检查清单（AI 协作强制项）

> 这组检查是对「AI 不了解架构就动手、重复造轮子」的直接约束。任何改代码任务开始前，依次确认：

```text
[  ] 1. 搜索仓库：我要实现的能力是否已有统一实现？（Result/ErrorCode/缓存配置/JwtUtil/GlobalExceptionHandler…）
[  ] 2. 分层归位：改动落在正确层次？Controller 不写业务，Service 不拼响应，DTO 进 req/resp/vo。
[  ] 3. 注入方式：用构造器注入，不新增 @Autowired/@Resource 字段注入。
[  ] 4. 缓存：数据缓存走 CacheConfig + 注解，不手写本地 Map 缓存，不引入 Redis。
[  ] 5. 异常与错误：业务违反抛项目异常（主后端 BusinessException / AI AIServiceException），不 try-catch 业务异常，不改用对方服务异常类型。
[  ] 6. 日志：按第 3 节级别打日志，审计日志不删不降级。
[  ] 7. 跨服务安全：JWT_SECRET 只在主服务；LIUTECH_INTERNAL_TOKEN 两服务一致；内部接口未暴露公网。
[  ] 8. 文档：改动触达模块，需同步《Docs/架构/README.md》索引或对应模块「总览.md」。
```

## 9. 服务边界

| 项 | 主后端 | AI 服务 | 状态 |
|---|---|---|---|
| 响应结构 | `{code,message,data}` `Result` | `{success,message,code}` SSE/Map | 边界内，保留 |
| 错误码 | `ErrorCode` 枚举分段 | `AIServiceException` 多级 | 合理隔离 |
| 注入方式 | 业务层构造器注入；安全/配置处 `@Lazy` 字段注入 | 同主后端（业务层构造器注入；安全/配置处字段注入） | 一致 ✅ |
| 缓存 | CacheConfig 集中业务缓存与身份 ID 缓存 | 身份内省60s缓存、TTS状态5s缓存 | 各自领域内 |
| JWT | `utils/JwtUtil.java` 唯一签发/解析 | 不解析 JWT，调用身份内省 | 主服务单一权威 |
| Service 分层 | 无 impl 后缀 | `service/impl` | 既成，沿用 |
| 认证 | JWT + 当前用户数据库校验 | 远程身份内省 + filter+策略+限流 | 稳定内部契约 |

> 两服务普通业务层继续使用构造器注入；安全过滤器属于框架装配边界。身份实现不得在 AI 服务重新引入 JWT 解析副本。

## 10. 数据库访问与事务

两服务均使用 Boot 自动数据源、Hikari、MyBatis-Plus。数据库、账号和连接池容量各自独立；不新增第二套连接管理或通用 BaseRepository。

本节约束新增和修改代码；现有 AI 分页与资源上传事务仍有待治理的实现，见[维护清单](../维护清单.md)。不能把规范目标当作全部存量代码已满足的声明。

### 10.1 配置来源

- JDBC 参数只在各服务 `application.yml` 定义。dev/prod 配置只切换账号和默认主机；Compose 传 DB_HOST/DB_PORT 和对应应用密码，不重复定义 URL。
- 本地默认 127.0.0.1:3306，prod 默认 mysql:3306；DB_HOST/DB_PORT 可覆盖。完整 SPRING_DATASOURCE_URL 仅作有意的整串覆盖。
- 池大小可通过 DB_POOL_MAX_SIZE/DB_POOL_MIN_IDLE 调整；默认仍为 20/5，按实际连接等待与事务时长调优。
- 保留项目认证、时区参数；不配置 autoReconnect，坏连接由连接池淘汰。省略 connection-test-query，使用 JDBC4 有效性检查。

### 10.2 SQL 分工

| 场景 | 入口与约束 |
| --- | --- |
| 单表简单筛选/更新 | BaseMapper + LambdaWrapper；只 SET 本次允许修改的列 |
| 多表、聚合、动态条件 | Mapper XML；明确列清单、排序、软删条件，使用 #{参数} |
| 短固定查询/原子更新 | Mapper 注解可保留；一个查询只有一个实现入口 |
| 页码分页 | 主服务 PageQuery 统一默认值与校验；MP Page/IPage 或绑定 offset/limit 的 Mapper；offset 参数为 long，排序以 id 收尾；Service 不拼 SQL 尾句 |
| 末尾 N 条历史 | 绑定 LIMIT 的 Mapper，倒序取尾部再恢复顺序；Service 不拼 SQL 尾句 |
| 恢复/物理删除 | 明确命名的 Mapper，自定义 SQL 显式处理 deleted_at；不能假定 XML 自动追加 MP 软删条件 |
| 批量写 | 参数绑定、批次上限与失败语义；不把普通循环当作 JDBC executeBatch |

主服务唯一页码入口：[PageQuery.java](../../LiuTech/src/main/java/chat/liuxin/liutech/common/PageQuery.java)。默认 page=1、size=10；非法参数返回 PARAMS_ERROR，通用上限 500，用户管理保留 100、动态保留 20 的领域上限。PageQuery.toPage 复用 MP；PageQuery.offset 供 XML 绑定，PageResp 构造器统一计算页数和翻页标记。AI MemoryService 保留既有最大 100、非法值归一化的协议，不在 Controller 再计算。ArchitectureBoundaryTest 检查 Controller 不依赖 Mapper、Mapper offset 为 long、Service 不拼 SQL 尾句或构造入站 ResponseEntity。

### 10.3 写入与锁

- 资料更新先锁用户行保证头像引用一致，资料、密码、登录时间只修改所属列；管理端账户更新排除 points/version，余额只经 PointsService 变更并记录流水。
- PointsAdminService 的正负调整也委托 PointsService，并保留 admin_adjust 流水类型；不在管理端另写余额更新或重试。PointsService 使用 `selectActiveForUpdate` 当前读锁定用户行，余额更新与 balance_after 流水在同一事务提交；version 是显式 SQL 防线，不依赖实体 @Version。禁止在同一 RR 事务中重试普通 SELECT 的旧快照。
- AI 消息保存先锁用户生命周期、再锁会话并校验属主，当前读取最后序号、插入消息、原子加计数。重命名/归档仅改目标字段；删除也先锁会话再操作消息。DB 还以 (conversation_id,seq_no) 唯一索引防止绕过业务入口产生重复。
- 文章互动先锁文章行再改互动与重算计数。当前文章软删仅隐藏文章，保留标签、点赞和收藏，恢复后重新按可见性查询；完整规则见[文章生命周期](后端/文章生命周期/总览.md)。
- 新增写入链路应缩短锁和数据库事务持有时间，把压缩、文件 I/O 与模型调用放到必要事务之外。当前资源上传由 FileUploadService 的公开入口事务管理，回滚补偿与分片恢复按[资源管理](后端/资源管理/总览.md)维护，不能误写为全部经 ResourceRecordService 短事务执行。

### 10.4 数据库验证

可选 MySQL 回归通过 LIUTECH_TEST_MYSQL_URL 启用，URL 必须是本机无库名地址，例如 `jdbc:mysql://127.0.0.1:33079/?allowPublicKeyRetrieval=true&useSSL=false`；账号/密码使用 LIUTECH_TEST_MYSQL_USER/PASSWORD。普通 `mvn test` 没有该变量时跳过这些测试。

测试创建随机 liutech_test_* 库，只从 [sql.sql](../SQL/sql.sql) 提取建表语句，结束删除本次临时库，不得把测试地址指向生产。当前两服务 MigrationMysqlTest 覆盖基线升级、结构一致性与配置保留；AI 的 MemoryMysqlTest 覆盖会话并发、分页、属主与永久清理，InfrastructureContextMysqlTest 覆盖 AI 完整 Spring 上下文。其它模块的单元测试不能自动视为真实数据库事务或压测验收。

初始化与发布规则见[数据库版本迁移](../SQL/migrations/README.md)。旧 AI DROP/CREATE 入口已移除；版本迁移长期保留且不可修改，独立发布账号执行，应用不自动 DDL。两服务启动检查关键结构；发布前必须完成迁移。

主库永久删除与 user_purge_tasks 入队在同一个事务提交，HTTP 清理交给独立定时任务，按租约确认与退避重试。AI 永久清理接口保留用户 ID 状态，旧缓存和在途请求不能重建数据。用户主动清空与永久清理必须使用不同入口，不能把 afterCommit 内存回调当作可靠队列。

### 10.5 流式请求与报表

- StreamingChatService 当前使用内部 StreamSession 管理上游订阅、心跳、TTS、截止时间与取消；容量参数和旧配置边界统一见[模型预算与安全](后端/AI服务/模型预算与安全.md#流生命周期与资源)。
- 日期趋势使用一次范围聚合并补零，不按每天查询。DashboardService 两组七天趋势从 14 次 Mapper 调用改为 2 次，返回仍是七个自然日。

## 11. 完整功能链路与维护入口

功能审查按前端触发、API 参数/响应、Controller、事务服务、Mapper/SQL 逐层核对。业务链路与统一行为集中到[架构总览](总览.md)及[模块索引](README.md)，在现有领域实现中修改，不另建通用数据访问层。
