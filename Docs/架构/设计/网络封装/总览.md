# 网络封装架构总览

> 全链路 HTTP/SSE 封装：浏览器 ↔ 主后端、浏览器 ↔ AI 服务、AI ↔ 主后端、AI ↔ 大模型、主后端 ↔ 外部 TTS。读完能定位"每个请求由谁发出、用哪个客户端、超时多久、失败怎么降级"。
> 本文只讲**传输层封装**；SSE 事件协议、心跳与断流排查见[看板娘 SSE 流式与心跳机制](../../前端/看板娘/SSE流式与心跳机制.md)；跨服务密钥等硬约束见 `AGENTS.md` 与 [当前架构.md](../../../记录/当前架构.md)。

## 模块职责

LiuTech 的请求分五条链路，每条链路的封装位置和失败策略都不同：

| 链路 | 封装位置 | 归属 |
| --- | --- | --- |
| 浏览器 → 主后端 | axios 实例 + 拦截器 | 前端 |
| 浏览器 → AI 服务（SSE） | `fetch` + `ReadableStream` | 前端 |
| AI 服务 → 主后端 | `RestTemplate` | 后端 |
| AI 服务 → 大模型 | Spring AI `ChatClient` → JDK `HttpClient` | 后端 |
| 主后端 → 外部 TTS | `RestTemplate` + JDK `HttpClient` | 后端 |

生产态所有浏览器请求先到 nginx，由 nginx 按 `location` 分流到各容器；开发态前端直连 `127.0.0.1:8080/8081`，只有静态资源走 vite proxy。

## 数据流概览

```
浏览器
  ├─ axios 实例（MAIN，30s）──────→ nginx /api/ ──→ backend:8080
  ├─ fetch SSE（AI，无超时）──────→ nginx /ai/  ──→ ai:8081 ──→ SiliconFlow 大模型
  └─ fetch SSE（Admin 写作）──────→ nginx /ai/  ──→ ai:8081
                                        │
ai:8081 ──RestTemplate(3s/8s)──────────→ backend:8080（查文章/分类/标签/作者）
        ──RestTemplate(3s/5s)+60s缓存───→ backend:8080 /user/current（账号状态与角色权威校验）
        ──RestTemplate+Semaphore───────→ backend:8080 /tts/speech
        ──ChatClient→JDK HttpClient────→ SiliconFlow（连接 15s / 读 90s）

backend:8080 ──RestTemplate + JDK HttpClient──→ SiliconFlow TTS / 本地 GPT-SoVITS
```

## 1. 浏览器 → 主后端：axios 多实例

**实例工厂**（[`api.ts:28-34`](../../../../Web/src/services/api.ts)）按 `ServiceType` 循环创建，**不预设 `Content-Type`**——让 axios 按 data 类型自动判断（普通对象 JSON、`FormData` 自动带 boundary）。曾因默认 `application/json` 覆盖 FormData 检测，导致 TinyMCE 粘贴图片上传 400。

**请求拦截器**（[`api.ts:44-58`](../../../../Web/src/services/api.ts)）：通过 [`utils/auth.ts`](../../../../Web/src/utils/auth.ts) 的 `getToken()` 取 token（不直接碰 localStorage），拼 `Authorization: Bearer ${token}`。

**响应拦截器双格式归一化**（[`api.ts:61-97`](../../../../Web/src/services/api.ts)）：

| 分支 | 判定 | 处理 |
| --- | --- | --- |
| 标准 | `code` 为 number 且含 `message`/`data` | `code !== 200` → Toast + 抛 `err.isBusiness = true` |
| AI | 含 boolean `success` | `success !== true` → 同上；成功则包装成 `{code:200,message,data}` |
| 未知 | 都不匹配（如裸数组） | 包装成标准格式放行 |

上层调用方拿到的永远是 `ApiResponse<T>`，不感知背后是哪个服务。

**错误分支**（[`api.ts:98-126`](../../../../Web/src/services/api.ts)）：

- `401`：URL 含 `/user/` → 只 Toast；否则 `Swal.close()` + 清 token + 弹全局登录弹窗，**停留当前页**
- `403`：清弹窗静默
- 其他 4xx 且带 `message`：Toast + `error.isBusiness = true`

**`isBusiness` 的用途**：业务错误已在拦截器提示过，调用方 `catch` 里不要再弹通用模态框，否则覆盖 Toast。

**Admin 侧对应实现**（[`Admin/src/services/httpClient.ts`](../../../../Admin/src/services/httpClient.ts)）：同一套约定——错误分支统一提示后端 `message` 并标记 `isBusiness`；401 跳 `/login`、403 跳 `/403`（不弹窗）。主后端与 AI 两个实例共用这个工厂，仅 `normalizeResponse` 取值不同。页面写法 `if (!error?.isBusiness) message.error('...')`。

**为什么这样设计**：后端业务异常统一返回 HTTP 400 + `{code, message, data}`（`message` 面向用户可读），走的是 axios 错误分支。若拦截器不提示、由页面写死"操作失败"，用户就看不到"分类名称已存在"这类具体原因——这正是 Admin 历史实现的缺陷（已修复）。

## 2. 浏览器 → AI 服务：fetch + ReadableStream

不用 `EventSource` 的原因（[`aiStream.ts:161-162`](../../../../Web/src/services/aiStream.ts)）：它不支持自定义请求头（JWT）和 POST。

### 分层：一条协议实现，两类消费方

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 协议层 | [`Web/src/services/sse.ts`](../../../../Web/src/services/sse.ts)（Admin 侧同名镜像） | 读流、切帧、JSON 解析、envelope 剥壳。不认识任何业务事件 |
| 写作助手客户端 | [`Web/src/services/writingStream.ts`](../../../../Web/src/services/writingStream.ts)（Admin 侧同名镜像） | `POST {AI}/writing/stream` 的完整客户端：fetch、HTTP 错误文案、事件分发、连接中断判定、协议类型 |
| 看板娘客户端 | [`Web/src/services/aiStream.ts`](../../../../Web/src/services/aiStream.ts) | 复用协议层读流，自己负责看板娘事件集合与断线重连 |

**分帧读取**（[`sse.ts:181-231`](../../../../Web/src/services/sse.ts)）三个要点：

```ts
buffer += decoder.decode(value, { stream: true })  // 避免多字节字符被截断
const frames = buffer.split(/\r?\n\r?\n/)          // 兼容 LF 与 CRLF
buffer = frames.pop() ?? ''                        // 保留半截帧留到下轮；流结束时再冲刷
```

**单帧解析**（[`sse.ts:118-169`](../../../../Web/src/services/sse.ts)）：按行取 `event:` / `data:` 前缀（忽略 `:` 注释行与 `id:`/`retry:`）；`data` 多行按 `\n` 拼接；JSON 解析失败返回 `invalid` 而不是抛异常，由调用方决定「跳过并留痕」。若 `payload.contractVersion === 1` 则剥掉 envelope 把 `payload` 交给上层——**后端当前不发送该字段**，走的是裸 payload 形态（见[看板娘 SSE 流式与心跳机制](../../前端/看板娘/SSE流式与心跳机制.md)）。

**事件集合**（与后端 `StreamingChatService` 对齐）：

| 消费方 | 消费的事件 |
| --- | --- |
| 看板娘 [`aiStream.ts:311-390`](../../../../Web/src/services/aiStream.ts) | `start` / `data` / `heartbeat` / `avatar-cue` / `audio` / `audio-skip` / `audio-complete` / `article-results` / `complete` / `error` |
| 写作助手 [`writingStream.ts:286-339`](../../../../Web/src/services/writingStream.ts) | `start` / `data` / `tool-start` / `tool-result` / `field-update` / `article-results` / `complete` / `error`（其余忽略） |

**重连策略（仅看板娘）**（[`aiStream.ts:219-266`](../../../../Web/src/services/aiStream.ts)）：

- 三种情况不重连：`userCancelled`、`isCompleted`（收到 complete）、`serverError`（服务端 error 事件）
- 其余异常按指数退避 `min(1000 * 2^retryCount, 30000)` 重连，最多 4 次
- 重连携带 `conversationId` + `lastSeq`（由 `wrappedOnEvent` 记录，[`aiStream.ts:121-129`](../../../../Web/src/services/aiStream.ts)）实现续传
- `cancel()` 会立即解除重连等待（`retryResolve`，[`aiStream.ts:395-408`](../../../../Web/src/services/aiStream.ts)）

**写作助手差异**：不做自动重连——流读完未收到 complete 时 `onError('连接中断，请重试')` 后照常结束 loading（[`writingStream.ts:273-276`](../../../../Web/src/services/writingStream.ts)）；HTTP 层显式处理 `429`/`403`，其余状态码优先透出后端 JSON 的 `message`（[`writingStream.ts:183-213`](../../../../Web/src/services/writingStream.ts)）。

**从后端真实帧格式出发的两个约定**：`start` 事件的 `conversationId` 取自 payload 顶层（不是 envelope）；`error` 事件的用户文案在 `error` 键而非 `message` 键（`SseEmitterHelper.safeSendError`），两个键都要读。


## 3. AI 服务 → 主后端

`BlogApiClient` 的三个约定：

1. **超时显式注入**（连接 3s / 读 8s），不用框架默认的无限等待
2. **统一解析** `extractData(JsonNode)`：`code == 200` 且有 `data` 才返回节点，否则 null
3. **失败降级**：查询类方法返回 `null` 或空列表，异常只 `log.error`，避免主后端抖动导致 AI 工具调用整体失败

响应形态兼容分页对象（`records`）与裸数组两种（[`BlogApiClient.java:120`](../../../../LiuTech-AI/src/main/java/chat/liuxin/ai/common/client/BlogApiClient.java)）。

`TtsClient` 用 `JdkClientHttpRequestFactory` + 读超时 30s，`Semaphore` 控制并发（默认 1，保护单卡推理），`/tts/status` 结果缓存 5 秒避免一次回复内多次查询。

## 4. AI 服务 → 大模型

出站传输层有**两处超时配置**，作用对象不同，排查超时问题要同时看：

- [`AiHttpClientConfig`](../../../../LiuTech-AI/src/main/java/chat/liuxin/ai/infra/config/AiHttpClientConfig.java)：`@Primary` 的 `RestClient.Builder` / `WebClient.Builder` 基于 JDK `HttpClient`（连接 15s、读 90s）。类注释记录根因：**Spring AI 默认链路用 WebClient 调 SiliconFlow 时 TLS handshake 被远端终止**，故显式切到 JDK `HttpClient`
- [`application.yml:32-35`](../../../../LiuTech-AI/src/main/resources/application.yml) 的 `spring.ai.openai.timeout: 300s`：Spring AI 2.0 OpenAI 客户端自身超时（注释写明默认仅 60s，大输入时首 token prefill 超 60s 会被本地掐断成 `Stream failed`），提到 300s 与 SSE 超时对齐

`SiliconFlowChatClient` 在其上封装业务语义：

- `CHAT` 模式直接 `call()`；`WRITING` 模式内部走 `stream().content().collectList()`（[`79-83`](../../../../LiuTech-AI/src/main/java/chat/liuxin/ai/service/SiliconFlowChatClient.java)）——用流式规避 RestClient 长响应读超时
- 两个方法都带 `@Retryable(maxAttempts = 2, backoff = 1000ms)` + `@CircuitBreaker(fallbackMethod = ...)`（68-69、117-118）
- 熔断兜底返回可读文案而非 5xx（141-150）

## 5. 主后端 → 外部服务

主后端有 3 处主动外呼，超时策略各不相同：

| 目标 | 客户端 | 超时 | 说明 |
| --- | --- | --- | --- |
| AI 服务健康聚合 | JDK `HttpClient` | 连接 1s / 请求级 1.5s | `AiRuntimeService` 聚合「TTS 状态 + AI 在线」，调 `GET {ai.service.url}/ai/models/default`；任何异常转成 `aiOnline=false`，**AI 挂了不会拖死主后端** |
| SiliconFlow TTS | `RestTemplate`（默认工厂） | **无超时（隐患）** | `TtsSpeechService.uploadSiliconFlowVoice` / `listSiliconFlowVoices`；默认 `SimpleClientHttpRequestFactory` 的 connect/read 是无限等待 |
| 本地 GPT-SoVITS 推理 | JDK `HttpClient` | 连接 10s | `HTTP_1_1` + 不跟随重定向 |
| TTS 状态探测 | 独立 JDK `HttpClient` | 连接 800ms / 请求级 1.2s | 结果缓存 5s（`STATUS_CACHE_TTL_MS`），避免频繁打爆推理服务 |

邮件走 SMTP（`JavaMailSender`，QQ 邮箱 465 SSL），不是 HTTP 链路；COS 的 HTTP 由 SDK 内部处理，不在此配置。

## 陷阱与约束

- **不要给 axios 实例预设 `Content-Type`**：会覆盖 FormData 自动检测，导致文件上传 400（[`api.ts:25-27`](../../../../Web/src/services/api.ts)）
- **不要用 `EventSource` 调 AI 流式**：它不支持 POST 与自定义头，拿不到 JWT
- **SSE 必须关 nginx 缓冲**：`proxy_buffering off` + `proxy_read_timeout 3600s`，否则失去流式（[`ai-proxy.include`](../../../../nginx/conf.d/ai-proxy.include)）
- **不要给非 SSE 路径加 `Accept: text/event-stream`**：会破坏 JSON 响应（406）
- **AI 服务与主后端的响应格式不同**：`{success,message,code}` vs `{code,message,data}`，新增 AI 非流式接口**不要引入第三种结构**；统一走 `api.ts` 归一化（见[跨服务规范](../../跨服务规范.md) 第 1 节）
- **`BlogApiClient` 无熔断**：只有超时与异常降级，主后端长时间慢时 AI 线程会被占用（可选改进项）
- **Admin 写作流无自动重连**：与 Web 看板娘不一致，写作长文断流需用户手动重试
- **`sse.ts` / `writingStream.ts` 是跨端镜像文件，必须逐字节一致**：Web 与 Admin 各存一份，改完一侧必须 `cp` 同步另一侧，否则 CI 的 [`scripts/check-mirrored-modules.mjs`](../../../../scripts/check-mirrored-modules.mjs) 会失败。镜像文件**不得引入应用内依赖**（`@/…`、`../…`），baseURL 与 token 由调用方注入——这样将来迁到 workspace 共享包时整体搬走即可
- **新增 SSE 消费方不要再写第三份解析**：读流与切帧一律用 `sse.ts` 的 `readSseStream`，写作助手类客户端复用 `writingStream.ts`；只有事件集合和重连策略属于各业务自己
- **坏帧只跳过，不中断整条流**：解析层把 JSON 非法帧标成 `invalid` 交给调用方（默认 `console` 留痕），不允许因为一帧脏数据把整轮对话判死
- **代理配置有两层**：前端容器内 nginx（`Web/nginx.conf` / `Admin/nginx.conf`）与根 nginx（`nginx/conf.d/`）都配了 `/api/`、`/ai/`，两套规则需同步，否则直接访问容器端口与走根网关的行为会不一致
- **跨服务密钥**：`JWT_SECRET`、`TTS_PROXY_INTERNAL_TOKEN` 两服务必须一致，见 `AGENTS.md`
