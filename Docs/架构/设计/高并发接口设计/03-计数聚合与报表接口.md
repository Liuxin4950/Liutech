## 1. 两类完全不同的问题

### 1a 读时写计数

> **任何高频读接口都不得在请求线程内同步写它的计数列。**

InnoDB 的 `UPDATE` 拿行独占锁直到事务提交 → "100 人同读一篇文章"退化为"100 人在同一行排队"。同时 `posts.updated_at` 有列级 `ON UPDATE CURRENT_TIMESTAMP`（`sql.sql:115`），被浏览量顶高后污染 `sitemap.xml` 的 `lastmod` 与按 `updated_at` 排序的语义。

#### 真相源（先定这个，再谈优化）

| 候选 | 能否作为 `view_count` 的真相源 | 证据 |
| --- | --- | --- |
| `user_view_history` | ❌ **绝对不行**。`uk_user_post(user_id,post_id)` 使每人每文**只一行**；重复浏览仅 `ON DUPLICATE KEY UPDATE viewed_at = NOW()`（`UserViewHistoryMapper.xml:13-14`），无计数列；游客**无法上报**（`/posts/` 只对 GET 公开，`PUBLIC_POST_EXACT` = `{"/messages"}`，`SecurityWhitelist.java:75-77`，`PostsController.java:249` 还再校验一次）；用户可自行清空（`:61-63`） | 同左 + `sql.sql:181-190` |
| 任一明细/事件表 | ❌ **全库不存在**。`sql.sql` 的 28 张 `CREATE TABLE` 中只有 `user_view_history` 与"浏览"相关，无 visit/pv/traffic/analytics 表；`system_logs` 只记 `@OperationLog` 标注的后台操作（`OperationLogAspect.java:50-63`），详情读与 `recordView` 都没这个注解 | `sql.sql:365-385` |
| Nginx access log | ❌ 不能作为**可对账**源。`log_format` 确含 `$request`（`Nginx/nginx.conf:21-23`，`:25` 是 `access_log` 指令），但 nginx 服务只挂了证书卷（`docker-compose.yml:154-157`），`/var/log/nginx` **未持久化**、无 logrotate | 同左 |
| `posts.view_count` 本身 | ✅ **它就是唯一真相源**，且与 `user_view_history` 统计的是**不同人群**（前者含游客与刷新，后者=去重的登录用户"我的足迹"） | `PostsService.java:193-197` |

> 所以"明细表才是真相源、计数是缓存"这句我首轮写下的话是**反的**。它适用于 `images.usage_count`（真相源确实能从 posts.content/cover/头像/轮播/系列封面反扫出来，`ImageUsageReconcileService.java:49-107` 就是这么做的 —— **reset-to-zero 再重扫权威引用方**），不适用于浏览量，因为**没有任何可反扫的浏览明细**。

#### 目标设计：计数器为主源 + 攒批，永不做绝对重算

```
① 请求路径：只做内存累加（LongAdder / Caffeine），不碰 DB
② 定时 flush：一条 CASE 多行 UPDATE 落增量（③ 见下）
③ 不对账。漂移上界 = flush 窗口 × QPS（产品语义上浏览量要的是"量级正确"）
```

这是一次**用有意的精度换吞吐**的交易，必须在文档和需求里明写这条取舍。**如果将来真要按天访问曲线/UV**，才引入真实事件表：一次详情读 = 一次顺序 `INSERT`（比 `UPDATE` 便宜，无行锁竞争），但表按 QPS 无界增长、需分区/归档，且绝对重算本身是全索引扫 —— **复杂度远大于当前收益，不选**。

#### 缓冲实现的四个真实风险（本轮修正）

现有 `CacheConfig.java:63-69` 的工厂方法是 `expireAfterWrite(ttlMinutes)` + `maximumSize` —— **不是 `expireAfterAccess`**（我上一版基于一个不存在的配置做论证）。对一个"写缓冲"来说：

| # | 风险 | 正确做法 |
| --- | --- | --- |
| 1 | **TTL 本身就是丢数据的机制**（写后 N 分钟强制过期，未 flush 即蒸发） | 缓冲**不设 TTL**；只设容量，且容量依据要写出来（本库文章数千级 → 上限取"文章总数 × 2"，驱逐实际不触发） |
| 2 | 容量驱逐（`maximumSize`）会丢残值 | 挂 **`removalListener`**（不是 `evictionListener`）把残值回灌到下一轮。区别很关键：`evictionListener` **只在 `RemovalCause.wasEvicted()`（SIZE/EXPIRED/COLLECTED）时触发**，且是懒执行、在变更线程上同步跑；Caffeine 官方把"缓存写回"类回调指向 `removalListener` |
| 3 | `drain()` 与 `@Scheduled` 竞态双计 | **逐键原子摘取** `asMap().remove(postId)`，不要 `cleanUp()` 后遍历快照 |
| 4 | **容器 stop 时最后一段增量丢失**（监听器也救不了 JVM 退出） | `@PreDestroy` 里强制 flush 一次；注意 `ThreadPoolTaskExecutor.setWaitForTasksToCompleteOnShutdown(true)` 只覆盖异步任务，**不覆盖缓冲** |

落点：这属于 `Docs/架构/跨服务规范.md` §4 里"**登录失败计数等有状态业务缓存**"的豁免范畴（**不是**该节 :84 禁止的"Service 里手写数据缓存"）→ 应建成独立 `@Component` + 原生 `Caffeine.newBuilder()…build()` 或 `ConcurrentHashMap`+`LongAdder` 分桶，**不要**塞进 `SimpleCacheManager` 的命名缓存里（那里装的是数据缓存）。采用时**同步在 `跨服务规范.md` §4 点名这个豁免类**，否则后来人无法判断。

**调度前置**：主后端只有 `@EnableScheduling`（`LiuTechApplication.java:13`）、无 `TaskScheduler` bean → **单线程**调度，而 `ImageUsageReconcileService.java:47`(02:55) 与 `OrphanImageCleanupService.java:42`(03:00) 是长任务（前者还 `@Transactional`(`:48`) 且加载全量 posts + content，`:59`）。不先配 `spring.task.scheduling.pool.size ≥ 3`（`05` §2.1），凌晨清理期间 flush 全停 → 缓冲溢出丢计数。

#### flush 的 SQL 形态（本轮修正）

```sql
-- ✗ 第二版建议："依赖 ExecutorType.BATCH" 仍会 N 次往返：
--   rewriteBatchedStatements 与 allowMultiQueries 在所有 URL 上都不存在
--   （application-prod.yml:3 / application-dev.yml:3 / docker-compose.yml:32），
--   Connector/J 只把【非 INSERT 批】合并成多语句当 allowMultiQueries=true
-- ✓ 正解：一条 CASE 多行 UPDATE，不依赖任何 JDBC 开关、不依赖 BATCH 会话
UPDATE posts
   SET view_count = view_count + CASE id
         <foreach collection="list" item="e" separator=" ">WHEN #{e.id} THEN #{e.delta}</foreach>
         ELSE 0 END,
       updated_at = updated_at                        -- ★ 显式自赋值抵消列级 ON UPDATE
 WHERE deleted_at IS NULL                             -- ★ 裸 XML 不受 MP 逻辑删除过滤，必须自己写
   AND id IN
       <foreach collection="list" item="e" open="(" separator="," close=")">#{e.id}</foreach>;
-- ⚠ 上一版这里的两处写法会直接 1064，照抄即挂：
--   ① CASE 不能带括号：CASE id <foreach open="(" …>  → 渲染成 CASE id ( WHEN … ) → 1064
--   ② IN 的 <foreach> 必须带 open="(" close=")"，否则渲染成 IN 1,2,3 → 1064
-- 每批 ≤500 行；MyMetaObjectHandler 只填实体入参的 MetaObject（config/MyMetaObjectHandler.java:49-57），
-- 裸 XML 不传 et → 不会干扰本语句
```

> 混合态注意：现状 `PostsService.java:194-197` 用的是 `this.update(LambdaUpdateWrapper)`，MP **会**自动追加 `deleted_at IS NULL`；改成裸 XML 后要自己加，加了之后不要两处都写（重复谓词无害但会误导读者）。

#### 其余计数写点

| 位置 | 现状 | 正确改法 |
| --- | --- | --- |
| `AnnouncementsService.java:94-101` + `AnnouncementsMapper.java:57` | `UPDATE` 后再 `SELECT` 一次"为了一致性" → 一次浏览 3 条语句 | 公告量小：不统计浏览量，或同样走缓冲。**删掉那句多余的 re-SELECT** |
| `MemoryService.java:119-127`（AI） | 读改写 → `message_count` 丢计 | 单条 `UPDATE … SET message_count = message_count + #{n}`（`02` §4.3） |
| `PostInteractionService.java:59-63` | `COUNT(*)` → 绝对 `SET` | 保留绝对重算，但按 `02` §2.2 形态 A/B 执行 |
| `ImagesMapper.java:38` | `GREATEST(0, usage_count + #{delta})`，列 `INT UNSIGNED` → 无符号下溢存疑（`06` V-17） | `GREATEST(0, CAST(usage_count AS SIGNED) + #{delta})`（与 sql_mode 无关，比守卫更稳） |

### 1b 聚合与报表

> **报表 SQL 的耗时必须由"数据保留窗口 / 预计算"约束，不能由"表当前多大"决定。**

判据与三档新鲜度（秒级 → 短 TTL 缓存 + 击穿保护；分钟级 → 增量物化表；天级 → 定时预计算 + 保留窗口）。它们**不在用户路径上，但会**占满连接池（拖垮前台）、在默认 buffer pool 里制造冷页读、与备份抢 IO。

## 4. 索引与 DDL 清单（每条 ADD 必配等价 DROP）

> **前置事实与三条硬规则**
>
> 1. `Docs/SQL/sql.sql` 只在 MySQL **首次初始化**执行（`docker-compose.yml:15` 挂 `docker-entrypoint-initdb.d`），已有 `mysql_data` 卷**不会重放** → 所有变更必须另写 `Docs/SQL/migration_*.sql`（惯例见 `migration_post_series.sql` 等 3 个）。
> 2. **但 `sql.sql` 才是 `AGENTS.md` 定义的"两个数据库唯一完整初始化脚本"** → 迁移执行完必须把同样的索引/列**回填进 `sql.sql` 的建表语句**，否则全新部署的库与生产库结构漂移，本文件与 `01` 的全部 `EXPLAIN` 结论在新库上失效（**一次 DDL = 两处修改**）。`sql.sql:24` 也提示 `IF NOT EXISTS` 不会修补已存在的表 → 更要走迁移脚本。
> 3. MySQL 8.0 **不支持** `ADD INDEX IF NOT EXISTS` → 脚本要先查 `information_schema.STATISTICS` 才能重跑；并遵循"先 `ADD` → `EXPLAIN` 验证命中 → 再 `DROP` 被左前缀覆盖的旧索引"的顺序，避免出现两边都无索引的窗口。

```sql
ALTER TABLE users    ADD INDEX idx_created (created_at);        -- 无同类索引，确实缺
-- posts 不加 idx_created：补上 status 谓词后 idx_status_deleted_created(sql.sql:126) 已够用
ALTER TABLE comments ADD INDEX idx_created (created_at);        -- /comments/latest 与列表相关子查询
ALTER TABLE post_likes ADD INDEX idx_post_like (post_id, is_like, deleted_at);
ALTER TABLE system_logs ADD INDEX idx_created_action (created_at, action);  -- 若保留窗口内要实时统计
-- 必须保留：user_view_history.idx_user_viewed（sql.sql:187）
--   —— /posts/view-history 按 user_id 等值 + vh.viewed_at DESC 排序分页（UserViewHistoryMapper.xml:54,57）
--   （第二版我把它的排序口径写成 ORDER BY (user_id, viewed_at)，不准确，已改）

-- 可删的冗余左前缀（行号已复核）：
ALTER TABLE post_likes     DROP INDEX idx_post_id;   -- ⚠ 若加了 idx_post_like 才成立；否则它是唯一 post_id 索引
-- sql.sql:156? 不：idx_user_id 在 :157 前一行，逐条以 information_schema 为准
ALTER TABLE post_favorites DROP INDEX idx_user_id;   -- :174，被 uk_user_post(:172) 覆盖
ALTER TABLE download_logs  DROP INDEX idx_user_id;   -- :247
ALTER TABLE points_transactions DROP INDEX idx_user_id; -- :276（第二版误写 :277），被 idx_user_created(:279?) 覆盖
ALTER TABLE user_achievement_claims DROP INDEX idx_user_claimed; -- :262 —— 【不是】uk 的左前缀，
                                                   -- 可删的真正理由：没有任何查询用到 claimed_at（UserActivityMapper.xml:23）
ALTER TABLE posts DROP INDEX idx_status, DROP INDEX idx_author_id; -- :121 / :120（第二版误引 :22,:23 —— 那两行是文件头注释）
```

> **删索引前一律用 `information_schema.STATISTICS` + `sys.schema_index_statistics`（root）复核**，不要照抄本清单的行号 —— 本仓库 `sql.sql` 已被多次增删改，行号漂移是常态。上面每条都标了"可删的根据"，根据比行号重要。

**FULLTEXT**：`mysql:8.0`（`docker-compose.yml:4`）内置 ngram 解析器，`ngram_token_size` 默认已是 **2**，**不加启动参数即可建索引**（改值才需重启并重建 `innodb_ft_*`；仓库任何位置都没有 ngram/my.cnf 配置，已 grep 确认）。但**行为不等价**：现 `/posts/search` 还匹配**分类名与标签名**（`PostsMapper.xml:444-455`）→ 只 `MATCH(title,summary,content)` 会静默丢结果，迁移时必须把分类/标签命中并回结果集。

## 5. 前台聚合端点（`/stats`、`/dashboard`）

已核实两半：① 二者**不在任何白名单列表**里，被 `SecurityConfig.java:137` 的 `anyRequest().authenticated()` 要求登录；② `Web/src` **从不调用**它们（唯一相近的是 `services/user.ts:232` 的 `/user/stats`），`Admin/src` 用的是 `services/dashboard.ts:61` 的 `/admin/dashboard*`。

> 提醒：`Web/src/components/TheSidebar.vue:89` 里的 `/dashboard` 是 **Vue 前端路由**，不是 API 调用，不能算作"有调用方"。

结论：它们是**孤儿端点（死代码）**，不是"首页打不开"的线上缺陷。三个选项：① 删除（连同 4 条无缓存 `COUNT`）；② 改匿名 + 全局单键缓存 + 与类型 A 一起走边缘缓存；③ 若要做首页一次性装配 `GET /bootstrap`，属**协议变更**，必须与 `Web/` 同批改。

## 8. 陷阱

- **计数与明细的语义要分清**：`view_count`（含游客与刷新）≠ `user_view_history` 行数（去重登录用户）。任何"用后者校验前者"的想法都是错的（§1a）。
- 计数 flush 的 `UPDATE … SET view_count = view_count + n` **必须显式带 `updated_at = updated_at`**，否则列级 `ON UPDATE` 仍会顶高 `lastmod`。
- 裸 XML 不受 MP 逻辑删除过滤 → 手写谓词；Wrapper 类语句会被自动追加 `deleted_at IS NULL` → 两种形态不要混用（§1a 末）。
- `dashboardStats` 加缓存后**不要**在每次后台写时清它 —— 它是聚合快照，接受 60 s 滞后。给它加失效路径只会让失效清单更长（`01` §5 的同一条原则）。
- `ALTER TABLE posts ADD FULLTEXT … WITH PARSER ngram` 会**重建表**，含 `LONGTEXT content` → 低峰执行；`innodb_ft_*`/`ngram_token_size` 变更需重启。
- 日志保留任务一旦上线即**不可逆**，先确认无合规留存要求。
- `system_logs` 若要分区，`PRIMARY KEY` 必须先改成 `(id, created_at)` —— 这是表重建级操作，不要顺手。
