# 05 · 认证管线与容量基线（类型 F / J + 横切 L4）

> 覆盖：`JwtAuthenticationFilter` 每请求成本、`/user/*` 认证端点、`/internal/auth/introspect`、`/ai/internal/users/*`，以及所有接口共享的容量基线（线程池、连接池、限流、异步执行器、JVM、MySQL、观测）。

## 1. 每请求成本解剖（类型 F）

### 1.1 事实（链路与次数已核准）


### 1.3 「公开」不等于「不解析 token」——但改法要克制

现状结构（已核）：`SecurityWhitelist.java` 是 **7 个列表 + 1 个 `shouldSkipAuthentication(uri, method)`**（列表起于 `:20,35,53,66,75,82,90`），消费方是 `SecurityConfig.java:98,103,109,112,117,123,126` 与 `JwtAuthenticationFilter.java:77`。**两处读同一批列表，所以"permitAll 集合"与"跳过鉴权集合"今天**列表内容**同源（漂移不可能）；但**匹配语义不同源** —— `SecurityWhitelist.java:129` 用裸 `uri.startsWith(prefix)`，而 `SecurityConfig.java:113` 用 Spring `PathPattern`（`prefix + "**"`，可匹配零个片段）。两者对边界路径的判定并不等价，差异实例：`GET /posts`、`/uploads/images` 这类**无尾斜杠**路径，SecurityConfig 放行而过滤器仍会去解析 JWT；`GET /posts` 解析、`GET /posts/x` 跳过（前缀带斜杠）。**

> **因此上一版"必须保证二者相等否则 403"的告诫，描述的是我这个改动【引入】的风险，不是现状的风险。** 这是方向性错误：把一个隐含不变量改成了需要人工维护的显式不变量。

**修正后的最小改法**：不新建独立枚举表，而是**在现有列表之上加一个派生视图**：

```java
// 保持 7 个列表为唯一真源，只新增一个读它们的函数
public enum AuthMode { ANONYMOUS_ONLY, OPTIONAL_AUTH, DENIED, REQUIRED_AUTH }
public static AuthMode authMode(String uri, String method) {
    if (matches(DENY_PREFIXES, uri))          return AuthMode.DENIED;          // 已有维度，别丢
    if (method 非 GET && matches(PUBLIC_POST_EXACT, uri)) return AuthMode.ANONYMOUS_ONLY;
    if (method == GET && matches(PUBLIC_GET_*, uri))      return /* 拆两档 */;
    return AuthMode.REQUIRED_AUTH;
}
// ⚠ 上面的 matches() 在本仓库【不存在】。现有唯一的公开入口是布尔函数
//   SecurityWhitelist.shouldSkipAuthentication(String uri, String method)（:107），内部顺序是
//   OPTIONS→true → AUTHENTICATED_PATHS(:114)→false → FULLY_PUBLIC(:119)→true
//   顺序：OPTIONS→true、AUTHENTICATED_PATHS(:114)→false、FULLY_PUBLIC(:119)→true、
//   GET(:125 contains + :129 startsWith)、HEAD(:138 PUBLIC_HEAD_PREFIXES)、POST(:147 PUBLIC_POST_EXACT)、else false。
//   ★ 判定顺序本身是语义的一部分：AUTHENTICATED_PATHS 先于 FULLY_PUBLIC —— 已在该表里的路径
//   无法靠"再加进某个公开列表"变成匿名。改可选鉴权时必须按这个优先级设计，否则会出现
//   "加进 PUBLIC_GET_EXACT 却仍然强制登录"的诡异现象。
//   且它【完全不读 DENY_PREFIXES】。因此最小可实现形态是：
//   若 GET/HEAD 且 uri 以 DENY_PREFIXES 某项开头 → DENIED
//   否则 return shouldSkipAuthentication(uri, method) ? (第8张 OPTIONAL 列表含 uri ? OPTIONAL_AUTH : ANONYMOUS_ONLY)
//                                          : REQUIRED_AUTH;
// 结论修正：OPTIONAL_AUTH 【无法】从现有 7 张表派生 —— 必须新增第 8 张显式列表，即引入一个新的真源。
//   这不是致命问题，但必须诚实标注：改动确实把"内容同源"变成了"两处需同步"，需配套一个启动期自检断言
//   （第 8 张表 ⊆ PUBLIC_GET_* 前缀集）来把漂移挡在启动时，而不是靠人工维护。
// 关键：OPTIONAL_AUTH 只能从"现在已经在 PUBLIC_GET_* 里、但业务需要用户态"的那批路径里挑，
//       并把选择结果回写进注释；过滤器改成 if (mode != ANONYMOUS_ONLY) 就尝试解析 token。
// 无任何测试覆盖这类白名单改动（grep 确认 SecurityWhitelist/SecurityConfig 无对应测试）→ 改完必须手工回归。
```

**上一版举的例子有 4 处端点级错误，照抄会出事**：

| 我写的 | 真实情况 |

### 1.4 撤销延迟（第二版低估）

`UserAuthLookupService.java:53` 写作 `return !StringUtils.hasText(tokenPasswordHash) || tokenPasswordHash.equals(sha256(dbHash));` → token **缺** `passwordHash` 声明时判为**有效**（fail-open），改密撤销对这类历史 token 永久无效。应改为缺失即拒绝。

**端到端陈旧上限是 300 s 而不是 60 s**：AI 侧 `RemoteAuthenticationFilter` → 内省 → 主后端 `AuthIntrospectionController` → `userUtils.getCurrentUser()` → 命中 `UserUtils` 的 **5 分钟** Caffeine（`UserUtils.java:39-42`）。要收紧必须**两处 TTL 一起改**。

**禁用/改密后必须清的写点**：`UserManagementService.java:264,329,541,625,666,712`（已有 `clearUserCache()`）**之外**，还必须覆盖 **`UserAuthService.java:429`（重置密码）、`:548`（改密码）** —— **这两条今天完全不清 `UserUtils` 缓存，是既有缺陷**，不是新增缓存才引入的；另需**新增**清理点两处：`UserProfileService.java:121`（改资料）与 `UserAchievementService.java:66`（成就领取，现走 `afterCommit`）—— 注意 `UserProfileService:121` **今天并不是** `clearUserCache()` 的调用方（已 grep 确认），列在这里是"待补"而不是"已有"，勿与上一组的既有调用者混为一谈。

## 2. 容量基线：把连接池与线程配平

```
可支撑 QPS ≈ 池大小 / 每请求平均持连接秒数        （Little 定律作用在"连接"这一资源上）
```

| 路径 | SQL 往返（已核） | 持连接（**估**） | λ=500 需要的连接 |
| --- | --- | --- | --- |
| 认证请求（管线固定） | 1 | ~1 ms 量级 | 1 |
| `GET /posts` 命中 | 0 | 0 | 0 |
| `GET /posts` 未命中 | 4（COUNT + 数据 + tags + 状态） | 估 20~40 ms | 10~20 |
| `GET /posts/{id}` | ≥5（含 1 次行锁 UPDATE；附件多则更多，N+1） | 估 30~60 ms | 15~25 |
| `GET /admin/dashboard/stats` | **25 条独立语句**（`7+2+7+7+1+1`，`DashboardService.java:75-186`），**方法无 `@Transactional`** → 25 次独立借还；配 `connection-test-query` 后真实往返约 **50** | 估 150~300 ms | — |
| 上传（COS 在事务内） | 3 | **1~3 s**（网络） | — |

**推论**：`connection-test-query: SELECT 1`（`application.yml:35`、AI `:24`）让**每次借还多一条 SQL**。删掉它安全：驱动 `mysql-connector-j:9.7.0` 支持 JDBC4 `isValid()`、`HikariCP:7.0.2` 会用。对 dashboard 这类"多条独立语句"的路径，这一项就能砍掉一半往返。

### 2.2 池大小怎么定（更正用法）

HikariCP 的 `cores*2 + spindles` 公式归属正确，但**输入必须是数据库主机的核数与磁盘数**，上一版代入了**应用容器的 `cpus: '2.0'` 配额** —— 用法错。本项目 DB 与两个 JVM 同机、mysql 容器未限资源（`docker-compose.yml:3-23`）→ 该公式与宿主机核数耦合，不能凭应用配额推。

- `cpus: '2.0'` 对 JVM 可见核数**确实生效**（两个 Dockerfile 都没有 `-XX:ActiveProcessorCount`，JDK 21 `UseContainerSupport` 默认开并读 cgroup）。但"两个 2 核 app + 一个无界 mysql"**超卖**宿主机。
- 现状 20 已高于任何合理推导值 → 重点不是调池，而是**降每请求 SQL 数**（`01`/`03`）+ **给 MySQL buffer pool 扩容**（`§6`）。
- MySQL `max_connections` 未调（默认值是外部事实，`06` V-2 实测）。**`init-users.sh` 没有 `MAX_USER_CONNECTIONS`，且 init 脚本只在容器首启执行** → 已有 `mysql_data` 卷时必须手工 `ALTER USER … WITH MAX_USER_CONNECTIONS n`。

### 2.3 JDBC URL

```
connectTimeout=5000&socketTimeout=120000&rewriteBatchedStatements=true
```

- 参数名对 Connector/J 正确。`socketTimeout` 语义是**每次 socket read**（不是累计）→ `UserManagementService.java:703` 事务内的 8 s HTTP 不会触它；真风险是**大批物理删/COMMIT 的单次响应超阈值**：连接被客户端撕断而 MySQL 仍会提交 → 先按 `§5` 拆长事务，再从 120000 降到 30000。
- `rewriteBatchedStatements` **只重写 INSERT**（UPDATE 批的正解见 `03` §3.1）；它与 `useGeneratedKeys`（`PostCreateResp` 依赖自增 id）是否兼容需验证 → `06` V-12。
- **单一真源问题（已核实）**：生产 URL 由 `docker-compose.yml:32`（主）/`:91`（AI）提供，**覆盖** `application-prod.yml:3`，丢掉 `zeroDateTimeBehavior`、`autoReconnect`、`failOverReadOnly`、`maxReconnects`。二选一保留并补齐参数集。

## 3. 限流（当前完全缺失）

**判据：限流应在离用户最近、且不占后端稀缺资源的地方** → Nginx 优先。

```nginx
# ── 第 1 段：conf.d/default.conf 文件【顶层】。nginx.conf:53 已把 conf.d/*.conf include 在 http{} 内
#    → 片段里再包一层 http{} 是配置错误（nested http）。
limit_req_zone $binary_remote_addr zone=all:10m    rate=30r/s;
limit_req_zone $binary_remote_addr zone=auth:10m   rate=5r/m;
limit_req_zone $binary_remote_addr zone=write:10m  rate=2r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;

# ── 第 2 段：写在各 server{} 内、且排在通用 location /api/ 【之前】
# 事实：浏览器永远带 /api 前缀（Web/Admin 的 axios baseURL=/api）；现有 location /api/ 是【前缀匹配】
#      + proxy_pass 带尾部斜杠 → Nginx 剥掉 /api 转发，所以能正常工作。
# ★ 但【正则 location 不可照抄这个写法】：nginx 官方明确"location 由正则定义时，无法确定被替换的
#   URI 部分，此时 proxy_pass 应不带 URI"。带了 URI 不报错，而是【URI 被忽略、按原始请求 URI 原样转发】
#   → 后端收到 /api/user/login 而 404，属【静默走错路】。正则 location 一律 rewrite + 不带 URI。
location = /api/user/login {                     # 精确匹配带 URI 是【合法】的：整个匹配串被替换
    limit_req zone=auth burst=5 nodelay;
    proxy_pass http://backend_servers/user/login;
}
location ~ ^/api/user/(register|forgot-password|reset-password|login/email)$ {
    limit_req zone=auth burst=5 nodelay;
    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://backend_servers;
}
location ~ ^/api/(comments|messages|user/checkin)$ {
    limit_req zone=write burst=5 nodelay; limit_conn conn 6;
    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://backend_servers;
}
location /api/upload/ { limit_req zone=write burst=3; client_max_body_size 100M; proxy_pass http://backend_servers/; }
location /api/        { limit_req zone=all burst=60 nodelay; …原有指令保持不变… }
```

**五条实施注意（已核）**：

1. **能用 `location =` 精确匹配或前缀匹配就别用正则** —— 少一层心智负担。
2. `limit_req_status 429;` 写在 http/server 级：默认 503 让前端无法区分"被限流"与"服务挂了"。
3. **`conf.d` 是 `Nginx/Dockerfile:10` COPY 进镜像**（非挂载卷）→ 改完 `docker compose build nginx`；替换前容器内 `nginx -t`，一处缩进错误整站 502。
4. `ai-proxy.include` 内容是 **4 个 `location` 块**（首行 `location ^~ /api/internal/ { return 404; }`），只能在 **server 级** include；放进 `location{}` 内非法（location 不可嵌套）。给 SSE 限流要在该 include **之前**写独立的 stream location 并重复 `/ai/` 的 proxy 指令（含 `proxy_buffering off`）。
5. 若将来挂 CDN，`$binary_remote_addr` 会变成 CDN 回源 IP → 必须先配 `set_real_ip_from <CDN 段>` + `real_ip_header`。

**应用层还要不要再限一次？** 要，只为**按用户/按 token** 维度。AI 侧 `AiRateLimitInterceptor` **已注册生效**（`AiSecurityWebConfig.java:22-27`），覆盖含 `/ai/chat/stream` 的 4 个路径、超限返回 429。三个缺陷：

| 缺陷 | 证据 | 修正（上一版建议已自我推翻） |
| --- | --- | --- |
| 超 10000 键 `buckets.clear()` 全清 → 反向 DoS 放大器 | `AiRateLimitInterceptor.java:117-119`（≥30 s 才触发，且在 `removeIf`(TTL 180 s) 之后） | **换 Caffeine `maximumSize` 不是修复**（逐出同样清零，攻击者造新键可持续挤掉正常用户；且 Caffeine 是 W-TinyLFU 不是 LRU）→ **溢出 fail-closed**，或给已知 IP 独立命名空间 |

## 4. 异步执行器（L1 的地基）

事实：**全仓零 `@EnableAsync`、零 `ThreadPoolTaskExecutor`**；`@Scheduled` 跑在 Spring 默认**单线程** scheduler。主后端 `ImageUsageReconcileService.java:47`(02:55) 与 `OrphanImageCleanupService.java:42`(03:00) 是长任务且**均无 `@ConditionalOnProperty`** → 多副本会各跑一份（cron 错峰≠互斥）。

**⚠ 上一版的接线是坏的**：`@EnableAsync` 只有在**恰好一个** `TaskExecutor` bean 时才拿它当默认；同时定义 `logExecutor` + `ioExecutor` 且无 `@Primary`/`AsyncConfigurer` → Spring **静默退回 `SimpleAsyncTaskExecutor`（每次新建线程、无界）**，而且 Boot 自带的 `applicationTaskExecutor` 会因为已存在 Executor bean 而退让 —— 结果是"配了两个有界池，实际一个都没用上"。

```java
@EnableAsync
@Configuration
public class AsyncConfig implements AsyncConfigurer {          // ★ 显式指定默认执行器
    @Override public Executor getAsyncExecutor() { return logExecutor(); }
    @Override public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, m, args) -> log.error("异步任务未捕获异常 {}", m.getName(), ex);
    }
    @Bean("logExecutor")
    public ThreadPoolTaskExecutor logExecutor() {
        ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(2); e.setMaxPoolSize(4); e.setQueueCapacity(2000);   // ★ 有界
        e.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());  // 满则回落调用线程，绝不静默丢
        e.setWaitForTasksToCompleteOnShutdown(true); e.setAwaitTerminationSeconds(20);
        e.setThreadNamePrefix("oplog-");
        // ★ MDC 只有一把 key：traceId（RequestTraceFilter.java:26，两服务同名）→ 复制它就够
        e.setTaskDecorator(r -> { String t = org.slf4j.MDC.get("traceId");
                                  return () -> { org.slf4j.MDC.put("traceId", t); try { r.run(); } finally { org.slf4j.MDC.remove("traceId"); } }; });
        return e;
    }
    @Bean("ioExecutor")   // SMTP / COS 补偿：慢且必须与请求线程隔离
    public ThreadPoolTaskExecutor ioExecutor() {
        ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(2); e.setMaxPoolSize(4); e.setQueueCapacity(200);
        e.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());   // 补偿类任务：拒绝即记失败，下轮重试
        e.setWaitForTasksToCompleteOnShutdown(true); e.setAwaitTerminationSeconds(10);
        e.setThreadNamePrefix("ext-io-");
        return e;                                   // ★ 真实返回，不是 null：@Bean 返回 null 会让容器语义混乱
    }
    // 注意：@Async 默认只走 getAsyncExecutor() 返回的那个（logExecutor）；
    //       要落到 ioExecutor，调用点必须显式写 @Async("ioExecutor")。
}
```

> 若不想实现 `AsyncConfigurer`，替代方案是**每个调用点写 `@Async("logExecutor")`** —— 但漏一处就静默走无界池，不如集中配。

三条纪律：① **有界队列 + 显式拒绝策略，没有例外**；② `@Async` 不得自调用（与 `01` §2.1 的 `@Cacheable` 自调用同坑）；③ 异步化只改执行线程，**不改"是否记录"**（`跨服务规范.md:71`）。

**操作日志异步化可行**：`OperationLogAspect` 在请求线程上的全部外部读取点是 `:71`（`RequestContextHolder`）、`:78`（`userUtils.getCurrentUser()`）、`:87`（IP）、`:88`（UA）、`:97-105`（SpEL）→ **必须在提交任务前取完值**，否则异步线程里两个 ThreadLocal 都是空的（异步化最常见的踩坑点）。

## 11. 陷阱与约束

- **白名单是本仓库最容易"改出静默 403/静默放行"的地方**：`SecurityWhitelist` 与 `SecurityConfig` 是一对必须同步的集合，且**没有任何测试覆盖**（已 grep）。任何档位调整都必须手工回归：匿名访问、带 token 访问、`/uploads/resources/**` 仍被拒、`/internal/**` 仍 403。
- **权限来源必须继续取 DB role**：`JwtAuthenticationFilter.java:125-126` 用数据库 `role` 而非 token claim 建权限（降级即时生效）—— 做 `§1.2` 的状态缓存时若图省事改读 token 里的 `role`，会静默削弱这个性质。缓存值必须带 DB role。
- **调小 `connection-timeout`（15 s → 5 s）会把"慢慢排队成功"变成"快速失败"**：必须与 `§3` 限流、`§1` 降载同批上线，否则先看到错误率上升。
- `Optional` 化鉴权后，**`/posts/{id}` 的响应会开始随用户变化** → 边缘缓存策略必须同步收紧（`01` §2.3 的"绝不可缓存"清单）。这是性能改动与安全改动的**耦合点**，不要分两拨人做。
- **Nginx 改完要重建镜像**（`Nginx/Dockerfile:10` 是 COPY 不是挂载），并且**先 `nginx -t`**。
- 不要用"关掉鉴权"来让压测脚本能跑 —— 那会让基线与真实形态不一致（`06` §1）。
