# 04 · 流式与 IO 密集接口（类型 G / H）

> 覆盖：`POST /ai/{chat,writing}/stream`、`POST /ai/{chat,writing}`、TTS 全链路、`/api/upload/*`（**13** 个 handler）、`/resource/download/{id}`、`/resource/download-url/{id}`、`/resource/check/{id}`、`/ai/tts/audio/{file}`、`POST /admin/announcements/{export,import}`
> 环境事实：Spring Boot **4.1.0**（版本在**根聚合 `pom.xml:19`**，不是各服务 pom）、Spring Framework 7.x、Spring AI 2.0.0（`LiuTech-AI/pom.xml:24`）、JDK 21 `eclipse-temurin:21-jre-alpine`（两个 `Dockerfile:1`）、Servlet/Tomcat 非 reactive。
> **修订说明（第三轮）**：本轮推翻本文件第二版最核心的一处判断 —— **`streamExecutor` 的 16 个线程根本不约束并发流数量**，因此"第 17 条流被拒/静默排队"的整条叙事与验收前提都是假的；`CallerRunsPolicy` 建议会**把一条流的阻塞变成全部流的阻塞**。逐条见 `§8`。

## 1. 判据

### 1a 流式长任务

> **一条长连接的容量成本 = 它占用的资源数 × 存活时间。**

四条硬要求：**显式配额**（超限立即拒绝，不排队到超时）、**取消传播**（客户端断开 → 上游中止）、**超时闭环**（每层都有且外层 > 内层）、**单一写者**（多写者 + 慢读者互相阻塞）。

已做对、**不要推翻**的：流式不占 Tomcat 线程（`:132` 立即返回 emitter）；15 s 心跳跨 CDN 保活（`:65-67,173-181`）；TTS 分段异步不阻塞文本流（`:561-578`）；Nginx `proxy_buffering off` + 高 `proxy_read_timeout` 已配对（`ai-proxy.include:53-55`）。

### 1b 文件与 IO 密集

> **一个字节都不该进 JVM 堆，除非业务必须处理它。** 最优形态是让数据绕过应用服务器。

## 2. 现状

### 2.0 先纠正约束点（本文件最重要的一条）

```text
runOnStreamPool(...) 提交的入口任务（:154）只做：
    组装 prompt → 同步 DB 写（建会话/存用户消息）→ flux.subscribe(...) → 【立即返回】
而 onNext / onComplete 回调运行在 JDK HttpClient 的响应线程上，不在 streamExecutor 上
（streamChat 返回 chatClient…stream().content()，SiliconFlowChatClient.java:126-128）
```

| 第二版（及以前）的说法 | 真实情况 |
| --- | --- |
| "16 线程 = 最多 16 并发流" | ❌ **`streamExecutor` 不约束并发流数**。池线程只在"prompt 组装 + 前处理 DB 写"这段亚秒工作期间被占用 |
| "第 17 条流静默排队到 300 s 超时" | ❌ 前提不成立。无界队列在流式场景几乎不积压；真正的并发上限是 **JDK HttpClient 的连接数（无上限）** 与 **上游 LLM 配额/费用** |
| "改成有界 + AbortPolicy 即可快速失败" | ⚠️ 部分成立且**有坑**，见下 |
| —— | ✅ **只有显式 permit 计数器（信号量）才提供并发流上限**。这是唯一必须新建的机制；线程池改造是次要的 |

**AbortPolicy 的坑**：`:461` 的 audio-complete 尾等任务是在**另一个池任务内部再次 submit**，其内部会阻塞等待 TTS future 最长约 300 s（`:465`）。整池换有界 + `AbortPolicy` 后，尾任务可能被自己拒绝 → 不发 `audio-complete`、不 `complete()` → **僵尸流 + permit 泄漏**。
**⚠ 绝不要采纳"整池改 `CallerRunsPolicy`"**（第二版给过这条）：那会把 300 s 的阻塞等待跑在**共享的 HTTP 响应线程**上 → 一条流卡住**全部**流。正确做法：尾等走**独立小池**，或改成非阻塞的"完成回调 + 超时定时器"。

## 3. 目标设计

### 3.1 生命周期：四条终止路径共用一个幂等 `release()`

```text
CREATED ──acquire──▶ RUNNING ─┬─ onComplete ─▶ 存全量(status=1)
     （失败立即 429）           ├─ onError     ─▶ 存 partial（:391-400 已有）
                               ├─ onTimeout   ─▶ 存 partial
                               └─ clientAbort ─▶ dispose 上游 + 存 partial
release() = ① disposable.dispose() ② shutdown 心跳/TTS 池 ③ 归还 permit ④ 落库
```

两个必须写对的细节：

1. **`release()` 里的落库要带"是否已落库"标志**。正常完成路径已在 `:195` 存过 `status=1` 的助手消息，`onCompletion` 再 `savePartial()` 会**写第二条助手消息**（第二版方案自带的 bug）。
2. **permit 必须在 `new SseEmitter`（`:132`）之前获取**。`onCompletion` 在 `:139` 注册、`runOnStreamPool` 到 `:154` 才调用；若异常发生在两者之间，异步上下文从未启动 → **`onCompletion` 永不触发** → permit 永久泄漏。

### 3.2 配额与取消（按本仓库真实依赖）

```java
// ① 并发流上限只能靠 permit（§2.0）
//    AI 服务【没有 Caffeine 依赖】→ 仿仓库既有实现：AiRateLimitInterceptor 的
//    ConcurrentHashMap + maxTrackedKeys + 惰性清理（属跨服务规范对"有状态业务缓存"的豁免范畴）
//    键要覆盖游客：游客 userId 为 null（:127-128）→ 用 userId 作键会 NPE，需退化到 IP
//    （复用 AiRateLimitInterceptor.java:158-166 的 resolveClientIp 口径，保持两服务一致）
if (!tryAcquirePermit(identityKey, conversationId)) {          // ★ 在 :132 建 emitter 之前
    throw new ResponseStatusException(HttpStatus.TOO_MANY_REQUESTS, "AI 繁忙或您已有进行中的对话");
}
// 已核实：REE 由 CompletableFuture.runAsync 在 servlet 线程【同步】抛出。
//   普通请求会落 GlobalExceptionHandler.java:89-98 = HTTP 500；
//   但 SSE 请求【不落 500】：:92 有 `if (response.isCommitted() || WebUtils.isSseRequest(request)) return null;`
//   而 WebUtils.java:16-21 判定 SSE 的条件是 Accept 含 text/event-stream 且 URI 含 /stream（两者本例都满足）
//   → 兜底 handler 直接返回 null = 空 body。
// ⚠ 关键差异：ResponseStatusException 的专属 handler（:67-71）**没有**这个 SSE 守卫 ——
//   它 setStatus(429) 后用 Jackson 写 Map，而 text/event-stream 写不了 JSON，
//   406 会被 ExceptionHandlerExceptionResolver 吞掉 ⇒ 客户端实际看到的是【429 + 空 body】，不是 406 也不是 500。
//   → V-18 的验证目标据此改写：确认 429 状态码可被前端识别；若要给 SSE 一个可读错误，
//     必须在建流前用"发一个 error 事件再 complete"的方式，而不是抛 ResponseStatusException。

// ② 取消传播
Disposable sub = flux.subscribe(onNext, onError, onComplete);
streamReg.register(conversationId, sub);
release = () -> { if (released.compareAndSet(false, true)) { sub.dispose(); shutdownPools();
                  releasePermit(); savePartialIfNotSaved(); } };
emitter.onCompletion(release);                  // 唯一覆盖全部终止路径的回调
// onNext 首行：if (emitterClosed.get()) { sub.dispose(); return; }；并放宽 catch 类型

// ③ 尾等任务走独立小池（绝不能 CallerRunsPolicy，见 §2.0）
```

线程池本身（`:89`）改有界仍**有益但非关键**：它保护的是"prompt 组装 + 前处理 DB 写"这段亚秒工作不被无限排队，与并发流数无关。
另需 `POST /ai/chat/cancel`（带 `conversationId`）：给服务端一条显式取消通道，不依赖 TCP 半关闭。

### 3.3 单一写者与背压

所有 SSE 写经 `synchronized (emitter)`（`SseEmitterHelper.java:41`）；要改成"写失败即视为断连并 `release()`"的位置是 `§2.1` 第 3 条列出的 **6 处调用点**。

改单写者（每流一个有界 `BlockingQueue` + 单序列线程）必须同步处理三件事：

1. **排序键**：`audio`（`:569`，TTS 线程发）与 `avatar-cue`（`:506`，flux 线程发）现在靠 `seq` 对齐 → 入队序 ≠ `seq` 序，必须按 `seq` 重排后再写。
2. **尾等**：`:460-487` 在另一线程 send → 改单写者后必须"offer 事件 + 队列排空后才 `complete()`"。
3. **异常类型**：`onNext` 现只 catch `IOException`，队列满/中断抛的是别的类型，catch 需同步放宽。

### 3.4 资源复用

心跳改共享 `ScheduledExecutorService(1)` + 每流 `ScheduledFuture`（`release()` 里 `cancel(false)`）；TTS 不再每流建池，改共享有界池 + 每流配额，与全局 `ttsSemaphore`（`TtsSpeechService.java:70-73`）**合并为一层**（现在两层并发控制会互相等待）。

### 3.5 熔断

**只有同步端点需要调阈值**。`slowCallDurationThreshold=2s` 相对同步调用（read 90 s）明显过低，需上调 —— 但**具体值要等实测**（`06` V-19），不要在无数据时改配置。若要更细，把同步与流式拆成两个 breaker 实例（零新依赖，`resilience4j-config.yml` 加 instance）。

### 3.6 超时矩阵

| 层 | 现状（行号已核） | 建议 | 说明 |
| --- | --- | --- | --- |
| Nginx `proxy_read_timeout` | 3600 s（`ai-proxy.include:54`；`:53` 是 `proxy_request_buffering off`，`proxy_send_timeout` 在 `:55`） | **只需 > async 超时** | 15 s 心跳使任何 >15 s 的空闲超时都不会因空闲触发；调小只为兜住异常挂起 |

## 6. 虚拟线程（Boot 4.1.0 支持，但先看清代价）

`spring.threads.virtual.enabled=true` 可用。适合类型 F/H 的长阻塞 IO。**但 AI 服务有 8 处 `synchronized` 会造成 carrier thread pinning**（第二版只列 3 处）：`SseEmitterHelper.java:41`、`PromptService.java:406`、`:454`、`TtsConfigService.java:71`、`AiRateLimitInterceptor.java:51`、`:65`、`WritingToolEventSink.java:76`、`StreamingChatService.java:359`（`Collections.synchronizedList`）。上虚拟线程前需逐个换 `ReentrantLock`。
且它**不解决配额问题**（并发流的真实约束是上游配额与费用，见 `§2.0`），也只把排队搬到连接池。**顺序：先 `§3.2` permit 与 `§5.1` 流式上传，再考虑虚拟线程。**

## 9. 陷阱与约束

- **改 SSE 必须同时改两端镜像文件，否则 CI 直接失败。** `Web` 与 `Admin` 是两个独立 Vite 根，SSE 协议解析与写作助手流式客户端以**镜像文件**维护，`scripts/check-mirrored-modules.mjs`（CI job `frontend-contract`，`.github/workflows/ci.yml:67-76`；镜像文件对共 **3 对**：`sse.ts`、`writingStream.ts`、`rich-content.css`，见 mjs `:33-35`）专门校验一致性；脚本注释记录过真实事故：Admin 那份有 429 限流提示与错误码上抛、Web 那份没有。本文件新增的事件类型（取消通道、事件重排）必须**两份同改**。
- **SSE 事件协议与 `isCommitted()` 分支不可动**（`跨服务规范.md:45`）：配额、取消、单写者改造必须做到**线上协议字节级不变**。
- **`emitter.send()` 在完成态抛 `IllegalStateException` 而非 `IOException`**，而 `:385-388` 只 catch `IOException` → 改单写者/背压时若换了异常类型，旧 catch 会静默失效（`§3.3` 第 3 点）。
- **心跳是唯一能穿透 CDN 空闲超时的机制**（`Docs/架构/前端/看板娘/SSE流式与心跳机制.md`）。当前 `proxy_read_timeout 3600s` 意味着真正约束来自应用层而非 Nginx。
- **`AiChatProperties.java:21` 的 120 s 与 `application.yml:90` 的 300 s 不一致** —— 改超时前先确认哪个真正被绑定，否则会出现"改了配置没生效"。
- **TTS 缓存目录是本地盘**（`LiuTech-AI/src/main/resources/application-prod.yml:17` = `${TTS_CACHE_DIR:/app/tts-cache}`）→ 多副本时 A 副本合成的文件 B 副本取不到（404）。这比"改哈希命名"更早撞上。
- **前端测试极薄**：`Web/src/__tests__/` 只有 4 个文件（`sseStream`、`chatTts`、`postListing`、`audioLipSync`），`Admin` **没有** test 脚本 → 流式改动几乎没有自动化回归网（`06` §7）。
- **不要用生产 API Key 压满并发**：按 token 计费，且流式不受熔断保护（`§2.1` 第 11 条）→ 流式压测的失败模式是"上游排队"，不是本地跳闸。

## 10. 第四轮补充：AI 服务清单盲查反校结果

> 本节由"先只读代码独立推清单、最后才对比我的归类"的盲查得出，证据均已二次复核。

### 10.1 【新发现·P0】会话属主只在读路径上偶然生效，写路径完全不校验

```java
// MemoryService.java  saveUserMessage(userId, conversationId, …)
m.setUserId(userId);                  // 调用者自己的 id
m.setConversationId(conversationId);  // ★ 客户端传入，无任何属主校验
messageMapper.insert(m);
touchConversation(conversationId);    // selectById 后 message_count+1 并 updateById，同样不校验属主
```

影响链（逐环已核）：

1. 已登录用户 A 调 `POST /ai/chat` 或 `/ai/chat/stream`，带用户 B 的 `conversationId`（`ChatRequest:65` 无 `@Valid`/白名单校验）→ **一条消息被写进 B 的会话**，同时 B 会话的 `message_count`、`last_message_at` 被改。
2. B 打开自己的会话：`listMessagesByConversation` 先 `getConversationOwnedByUser(B, id)`（B 当然通过），随后**只按 `conversationId` 过滤** → **A 注入的消息出现在 B 的界面里**。
3. 同一过滤方式也用于提示词装配（`listLastMessagesByConversation`）→ **A 的文本会进入 B 的 LLM 上下文**，属内容/提示注入。
4. 属主校验目前"看起来存在"，只是因为读路径 `limit > 0` 才顺带执行：`listLastMessagesAsPromptMessages` 与 `listLastMessagesByConversation` **第一行都是 `if (limit <= 0) return …`**，早于 `getConversationOwnedByUser`。现配置 `chat-history-limit: 14`（`application.yml:85`）所以读校验会跑；**把历史长度设为 0（"关闭历史"这种合理配置）就会连读路径的校验一起跳过**。

修法（必须做在读/写两侧，不能只补读侧）：

```java
// 进入任何会话写/读之前，唯一入口化：
AiConversation c = memoryService.getConversationOwnedByUser(userIdStr, conversationId);  // 不通过即抛业务码
// saveUserMessage / touchConversation / getMaxSeqNo 一律接收"已校验过的会话对象"，不再收裸 conversationId
```

**DB 层兜底（比应用层校验更可靠，能防未来新增调用点再漏校验）** —— 上一版我在这里只写了"用 `idx_user_created` 组合断言"，那是含糊话：**索引不是约束**，拦不住任何写入。真正可行的是组合外键，两侧列类型已核对（父 `ai_conversation.id BIGINT UNSIGNED` + `user_id VARCHAR(64) NOT NULL`；子 `conversation_id BIGINT UNSIGNED` + `user_id VARCHAR(64) NOT NULL`）：

```sql
-- 1) 先查存量违规（有则必须先修数据，否则 ALTER 直接失败）
SELECT m.id, m.conversation_id, m.user_id AS msg_user, c.user_id AS conv_user
  FROM ai_chat_message m JOIN ai_conversation c ON c.id = m.conversation_id
 WHERE m.user_id <> c.user_id;

-- 2) 父表提供组合候选键
ALTER TABLE ai_conversation ADD UNIQUE KEY uk_id_user (id, user_id);

-- 3) 用组合外键替换现有单列外键 fk_message_conversation（sql.sql 内定义），保留 CASCADE 语义
ALTER TABLE ai_chat_message DROP FOREIGN KEY fk_message_conversation;
ALTER TABLE ai_chat_message ADD CONSTRAINT fk_msg_owner
  FOREIGN KEY (conversation_id, user_id) REFERENCES ai_conversation (id, user_id) ON DELETE CASCADE;
```

生效后可能关系变成：**"`user_id` 与所属会话的 `user_id` 不一致的消息行"根本无法插入** —— 越权写从"要靠每个调用点记得校验"变成 DB 拒绝。

前置确认三件：① `ai_conversation.user_id` 在业务上**永不被改** —— 已核：仅 `MemoryService:176` 创建时写入，`:127/:297/:308` 的 `updateById` 都是把 `selectById` 载入的对象**原值写回**，全仓不存在对 `AiConversation.user_id` 的改写点（`grep setUserId` 在会话相关代码里 0 命中）。若将来加"转移会话属主"功能，这条组合外键会直接挡住它 —— 届时要显式设计，而不是发现写不进去；② 子表上原 `fk_message_conversation` 必须一并处理，否则同列两个外键冗余；③ DDL 需 root，且按 `03` §4 的双写规则同时回填 `Docs/SQL/sql.sql`。应用层的 `getConversationOwnedByUser` 校验**仍然必须补在读/写两侧**（DB 约束只保证一致性，不替代"拒绝并返回业务码"的语义）。
