# 06 · 压测基线与观测落地（验收前置）

> **为什么这份文档必须最先做。** 外部审查与本仓库自我审计达成的核心共识是：`总览`~`05` 里所有耗时、QPS、命中率、"贵两个数量级"之类的说法**全部是由配置推导的估测，没有一个是实测值**；而且**当前这套部署根本拿不到实测值**（主后端没有暴露指标、应用账号没有排障权限）。所以在补好测量能力之前，任何"优化效果"都是不可证伪的陈述。
> 本文只写**已核实的事实**与**最小可执行步骤**。

## 1. 阻塞项（已核实为"当前不可用"）

> **第 0 项是安全前置，不是可选项。** `default.conf:73-74` 的 `location /api/` + 尾部斜杠 `proxy_pass http://backend_servers/` 会让 `/api/actuator/health` **现在就公网可达**（已核实 Nginx 未显式代理也未屏蔽 `/actuator`）。一旦按下面第 1、2 项打开 prometheus 端点，`/api/actuator/prometheus` 会把 SQL 耗时、连接池、JVM 明细直接暴露到公网。
> **所以顺序必须是：先加屏蔽，再开端点。**

```nginx
# 与"暴露指标"同批提交，写在 conf.d/default.conf 的每个 server{} 内、location /api/ 之前
location ^~ /api/actuator/ { deny all; return 404; }     # 需要保留健康检查则单独放行 /api/actuator/health
location ^~ /ai/actuator/  { deny all; return 404; }
```

## 2. 基线口径（先把"要什么数"定死，再动手）

对**每一类**选 1~2 个代表端点，固定记录这 5 个数（改前 / 改后各一次，同机同温）：

| 指标 | 定义 | 取法 |
| --- | --- | --- |
| P50 / P95 / **P99** | 延迟分布，**不看均值** | 压测工具输出；或 `http_server_requests_seconds` 的 histogram |
| 每请求 SQL 往返数 | 本项目最关键的 KPI（决定连接占用时间） | 临时开 `mybatis-plus.configuration.log-impl: StdOutImpl` 或 `logging.level.chat.liuxin.liutech.mapper: DEBUG` **数条数**，测完必须关（`跨服务规范.md:75` 禁止业务包整体 DEBUG） |
| 连接池饱和度 | `hikaricp_connections_pending`、`hikaricp_connections_active` | §1-1 修复后 `/actuator/prometheus` |
| MySQL 侧压力 | `threads_running`、`innodb_row_lock_time_avg`、慢日志条数 | §1-4/7 修复后 |
| 缓存命中率 | Caffeine 统计（`CacheConfig.java:67` 已 `recordStats`）。注意 Boot 暴露的是 `cache_gets_total{result=…}` 这类计数器，**不是** `CacheStats` 对象，实际指标名待 V-14 确认 | 需先按 §1-1/2 暴露 `/actuator/prometheus`；现成的 `GET /admin/cache/names` 只给名字，不给统计 |

## 3. 可复制的最小压测脚本

```bash
# 前置：export HOST=https://liutech.chat  TOKEN=<ADMIN 或 用户 JWT>   （30 天有效期，application.yml:109）
# 1) 匿名只读：列表缓存命中 vs 击穿（先清缓存再打 = 击穿；不清 = 命中）
curl -s "$HOST/api/carousels" -o /dev/null -w 'p50-ish=%{time_total}s status=%{http_code}\n'
for i in $(seq 1 200); do
  curl -s "$HOST/api/posts?page=1&size=10&sort=latest" -o /dev/null -w "%{time_total}\n" &
done; wait

# 2) 详情：验证"读时行锁写"是否已移出（改造前重点项）
for i in $(seq 1 200); do curl -s "$HOST/api/posts/1" -o /dev/null -w "%{time_total}\n" & done; wait

# 3) 需鉴权的写：签到幂等（期望 1 行 + 无 5xx）
for i in $(seq 1 50); do
  curl -s -X POST "$HOST/api/user/checkin" -H "Authorization: Bearer $TOKEN" -w "%{http_code}\n" -o /dev/null &
done; wait

# 4) SSE 取消传播：3 秒后主动断开，然后立刻再开一条 —— 若能立即建立说明配额已释放
timeout 3 curl -sN -X POST "$HOST/ai/chat/stream" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" -d '{"message":"你好"}' | head -5

# 5) 并发流配额：同用户同时开 3 条，第 3 条应【立即】失败，而不是静默等到超时
```

> 注意浏览器/前端永远走 `/api/` 前缀（Nginx 剥前缀转发），`/ai/` 原样透传。**不要用裸 `/user/login` 这类路径压测** —— 那不是我第一轮文档里的写法，而是真实路由下的错误写法（见 `05` §3）。

## 6. 陷阱

- 打开 MyBatis SQL 日志数语句条数之后**必须还原**：生产 `root: INFO`，业务包 DEBUG 会打印参数与结果，既泄露数据又放大 IO（`跨服务规范.md:75`）。
- 用 `ab` 压带 JWT 的接口时要注意 token 有效期与"同一用户"造成的缓存/行锁串行化 —— 那测的是**单用户路径**，不是多用户命中率。多用户命中率需要 N 个 token 轮换。
- 压测会污染真实数据（`admin_logs`/`system_logs` 会被写爆、`points_transactions` 会有测试流水）。在隔离环境或专门的测试用户/测试文章上做，并记录清理语句。
- 不要在开发机上压生产：compose 里 mysql 未限资源，两个 JVM 各限 2C/2G，压测会把同机其它服务一起拖慢。
- 基线表要连**当时的配置**一起存档（commit hash、`application.yml` 摘要、宿主机规格、是否重启过容器），否则两周后的复测不可比。

## 7. 回归网：现有测试能当哪一级门禁（新增，重要）

**实测基线（2026-09-26 本机 `mvn test`，按 surefire 产物核对而非退出码）**：主后端 **499 个测试全绿**（51 个报告文件，`failures=0 errors=0 skipped=0`）、AI 服务 **96 个全绿**（16 个报告），合计 **623 全绿**（另 Web 前端 vitest **4 文件 / 28 用例**，1.03 s，`EXIT=0` 取自日志行而非通知）。本地可离线构建（依赖已缓存），三层门禁随时可复现 —— 这也是本文档集唯一一组**实测**数字。

**但 623 这个数字恰恰证明不了任何并发结论**：仓库共 **67 个测试类**（主后端 51 + AI 服务 16），CI 会跑 —— `.github/workflows/ci.yml:52`（`mvn -f LiuTech/pom.xml test`）、`:65`（AI 服务）、`:93`（`Web` 的 `npm test`）。注意**只有 `Web` 前端有 `test` 脚本**（`Web/package.json:10` = `vitest run`），`Admin/package.json` **没有** → Admin 侧只有构建 job，改 Admin 时 CI 不会给你任何测试信号。

测试风格是**纯 Mockito 单测**：两个后端的 `@SpringBootTest` 均为 **0**，控制器直接 `new` 出来（如 `PostsControllerTest.java:36` `new PostsController(postsService, postInteractionService, viewHistoryService, userUtils)`），Service 与依赖全是 `mock(...)`。

由此得到三条必须遵守的结论：

| 结论 | 影响 |
| --- | --- |
| **`mvn test` 不能为本套文档的任何一条并发/缓存/SQL 建议作证** | 不起 Spring 上下文 → `@Cacheable`、`@Transactional`、MyBatis 代理**全部不生效**；无数据库 → 索引、行锁、幂等约束、`EXPLAIN` 一律不覆盖。把 CI 绿当作"优化已验证"是**假信号** |
| 但 CI 是**行为契约的守卫**，改动会真红 | `PostsControllerTest.java:189,200,231` 断言 `toggleLike`/`toggleFavorite` 返回字符串 `"liked"`/`"unliked"`/`"favorited"`；`:322,332` 断言 `recordView` 的调用与否。→ `02` §2.2 提议把 toggle 改成 `PUT + {liked}` **必然破坏这些断言**，属于"契约变更"，必须连测试一起改，不能只改后端 |
| 构造器直连意味着**改依赖签名会连锁改测试** | 新增 `UserAuthStateCache`、`PostBodyResp`、`ViewCountBuffer` 等 bean 会改控制器/Service 构造器参数（`@RequiredArgsConstructor`），15 个 mock 型测试类需同步更新 |

**因此每步改动的完整门禁应是三层**，缺一层就等于没验：

1. **CI 三层**：`mvn -f LiuTech/pom.xml test` + `mvn -f LiuTech-AI/pom.xml test` + `Web` 的 `npm test`（**Admin 没有测试脚本，改 Admin 只能靠人工回归**）——现状能力，只保证不破坏行为契约；
2. **集成/并发验证**：`02` §8 与 `03` §6 的并发打点与 `EXPLAIN` 回归 —— **当前仓库没有这一层自动化**，需要手工跑或补一批真正起上下文的集成测试（可用 `@SpringBootTest` + Testcontainers MySQL，依赖已具备 CI 环境；这属于新增能力，需你决定是否投入）；
3. **压测与指标**：本文件 §2/§3（前提是 §1 的观测补齐已完成）。

**建议**：若只做一件事，就做第 2 层的**最小版** —— 给 3 个最关键场景补集成测试（签到并发唯一键、点赞重放幂等、恢复文章不丢点赞计数），它们能同时守住 `02` §2.3 那三个真实数据缺陷不复发。这比引入压测流水线的收益更直接，也更容易维持。
