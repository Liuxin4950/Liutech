# 01 · 只读与缓存类接口（类型 A / B / C）

> 覆盖：`/carousels` `/about` `/categories(/​{id})` `/tags(/hot|/​{id}|/post/​{postId}|/search)` `/series(/​{id})` `/announcements/*` `/music/*` `/sitemap.xml` `/posts/*` `/comments/post/​{postId}/*` `/messages/public` 等约 45 个只读端点。
> **修订说明（第三轮）**：本轮查出我上一版**照抄即挂**的三处错误 —— ① `unless = "#result.isEmpty()"` 作用在 `PageResp` 上会抛 `SpelEvaluationException`（该类**没有** `isEmpty()`）→ 每次调用 500；② `images` 的生成列表达式与真实去重谓词不一致，上线后**重复哈希会撞 1062 打挂上传**；③ `aboutPage` "无失效路径"是我误判。逐条见 `§7`。

---

## 1. 判据

> **只读接口的优秀程度只由一个问题决定：这个请求有没有必要走到 MySQL。**

四条公理：① 能缓存就缓存，且**键基数必须可控**；② 未命中时**同键只允许一个请求回源**；③ **公开内容与"我的状态"必须分层**，混在一个键里会让缓存按在线用户数裂变；④ 读路径**绝不写库**（见 `03`）。

### 2.3 边缘层：Nginx 微缓存与击穿保护

```nginx
# 写在 Nginx/conf.d/default.conf 的【文件顶层】。nginx.conf:53 已把 conf.d/*.conf include 在
# http{} 内部 → 再包一层 http{} 是配置错误。
proxy_cache_path /var/cache/nginx/api levels=1:2 keys_zone=apicache:20m
                 max_size=200m inactive=10m use_temp_path=off;

# ★ 正则 location 必须配 rewrite + 不带 URI 的 proxy_pass，理由见下方"正则规则"
location ~ ^/api/(carousels|about|categories|tags|series|posts/(hot|latest))$ {
    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://backend_servers;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    include conf.d/cors.include;                    # cors.include 是裸 add_header，可在 location 内 include
    proxy_cache apicache;
    proxy_cache_valid 200 15s;                      # 边缘要"短"，正确性由应用层 TTL 兜底
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
    proxy_cache_lock on;                            # ★ 击穿保护：同键只放一个请求回源
    proxy_cache_background_update on;               # ★ stale-while-revalidate
    add_header X-Cache-Status $upstream_cache_status always;
}
location = /sitemap.xml {                           # 已有该 location（default.conf:55-61），内部补三行
    proxy_cache apicache; proxy_cache_valid 200 2m; proxy_cache_lock on;
}
```

**三条必须知道的约束**：

1. **正则 location 与 `proxy_pass` 的 URI**：nginx 官方文档明确"当 location 由正则表达式定义时，无法确定要被替换的 URI 部分，此时 `proxy_pass` 应当不带 URI"。这不是"未定义行为"——带了 URI **不报错**，而是该 URI 被忽略、按**原始请求 URI 原样转发** → **静默走错路径**（后端收到 `/api/carousels` 而 404）。因此正则 location 一律 `rewrite … break` + 不带 URI；`location = /exact/path` 这类精确匹配带 URI 是**正确**的。
2. **公告类端点不要上边缘缓存**：`/announcements/*` 的可见性由 `start_time/end_time` 决定（`§2.4` 第 1 条），15 s 边缘缓存会与应用层"过期后 ≤30 s 不可见"的验收口径叠加成 ~45 s。要么排除，要么把口径写成 ≤45 s —— 二者择一，**别两边各定一个数**。
3. **`conf.d` 是 `Nginx/Dockerfile:10` COPY 进镜像**（不是挂载卷）→ 改完必须 `docker compose build nginx`；替换前在容器内 `nginx -t`，一处缩进错误整站 502。

**绝不可缓存**：`/api/posts`、`/api/posts/{id}`、`/api/comments/**`、`/api/user/**` —— 它们会读当前用户（`PostsController.java:67,83` 的 `UserUtils.getCurrentUserId()`），而缓存键默认是 `$scheme$proxy_host$request_uri`，**不含 `Authorization`** → 会把第一个人的状态返回给全站。
可缓存性前提已核：后端 `STATELESS`（`SecurityConfig.java:91`）、CSRF 关闭（`:65`）、无 `Set-Cookie`、未开 `server.compression`（上游回 identity，`nginx.conf:36` 的 `gzip_vary on` 不产生编码变体）。

### 2.4 三个缓存正确性缺陷（第三轮修正）

| # | 缺陷 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **公告缓存冻结时间窗**：键只有 `#limit`，SQL 过滤 `start_time<=NOW() AND end_time>=NOW()`，且 `isValid` 在缓存时算好写死 | `AnnouncementsService.java:82` + `:595-597`；`AnnouncementsMapper.java:65-71` | 已到 `end_time` 的公告最长 10 min 仍展示；未到 `start_time` 的最长 10 min 不出现 |
| 2 | **缓存 null 且混用命名空间**：`getCategoryByName` 的 `@Cacheable` 无 `unless` → null 入缓存，重名校验读到 15 min 前的 null；且与 `List<CategoryResp>` 共用 `categories` 名 | `CategoriesService.java:129-131` vs `:51`；重名校验 `:154` | 可插入重名分类（唯一索引 `name` 会挡数据，但接口返回 500 而非业务码） |
| 3 | **改资料不会刷新关于页**（上一版这条写反了）：`aboutPage` **有**失效路径（`AboutPageService.java:45 updateAboutPage` 带 `@CacheEvict`，且它是 `SystemSettingService.upsert` 的唯一调用方）。真正的漏点是 `UserProfileService.java:67 updateProfile` 只清 `userStats`，而 aboutPage 缓存里含 `authorFrom(getDefaultProfile())` 读出的 `author.*` | `AboutPageService.java:40,45`、`UserProfileService.java:67,242-245` | 后台改作者资料后，关于页的作者信息最长陈旧 10 min |

修法：① 公告不缓存，或 TTL ≤ 30 s 且键加"时间桶"（`#limit + ':' + 5分钟槽`），到点由定时任务清；② 拆独立缓存名 `categoriesByName` + `unless = "#result == null"`；③ `updateProfile` 的 `@CacheEvict` 同时清 `userStats` 与 `aboutPage`（放 `afterCommit`）。

> 上一版"`AnnouncementsMapper.java:70` 处又不缓存地被调用"一句是**我的杜撰**（`:70` 是 SQL 字符串所在行）；`selectLatestAnnouncements` 的唯一调用点就是带缓存的 `AnnouncementsService.java:85`。

## 3. 类型 B：个性化分页列表

### 3.1 键必须覆盖"所有影响结果的输入"

`PostQueryReq` 共 9 字段：`page,size,categoryId,tagId,seriesId,keyword,sort,status,authorId`（`req/PostQueryReq.java:13-53`）；`selectPostListResp` 影响结果的参数是**这 9 个 + `userId`**（`PostsMapper.xml:410-425` 的 `<if test="userId != null">` 决定 `like_status/favorite_status` 与两张 JOIN）。

**现有键是完整的**（`PostsService.java:108` 覆盖 9 项 + `#userId`）→ 首轮审查说的"键漏了 keyword"针对的是**我文档里的示例**，不是你们的代码。真正的问题只是 `#userId` 让缓存裂变。

### 3.2 正确拆法

```java
// 公共列表：新增强制 userId=null 的方法；键覆盖 9 个入参并归一化 keyword
@Cacheable(value = "postList",
    key = "#req.page + ':' + #req.size + ':' + #req.sort + ':' "
        + "+ (#req.status ?: '-') + ':' + (#req.categoryId ?: '-') + ':' + (#req.tagId ?: '-') + ':' "
        + "+ (#req.seriesId ?: '-') + ':' + (#req.authorId ?: '-') + ':' "
        + "+ (T(org.springframework.util.StringUtils).hasText(#req.keyword) ? #req.keyword.trim().toLowerCase() : '-')",
    unless = "#result == null || #result.records.isEmpty()")      // ★ records，不是 #result
public PageResp<PostListResp> getPublicPostList(PostQueryReq req) {
    return getPostList(req, null);
}
```

三点必须说清（上一版这里有误）：

1. SpEL 合法性已核：Java 字符串拼接出的表达式语法成立，`?:`、`T(...)`、`+`（Integer 遇 String 走 concat，null 变 `"null"`）可用；`-parameters` 由 `spring-boot-starter-parent` 提供（现有 `:108` 已依赖）；`unless` 只用 `#result`，不涉及 `#req`。
2. **`getPublicPostList` 内部调 `getPostList` 是自调用，不经过代理** → 不存在"双层缓存"，因此**不需要**把 `@Cacheable` 从 `getPostList(req, userId)` 上移走。
3. 那注解**移走的唯一代价**是让 `/posts/my` 失去缓存 —— 两参版的真实调用方只有 `PostsController.java:77`（`/posts`）与 `:227`（`/posts/my`），而 `/posts/my` 按 `authorId` + 草稿态过滤，**无法复用公共方法**。→ 正确做法：保留两参版注解，另为私有视图各建**带用户维度的独立缓存实例**：

```java
buildCache("postMine",   2, 200);   // key 含 #userId，基数 = 作者数 × 页码，远小于全站用户 × 页码
buildCache("postDrafts", 1, 50);
```

`sort` 归一化目前只在 `/posts` 做了（`PostsController.java:75`），`/search`、`/drafts`、`/my` 未钳 → 键基数不可控，补同一行归一化。

### 3.6 唯一索引：NULL 语义与"表达式必须等于查询谓词"

MySQL 唯一索引视 `NULL` 互不相等，而活跃行 `deleted_at` 恰为 `NULL`（`logic-not-delete-value: "NULL"`）→ `UNIQUE(file_hash, deleted_at)` **约束不了任何活跃行**（上一版建议无效）。用 STORED 生成列把 NULL 变体：

```sql
-- ★ 表达式必须与真实去重谓词【逐字一致】。ImagesMapper.java:28 是
--   WHERE file_hash = ? AND deleted_at IS NULL AND status = 1
--   只判 deleted_at 会让"存在 status=0 的同哈希活跃行"时应用判为不存在 → INSERT → 撞 1062 → 上传 500
ALTER TABLE images ADD COLUMN active_hash VARCHAR(64)
  GENERATED ALWAYS AS (IF(deleted_at IS NULL AND status = 1, file_hash, NULL)) STORED,
  ADD UNIQUE KEY uk_active_hash (active_hash);
-- 列型用 VARCHAR(64) 与 file_hash 一致（sql.sql:495）；CHAR(64) 会被表达式类型覆盖，徒增误解
-- 合法性：STORED 生成列可建 UNIQUE、可引用 deleted_at、NULL 允许重复、64*4=256 字节 < 3072 上限
```

`post_attachments` 的上一版表达式**有两处错**：`bindDraftToPost`（`PostAttachmentsMapper.xml:21-26`）只 `SET post_id` **保留 `draft_key`** → 已绑定行仍以 `draft_key` 入键，**不是**"每 (post,resource) 唯一"；且 `draft_key`/`post_id` 双 NULL 时 `CONCAT_WS` 会跳过 NULL 得到裸 `resource_id` → **跨文章互撞**。正确写法（按"活跃 + 文章维度"唯一，草稿态另表约束）：

```sql
ALTER TABLE post_attachments ADD COLUMN active_post_resource VARCHAR(80)
  GENERATED ALWAYS AS (IF(deleted_at IS NULL AND post_id IS NOT NULL,
                          CONCAT(post_id, ':', resource_id), NULL)) STORED,
  ADD UNIQUE KEY uk_active_post_resource (active_post_resource);
```

**上线前必跑这两条查重**（有重复数据时 `ALTER` 会直接 1062 失败）：

```sql
SELECT file_hash, COUNT(*) FROM images
 WHERE deleted_at IS NULL AND status = 1 GROUP BY file_hash HAVING COUNT(*) > 1;
SELECT post_id, resource_id, COUNT(*) FROM post_attachments
 WHERE deleted_at IS NULL AND post_id IS NOT NULL GROUP BY post_id, resource_id HAVING COUNT(*) > 1;
SELECT COUNT(*) FROM post_attachments WHERE deleted_at IS NULL AND post_id IS NULL AND draft_key IS NULL;  -- 孤儿行
```

若不想改表：单实例下 `SELECT GET_LOCK(CONCAT('img:', ?, ''), 5)` 是可用过渡（`ImagesService.java:49-57` 的去重 TOCTOU）。

## 5. 失效时机与覆盖面

> **`@CacheEvict` 必须在事务提交之后生效。** 否则存在窗口：T1 写库 → 方法返回 → 清键 → **T2 回源读到旧值并回填** → T1 commit ⇒ 缓存里是已被覆盖的旧值，直到 TTL 到期。

项目已有正确范式：`UserAchievementService.java:65-67`（`TransactionSynchronization` 的 `afterCommit`）。反例：`UserProfileService.java:66-67`。统一改为前者。

| 变更 | 现有失效 | 漏 |
| --- | --- | --- |
| 发文/改文/删文 | `hotPosts,latestPosts,postList,postSeries,allTags`（`PostsService.java:397` 等 6 处） | **`hotTags`、`categories`**（`postCount` 会变）、`postDetail` |
| 新增/删除评论 | 无 | `postList`/`postDetail`（列表带 `commentCount`） |
| 改作者资料 | 只清 `userStats` | **`aboutPage`**（§2.4 第 3 条） |
| 改系统设置 | `AboutPageService.updateAboutPage` 清 `aboutPage` ✅ | —— |
| 轮播/音乐增删改 | **无（今日无缓存）** | 一旦按 §2.2 加缓存，必须同时补 `CarouselService` 10 个、`MusicService` 5 个写方法的 `@CacheEvict` |

**消除耦合优于增加失效**：把 `postCount`/`commentCount`/`hot_score` 落成冗余列，则"评论/发文变了"不再需要清列表缓存 —— 否则失效清单会随功能单调增长。**前提是 `03` 先定义对应的对账任务（目前只有 `usage_count` 有）。**

## 8. 陷阱与约束

- **缓存注解的两个静默失效面**：`@Cacheable` 自调用不过代理（`§2.1`）；`unless`/`key` 里的 SpEL 属性写错不会在启动期报错，而是**每次调用抛异常**（`§2.2` 的 `records`）。上线前必须手工打一次该端点，不能只看 CI（原因见 `06` §7：本仓库 67 个测试类里 `@SpringBootTest` 为 0，缓存代理根本不参与）。
- **`@Cacheable` 与 `@Transactional` 的顺序**：现方法上 `@Cacheable` 位于 `@Transactional(readOnly=true)` 内侧（`PostsService.java:107-108`），未命中时仍会**带着 DB 连接去查** —— 这是"加缓存不等于释放连接"的实证。
- **新增缓存名必须先建实例**（`跨服务规范.md:84` 要求集中在 `CacheConfig`），否则 SpEL 解析处抛 `IllegalStateException`；而 `§2.2` 这类**有状态**缓冲才允许走"业务缓存"豁免。
- `categories` 命名空间混放 `List<CategoryResp>` 与单个 `Categories` 实体（`CategoriesService.java:51` vs `:130`），靠 `allEntries` 一起清 —— 新增缓存不要复用已有名称放异构值。
- `CategoriesMapper.xml:6-17` 的 `resultType` 是 `model.Categories` 而接口签名返回 `List<CategoryResp>`（`CategoriesMapper.java:23`），靠泛型擦除蒙混 —— 改 SQL 时别以为是 `Resp`。
- `/tags` 的 `postCount` **未过滤 `status`**（`TagsMapper.xml:6-17`，与 `/categories` 行为不一致）→ 草稿被计入标签数。属正确性缺陷，与缓存重构同批修。
- 唯一索引上线前**必须跑 §3.6 的三条查重**：MySQL 的 `ADD UNIQUE` 在存量重复数据上是直接失败，不是"忽略重复"。
