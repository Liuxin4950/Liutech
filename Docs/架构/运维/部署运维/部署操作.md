# 部署、验证与回退

> 本文维护通用操作顺序。当前生产版本、目录、证书与备份事实见[运维总览](总览.md)，数据库版本与增量执行见[迁移说明](../../../SQL/migrations/README.md)。SSH 凭据、环境密码与私钥按环境保存，不进入仓库。

## Git 版本与已部署基线

主目录 `E:\我的项目\Liutech` 的 `main` 是默认交付与构建入口。工作树可用于隔离实现，但交付前必须把有效提交合入主目录并正常推送 `origin/main`；保护其它工作树和设备的未提交修改。默认约定见[AGENTS.md](../../../../AGENTS.md#交付与-git-同步)。

发布前先读取云端运行容器的镜像 ID 和 `org.opencontainers.image.revision`，再检查该提交是否已被 `main` 包含，并按服务比较差异。某个服务无代码或配置变化时可保留旧镜像；整个仓库 HEAD 不必等于每个服务镜像 revision。只更新部署记录的提交不要求重建服务。

在主目录执行以下只读核验；远端失败或出现未处理修改、未合入的有效提交时，先完成同步和审查，再构建：

```bash
git fetch origin
git status --short
git branch --no-merged main
git rev-list --left-right --count main...origin/main
git merge-base --is-ancestor <实际运行服务的revision> main
git diff <实际运行服务的revision> main -- <服务目录>
```

Git 祖先关系只证明提交被包含，不能证明合并冲突没有覆盖逻辑。还需检查合并差异和受影响链路，运行对应回归；有疑问时对照实际运行产物。构建产物写入 revision 与 SHA256 清单，部署后同时核对容器镜像 ID、标签和实际 JAR/前端文件。实际版本和验证结果只记录在[运维总览](总览.md#当前生产版本)。

## 发布前

1. 确认 Git 版本和干净工作区，检查待发布服务、Compose 与 SQL 的差异。
2. 核实服务器正在运行的镜像 ID、revision 标签、数据库迁移台账与剩余空间，不只比较构建时间。
3. 备份两库、当前 Compose、环境文件、完整初始化 SQL 与旧容器/镜像记录，保留可用的旧镜像标签。
4. 通过必要构建、测试和数据库回归后再发布；数据库有待执行增量时先迁移，再启动新版服务。

备份目录应只允许运维账户访问。MySQL `mysqldump` 使用一致性快照与管道失败检查，压缩备份完成后执行 `gzip -t`。密码通过环境或安全配置提供，不直接写到命令行或日志。

## 构建与产物

JDK 使用 21；前端依赖按对应锁文件安装。从仓库根目录运行：

```bash
mvn package
npm --prefix Web test
npm --prefix Web run build
npm --prefix Admin run build
node Web/node_modules/vitest/vitest.mjs run --config Admin/vitest.config.mts
# 核验 Web/Admin 四对镜像文件逐字节一致
# 核验文档链接、章节锚点、索引及路径大小写
```

普通 Maven 测试未配置本机 `LIUTECH_TEST_MYSQL_URL` 时会跳过 MySQL 回归。数据库变更需按[数据库验证](../../跨服务规范.md#104-数据库验证)启用独立测试实例，不能指向生产。

### 本机有 Docker

按服务使用仓库 Dockerfile 构建，并以本次 Git revision 打标签。后端 Dockerfile 使用刚构建的 `target/*.jar`，前端 Dockerfile自行构建 `dist`：

```powershell
$revision = (git rev-parse --short=8 HEAD).Trim()
docker build --provenance=false --sbom=false -t "liutech-backend:$revision" -f LiuTech/Dockerfile LiuTech
docker build --provenance=false --sbom=false -t "liutech-ai:$revision" -f LiuTech-AI/Dockerfile LiuTech-AI
docker build --provenance=false --sbom=false -t "liutech-web:$revision" Web
docker build --provenance=false --sbom=false -t "liutech-admin:$revision" Admin
docker build --provenance=false --sbom=false -t "liutech-nginx:$revision" nginx
```

导出所需业务镜像后上传到独立发布目录。关闭 provenance/SBOM 是现有离线导入流程的要求，避免导出包引用缺失的 attestation blob。`docker load` 必须检查退出码和导入后的镜像 ID。

### 本机没有 Docker

本地构建 JAR 与 Web/Admin `dist`，将这些产物、对应 Nginx 配置和完整 SQL/迁移目录打包上传，在服务器使用已缓存的 Java 21 JRE 与 Nginx 基础镜像构建。运行时 Dockerfile只复制已验证产物，保留原 CMD、时区、工作目录和必要数据目录。

服务产物与配置分别计算 SHA256，发布清单记录源 Git revision、镜像标签和校验值。构建上下文仅包含必要产物，不包含 `.env`、SSH 凭据、证书私钥、上传文件或测试数据。此路径仍应使用 `--provenance=false --sbom=false`，离线构建需提前确认基础镜像与时区数据可用。

## 统一 Compose 与环境参数切换

本地和云端共用根目录 [docker-compose.yml](../../../../docker-compose.yml)、各服务原 Dockerfile，以及同一套 `.env` 变量。模板见 [.env.example](../../../../.env.example)；已有 `.env` 保留实际配置，只补缺少的键或修改需要切换的值。环境切换不创建另一份 Compose、override 或 local/prod 环境文件。

本地 Docker 用于部署预演，日常开发由用户手动启动服务。两边使用原 [Dockerfile](../../../../nginx/Dockerfile) 和 [default.conf](../../../../nginx/conf.d/default.conf) 的 HTTPS 配置，不增加模式变量或启动脚本。`http://localhost:3000` 和 `http://localhost:3001` 可辅助定位 Web/Admin，但只验证直连端口不足以确认 Nginx 入口、HTTPS 与代理配置。部署验收还需要请求经过 Nginx → Web/Admin/API → 后端；本机 80 按原配置跳转域名，81 为 HTTPS。

本机可用以下命令只改变本次请求的 DNS 解析，保持域名和 Nginx 配置与云端相同，不修改系统 hosts。`--noproxy` 确保请求直连本机，`--cacert` 信任该本机测试证书并继续校验域名；证书必须包含对应域名。运行目录为仓库根目录：

```powershell
curl.exe --noproxy "*" --resolve liuxin.chat:443:127.0.0.1 --cacert nginx/certs/liuxin.chat_bundle.crt https://liuxin.chat/api/posts
curl.exe --noproxy "*" --resolve admin.liuxin.chat:443:127.0.0.1 --cacert nginx/certs/admin.liuxin.chat_bundle.crt https://admin.liuxin.chat/
```

这两项只验证公开 API 与后台静态入口；还需按本次改动验证登录后的业务、上传、SSE 和适用的外部服务。COS、模型与邮件不因机器在本地就必须关闭；以云端同样的功能配置验收，明确排除的外部服务单独记录为未验证。

### 在同一个文件中用注释保存替代值

以下是本机 `.env` 的非凭据片段示例，不是第二份配置。每个键只保留一行未注释，切换时注释当前行、启用对应替代行。模板 [.env.example](../../../../.env.example) 的生效行取**云端安全值**（`NGINX_BIND_IP=0.0.0.0`、`MAIL_HEALTH_ENABLED=true`、`SERVER_BASE_URL=https://liuxin.chat`），本机值以注释紧随其后；本机 `.env` 与此相反。`COMPOSE_PROJECT_NAME` 先核验已有卷再保持原值，不能把本机 `liutech-local` 直接复制到已有云端。

```dotenv
NGINX_BIND_IP=127.0.0.1
# 云端公开入口，切换时只保留一个同名键生效：
# NGINX_BIND_IP=0.0.0.0
INTERNAL_BIND_IP=127.0.0.1
SERVER_BASE_URL=https://liuxin.chat
# 部署预演可通过 --resolve 保留域名；仅直接端口调试时启用：
# SERVER_BASE_URL=http://localhost:3000
UPLOADS_PATH=uploads
# 已有云端挂载：
# UPLOADS_PATH=/liuxin/uploads
LOGS_PATH=./logs
# 已有云端挂载：
# LOGS_PATH=/liuxin/logs
NGINX_SSL_PATH=./nginx/certs
# 云端证书目录：
# NGINX_SSL_PATH=/opt/liutech/nginx
COS_ENABLED=false
# 需要验收COS时启用，并配好对应COS_*参数：
# COS_ENABLED=true
COS_MIGRATE=false
MAIL_HEALTH_ENABLED=false
# 验收SMTP时启用，并使用有效的MAIL_*配置：
# MAIL_HEALTH_ENABLED=true
BACKEND_IMAGE_TAG=local-review
# 云端改为本次已验证提交标签；其余四个 IMAGE_TAG 采用同样方式
```

注释优先独立成行；值后注释必须留空格，例如 `MAIL_HEALTH_ENABLED=false # 仅跳过健康探测`。不能写 `false#说明` 或 `465#说明`，这些内容会成为值的一部分，使布尔值或端口绑定失败。修改后先执行 `docker compose config -q`；该命令不能替代应用实际启动和功能验证。

同步 Compose 到云端前，先在服务器确认内部端口空闲——统一 Compose 后这些端口在生产同样会发布，只是绑到 `127.0.0.1`：

```bash
sudo ss -lntp | grep -E ':(3306|8080|8081|3000|3001)\b'
```

2026-10-11 实测服务器这五个端口均空闲，公网监听只有 80/443/81。若被占用，`docker compose up -d` 会直接失败，改云端 `.env` 的对应 `*_PORT` 键即可，不改 Compose。

### 构建、启动与持久化验收

先以 JDK 21 构建两个后端 JAR，主 Compose 的 `build` 使用原 Dockerfile；Web/Admin 在 Dockerfile 中安装依赖并构建 `dist`。从仓库根目录执行同一组命令：

```powershell
mvn -f LiuTech/pom.xml package
mvn -f LiuTech-AI/pom.xml package
docker compose config -q
docker compose build
docker compose up -d mysql
```

新数据库卷初始化完成后，由数据库管理员显式创建 `liutech_app` 和 `liutech_ai_app`，分别赋予各自数据库的应用读写权限，密码匹配上表。`sql.sql` 不自动创建这些账号；已有库核验账号后继续使用，不重复初始化。随后启动其它服务：

```powershell
docker compose up -d
docker compose ps
docker exec liutech-nginx nginx -t
```

`COMPOSE_PROJECT_NAME` 决定 `mysql_data` 和 `uploads` 命名卷的项目名前缀。当前本机保持 `liutech-local`，继续使用原 `liutech-local_mysql_data/liutech-local_uploads`，不迁移或重置；容器名由主 Compose 固定为 `liutech-*`。已有云端同样保持自己的原项目名和上传挂载，不能为“切换环境”改成新项目名，也不要执行 `down -v`。

新卷才执行完整快照；已有卷遵循[增量迁移](../../../SQL/migrations/README.md)。普通新库没有生产用户或固定管理员，本机测试账号需明确建立，正常环境的管理员入口见[首次管理员](#首次管理员)。本机模型、SMTP 和存储是否可用取决于实际配置与调用，健康检查不能代替对应功能验收。

本机部署预演不能代替云端验收；模型/TTS 供应商、邮箱及 COS 上传需按实际调用记录验证。当前生产版本、证书和实际部署状态保持在[运维总览](总览.md#当前生产版本)。

## 同步配置与 SQL

本地和云端使用相同的根目录 [docker-compose.yml](../../../../docker-compose.yml)，只调整同一组 `.env` 参数。核对新版解析结果中的项目名、数据卷、挂载路径、数据库账户、内部令牌与密钥归属后，执行 `sudo docker compose config -q`。

`.env` 在生产为 `root:root` 且权限 `600`，普通用户读取会被拒绝，因此**所有 compose 子命令都必须带 `sudo`**。不带 `sudo` 时 compose 读不到 `.env`，`config` 直接失败；而 `up` 一类命令会把 `${*_IMAGE_TAG:-latest}` 静默回退到 `latest`，而服务器上的 `latest` 可能是数月前的旧镜像，等于发错版本。发布前用 `sudo docker compose config | grep 'image: liutech'` 确认每个服务解析到的标签。

已有 `.env` 保留真实环境值，只更新本次服务的 `*_IMAGE_TAG`。不能导入新镜像后仍让 Compose 指向旧标签。备份后再替换 Compose，MySQL 的数据卷名、上传目录、日志目录和证书挂载路径必须保持一致。

[Docs/SQL/sql.sql](../../../SQL/sql.sql) 同步到服务器作为完整新库快照，不重放到已有生产库。已有库通过 独立 Flyway Maven 工程分别执行两库增量并严格 validate；凭据、首次 baseline 与失败处理按[迁移说明](../../../SQL/migrations/README.md)。校验和漂移时停止发布，不自动 repair。

## 切换服务

两库迁移通过后，按兼容顺序更新服务：

```bash
cd /opt/liutech
sudo docker compose up -d --no-deps --force-recreate ai
# 等待 AI /actuator/health 为 UP，失败则停止后续切换。
sudo docker compose up -d --no-deps --force-recreate backend
# 等待 backend /actuator/health 为 UP。
sudo docker compose up -d --no-deps --force-recreate web admin nginx
sudo docker exec liutech-nginx nginx -t
```

只更新有变动的服务。任一 backend/ai/web/admin 重建后都需重启或重建 Nginx，刷新缓存的 upstream 地址；Nginx 自身已重建则不必额外重启。业务发布不重建 MySQL，也不删除 `mysql_data`。

## 验证

- 比较运行容器的 `.Image` 与目标镜像 ID，再比较完整 `org.opencontainers.image.revision` 标签与实际 JAR、HTML、Nginx 配置校验值。
- 主后端与 AI 容器内 `/actuator/health` 返回 UP，Nginx 配置校验通过。
- 主站、后台、公开 API、静态文件与必要鉴权接口正常；公网 `/api/internal/**` 与 `/ai/internal/**` 返回 404。
- 当前版本涉及资料、会话或用户永久删除时，使用明确标记的临时账户验证，并清理测试账户与会话，保留审计和清理台账。
- 核对原有业务数据、数据库账户、持久化挂载及 MySQL 容器未变，检查未完成清理任务与 ERROR 日志。
- 记录实际验证范围；未调用供应商时不宣称模型生成或 TTS 已做线上端到端验证。公网 CDN 与源站应分别核对。

完成后更新[当前生产版本](总览.md#当前生产版本)，写清镜像标签、数据库版本、备份/回退路径和验证边界。

## 回退

保留发布前的 Compose、环境文件、镜像 ID 与标签。应用切换失败时恢复这两份配置，重建对应旧业务镜像并刷新 Nginx；重新检查健康与 API。

数据库新增表、索引、清理任务和 Flyway 台账保留，不随着应用回退自动删除。不要直接恢复全库备份覆盖发布后产生的数据。需要恢复数据库时，先核对影响范围并制定单独的数据恢复步骤。

## 首次管理员

完整初始化不创建固定用户名或密码的管理员。新环境通过正常注册创建真实账户，再由数据库管理员核验后显式提升该账户角色：

```sql
UPDATE users SET role = 'admin'
WHERE username = '<真实用户名>' AND deleted_at IS NULL;
```

核对只影响目标账户。账号密码和可复用密码哈希不写入初始化 SQL。

## 证书更新

证书与应用镜像分开维护。按[运维总览](总览.md#证书)核实域名、路径和证书范围，备份后替换证书文件并重启 Nginx，再验证域名与有效期。私钥不打入镜像，也不进入 Git。
