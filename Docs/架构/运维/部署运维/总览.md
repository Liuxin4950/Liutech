## 域名与流量拓扑

```
访客
 ├─ https://liuxin.chat          ──CNAME──▶ 腾讯云 CDN  ──HTTPS回源──▶ 源站 nginx(443)
 ├─ https://www.liuxin.chat      ──CNAME──▶ 腾讯云 CDN（见下方"www 现状"）
 ├─ https://admin.liuxin.chat    ──A记录──▶ 源站 132.232.149.184(443，直连，不走CDN)
 ├─ https://liuxin.chat:81       ──A记录──▶ 源站 nginx(81，admin 备用入口)
 └─ https://static.liuxin.chat   ──CNAME──▶ COS 桶 liutech-1341692466（重庆，图片/文件直出，不过源站）
```

- **主域名 `liuxin.chat`** 走腾讯云 CDN，CDN 上绑定覆盖 `liuxin.chat` 的证书，HTTPS 回源到 `132.232.149.184:443`，回源 HOST 为 `liuxin.chat`。
- **后台 `admin.liuxin.chat`** 直接 A 记录到源站，绕开 CDN。nginx 以独立 server 块（`server_name admin.liuxin.chat`，443）托管，指向 admin 容器。后台使用覆盖 `admin.liuxin.chat` 的独立证书，严格 TLS 校验已通过；该站点不发 HSTS。81 端口的 admin 块保留作为备用。
- **源站公网 IP**：`132.232.149.184`（腾讯云 Lighthouse）。当前线上安全组仅放行 80/443/81；线上实际容器配置见本文“容器部署”，本地源码的统一参数流程见[部署操作](部署操作.md#统一-compose-与环境参数切换)。
- **图片/文件域名 `static.liuxin.chat`**：CNAME 到 COS 默认域名，浏览器直连 COS（重庆桶 `liutech-1341692466`），图片流量不经过源站。桶为公有读私有写；证书在 COS 控制台绑定（独立免费证书，SAN 含 `static.liuxin.chat`，2026-11-03 到期）。URL 形态由后端 `CosStorageProperties.getBaseUrl()` 决定（[存储抽象](../../后端/图片管理/存储抽象.md)）。

### CDN 缓存策略

CDN 控制台对 `liuxin.chat` 的节点缓存规则（列表底部优先级高于顶部）：

1. 全部文件 → 不缓存（兜底）
2. 目录 `/uploads/` → 缓存30天
3. 目录 `/assets/` → 缓存30天

即 HTML、`/api/`、`/ai/`（SSE）、`/tts/`、`sitemap.xml` 全部实时回源；只缓存 Vite 打包产物（`/assets/`，文件名带哈希，内容变文件名也变）与上传图片（`/uploads/`）。缓存键对静态文件后缀忽略查询参数。

**陷阱**：CDN 对非浏览器 UA（如 curl 无正常 UA）可能返回 418 反爬，这不影响真实访客，但会让服务器端脚本抓取本站内容失败——脚本应直连源站或带浏览器 UA。

### www 现状

`www.liuxin.chat` 的 DNS 虽 CNAME 到 CDN，但**未在 CDN 控制台作为加速域名添加、未绑定证书**，CDN 对其返回 `*.cdn.myqcloud.com` 默认证书，浏览器直接拦截。因此：

- 站内**不使用** `www.liuxin.chat`——图片/文件 URL 已全部迁移到 `static.liuxin.chat`（完整 URL，不依赖当前页面域名），无 www 混入问题。
- 若要让 `www.liuxin.chat` 可直接访问，二选一：
  1. CDN 控制台添加 `www.liuxin.chat` 加速域名，绑定同一张 TrustAsia 证书（推荐，保持走 CDN）；
  2. www 改 A 记录直连源站，在 nginx 加 443 server 块 301 跳转到 `liuxin.chat`（证书 SAN 含 www，握手不报错）。

## 容器部署

- 6 服务为 mysql / backend / ai / web / admin / nginx；仓库编排只发布 Nginx 的 `80/443/81`，其它服务通过 Docker 内网通信，不发布宿主机端口。实际运行版本、尚未重建的服务与端口生效情况以[当前生产版本](#当前生产版本)记录为准，通用流程见[统一 Compose 与环境参数切换](部署操作.md#统一-compose-与环境参数切换)。本地 Docker 用于部署预演，不另设开发编排。
- nginx 配置是 `COPY conf.d/*.conf` 烤进镜像的，改 nginx 配置**必须重新 build nginx 镜像并部署**，改宿主机文件不生效。
- 国内服务器无法从 DockerHub 拉镜像，采用本地离线打包：`docker build` → `docker save` tar → scp → `docker load` → `docker compose up -d --force-recreate`。所有 `docker build` 必须加 `--provenance=false --sbom=false`，否则 `docker load` 会因 attestation blob 缺失失败并静默沿用旧镜像。
- force-recreate backend/ai/web/admin 任意一个后，**必须 restart nginx**（upstream 缓存的容器 IP 会失效）。nginx 自身重建则不需要额外 restart。
- backend 与 ai 使用独立镜像标签变量和最小权限数据库账户；root 仅用于备份、结构迁移和显式配置应用账号。
- `JWT_SECRET` 只给 backend，`LIUTECH_INTERNAL_TOKEN` 同时注入 backend/ai；SiliconFlow 与 TTS 密钥只给 ai。
- 完整步骤与排错入口见[部署操作](部署操作.md)。

## 已踩过的坑

- **COS 自定义域名边缘节点分批生效**：绑定域名/证书后约 30 分钟内，不同边缘节点新旧配置并存——同一时刻部分节点返回新证书（200）、部分还是 COS 默认证书（TLS 不匹配 / 400）。2026-08-05 实测绑定后 14 分钟全量生效。判断标准：连续访问（可 `--resolve` 指定不同 IP）都 200。
- **桶权限没设公有读 → 403**：桶默认私有读写，图片 URL 返回 403（对象存在但无读权限）。需在控制台设「公有读私有写」并**确认保存**。
- **证书 SAN 不含子域名**：主站证书 SAN 只有 `liuxin.chat`/`www.liuxin.chat`。`static.liuxin.chat`（COS 自定义域名）与 `admin.liuxin.chat`（源站）都各自踩过——子域名必须单独申请证书，不能复用主站证书。
- **CDN 证书只对已登记域名生效**：给主域名 `liuxin.chat` 绑了证书，不等于 `www.liuxin.chat` 也能用——每个走 CDN 的域名都要单独添加并绑证书。否则 CDN 返回 `*.cdn.myqcloud.com` 默认证书，浏览器在 TLS 层直接拦截，连 HTTP 请求都发不出，CDN 缓存里有图也没用（TLS 在 HTTP 下层）。
- **绝对 URL 历史数据**：早期 `SERVER_BASE_URL=https://www.liuxin.chat` 被当时的 URL 生成方法 `generateFileUrl`（现已重构为 `FileStorage.generateUrl`）拼进绝对 URL 存库，导致这些链接绑死在 www 上，而 www 证书不匹配 → 图裂。2026-08-03 已把 `images.file_url`、`carousels.image_url`、`posts.cover_image` 中的 `https://www.liuxin.chat/uploads/` 全部替换为相对路径 `/uploads/`，全库零残留。备份在服务器 `/tmp/images_backup_20260803231037.sql`。
- **缺失文件返回 500 而非 404**：后端读取不存在的上传文件抛异常返回 500，CDN 可能缓存错误响应。`ResourceDownloadService` 已改走 `FileStorage.open`（返回空流 → 业务异常"文件不存在"），该问题在资源下载上已解决。
- **compose 命令漏 `sudo` 会发错版本**：生产 `.env` 是 `root:root` 权限 `600`，普通用户读不到。`docker compose config` 会直接失败（还算显眼），但 `up` 一类命令会把 `${*_IMAGE_TAG:-latest}` **静默回退到 `latest`**——而服务器上的 `latest` 标签可能停留在数月前的构建（2026-10-08 核验时为 2026-09-06），等于把旧版本发上线，且 `compose ps` 看不出异常。所有 compose 子命令一律带 `sudo`，发布前用 `sudo docker compose config | grep 'image: liutech'` 逐个确认解析到的标签。
- **只看 `compose ps` 无法确认镜像真的换了**：`docker load` 失败或标签没对上时，`force-recreate` 仍会"成功"并沿用旧镜像。必须比对 `docker inspect <容器> --format '{{.Image}}'` 与 `docker images` 里新镜像的 ID。
