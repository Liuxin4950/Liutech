# 对话时序与延迟

> 基于当前代码的语音对话链路、延迟拆分、开源参考与验收边界。真实供应商耗时需要实际环境采样；受控测试不能代表线上响应速度。

## 完整链路

```text
用户结束说话 / 点击发送
  → 最终识别结果（Web Speech）
  → AiChat → chatStore.sendMessage → AiStream.streamChat
  → 身份确认、准备队列、页面资料、历史与提示词预算
  → LLM 首个正文字符 → TtsSegmenter 首个可朗读片段
        ├→ data：立即更新聊天正文
        └→ TTS 请求排队 → 合成整段音频 → 缓存文件 → SSE audio
            → 浏览器预加载 → audio.play → playing
                → 对应表情、口型采样
                → ended → 下一段
  → complete：仅表示正文生成完成
  → audio-complete / 连接结束：音频生成阶段结束，填补缺失序号
  → 最后一段实际 ended：回复播放完成
  → 免提模式再开始聆听

并行支路：用户打开模型 → 脚本下载 → moc/纹理下载 → 模型初始化 → ready
           声音不等待这一支路；ready 后对正在播放的音频补接口型，不重播。
```

[StreamingChatService](../../../../LiuTech-AI/src/main/java/chat/liuxin/ai/service/StreamingChatService.java) 的模型流和分段 TTS 在不同执行路径上工作。当前 TTS 是“文本分段后，每段完整合成”，不是音频字节流或语音原生模型。

## 延迟如何计算

首声等待包含：识别收尾、网络与身份确认、上下文准备、LLM 到首个可朗读片段的时间、TTS 队列与合成、音频下载与浏览器起播。LLM 首字不是首声，服务端返回音频 URL 也不是用户已经听到声音。

| 等待来源 | 当前处理 | 不能据此声称 |
| --- | --- | --- |
| Live2D 首次加载 | 脚本预下载并行、执行顺序保持；音频独立起播，ready 后补接口型 | 已降低真实 LLM 推理时间 |
| LLM 准备与推理 | 首字指标与准备阶段指标分开；等待期间显示真实状态并保持思考表情 | 首字慢必然是模型太大，或固定“几秒内回复” |
| 等待切句 | 完整短句优先，取首个强标点；首段可按较短软标点切开 | 所有句子越短越好，或任意位置硬切会更自然 |
| TTS 合成 | 模型继续生成、浏览器继续播放时，后台合成后续段；默认并发保持原值 | 增加并发一定更快；全局 `TTS_CONCURRENCY` 仍约束真实能力 |
| AudioContext 挂起 | 不阻塞原生音频；恢复后补挂分析，保留用户点击恢复入口 | 浏览器一定允许自动播放 |
| 音频起播/卡顿 | 真实 `playing` 才切表情；准备与缓冲有可见状态和有限等待 | 音频下载完成等于实际发声 |

第 i 段相对于上一段的额外停顿，取决于它的实际可播时间是否晚于上一段结束。若平均合成速度赶不上朗读速度，任何前端队列都无法消除所有停顿；此时需要实测供应商、合成段长、网络和并发容量。

## 已处理的时序问题

- `complete` 不再清掉尚未结束的 TTS 等待。`audio-complete` 或连接结束处理生成终态，播放器维护自己的实际播放终态。
- 等待期间输入框仍可编辑。空输入时发送区显示停止，有新文本时发送会先中断旧回复，再提交本轮；麦克风同样可以接话。
- 每次新提问都有独立回复代次；上一轮仍在等待音频时，新提问不会被旧请求的收尾回调清掉状态。
- 后续分句原先未记录软标点，逗号切句分支无法命中；现在按实际标点切句。完整短句不再等待凑满首段最小长度。
- 纯符号也返回 `audio-skip`。终态包含 `segments`，前端将丢失的段补成跳过项，避免缺一个序号卡住整轮。
- 音频按序出队时才取对应表情，乱序到达不会提前推进表情游标。
- 表情与口型由 [角色控制器](Live2d渲染.md#单一参数写入入口) 在真实模型帧内混合；复位清空目标并平滑撤销，不再用多个入口直接调用 expressionManager。
- 表情以 `playing` 为准，绕过通用表情限速；分段间不插入 neutral，整轮结束或取消才复位。没有声音的跳过项仍按自身表情时长复位。
- GPT-SoVITS 的逐段真实合成不再先做诊断 GET；状态探测仍由 runtime/管理检测保留。SiliconFlow 的实际失败冷却继续生效。
- 模型隐藏时不请求无法播放的 TTS，避免后台合成和重新显示时积压旧朗读。
- 模型下载或加载失败不阻塞声音；音频上下文解锁也不再增加最多 2 秒的口型等待。
- `play()` 一直不返回也能结束等待。启动等待上限 12 秒，缓冲停滞上限 10 秒；播放阶段按剩余时长加 10 秒（至少 15 秒，无有效时长时 60 秒）。失败停止本轮自动播放，保留文字并提示接话。

分句默认值由 [TtsSegmenterProperties](../../../../LiuTech-AI/src/main/java/chat/liuxin/ai/infra/config/TtsSegmenterProperties.java) 管理：首段软切最小 12、无标点硬切 40；后续软标点长度 40、硬切 72。完整句子可以短于这些长度。硬切保护 UTF-16 代理对。这些是当前默认值，仍需真实中文、英文、数字和代码文本试听。

## 可观测数据

### 服务端

[AiMetrics](../../../../LiuTech-AI/src/main/java/chat/liuxin/ai/common/monitor/AiMetrics.java) 复用现有 Micrometer 指标。指标通过原有内部受保护入口读取，不新增公开诊断接口。

| 指标 | 含义 |
| --- | --- |
| `ai_stream_first_token_seconds` | 从服务端流请求建立到首个正文字符，包含准备、工具及模型等待 |
| `ai_speech_stage_seconds{stage="prepared"}` | 聊天资料与提示词准备完成时，距服务端流请求建立的时间 |
| `stage="first_segment"` | 首个分段提交时的累计耗时，包含正文生成和切句等待 |
| `stage="segment_queue"` | 单段在线程池中等待执行的时间 |
| `stage="segment_total"` | 从该段提交到合成与发送收尾，包含线程池排队、全局许可等待、状态检查和供应商调用 |
| `stage="first_audio_ready"` | 首个有效音频 URL 就绪时的累计耗时；不是浏览器首声 |

`stage/model` 使用有限的阶段值与已有模型标签，不把请求 ID、正文或用户信息作为标签。单段许可等待和供应商推理尚未独立计时；不能把 `segment_total` 全部归给供应商。

### 浏览器

[chatStore](../../../../Web/src/stores/chat.ts) 当前轮的 `speechTimings` 不持久化、不上报正文，使用同一浏览器的 `performance.now()`：

- `firstTextMs`：从本轮流式发送开始到收到首个正文字符。
- `firstAudioMs`：从本轮流式发送开始到收到首个音频 URL。
- `firstPlaybackMs`：从本轮流式发送开始到首次真实 `playing`。
- `maxGapMs`：相邻音频段实际结束到下一次 `playing` 的最大间隔，包含合理句间停顿与缓冲时间，不能等同于纯网络延迟。

模型加载通过 Performance 条目 `liutech-live2d-load` 记录，从开始加载脚本到 `ready`。前后端时钟起点不同，不相减；聚合指标只能看分布，也不能从不同请求的平均数得出单次请求因果。

## 开源参考及适用范围

| 参考 | 已核对的机制 | 在本项目的取舍 |
| --- | --- | --- |
| [Open-LLM-VTuber TTSTaskManager](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/main/src/open_llm_vtuber/conversations/tts_manager.py) | 合成与发送分开；保序；纯符号/合成失败也发送静音项 | 沿用已有 SSE、seq 和 AI 服务，补齐所有段的终态 |
| [AIRI streaming-pipeline](https://github.com/moeru-ai/airi/blob/main/packages/stage-ui/src/libs/speech/streaming-pipeline.ts) | 文本流、语音结束、取消分开；部分供应商的字幕边界不能直接充当音频切点 | 保留当前供应商完整音频契约，先消除额外等待；没有直接引入 WebSocket/PCM 播放栈 |
| [LiveKit turn tuning](https://docs.livekit.io/agents/logic/turns/tuning/) | 结束发言判断、误打断恢复、预生成各有不同职责与代价 | 当前只在最终识别结果后提交；未用中间文本提前触发付费推理 |

参考的是生命周期与时序机制；没有把这些项目的完整服务接入站点，也没有更换现有模型或扩大默认并发。

## 仍需真实验收的边界

当前模型文件配置了四张纹理和 26 个表情，没有 `Motions` 分组。`ParamMouthOpenY/ParamMouthForm` 等参数存在，并不代表已有音素识别、正确嘴形映射或挥手动作。当前为带滞回静音门、有界归一化和毫秒包络的 RMS 开合；嘴角随情绪混合，不能把这些称为音素口型。

轮流免提仍基于浏览器 Web Speech；播放中需要点击麦克风接话。未实现人声持续检测、外放回声消除、语义打断、误打断续播，或按“实际听到的文本”回写后端历史。

真实验收应覆盖：冷/热模型加载、短问候与长回答、工具查询、慢首字、慢首段合成、下一段晚到、合成失败、自动播放拒绝、播放缓冲、切会话、音乐互斥、手机前后台切换。每类分别记录首声、最大句间间隔、取消到静音时间和失败率。耳机/外放、桌面/移动端分别记录，不以本地受控测试替代设备验收。

隔离 Chromium 已用受控 SSE、两段各 2 秒的合成测试音频与人为延迟 4 秒的模型 JSON 验证：模型仍在 loading 时音频已进入 playing，模型随后 ready 没有重播音频，最终回到 idle，未发生页面异常。该测试不含真实识别或模型推理，不能用其中的毫秒数表示线上首声。

当前没有真实供应商的 p50/p95 首声或回声数据。用户结束说话到识别最终结果的耗时、准备阶段内部各外部查询、真实推理队列和全局 TTS 许可等待仍需进一步分段采样；不能承诺低于固定秒数，也不能声称这些时序修复已经让模型本身推理更快。
