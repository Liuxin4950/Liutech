## 1. 目标与边界

让现有博客的引导、阅读、搜索、AI 与音频交互稳定可用；让个人页以普通读者为中心展示真实行为、真实进度和可领取的积分；利用已有 CDN/COS 和 SEO 基础改善访问体验。

本轮先形成可执行计划。后续按本文分批实施，不同时重写整站，不迁移前端框架，不引入 Redis，不另建积分系统或文件存储系统。附件中的描述作为需求与观察证据；其中举例的奖励规则转为下文明确标注的建议方案，不当作已经上线的规则。

保留现有品牌、主题变量、响应式布局和权限边界。普通用户继续以阅读、评论、收藏、签到为主要行为；写作仍属管理员权限。本轮“内容扩展”优先完善已有内容的组织与发现入口，不擅自加入新的产品频道或自动生成文章。

## 4. 逐项实施方案

### R01：首次引导第二步

1. 用全新本地存储依次复现欢迎、聚光、模型提示、输入提示；记录气泡实际宽度、父容器布局、computed style 和视口坐标，确认截图是文本换行、挤压还是溢出裁切。
2. 模型气泡设定明确的响应式宽度，上限建议 320px，左右至少留 16px；文本正常换行，步骤标识和关闭按钮不压缩，正文允许缩小但不被挤成单字列。
3. 根据气泡实际尺寸进行上下翻转与边界限制，不再假设固定 56px 高度；加载状态变更、模型 ready、窗口缩放、横竖屏切换后重新定位。
4. 沿用当前 loading/ready/error 文案与重试能力；失败时可跳过，目标不可见时不画错位气泡。清理延迟任务，防止跳过后提示重新出现。
5. 本次样式修复不提升引导版本，不让已完成用户被迫重走流程。

验收：手机、平板、桌面和 125%/150% 缩放下文案完整、可自然换行，气泡与箭头在屏内，关闭按钮可点；模型加载慢/失败也不阻塞退出。

### R02：下一步建议暂缓（用户于 2026-09-04 调整）

用户认为自动推断下一步问题的额外 token 成本不合适，本轮隐藏整个建议区域，移除自动生成请求与新增的生成接口。普通聊天和用户主动发起的文章总结继续沿用原有链路。

验收：聊天输入区不再显示下一步建议；完成回复后不请求 suggestions 接口；代码与运行中的 AI 服务均不保留本次新增的推断入口。以后如需恢复，先明确调用成本和触发条件。

### R03 / R05 / R06：音乐、TTS 与 Live2D 统一修复

这三项按一个音频批次处理，分别验收。保留 `MusicCapsule → BottomNavigation → useTtsPlayer → Live2d` 的责任边界，在已有协调入口解决状态和生命周期问题。

**状态来源**

| 信息 | 权威来源 | 约定 |
| --- | --- | --- |
| 用户是否希望 AI 朗读 | chat store 持久化偏好 | 临时网络/服务故障不改写用户选择 |
| TTS 服务状态 | 现有 runtime 检测 | 区分检测中、可用、不可用，提供重试入口 |
| 实际播放状态 | 当前 HTMLAudioElement 事件 | UI 不能只靠“点击成功”或一个 Promise 推断 |
| 当前音乐/人声音轨 | MusicCapsule | 暴露当前音源与播放快照，ready 后可查询 |
| 当前口型来源 | useTtsPlayer 协调 | 同时最多一个来源；TTS 优先，音乐按实际状态恢复 |
| 模型是否能接收口型 | Live2d ready/visible | 模型是否存在不决定音乐能否正常播放 |

**连接和生命周期**

1. 音乐先播放时保留可查询的当前音源；模型 ready、显示恢复、重新加载后，协调器根据当时实际播放状态重新连接，不从头播放音乐。
2. `useLipSync` 绑定音源后等待 `playing`/成功开始播放再启动采样；暂停/结束时停止采样并闭嘴，恢复播放时可再次启动。等待网络期间不永久丢失采样循环。
3. 修复隐藏/销毁模型时关闭其 AudioContext 导致正在播的音乐失声或下次无法重绑的风险。将需跨模型生命周期存在的音频节点注册与连接逻辑从渲染组件提升到现有播放器生命周期内；Live2D 只订阅口型值。局部提取 composable 即可，不建设通用音频框架。
4. 每个音频元素复用其 source node；切换音源、TTS 结束和组件销毁时明确断开节点、清理事件与 RAF。建立音频图失败要保住可用播放路径，并显示轻量提示，不用 catch 后继续假定同步成功。
5. 真正需要播放的 AudioContext 在用户交互中恢复，不把另建临时 context 的成功当作所有 context 已解锁。自动播放受限时提示点击播放，不持续重试。
6. 先设置 `crossOrigin` 再设置音频 URL；实际检查同源、COS、自定义域名和重定向后的响应，区分网络错误、跨域失败、静音、分析值为零及模型口型参数映射问题。

**开关、互斥和异常**

1. 关闭 AI 语音立即取消当前播放代次、停止音频、清空旧队列并复位口型；迟到的旧 SSE 音频不能在重新开启时复活。重新开启从后续有效回复开始，不自动补播刚取消的历史片段。
2. 顶部和折叠菜单使用相同状态、文案、可访问属性。服务不可用时清楚提示原因并提供重新检测，恢复后尊重用户原偏好，不出现永久禁用按钮。
3. TTS 开始时暂停音乐；只在“此前因这轮 TTS 被暂停，且用户未随后主动暂停/停止/切歌”时恢复。音乐暂停事件不能误停当前 TTS 的口型。
4. 隐藏模型沿用当前产品行为：停止本轮 TTS 并清理待播旧音频，音乐可继续；再次显示重新连接当前音乐，下一轮 TTS 正常工作。
5. 双轨播放不能用任意一轨成功就宣告完整成功：优先同步人声；人声失败而伴奏成功时按实际音轨降级并提示，不能仍将失败的人声作为口型输入。切歌、连点、超时都用播放代次避免旧 Promise 回写。
6. 播放等待改成一个可取消的完成/错误/暂停监听集合，完成时清理其它监听和计时器；现有 `Promise.race(waitOnce...)` 的剩余监听不能长期残留。

验收矩阵：

| 场景 | 通过标准 |
| --- | --- |
| 音乐先播 → 打开模型；模型先开 → 播音乐 | 两种顺序都同步，无需暂停重播 |
| 模型加载失败 → 重试；隐藏 → 显示；卸载 → 重建 | 音乐连续可听，重建后恢复口型，无重复 source node 异常 |
| TTS 预加载慢、分段间隔长、暂停后恢复 | 实际播放开始后采样持续有效；停止后闭嘴，无旧段串入 |
| 音乐播放中 TTS 插入 → 完成/关闭/失败 | 音乐与 TTS 的恢复规则一致，用户后续操作优先 |
| 双轨之一失败、音频 404、弱网、跨域、自动播放受限 | 状态不假成功，错误可恢复，不使正常音轨永久无声 |
| 快速开关语音、切会话、连发消息、前后台切换 | 无重叠音频、卡死按钮、旧回调覆盖或持续增长的监听 |

至少在桌面 Chrome/Edge 与用户使用的安卓平板浏览器真实播放验证。记录使用的音乐/TTS URL 类型、触发顺序、控制台和听感；构建通过不能替代声音与口型验收。

### R08：个人页与可领取成就

**面向读者的展示**

普通用户主要统计显示积分余额、评论数、收藏数、已浏览文章数；不以发文/草稿/作者访问量作为主要成长目标。管理员写作入口仍按现有权限保留，普通用户不获得写作权限。

保留已有注册、签到、收藏徽章。积分徽章如继续保留，改为明确的余额条件文案，不再用余额冒充“累计获得”；本轮不为其额外发奖。加载、无记录、请求失败分别显示，不把统计失败显示为正常的 0。

**首期建议规则**（用户原文给的是示例，本文采用以下默认方案，实施时可直接按此设计；若用户另有规则则修改本节）：

| 任务 | 达成标准 | 奖励 | 领取次数 |

| 热心评论者 `comment_10` | 当前保留的有效评论达到 10 条 | 2 积分 | 每用户一次 |
| 阅读探索者 `read_10` | 当前保留的浏览历史中有 10 篇不同的公开文章 | 2 积分 | 每用户一次 |

1. 评论按当前用户、未删除评论且关联文章公开可见统计；回复计一条评论。复用现有评论限制；不将这 2 分奖励扩大为每 10 条反复领取或每日任务。
2. 浏览按用户与文章 ID 去重，文章已发布且未删除；沿用详情加载成功后上报的“浏览”含义，不声称读完或有阅读时长。补齐 `recordView()` 的公开状态校验，防止直接上报草稿达标。
3. 历史旧数据可计入，只统计实际保留的数据；不推测已经清空的历史。清空历史或删除有效记录会影响**尚未领取**的进度，界面明确说明；已经领取的奖励和状态永久保留，不撤回、不重复发放。
4. 若以后要做“终身阅读累计”或循环奖励，需要单独设计不可重复计数的累计来源；本轮不悄悄增加隐藏阅读追踪表。
5. 状态为 `进行中 → 可领取 → 领取中 → 已领取`，失败可重试；前端只呈现服务端进度和资格，不能传入奖励金额或自行增加余额。

**后端与数据设计**

1. 建议新增 `GET /user/achievements` 与 `POST /user/achievements/{code}/claim`；读取返回 `code/title/progress/target/rewardPoints/status/claimedAt`，领取返回该任务的最终状态与最新余额。路径为拟新增，不代表已存在。
2. 在现有主后端分层中增加成就业务入口，复用 `UserUtils`、`Result`、`BusinessException/ErrorCode`、`PointsService`、现有评论/历史 Mapper。用户 ID 只从认证上下文取，校验普通用户/管理员均只能领取自己的任务。
3. 新增最小领取记录表，建议 `user_achievement_claims`：`id/user_id/achievement_code/reward_points/claimed_at`，唯一键 `(user_id, achievement_code)`；奖励金额用与现有积分相容的十进制类型。任务定义首期放服务端固定配置，不新增任务管理后台。
4. 领取在一个事务内完成：校验任务、实时查询资格、写入唯一领取记录、调用 `PointsService.addPoints()`、写入已有积分流水；流水 `source_id` 关联领取记录。检查外部调用事务传播和影响行数，任何一步失败整体回滚。
5. 同一任务重复请求返回已领取结果；并发冲突由数据库唯一约束兜底，按项目异常规范映射结果，不只靠前端按钮禁用或“先查再写”。不在已回滚的事务内继续发奖。
6. 积分流水新增清楚的成就奖励类型/来源，复用现有流水展示和审计日志；检查 Admin 的类型标签/筛选与 Web 的积分展示是否需同步映射。
7. 成就资格直接查询权威数据，不信任有 TTL 的 `userStats`。领取成功后失效相关用户统计缓存并刷新用户信息；评论、收藏、签到、清空历史触达的统计失效一并核对。
8. 新表同时更新初始化 SQL 和独立增量迁移文件，不能只改 `sql/sql.sql` 后假设生产自动建表。发布前备份，迁移后确认唯一键；回滚应用时保留领取记录和积分流水，不能删表再发一次奖励。

验收：第 9/10 条边界正确，同文章刷新不累计；未登录、他人身份、无效 code、未达标请求拒绝；双标签页并发和超时重试仅入账一次；模拟流水失败时领取记录与余额一起回滚；清空历史后已领取标识不变；老用户可按现存真实数据领取。

### R09：最近动态

1. 用真实活动记录替换当前四类时间字段的固定拼接，建议新增 `GET /user/activities?page=1&size=10`，上限 20，只查询当前认证用户。

验收：与数据库抽样记录逐条对照，排序及分页无重复，操作后刷新能看到变化；清空/删除后消失规则一致；用户之间不串数据。

### R12：内容发现、性能与 SEO

**内容发现**

优先由 R04 的系列阅读、R10 的真实热门标签组成发现链路；检查首页、分类、标签、系列、相关文章与上下篇是否可互达，补齐真实摘要、缺失封面占位与空态。不虚构文章、标签、更新记录或“热门”数据。新的内容栏目、专题选题或批量文章生产另行定义范围。

**CDN / COS 与性能**

1. 先记录首页、长文章、标签页冷/热缓存的首屏资源、请求数、传输体积、LCP/CLS，以及打开搜索/AI 的响应时间。使用相同设备、网络和数据各测 3 次，以中位数对照优化前后。
2. 复用现有 `FileStorage` 和 URL 归一化策略；盘点公开图片、音乐、Live2D、字体、构建资源实际来自哪个域名。CDN 与 COS 已可用不代表全部资源已经正确命中缓存，不按旧 PRD 再做一次迁移。
3. 首屏主图不盲目懒加载；非首屏封面/正文图片按需加载并提供尺寸，使用已有缩略图能力减少下载体积。Live2D 保持用户需要时加载，评估可延迟的脚本和不必要的预加载，避免使正文等待模型。
4. 带内容 hash 的构建资源允许长缓存；入口 HTML 保持及时更新；用户资料、登录、积分、个性化 API 和 SSE 不进入公共缓存。验证实际 CDN 规则、缓存命中和发布失效，不仅检查仓库配置。
5. 音频验证 CORS、MIME、Range/206、重定向与过期缓存，并覆盖 COS 自定义域名；不能把更换 CDN 当作音频时序 Bug 的修复。COS CORS 的配置与实际响应核对参考[腾讯云文档](https://cloud.tencent.com/document/product/436/13318)。
6. 私有下载继续走购买/权限校验，TTS 临时音频遵循当前代理与缓存边界；不将这类 URL 当作公开静态资源统一迁移。

性能目标是消除已记录的瓶颈，不预先宣称固定提速百分比。目标参考：移动端实验室 LCP ≤ 2.5 秒、CLS ≤ 0.1；若当前基线差距较大，记录受限原因和相对改进。交互延迟按真实输入/操作单独测量，不能用一次 Lighthouse 分数冒充线上 INP。

**SEO 补齐**

1. 保留文章页 `useHead` 和 Article JSON-LD，统一它与 router `document.title` 的职责，消除页面切换后的旧 meta/重复标签。摘要先转纯文本，不能直接截取 HTML 放进 description。
2. 首页、文章、分类、标签、系列分别提供正确标题、描述和 canonical；个人中心、登录等非公开内容设置适当的索引策略，不能把 robots 禁止抓取当作认证手段。
3. 统一文章 canonical、站内链接、sitemap 的路径规则；兼容历史 `/post/{id}`，带 slug 地址的处理以现有 `buildPostPath` 为基础，避免修改标题后出现多个互相冲突的规范地址。
4. 复用 `SitemapController`，检查只列公开未删除内容、标签/分类/系列路径有效、更新时间真实、XML 特殊字符正确转义。排除草稿、私有页、失效链接，验证新增系列覆盖是否需要补充。
5. 使用真实封面与作者信息校验 OG/Twitter/结构化数据；验证资源为绝对公开 URL，单页导航后数据随文章变化，不保证富结果或搜索排名。
6. 分别检查原始 HTML 与浏览器渲染后的 DOM，以及 404/草稿/已删除文章的 HTTP 与索引表现。当前是 SPA，客户端 meta 更新不代表所有分享抓取器都能读取；Google 的抓取和渲染机制参见[JavaScript SEO 文档](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)。
7. 若上述验证证实公开正文或分享元信息不可被目标抓取器读取，再针对公开内容页增加可更新的预渲染方案：从真实公开 API 取数据、发布/更新/下线触发刷新、删除旧产物、保证旧 URL/404 与缓存一致；不以整站 SSR 重构作为本轮前提。是否启用及维护成本在本批基线报告后记录。
