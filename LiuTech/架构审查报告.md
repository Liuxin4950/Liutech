## 一、Controller 层：RESTful 接口设计

**评级：良好**

### 1.1 优点

- **分层清晰**：`controller/admin/` 和 `controller/web/` 严格分目录。管理端统一 `/admin/*` 前缀，公开端按资源名分组。共 17 个管理端 Controller + 15 个公开端 Controller，职责边界明确。
- **HTTP 方法使用规范**：GET 用于查询、POST 用于创建/批量操作、PUT 用于更新、DELETE 用于删除，绝大多数接口遵循了 REST 语义。管理端统一支持批量操作（`/batch`）、软删除恢复（`/restore`）和物理删除（`/permanent`），操作模式一致。
- **统一基类**：`BaseAdminController` 提供了 `handleOperationResult()` 和 `handleException()` 复用方法，减少管理端 Controller 的样板代码。
- **权限注解**：管理端统一使用 `@PreAuthorize("hasRole('ADMIN')")`，授权声明清晰。

### 1.2 具体问题

#### 问题 1：公告 Controller 混入管理端接口

`AnnouncementsController` 位于 `controller/web/` 包下，却包含 10+ 个管理端接口（`/admin/list`、`/admin/export`、`/admin/import`、POST/PUT/DELETE 等），通过 `@PreAuthorize` 单独加权限。这打破了"admin 包 = 管理接口"的约定。

**证据** — `controller/web/AnnouncementsController.java`：

```java
@PostMapping
@PreAuthorize("hasRole('ADMIN')")
@OperationLog(action = "create", targetType = "announcement", ...)
public Result<Long> createAnnouncement(@Valid @RequestBody AnnouncementReq req) { ... }

@PostMapping("/admin/export")
@PreAuthorize("hasRole('ADMIN')")
public void exportAnnouncements(...) { ... }

@PostMapping("/admin/import")
@PreAuthorize("hasRole('ADMIN')")
public Result<Map<String, Object>> importAnnouncements(@RequestParam("file") MultipartFile file) { ... }
```

**建议**：将管理端接口迁移至 `controller/admin/AnnouncementsAdminController.java`。

---

#### 问题 2：PostsController 混合公开接口与需认证接口

`PostsController`（web 包）中既有公开的 GET 接口，也有需要认证的 POST/PUT/DELETE 操作（`/posts/drafts`、`/posts/my`、`/posts/favorites`）。

**证据** — `controller/web/PostsController.java`：

```java
@GetMapping("/drafts")    // 需要认证 — 当前用户的草稿
@GetMapping("/my")        // 需要认证 — 当前用户的文章
@GetMapping("/favorites") // 需要认证 — 当前用户的收藏
@PostMapping              // 需要认证 — 创建文章
@PutMapping("/{id}")      // 需要认证 — 更新文章
@DeleteMapping("/{id}")   // 需要认证 — 删除文章
```

**建议**：将"我的文章"相关操作独立为 `controller/web/MyPostsController.java`，映射 `/user/posts/*`。

---

#### 问题 3：URL 命名风格不一致

| Controller | 实际映射 | 问题 |
|-----------|---------|------|
| `MusicController` | `@GetMapping("/music/list")` | 无类级 `@RequestMapping`，直接在方法上写完整路径 |
| `CheckinController` | `@RequestMapping("/user")` | 与 `UserController` 的 `/user` 前缀冲突 |
| `HomeController` | `@RequestMapping("/")` | 根路径映射，`/dashboard`、`/stats` 与 admin DashboardController 功能重叠 |

**证据** — `controller/web/MusicController.java`：

```java
// 没有 @RequestMapping("/music") 类注解
@GetMapping("/music/list")   // 完整路径写在方法上
@GetMapping("/music/{id}")
```

**建议**：统一所有 Controller 都有类级 `@RequestMapping`，消除路径前缀冲突。

---

#### 问题 4：UserController 职责过重

`UserController` 映射 `/user`，同时承担了注册、登录、资料管理、用户 CRUD（admin 级别）四种职责。

**证据** — `controller/web/UserController.java`：

```java
@PostMapping("/register")   // 公开 — 注册
@PostMapping("/login")      // 公开 — 登录
@GetMapping("/current")     // 认证 — 当前用户
@PutMapping("/profile")     // 认证 — 更新资料
@GetMapping                 // ← 管理接口？获取用户列表
@PostMapping                // ← 管理接口？创建用户
@PutMapping("/{id}")        // ← 管理接口？更新用户
@DeleteMapping("/{id}")     // ← 管理接口？删除用户
```

后四个接口看起来是管理操作，应归入 `UsersAdminController`。

---

#### 问题 5：缺少 API 版本号

所有接口没有版本前缀（如 `/api/v1/`），未来迭代可能产生兼容性问题。

**建议**：新接口引入 `/api/v1/` 前缀，旧接口保持兼容并标注废弃计划。

## 二、Service 层：抽象、耦合、事务管理

**评级：良好**

### 2.1 优点

- **职责拆分合理**：用户域拆为 `UserAuthService`（认证）、`UserProfileService`（资料）、`UserManagementService`（管理）。TTS 拆为 `TtsSpeechService`、`TtsStatusService`、`TtsConfigService`、`TtsVoiceCatalogService`。
- **事务使用得当**：写操作标注 `@Transactional(rollbackFor = Exception.class)`，只读查询标注 `@Transactional(readOnly = true)`。
- **缓存注解**：热门文章、标签、分类等使用了 `@Cacheable` + `@CacheEvict`。
- **N+1 优化**：文章列表查询后的标签批量加载（`fillTags` 方法），避免了嵌套查询。

### 2.2 具体问题

#### 问题 1（严重）：吞异常

`PostsService.permanentDeletePost()` 和 `batchPermanentDeletePosts()` 的 boolean 重载版本吞掉了异常，调用方无法知道失败原因。

**证据** — `service/PostsService.java`：

```java
@Transactional
public boolean permanentDeletePost(Long id) {
    try {
        this.permanentDeletePost(id, null);
        return true;
    } catch (Exception e) {
        return false;  // ← 异常被吞掉，调用方无法知道失败原因
    }
}

@Transactional
public boolean batchPermanentDeletePosts(java.util.List<Long> ids) {
    try {
        this.batchPermanentDeletePosts(ids, null);
        return true;
    } catch (Exception e) {
        return false;  // ← 同上
    }
}
```

**建议**：移除这两个 boolean 重载方法，统一使用抛异常的版本，让异常自然传播到 Controller 层。

---

#### 问题 2：RuntimeException 代替 BusinessException

多处直接 `throw new RuntimeException(...)` 而非使用已定义的 `BusinessException`，导致 `GlobalExceptionHandler` 无法返回结构化的错误码。

**证据** — `service/PostsService.java`：

```java
// permanentDeletePost(Long id, Long updatedBy) 方法内
if (result <= 0) {
    throw new RuntimeException("文章删除失败，可能文章不存在");
}

// batchPermanentDeletePosts 方法内
throw new RuntimeException("批量彻底删除文章失败: " + e.getMessage(), e);
```

**证据** — `service/CheckinService.java`：

```java
// checkin 方法内
throw new RuntimeException("积分奖励发放失败，请稍后重试");
```

**建议**：全局搜索 `throw new RuntimeException`，统一替换为 `BusinessException(ErrorCode.XXX)`。

---

#### 问题 3：Service 返回 Result 对象 — 层级越界

`CheckinService.checkin()` 直接返回 `Result<CheckinResp>`，而其他 Service 返回裸数据对象。`Result` 是 Controller 层的 HTTP 响应包装，不应出现在 Service 层。

**证据** — `service/CheckinService.java`：

```java
@Transactional(rollbackFor = Exception.class)
public Result<CheckinResp> checkin(Long userId) {
    // ...
    if (todayCheckin != null) {
        return Result.fail(ErrorCode.PARAMS_ERROR, "今日已签到");  // ← Service 不应返回 Result
    }
    // ...
    return Result.success("签到成功", response);  // ← 同上
}
```

`getCheckinStatus()` 方法同样返回 `Result<CheckinStatusResp>`。

**建议**：Service 返回裸数据对象或抛出 `BusinessException`，由 Controller 统一包装 `Result`。

---

#### 问题 4：部分 Service 缺少接口抽象

所有 Service 都是直接的类实现，没有定义 Service 接口。虽然在 Spring 单实现场景下不是硬性要求，但 `PostsService extends ServiceImpl<PostsMapper, Posts>` 暴露了 MyBatis-Plus 的 `ServiceImpl` 给上层，Controller 可以直接调用 `this.save()`、`this.getById()` 等 ORM 方法，增加了耦合。

---

#### 问题 5：循环依赖隐患

`OperationLogAspect` 通过 `@Lazy` 注入 `LogService` 来避免循环依赖，说明依赖图中存在环路。

**证据** — `aspect/OperationLogAspect.java`：

```java
@Lazy  // 延迟加载，避免循环依赖
private final LogService logService;
```

**建议**：通过 `ApplicationEventPublisher` 发布日志事件，由独立的 `LogEventListener` 异步记录，彻底解耦。

---

#### 问题 6：PostsService 过于庞大

`PostsService` 包含文章 CRUD、点赞、收藏、标签管理、统计、永久删除、批量操作等全部逻辑，超过 1300 行。

**建议**：拆分为：
- `PostCrudService` — 文章增删改查
- `PostInteractionService` — 点赞、收藏
- `PostAdminService` — 管理端文章操作（永久删除、批量操作、状态变更）

## 三、Mapper 层：MyBatis-Plus 使用

**评级：良好**

### 3.1 优点

- **MyBatis-Plus 用法规范**：继承 `BaseMapper<T>`，分页使用 `IPage<T>` + `Page<T>`，条件查询使用 `LambdaQueryWrapper`。
- **复杂查询用 XML**：文章列表查询、评论树、用户统计等复杂 SQL 用 XML 编写，简单查询用注解 `@Select`/`@Update`，风格合理。
- **ResultMap 设计精细**：`PostListReslMap` 和 `PostDetailReslMap` 使用 `association` 和 `collection` 映射嵌套对象，避免了 N+1 查询。
- **乐观锁**：积分操作使用版本号乐观锁（`deductPointsWithVersion`/`addPointsWithVersion`），保障并发安全。

### 3.2 具体问题

#### 问题 1（安全风险）：SELECT * 滥用

多个查询使用 `SELECT *`，会将 `password_hash` 等敏感字段查出来。

**证据** — `mapper/UserMapper.xml`：

```xml
<select id="findByUserName" parameterType="string" resultType="chat.liuxin.liutech.model.Users">
    SELECT * FROM users WHERE username = #{username}
</select>

<select id="findByEmail" parameterType="string" resultType="chat.liuxin.liutech.model.Users">
    SELECT * FROM users WHERE email = #{email}
</select>
```

`UserAuthService` 调用 `findByUserName` 后返回的 `Users` 对象包含密码哈希，如果被序列化到日志中会造成信息泄漏。

**证据** — `mapper/AnnouncementsMapper.xml`：

```xml
<select id="selectValidAnnouncements" ...>
    SELECT * FROM announcements ...
</select>
```

**建议**：所有查询改为明确列出需要的字段，排除 `password_hash`、`deleted_at`（非管理端）等敏感/不必要字段。

---

#### 问题 2：子查询性能隐患

文章列表查询使用关联子查询获取评论数，每行都会执行一次子查询。

**证据** — `mapper/PostsMapper.xml`：

```xml
(SELECT COUNT(*) FROM comments cm
 WHERE cm.post_id = p.id AND cm.deleted_at IS NULL) as comment_count
```

**建议**：
- 短期：改为 `LEFT JOIN` + `GROUP BY` + `COUNT`
- 长期：在 `posts` 表维护 `comment_count` 冗余字段，通过触发器或 Service 层同步更新

---

#### 问题 3：自定义分页未统一

`UserMapper.selectUsersForAdmin` 使用手动 `LIMIT #{offset}, #{limit}` 而非 MyBatis-Plus 的 `IPage` 分页。

**证据** — `mapper/UserMapper.xml`：

```xml
<select id="selectUsersForAdmin" resultType="chat.liuxin.liutech.resp.UserResp">
    SELECT ...
    LIMIT #{offset}, #{limit}
</select>
```

需要额外的 `countUsersForAdmin` 查询来获取总数，且与其他 Mapper 的分页风格不一致。

**建议**：改用 `IPage<UserResp>` 参数，让 MyBatis-Plus 自动处理分页和 count 查询。

---

#### 问题 4：Mapper 方法命名不一致

- `selectPostListResl` — "Resl" 是 Response 的缩写？
- `convertToUserResl` — Service 中的方法名也用了 "Resl"

**建议**：统一为完整单词 `Resp` 或 `Response`，与 `resp/` 包名保持一致。

---

#### 问题 5：物理删除缺少审计

存在多处 `permanentDeleteById`、`deleteByPostId` 等物理删除方法，但缺少操作审计日志记录（哪些数据被永久删除了、被谁删除的）。

**建议**：在物理删除前，将被删除数据的关键信息（ID、标题、操作人）记录到 `AdminLogs`。

## 四、Model 层：实体设计

**评级：良好**

### 4.1 优点

- **继承体系清晰**：`IdEntity`（主键）→ `BaseEntity`（审计字段 + 软删除）→ 具体实体，层次分明。
- **DTO/VO 分离**：`req/` 包（请求 DTO）和 `resp/` 包（响应 VO）独立存放，请求和响应模型不混用。
- **UsersSafe 设计巧妙**：通过继承 `Users` 并用 `@JsonIgnore` 重写 `getPasswordHash()`，实现了响应级别的密码脱敏。
- **model/dto 子包**：TTS 相关 DTO 独立放在 `model/dto/`，区分于数据库实体。

**实体继承体系**：

```
IdEntity                    # 主键 id (Long, AUTO)
  └── BaseEntity            # createdAt, updatedAt, createdBy, updatedBy, deletedAt (@TableLogic)
        ├── Users           # username, email, passwordHash, avatarUrl, points, version, role, status, ...
        ├── Posts           # title, content, summary, categoryId, authorId, status, coverImage, ...
        ├── Comments        # postId, userId, content, parentId
        ├── Categories      # name, description, sortOrder
        ├── Tags            # name
        ├── Announcements   # title, content, type, priority, status, startTime, endTime, isTop, viewCount
        ├── Carousel        # title, imageUrl, linkUrl, sortOrder, status
        └── ...
  └── AdminLogs             # 只继承 IdEntity，不继承 BaseEntity（日志不可变）
```

### 4.2 具体问题

#### 问题 1：Resp 类大量继承实体类 — 领域泄漏

多个 Resp 类直接继承 Model 实体，导致数据库表结构变更直接影响 API 响应结构。

| Resp 类 | 继承自 |
|---------|-------|
| `CategoryResp` | `Categories` |
| `TagResp` | `Tags` |
| `ResourceResp` | `Resources` |
| `PostListResp` | `Posts` |
| `PostDetailResp` | `Posts` |
| `PostCreateResp` | `Posts` |
| `DownloadLogResp` | `ResourceDownloads` |
| `PointsTransactionResp` | `PointsTransaction` |
| `UserCheckinResp` | `UserCheckin` |
| `UserResp` | `UsersSafe`（→ `Users`） |

**建议**：逐步改为组合模式（`private CategoryInfo category`），隔离数据库结构与 API 契约。短期可通过 `@JsonIgnore` 屏蔽不该暴露的字段。

---

#### 问题 2：PostListResp 继承 Posts 会暴露 content

`PostListResp extends Posts`，而 `Posts` 有 `content`（全文 Markdown）字段。列表接口不需要返回全文内容。虽然 XML 查询未 SELECT content，但如果有其他地方直接 `BeanUtils.copyProperties()`，content 会被拷贝。

**建议**：`PostListResp` 不应继承 `Posts`，改为独立类或排除 `content` 字段。

---

#### 问题 3：贫血模型（可接受）

所有 Model 都是纯数据载体（`@Data` + 字段），没有领域方法。签到奖励计算、积分扣减等业务规则全部在 Service 中。

对于当前项目规模（个人博客），这是可以接受的架构选择。但如果后续业务复杂度增加，可以考虑在 `Users` 中加入领域方法。

---

#### 问题 4：内部类作为 Response 字段

```java
// PostListResp.java
private CategoryInfo category;  // CategoryInfo 是 PostListResp 的内部类
private AuthorInfo author;      // AuthorInfo 是 PostListResp 的内部类
private List<TagInfo> tags;     // TagInfo 是 PostListResp 的内部类
```

项目规模不大时可接受，但随着嵌套类型增多，建议独立为顶层类以提高复用性。

## 五、Common / Utils 公共组件

**评级：优秀**

### 5.1 优点

- **统一异常体系**：`BusinessException` + `ErrorCode` 枚举 + `GlobalExceptionHandler`，三层配合完善。ErrorCode 按功能域划分：
  - 200: 成功
  - 400-499: 客户端错误
  - 1000-1099: 用户相关
  - 1100-1199: 文章相关
  - 1200-1299: 分类相关
  - 1300-1399: 评论相关
  - 1400-1499: 文件相关
  - 500-599: 系统错误
- **Result 统一响应**：`Result<T>` 提供 `success()`/`fail()` 静态工厂、`@JsonIgnore isSuccess()` 便捷方法，设计完善。
- **ValidationUtil 覆盖全面**：提供 `validateNotNull`、`validateEmail`、`validateUsername`、`validatePassword`、`validateRange` 等常用校验。
- **BeanConvertUtil 统一转换**：封装了 `convertToUserResl` 脱敏逻辑和通用 `BeanUtils.copyProperties` 转换。

### 5.2 具体问题

#### 问题 1：BeanConvertUtil 通用方法有冗余判断

**证据** — `utils/BeanConvertUtil.java`：

```java
public static <T> T convert(Object source, Class<T> targetClass) {
    // source 在上方已判空返回 null
    T target = targetClass.getDeclaredConstructor().newInstance();
    if (source != null && target != null) {  // ← source 已判空，target 刚 new 出来不可能是 null
        BeanUtils.copyProperties(source, target);
    }
    return target != null ? target : targetClass.getDeclaredConstructor().newInstance(); // ← 同理
}
```

---

#### 问题 2：FileUtil 同时是工具类和 Spring 组件

`FileUtil` 使用 `@Component` 注解并注入了 `FileUploadConfig` 和 `ImagesMapper`，实际上是 Service 层的辅助组件。它包含了：
- 纯静态逻辑（URL 提取正则 `IMG_SRC_PATTERN`、`MARKDOWN_IMAGE_PATTERN`）
- Spring 依赖的 I/O 操作（`saveFile`、`extractImageUrls`、`decrementImageUsageCountByUrl`）

**建议**：
- 纯静态逻辑保留在 `FileUtil`（无 `@Component`）
- I/O 操作移入 `FileService` 或保留在 `FileUploadService` 中

---

#### 问题 3：UserUtils 中 getCurrentUser() 直接查询数据库

`UserUtils` 从 `SecurityContextHolder` 获取 userId 后直接调用 `UserMapper.selectById()`，每次调用都会查库。高频接口中如果触发此方法，会产生不必要的数据库压力。

**建议**：在 `JwtAuthenticationFilter` 或 `RequestTraceFilter` 中将用户信息缓存到 `RequestAttribute`，后续通过 `request.getAttribute()` 获取。

## 六、Filter / Aspect：AOP 设计

**评级：良好**

### 6.1 优点

- **Filter 设计规范**：
  - `JwtAuthenticationFilter extends OncePerRequestFilter`，保证每次请求只执行一次。
  - `RequestTraceFilter` 生成 traceId 并绑定 MDC，支持日志链路追踪。优先复用网关传入的 `X-Request-Id`，否则生成本地 UUID。
- **OperationLog 注解 + 切面**：自定义 `@OperationLog` 注解支持 SpEL 表达式描述操作内容，切面自动记录操作人、IP、耗时、结果。设计优雅。
- **RequestTimingAspect**：记录所有 Controller 请求耗时，并对 >3s 的请求发出性能告警。

### 6.2 具体问题

#### 问题 1：RequestTimingAspect 日志量过大

每个请求输出 3-4 行 INFO 日志，在生产环境会产生大量日志。

**证据** — `aspect/RequestTimingAspect.java`：

```java
log.info("请求URL: {} {}", httpMethod, requestUrl);
log.info("调用方法: {}.{}", className, methodName);
log.info("客户端IP: {}", clientIp);
log.info("请求参数: {}", argsStr);
```

**建议**：降级为 DEBUG 级别，或只记录慢请求（>1s）。

---

#### 问题 2：RequestTimingAspect 与 RequestTraceFilter 信息重复

两个组件都记录了请求 URL、方法和耗时，造成日志冗余。

| 信息 | RequestTraceFilter | RequestTimingAspect |
|------|-------------------|---------------------|
| 请求 URL | ✅ | ✅ |
| HTTP 方法 | ✅ | ✅ |
| 耗时 | ✅ | ✅ |
| traceId | ✅ | ❌ |
| 客户端 IP | ❌ | ✅ |
| 请求参数 | ❌ | ✅ |
| Controller 方法名 | ❌ | ✅ |

**建议**：合并为一个组件，或降低 `RequestTimingAspect` 日志级别为 DEBUG，只在慢请求时输出 INFO。

---

#### 问题 3：JwtAuthenticationFilter 白名单与 SecurityConfig 不同步

Filter 中硬编码了一套白名单路径，同时 `SecurityConfig` 也定义了一套 `permitAll` 规则。两处必须手动保持同步，容易遗漏。

**证据** — `filter/JwtAuthenticationFilter.java`：

```java
private boolean shouldSkipAuthentication(String requestURI, String method) {
    if ("/user/login".equals(requestURI) || "/user/register".equals(requestURI)) {
        return true;
    }
    if ("GET".equalsIgnoreCase(method)) {
        if ("/posts".equals(requestURI) || "/posts/".equals(requestURI)
                || requestURI.startsWith("/posts/slug/")
                || requestURI.startsWith("/posts/id/")
                || requestURI.startsWith("/posts/category/")
                || requestURI.startsWith("/posts/tag/")
                || requestURI.startsWith("/posts/archive/")) {
            return true;
        }
        if (requestURI.startsWith("/categories/")
                || requestURI.startsWith("/tags/")
                || requestURI.startsWith("/comments/")
                || requestURI.startsWith("/messages/")
                || ...) {
            return true;
        }
        // ... 更多路径
    }
}
```

**建议**：Filter 中移除 `shouldSkipAuthentication` 白名单，仅依赖 Security 框架的 `permitAll` 配置。对于公开的 GET 接口，Security 框架会自动放行，无需在 Filter 层重复判断。

---

#### 问题 4：OperationLogAspect 同步记录拖慢业务

日志记录在主线程的 `finally` 块中执行，如果数据库慢查询，会拖慢业务请求。

**证据** — `aspect/OperationLogAspect.java`：

```java
} finally {
    try {
        recordOperationLog(point, operationLog, success, errorMessage, result,
            System.currentTimeMillis() - startTime);  // ← 同步写库
    } catch (Exception e) {
        log.error("记录操作日志失败", e);
    }
}
```

**建议**：使用 `ApplicationEventPublisher` 发布日志事件，由 `@EventListener` + `@Async` 异步记录。

## 七、Config 配置类

**评级：良好**

### 7.1 优点

- **SecurityConfig 设计完善**：CORS 配置支持多种源（localhost、IP、域名、www 子域名），`BCryptPasswordEncoder` 集中注册为 Bean。
- **MybatisPlusConfig**：配置了分页插件（最大 500 条限制）和乐观锁插件。
- **TransactionConfig**：30 秒超时、支持嵌套事务、校验已有事务。
- **FileUploadConfig**：通过 `@ConfigurationProperties` 绑定，支持环境变量覆盖（Docker 兼容）。
- **MyMetaObjectHandler**：自动填充审计字段（`createdAt`/`updatedAt`/`createdBy`/`updatedBy`），使用 `@Lazy` 避免循环依赖。

### 7.2 具体问题

#### 问题 1：CacheConfig 使用 ConcurrentMapCacheManager — 无淘汰机制

**证据** — `config/CacheConfig.java`：

```java
@Bean
public CacheManager cacheManager() {
    ConcurrentMapCacheManager cacheManager = new ConcurrentMapCacheManager();
    cacheManager.setCacheNames(java.util.Arrays.asList(
        "hotPosts", "latestPosts", "postList", "hotTags",
        "categories", "announcements", "userStats"
    ));
    cacheManager.setAllowNullValues(true);
    return cacheManager;
}
```

`ConcurrentMapCacheManager` 是内存缓存，没有 TTL、没有 LRU 淘汰、没有容量上限。在长时间运行后会导致内存持续增长。

**建议**：迁移到 Caffeine 缓存：

```java
@Bean
public CacheManager cacheManager() {
    CaffeineCacheManager cacheManager = new CaffeineCacheManager();
    cacheManager.setCaffeine(Caffeine.newBuilder()
        .expireAfterWrite(10, TimeUnit.MINUTES)
        .maximumSize(1000));
    return cacheManager;
}
```

## 九、总评

| 层 | 评级 | 核心评价 |
|----|------|---------|
| **Controller** | **良好** | REST 风格整体规范，个别 Controller 位置和职责需调整 |
| **Service** | **良好** | 拆分合理、事务使用得当，但有吞异常和层级越界问题 |
| **Mapper** | **良好** | MyBatis-Plus 用法规范，XML 与注解分工明确，需消除 SELECT * |
| **Model** | **良好** | 继承体系清晰、DTO/VO 分离，但 Resp 继承实体类存在领域泄漏 |
| **Common/Utils** | **优秀** | 异常体系、统一响应、校验工具设计完善 |
| **Filter/Aspect** | **良好** | traceId 链路追踪和操作日志注解设计优秀，但有日志冗余和白名单同步问题 |
| **Config** | **良好** | 配置完整，但缓存无淘汰和 CORS 硬编码需改进 |

### 项目亮点

1. **统一异常体系**：`BusinessException` + `ErrorCode` + `GlobalExceptionHandler` 三层配合，错误码分域管理，是教科书级的实践。
2. **UsersSafe 设计**：用继承 + `@JsonIgnore` 实现响应脱敏，优雅且零侵入。
3. **操作日志注解**：`@OperationLog` + SpEL 表达式，声明式日志记录，代码侵入性极低。
4. **traceId 链路追踪**：`RequestTraceFilter` 支持网关透传 + 本地生成，MDC 绑定，是生产级的可观测性实践。
5. **乐观锁积分操作**：版本号 + 原子 SQL，保障并发安全。
6. **BaseEntity 自动填充**：`MyMetaObjectHandler` 统一处理审计字段，Service 层无需手动赋值。

### 核心风险

1. **安全**：`SELECT *` 可能导致密码哈希泄漏到日志或响应中。
2. **稳定性**：吞异常导致错误被静默忽略，排查困难。
3. **内存**：`ConcurrentMapCacheManager` 无上限，长时间运行可能导致 OOM。
4. **可维护性**：白名单重复定义、日志组件信息重复，增加维护成本。
