# 交付工作流

## 目标

使用本 skill 将”已确认的 PRD”或”小修/Bug 修复范围”交付成可验证的代码变更，并沉淀开发记录和项目架构变化。

如果项目存在 `.codex/project-adapter.md`，先读取它以获取项目模块、过程文档目录、验证命令和高风险定义。复制本 skill 到其他项目时，替换 adapter 和 `references/excellent-code-index.md`，不要改 skill 主体。

它和 `prd-workflow` 的分工：

- `prd-workflow`：业务需求共创、生成合并 PRD（业务需求 + 实现方案）。
- `delivery-workflow`：编码、验证、开发记录、架构更新。

## 进入条件

进入本 skill 前先判断：

1. 如果用户只是讨论想法、需求边界或实现方案，不进入本 skill，改用 `prd-workflow`。
2. 如果用户要求”帮我实现””开始开发””修复 bug””重构””整改””优化”，进入本 skill。
3. 如果是普通功能或重大/高风险变更，但没有已确认 PRD，先暂停并要求回到 `prd-workflow`。
4. 如果是小修 / Bug 修复，可以跳过 PRD，但必须写开发记录。
5. 如果只是文案、注释、格式、无行为变化的极小修，可以不写开发记录，但最终回复必须说明无行为影响。

## 交付流程

1. 读取 `.codex/rules/ai-development-workflow.md` 和 `.codex/project-adapter.md`，确认变更级别与项目适配规则。
2. 普通功能或重大/高风险变更：读取同名 PRD。
3. 普通功能或重大/高风险变更：先执行”PRD 开发门禁”，不合格则暂停并回到 `prd-workflow`。
4. 小修 / Bug 修复：定位问题和影响范围，不强制读取 PRD。
5. 涉及以下场景时建议参考 `references/excellent-code-index.md`：统一响应、业务异常、全局异常处理、统一 API 封装、流式响应、跨服务调用、文件上传下载。否则可跳过。
6. 按最小必要范围修改代码，不擅自扩大需求。
7. 执行与影响范围匹配的验证命令。
8. 使用 `references/development-record-template.md` 写开发记录。
9. 判断架构影响；需要时使用 `references/architecture-update-template.md` 写项目架构。
10. 如果本次变化改变长期稳定的模块边界、数据流、接口协议或部署拓扑，同步更新 `doc/记录/当前架构.md`。
11. 最终回复说明变更、验证结果、开发记录路径、架构影响判断。

## PRD 开发门禁

普通功能或重大/高风险变更开始编码前，必须确认 PRD（业务需求 + 实现方案）包含：

1. 最终需求摘要。
2. 代码库审查摘要和实际检查路径。
3. 影响范围和预计修改模块。
4. 后端、前端、数据库、配置等相关方案；无影响也要写明原因。
5. 接口、数据流、权限和错误处理。
6. 安全影响、性能影响。
7. 测试方案和验证命令。
8. 回滚方案。
9. 架构影响判断。

任一缺失，暂停开发，回到 `prd-workflow` 补齐 PRD。

## 文件规则

同一功能的过程文件必须使用完全一致的文件名：

```text
功能名_YYYY-MM-DD.md
```

交付阶段至少创建或更新：

```text
doc/记录/开发-功能名_YYYY-MM-DD.md
```

有架构影响或属于重大/高风险变更时，还必须创建或更新：

```text
doc/记录/架构-功能名_YYYY-MM-DD.md
```

如果本次变化改变长期稳定的总体架构，还必须更新：

```text
doc/记录/当前架构.md
```

## 变更分级

### 小修 / Bug 修复

- 不强制 PRD。
- 必须记录问题、原因、修复、验证和架构影响判断。
- 如果修复过程中发现影响范围扩大，升级为普通功能或高风险变更。

### 极小修

- 仅限文案、注释、格式、无行为变化。
- 不涉及接口、数据、权限、安全、性能、构建配置。
- 可以不写开发记录。
- 最终回复必须写明”无行为影响”。

### 普通功能

满足以下**所有**条件可跳过 PRD，直接进入交付：

- 改动行数 < 约 200 行
- 不跨服务调用
- 不触及高风险领域（认证、积分、AI/SSE/TTS、上传下载、数据库结构、Nginx、Docker、CI/CD、部署）
- 不引入新接口或修改现有接口协议
- 不引入新数据库表或迁移脚本

不满足任一条件时仍按”重大/高风险”走完整 PRD 流程。

按 PRD 开发时：

- 必须先有已确认的 PRD。
- 按 PRD 实现，不擅自改需求。
- 开发完成后写开发记录。
- 如有架构影响，更新项目架构。

### 重大功能 / 高风险变更

涉及认证授权、安全策略、积分/支付/下载权限、数据库结构、上传下载、AI/SSE/TTS、Nginx、Docker、CI/CD、部署、跨服务调用、核心业务流程或明显性能风险时，必须完整执行：

```text
PRD -> 开发 -> 验证 -> 开发记录 -> 项目架构更新
```

## 验证要求

按影响范围选择验证，不要机械运行无关命令。验证命令以 `.codex/project-adapter.md` 为准；如果 adapter 不存在，则根据项目技术栈自行识别构建、测试、类型检查、配置校验命令。

无法执行时，必须在开发记录和最终回复中写明原因。

## 优秀代码索引维护

使用 `references/excellent-code-index.md` 时必须检查样例是否仍然准确：

1. 如果样例路径不存在，立即停止引用并更新索引。
2. 如果样例与当前项目风格冲突，标注为过时或移除。
3. 如果本次新增了可复用的高质量范式，可补充到索引。
4. 不允许为了省事复制过时范式。

## 输出要求

结束时总结：

1. 变更内容。
2. 验证命令和结果。
3. 开发记录路径。
4. 项目架构路径，或无架构影响判断。
5. 遗留风险或未执行项。
