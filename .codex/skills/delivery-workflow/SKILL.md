# 交付工作流

## 目标

将"已确认的 PRD"或"小修/Bug 修复范围"交付成可验证的代码变更，并沉淀开发记录和项目架构变化。

## 触发与退出

- 触发：用户说"帮我实现/开始开发/修复 bug/重构/优化/写开发记录/更新项目架构"。
- 退出：编码完成、验证通过、开发记录与必要的架构文档写好后，回复变更摘要。如果用户在过程中改口要求"先设计方案"，切到 `prd-workflow`。

## 流程（按变更级别分流）

| 变更级别 | 步骤 |
| --- | --- |
| 极小修（仅文案/注释/格式，无行为变化） | 改完 → 回复"无行为影响" |
| 小修 / Bug 修复 | 定位根因 → 改 → 验证（针对改动范围）→ 写开发记录 |
| 普通功能（PRD 豁免条件全满足，见 `ai-development-workflow.md`） | 读 `project-adapter.md` 取验证命令 → 改 → 验证 → 写开发记录 |
| 普通功能（不满足豁免） / 重大 / 高风险 | 读 `project-adapter.md` + 同名 PRD → 改 → 验证 → 写开发记录 → 必要时写架构文档 → 必要时改 `当前架构.md` |

## 进入编码前必读

- 极小修 / 小修：不需要读 PRD。直接定位问题。
- 普通功能及以上：先读 `.codex/project-adapter.md` 取本项目验证命令与高风险定义。
- 普通功能及以上（不满足豁免）/ 重大 / 高风险：再读同名 PRD。
- 跨服务、触及认证/AI/数据库/部署/上传下载时，**主动**参考 `references/excellent-code-index.md` 的相关条目；其它场景跳过。

## 自检清单

编码前确认（普通功能及以上不满足豁免、重大、高风险）：

1. 已读 PRD 整体（业务需求 + 实现方案）
2. 影响范围、接口、数据流、权限、错误处理都在 PRD 中明确
3. 验证命令与 `project-adapter.md` 匹配

编码后确认：

1. 按最小必要范围修改代码
2. 验证命令已执行，结果已记录
3. 已写 `doc/记录/开发-功能名_YYYY-MM-DD.md`（含变更内容、验证结果、遗留风险）
4. 有架构影响时已写 `doc/记录/架构-功能名_YYYY-MM-DD.md`
5. 改动改变长期稳定的模块边界/数据流/接口协议/部署拓扑时，已同步更新 `doc/记录/当前架构.md`

## 范式索引维护

**仅当本次交付实际参考了 `excellent-code-index.md` 时**，检查样例是否仍然准确：路径不存在立即标注或移除；风格冲突的弃用；新出现的可复用范式可补充。不要为了"保险"复制过时范式，也不要为了维护而维护。

## 输出

结束时总结：变更内容；验证命令与结果；开发记录路径；有架构影响时给架构文档路径，否则说明"无架构影响"；遗留风险或未执行项。
