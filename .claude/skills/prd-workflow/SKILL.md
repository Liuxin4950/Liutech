# PRD 工作流

## 目标

将功能想法推进到合并的 PRD 文档：`doc/PRD/功能名_YYYY-MM-DD.md`，含 `## 业务需求` 与 `## 实现方案` 两章。用户整体确认后切到 `delivery-workflow`。

## 触发与退出

- 触发：用户说"生成 PRD / 先设计方案 / 实现前规划 / 审查 PRD"。纯讨论、头脑风暴不触发。
- 退出：PRD 整体确认后切到 `delivery-workflow`；如果用户改口说"先帮我实现/修 bug"，按 `ai-development-workflow.md` 重新做变更分级。

## 业务需求共创

聚焦业务逻辑：背景、用户目标、用户场景、功能范围、非目标范围、用户流程、验收标准、约束假设、待确认问题。**不写未经代码库验证的实现方案**。

在 `doc/PRD/功能名_YYYY-MM-DD.md` 创建 `## 业务需求` 章节，套用 `references/requirement-prd-template.md`。完成后请用户确认；未确认前不进入下一阶段。

## 实现方案生成

业务需求确认后，读取项目架构（`doc/记录/`、`doc/记录/当前架构.md`），用 `rg`、文件阅读、定向检查 mapper/controller/service/component 等方式查真实代码路径。

在同一个 PRD 文件追加 `## 实现方案` 章节，套用 `references/implementation-prd-template.md`。必须覆盖：当前系统现状、影响范围、后端/前端/数据库/配置方案、接口与数据流、权限与错误处理、安全影响、性能影响、测试方案、回滚方案、开放问题。

完成后按以下清单自检，任一缺失**暂停并回业务需求共创**重新对齐，不直接进开发：

1. 业务需求已被用户确认
2. 已记录实际检查过的代码路径
3. 已列出影响范围和预计修改模块
4. 已说明接口、数据流、权限和错误处理
5. 已说明安全影响和性能影响
6. 验证命令与 `project-adapter.md` 匹配
7. 已给出回滚方案
8. 已判断是否需要更新项目架构

## 暂停与升级

出现以下情况暂停并询问用户：需求与现有架构或数据模型冲突；触及认证/授权/积分/下载/上传/AI/SSE/TTS/数据库结构/部署/CI/CD/跨服务调用；验收标准不清晰；存在多个可行方向且带来用户可见取舍；用户提供的 PRD 与当前仓库行为冲突。

## 输出

结束时总结：PRD 文件路径；业务需求与实现方案要点；实现方案自检结果；仍需用户决策的问题；明确尚未编码，下一步切到 `delivery-workflow`。
