# PRD 审查清单

> 使用说明：当用户提供已有 PRD，或 PRD 的业务需求章节初稿完成后，读取本清单辅助审查。审查目标不是替用户降低需求，而是暴露代码库约束、风险和需要用户决策的问题。

## 1. 需求完整性

- 用户是谁是否明确。
- 要解决的问题是否具体。
- 必须做、可选做、本次不做是否区分清楚。
- 用户流程是否覆盖入口、操作、结果、取消和失败。
- 验收标准是否可测试。
- 是否存在“优化体验”“功能正常”等不可验证表述。

## 2. 与现有产品的一致性

- 是否复用现有页面入口和交互习惯。
- 是否改变已有用户路径。
- 是否影响 Web 前台和 Admin 后台的一致性。
- 是否需要补充空状态、错误状态、移动端表现。

## 3. 与代码库的一致性

审查时优先检查：

```text
Web/src/views/
Web/src/components/
Web/src/services/
Web/src/stores/
Admin/src/views/
Admin/src/components/
Admin/src/services/
LiuTech/src/main/java/
LiuTech/src/main/resources/mapper/
LiuTech-AI/src/main/java/
sql/
nginx/
docker-compose.yml
```

需要回答：

- 当前是否已有相似模块可复用。
- 当前接口是否已经支持需求。
- 当前数据模型是否能表达需求。
- 当前权限模型是否支持需求。
- 是否会破坏旧流程或旧数据。

## 4. 安全审查

重点检查：

- 登录态和角色权限。
- 用户是否能访问或修改不属于自己的数据。
- 富文本、公告、评论、上传内容是否可能 XSS。
- 文件上传/下载是否涉及可执行文件、路径穿越、MIME 伪造。
- SQL 是否可能拼接用户输入。
- Token、密码、密钥、隐私字段是否可能进入前端、日志或响应。
- AI 输出是否被直接信任或直接渲染。

## 5. 性能审查

重点检查：

- 列表页是否会引入 N+1 查询。
- 搜索是否使用 `%keyword%` 全表扫描。
- 是否需要分页、索引或缓存。
- SSE、TTS、AI 调用是否可能创建过多线程或长连接。
- 前端是否会一次性加载大文件、大列表或过多资源。

## 6. 实现复杂度与拆分

需要判断：

- 是否能作为一个功能完成。
- 是否应该拆分为多个 PRD。
- 是否存在必须先完成的基础能力。
- 是否有迁移、兼容、灰度或回滚成本。

## 7. 用户决策点

凡是出现以下情况，必须停下来问用户：

- 多个实现方向会影响用户体验或业务规则。
- 需求和现有架构冲突。
- 需要改变权限、安全、计费、积分、下载、上传、AI、数据库或部署。
- 验收标准不清晰。
- 需要删除或改变已有功能。

## 8. 审查输出格式

```markdown
## 需求审查结果

### 1. 可以直接支持的部分

### 2. 与当前代码或架构冲突的部分

### 3. 安全风险

### 4. 性能风险

### 5. 需要用户决策的问题

### 6. 建议调整后的需求边界

### 7. 是否可以进入实现方案

结论：可以 / 不可以
原因：
```
