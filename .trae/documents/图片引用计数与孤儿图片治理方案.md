## 你现在的设计“凑合吗”
- **思路本身是合理的**：用 DB 维护图片元数据 + 引用计数，清理任务只处理候选集，避免全盘扫描 `uploads` 目录的 IO。
- **问题在于语义错位**：你现在的 `usage_count` 实际上是“上传次数/被上传返回过几次”，而你想要它承担“被业务字段引用了几次”。
- 一旦“上传”和“引用”不是同一时刻发生（TinyMCE 先上传、用户可能不发文/不保存），就必然产生你说的“假引用”。

## 现状证据（仓库里已经体现了这种错位）
- `ImagesService.uploadImage`：新图 `usage_count=1`，去重命中也直接 `+1`。
- `PostsService/CarouselService/MusicService`：创建/更新都写了“上传时已建立引用，所以不调整 usage_count”。
- `UserProfileService`：头像变更时却会显式 `+1/-1`，这会在“上传时已 +1”的前提下造成重复计数风险。
- `OrphanImageCleanupService`：只清理 `usage_count=0`，但当前上传就会把它变成 1，导致“未引用图片”永远清不掉。

## 推荐的正确语义（最重要的决定）
- 把 `usage_count` 明确为：**真实引用次数**（按出现次数计数，与你前面“不要去重”的删除逻辑一致）。
- 这样：
  - “上传但不使用”天然就是 `usage_count=0`，不再是假引用。
  - 清理任务也就变得可靠。

## 关键风险点：不要误删正在编辑中的图片
- 如果我们把“上传不计数”落地，用户正在写文章但尚未保存，图片短时间内会是 `usage_count=0`。
- 所以清理任务必须加 **TTL 保护**：只清理 `usage_count=0 AND created_at < now - N`（例如 24h 或 7d）。

## 落地方案（不再扫全盘目录，仍然走 DB 候选集）
### 1) 调整上传链路：上传不再修改 usage_count
- 修改 `ImagesService.uploadImage`：
  - 新图 `usage_count=0`
  - 去重命中不再 `+1`
  - “是否重复”改为按 `file_hash` 是否已存在判断，而不是 `usage_count>1`
- 修改 `FileUploadService.uploadImage`：`isDuplicate` 字段改用“hash 是否命中”的布尔值。

### 2) 调整引用建立/变更：在业务字段落库时 +1/-1
- 文章：`PostsService.createPost/updatePost` 解析 cover/thumbnail/content，按出现次数对 URL 逐次 `+1`；更新时对 old/new 做差量。
- 轮播图：`CarouselService.createCarousel/updateCarousel` 对 `imageUrl` 变更做 `+1/-1`。
- 音乐：`MusicService.uploadMusic/updateMusic` 对 `coverUrl` 变更做 `+1/-1`。
- 头像：`UserProfileService` 保持现有 `+1/-1`，但因为上传不再 +1，最终计数会回归正确。

### 3) 调整清理任务：加 TTL + 频率合理化
- 修改 `OrphanImageCleanupService.queryZeroUsageImages`：增加 `created_at < now - TTL`（TTL 可配置）。
- 频率：开发环境可以分钟级，生产建议每天凌晨跑；避免误删与 DB 压力。

### 4) 一次性“对账修复”历史数据（强烈建议）
- 因为你历史 `usage_count` 里混了“上传计数”，改完语义后建议做一次：
  - 先把全部 `usage_count` 置 0
  - 再扫描 posts/users/carousel/music 的 URL 字段与正文内容，重新按出现次数回填计数
- 这一步不需要扫文件系统，只读 DB 文本字段，IO 压力远小于全盘文件遍历。
