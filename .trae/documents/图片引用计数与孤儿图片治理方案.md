## 现状诊断
- 当前 `images.usage_count` 在上传时就 `+1`（去重命中也 `+1`），而文章创建/更新处明确“不再调整 usage_count”。
- 这会天然制造“假引用”：用户上传但没发文，计数也会上升；而且 `usage_count` 的语义已从 SQL 注释的“被多少篇文章使用”变成了“被引用次数（按出现次数）”。

## 目标语义（建议你选其一）
- **推荐语义 A（按出现次数）**：文章正文/封面/缩略图里出现一次就算一次引用（与你刚实现的“不要去重”一致）。
- **可选语义 B（按文章数）**：同一篇文章里出现多次也只算 1 次；删除/更新需要去重并按文章维度维护。

## 方案对比（从凑合到长期正确）
### 方案 1：最小改动凑合（不改上传逻辑）
- 新增“定时对账/清理”任务：周期性扫描所有 posts（cover/thumbnail/content），重新计算每个图片实际引用次数，然后把 `images.usage_count` 修正为真实值；对 `usage_count=0` 且创建时间超过 TTL 的图片做物理文件删除 + DB 软删/硬删。
- 优点：侵入小、风险低；能逐步修正历史脏数据。
- 缺点：计数不是实时一致；扫描会有一定成本。

### 方案 2：推荐落地（把 usage_count 变成“真实引用”，上传不再加 1）
- 调整上传：`ImagesService.uploadImage` 不再修改 `usage_count`，新图 `usage_count=0`，去重命中也不再 `+1`。
- 调整文章保存：
  - 创建文章：解析 cover/thumbnail/content，按出现次数对每个 URL 执行 `usage_count +1`。
  - 更新文章：对比 old/new 的引用列表差异，old 多出来的逐次 `-1`，new 多出来的逐次 `+1`。
  - 物理删除文章：沿用你现在的解析逐次 `-1`。
- 再加一个轻量定时清理：删除 `usage_count=0` 且超过 TTL 的图片（防止无限堆积）。
- 优点：语义正确、实时一致；“上传不发文”天然就是 0 引用，不再是假引用。
- 缺点：需要补齐 create/update 的计数逻辑；更新时要做 diff。

### 方案 3：长期最正确（建立引用关系表）
- 新建 `post_images`（或更通用 `image_refs`）表：`post_id, image_id, occurrences, ref_type`。
- `usage_count` 变为冗余字段/缓存，或干脆不存，查询时聚合。
- 优点：可追溯、易对账、支持更多引用源（评论、头像等）。
- 缺点：改动最大。
